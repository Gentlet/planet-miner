# V2 코드 검수 실행 규칙

이 문서는 메인 에이전트의 검수 실행 절차와 검수자의 공통 계약을 정의한다. 게임 설계와 컴포넌트 계약의 기준은 루트 AGENTS.md와 작업 영역의 현재 소스/명세다. 실행 순서, Writer 표, 개별 게임 규칙의 전문은 이 문서에 복제하지 않는다.

## 적용 범위와 실행 책임

- 게임 코드 또는 동작에 영향을 주는 에셋을 변경한 한 작업 묶음에 적용한다. 사용자 지시가 우선하며, 읽기 전용 요청에서는 메인도 수정하지 않는다.
- 메인은 구현, 영향 분석, 검수자 선택, 지적 판정, 승인된 범위의 수정과 Unity 검증을 소유한다. 검수자는 읽기 전용 분석만 수행하며 직접 수정하거나 Unity 명령을 실행하지 않는다.
- 코드/에셋 변경이 없는 문서/에이전트 설정 작업에는 게임 페이즈 검수를 기계적으로 실행하지 않는다. 설정 문법, 로더 인식, 경로와 작업 범위를 확인한다.
- 역할별 프로필은 .codex/agents/*.toml이다. 일반 검수 중 readability_review는 gpt-6.1-terra / xhigh, 나머지 11개는 gpt-6-luna / xhigh를 사용한다. boundary_review는 gpt-6.1-sol / xhigh를 사용하며 메인 모델은 바꾸지 않는다.
- 메인을 제외한 동시 검수 상한은 6개다. 평소에는 변경에 필요한 역할만 3~4개 선택한다. 작은 변경은 필요한 역할이 1~2개면 그 수만 실행하며, 숫자를 채우려고 관련 없는 역할을 추가하지 않는다. 여러 페이즈/데이터 경계에 걸친 변경은 필요한 경우 5~6개까지 동시에 실행한다. 필요한 검수가 상한을 넘으면 종료한 검수 결과를 회수한 뒤 다음 역할을 실행한다. 검수자는 다른 에이전트를 생성하지 않는다.
- .codex/config.toml의 [agents].max_concurrent_threads_per_session = 6은 로컬 실행 상한을 설정한다. 현재 세션에 적용된 실제 도구/서버 한도가 더 낮으면 그 한도 내에서 나누어 실행하고 제한을 보고한다. 설정 로드 확인과 실제 6개 동시 실행 확인은 구분한다. 이 기존 로컬 설정 파일은 Git 추적 대상이 아니며, 공유 프로필과 본 규칙은 추적 대상이다.
- 커스텀 에이전트는 부모의 실제 권한/도구를 상속한다. 프로필의 수정 금지는 행동 계약이며 별도 읽기 전용 sandbox를 만들었다고 보고하지 않는다.

## 호출할 역할 선택

검수 단위는 역할 × 도메인이다. Packet에 Common, Initialization, Power, Building, Drone, Synchronization 중 필요한 도메인과 직접 연결된 생산자/소비자를 지정한다. 파일명과 폴더만으로 역할을 선택하지 않는다.

| 역할 | 호출 조건 |
| --- | --- |
| initialization_review | 설정 parser/게시, Authoring/Baker, 공통 생성 구성, 준비 gate 변경 |
| command_review | 요청 접수/승인/취소/철거 승인, Command 순서/소비 변경 |
| preparation_review | 작업 준비/수요/초기화 Writer 또는 준비 상태 변경 |
| decision_review | 선택/자격/실행 후보의 판단 또는 입력 계약 변경 |
| reservation_review | 경합 중재/배분/슬롯/예약 생성/유지/해제 변경 |
| execution_review | 진행/재료 선소비/연료 소비/행동 계획 준비 변경 |
| apply_commit_review | StateApply 수명주기/실물 인계/결과 정산/ECB 기록과 공개 변경 |
| synchronization_review | 공유 인덱스/Fence/재할당/해제/최종 불변식 검사 변경 |
| component_contract_review | 타입/필드/Writer/Reader/enable/수명/쿼리/새 상태/캐시 의미 변경. 타입 파일이 변경되지 않아도 적용 |
| guard_contract_review | guard/존재 검사/조기 반환/fallback/clamp/재시도/동기화 대기 추가/변경/삭제 |
| readability_review | 새 처리 흐름/조건 분기/메서드 구조 또는 역할을 드러내는 명명 변경 |
| comment_contract_review | 주석 수정 또는 소유권/페이즈/수명/실패 정책 등 설명 대상 계약 변경. 직접 영향을 받는 기존 주석과 필요한 설명의 누락도 포함 |
| boundary_review | 그룹/순서/ECB 대상/공개 시점/소유권 인계/예약 정산/Fatal 범위/공유 자료 의존성 변경 또는 중요한 검수 이견 |

- 동작 변경에는 최소 하나의 관련 페이즈 검수를 배정한다. 생산자 출력의 의미가 바뀌면 수정되지 않은 직접 소비자도 검수 범위에 넣는다.
- 해당하지 않는 역할은 생략 이유를 기록한다. 단순 이름 변경/서식 정리에 모든 역할을 호출하지 않는다.
- 경계 변경 조건이 하나라도 있으면 boundary_review를 필수로 실행한다. 일반 검수의 찬성 수로 이를 대체하지 않는다.
- 처음에는 각 검수자의 독립 결과를 받는다. 이후 중복 지적/충돌을 정리하고, 필요한 경우 boundary_review에 쟁점과 원본 근거를 함께 전달한다.
- 루트 AGENTS.md의 현재 구현 경계를 따른다. 미구현 드론 이동/연구 등 후속 기능을 이번 변경의 누락으로 임의 요구하지 않는다.

## 가독성/주석 검수의 운영

- 두 역할은 위 호출 조건에 해당할 때 선택한다. 모든 변경에 둘을 의무 추가하거나 필요한 페이즈/컴포넌트/방어 로직 검수를 대체하지 않는다. 기존 동시 실행 상한과 변경 범위에 따른 역할 선택 원칙을 유지한다.
- 가독성은 루트 AGENTS.md의 현재 작성 기준으로 판단한다. 의미가 드러나는 이름, 메서드 책임과 처리 순서, 조건식과 흐름을 숨기는 분해/추상화를 확인하며 줄 수만으로 분리하거나 호환 계약을 무시한 이름 변경을 요구하지 않는다.
- 주석은 변경된 설명과 계약 변경의 직접 영향을 받는 기존 설명을 코드/확정 계약과 대조한다. 비자명한 이유/소유권/수명/공개 시점의 설명 누락을 구체적으로 확인하되 모든 코드에 주석을 요구하지 않는다. 코드 설명과 관련 기획 문서/절의 확정 규칙에 집중하고 추측/Task ID/티켓 번호/작업 이력을 추가하지 않는다.
- 각 지적에 실제 위치/심볼, 오해 가능한 내용, 현재 코드/작성 규칙/확정 계약의 근거와 최소 수정 방향을 요구한다. 명시적 작성 규칙 위반과 취향 수준의 P3 개선 제안을 구분하며, 취향 제안은 완료를 막는 필수 수정으로 만들지 않는다. 스타일/주석만으로 실행 결함이나 높은 우선순위를 주장하지 않는다.
- 코드와 주석이 충돌하면 현재 확정 계약으로 어느 쪽이 잘못됐는지 먼저 판정한다. 구현 결함은 관련 페이즈/컴포넌트 검수로, 중요한 경계 이견은 boundary_review로 이관하며 주석만 고쳐 코드 오류를 덮지 않는다. 의도가 미확정이면 설계 질문으로 남긴다.

## 메인 실행 절차

1. 요구사항과 유지할 동작, 적용되는 현재 계약을 확인한다. 알려진 코드 사실과 설계 미확정 사항을 구분한다. 게임 규칙/설계 선택이 필요한 경우에만 사용자에게 확인한다.
2. 승인된 범위의 구현을 한 묶음으로 마친다. 기존 staged/unstaged/untracked 사용자 변경을 보존하고 이번 작업 diff를 구분한다.
3. 루트 AGENTS.md에 따라 필요한 컴파일을 확인한다. 컴파일 오류부터 수정하며, 문서/설정만의 변경에는 Unity 컴파일을 실행하지 않는다.
4. 아래 Packet으로 검수 버전을 고정하고 관련 역할을 선택한다. 검수 중 대상 파일을 수정하지 않는다. 다른 작업자의 변경이 있으면 영향받은 결과를 무효화하고 범위를 다시 정한다.
5. 평소에는 필요한 검수 역할 3~4개를 독립적으로 실행한다. 작은 변경은 필요한 역할 수만 실행하고, 여러 페이즈/데이터 경계에 걸친 변경은 필요한 경우 최대 6개까지 동시에 실행한다. 관련 역할을 숫자에 맞추어 추가하거나 필수 검수를 3~4개에 맞추어 생략하지 않는다. 실제 커스텀 역할 이름과 프로필에 고정된 모델/effort를 사용한다. 부모 모델을 암묵적으로 상속한 실행을 해당 프로필 실행으로 보고하지 않는다.
6. 지적을 원인별로 합쳐 수용/기각/미확정으로 판정한다. 기각에는 현재 코드/계약의 반증을 남긴다. 중요한 이견은 boundary_review로 넘긴다. 설계 선택이 아닌 일반 구현 세부사항은 메인이 해결한다.
7. 수용한 지적만 승인 범위에서 수정한다. 새 C# 변경 이후 컴파일을 확인하고, 동작/계약 변경이나 구체적 회귀 위험이 있으면 가장 작은 관련 기존 EditMode 묶음을 실행한다. 테스트 추가/범위 확대/Play Mode는 루트 AGENTS.md의 기준을 그대로 따른다.
8. 수정된 계약과 직접 연결된 경계만 재검수한다. 변경되지 않은 부분의 검수와 유효한 동일 버전 검증을 반복하지 않는다. 두 차례 재검수 후에도 남은 중요한 쟁점은 독립 경계 판단/사용자 설계 결정으로 넘기며 자동 통과시키지 않는다.
9. 완료 보고에는 검수 역할/버전/범위, 수용/기각 이유, 미해결 사항, 실제 컴파일/테스트 결과와 미수행 범위를 구분한다.

프로필이 현재 세션에 노출되지 않거나 노출된 역할의 고정 모델/effort가 현재 프로필 파일과 다르면 프로젝트의 새 세션에서 로드를 확인한다. 직접 역할 지정이 불가능하거나 고정 모델/effort가 불일치하는 세션에서 모델 지정은 지원하면, 커스텀 역할명을 지정하지 않고 해당 TOML의 developer_instructions와 Packet을 독립 자식 과제로 전달하여 현재 프로필의 모델/effort를 명시한다. 이전 세션에 남은 모델로 실행한 결과를 변경된 프로필의 검수로 보고하지 않는다. 둘 다 불가능하거나 모델을 사용할 수 없으면 검수 불완료로 보고한다. 다른 모델로 조용히 대체하거나 새 사용자 채팅을 대신 만들지 않는다.

## 검수 Packet

메인은 다음 정보를 중립적으로 제공한다. 작성자의 장황한 정당화와 다른 검수자의 결론은 첫 독립 검수에 넣지 않는다.

- Review ID / iteration, 저장소 절대 경로, 브랜치, 기준 커밋
- 이번 작업의 staged/unstaged/untracked diff와 대상 파일 내용의 식별값. 기존 사용자 변경과의 구분
- 요구사항, 기대 동작, 유지할 계약, 승인된 예외/범위
- 역할/도메인, 대상 파일/심볼, 직접 생산자/소비자와 관련 현재 계약 경로
- 변경된 Writer/필드/enable/소비/ECB/같은 틱/다음 틱 경계
- 가독성/주석 역할에 적용할 현재 작성 규칙, 직접 영향을 받는 기존 주석과 확정 기획 문서/관련 절(해당 시)
- 확인할 기존 테스트 경로와 해당 버전의 실제 검증 결과. 과거 문서 수치는 현재 결과로 제공하지 않음
- 읽기 전용 범위, 필요한 질문과 미확정 설계 사항

Packet이 빠졌다고 즉시 중단하지 않는다. 현재 지시와 읽기 가능한 코드에서 보완할 수 있는 항목은 확인한다. 검수 버전/요구사항/핵심 계약을 확정할 수 없으면 확인한 범위와 필요한 추가 정보를 남기고 불완료로 반환한다.

## 검수자 공통 계약

1. 루트 AGENTS.md의 현재 지시와 적용 영역의 현재 소스를 우선한다. CodeMemory/명세는 관련 절만 읽고 실제 심볼/호출/쿼리/UpdateInGroup/순서/Job 의존성과 대조한다. 심볼/참조/코드 구조는 Serena MCP를 우선한다. 자식 세션의 첫 의미 탐색 전에 initial_instructions를 한 번 읽고 Packet의 저장소 절대 경로로 activate_project를 수행하며 저장소/작업 트리가 바뀌면 다시 확인한다. 집중된 개요/심볼 본문/참조만 조회한다. 도구 부재/활성화 실패/필요 질의 미지원이면 구체적 제한을 짧게 밝히고 일반 코드 검색으로 진행하며 같은 실패를 반복하지 않는다.
2. 이번 diff와 직접 생산자/소비자까지 확인한다. 근거 없이 저장소 전체나 모든 CodeMemory를 읽지 않는다. 다른 검수자의 담당 문제를 발견하면 연결 근거를 적고 이관하며 전체 감사로 확장하지 않는다.
3. 파일/설정/에셋/Git 상태/메모리를 수정하지 않는다. 빌드/컴파일/테스트/Play Mode, 패키지 설치, 커밋/푸시, 외부 메시지, 다른 에이전트 생성은 수행하지 않는다. 관련 테스트 소스는 읽을 수 있다.
4. State/Preparation/Decision/Request/Result/Requirement, 컴포넌트 존재/enable, 원본/파생 인덱스, ECB 기록/Playback을 구분한다. 이름 접미사만으로 소속/Writer/소비 시점을 단정하지 않는다.
5. 같은 틱에서 실제로 바뀔 수 있는 원본과 지정 Writer 이후 불변인 원본을 구분한다. 지원하지 않는 중간 Writer를 가정해 방어 로직이나 테스트를 요구하지 않는다. 새 Writer가 추가되면 계약 변경 자체를 검수한다.
6. 결함은 현재 경로에서 발생 조건과 영향을 설명할 수 있어야 한다. 기존 구현과 요구 계약이 충돌하면 사실과 미확정 의도를 구분하고 임의의 새 게임 규칙으로 해결하지 않는다.
7. 지적 수나 점수 목표는 없다. 근거 없는 장점/단점 나열, 취향만의 구조 변경, 필드 모양만 보고 타입 병합, 요청 범위 밖 스타일 정리는 제안하지 않는다. 새로 수정한 구간의 명시적 가독성 규칙 위반은 구체적으로 보고할 수 있다.
8. 문제 없음과 미확인을 구분한다. 정적 추론을 실행 재현으로 부르지 않으며 컴파일/EditMode를 Play Mode/현장 증거로 확대하지 않는다. 기존 결함/알려진 제한/이번 회귀도 구분한다.
9. 최소 수정 방향과 가장 작은 확인 방법만 제안한다. 직접 패치하지 않는다. 테스트는 구체적 결함 재현 또는 기존에 없는 핵심 흐름에 한해 제안하며 기존 통합 테스트 보완을 우선한다.
10. 검수 버전과 실제 읽은 범위가 달라지면 완료로 반환하지 않는다. 미지원 도구/누락 자료/모델 오류를 숨기지 않는다.

## 결과 형식

한국어로 다음 형식을 사용한다. 실제 위치는 절대 경로/심볼/검증한 1-based 줄 번호로 명시한다.

```text
역할 / 도메인 / Review ID / iteration / 검수 버전:
상태: 완료 / 불완료 / 해당 없음
확인한 파일/심볼 / 적용 계약:
검수하지 못한 범위:

지적 ID:
종류: 결함 / 계약 위반 / 개선 제안 / 설계 질문
우선순위: P0 / P1 / P2 / P3
근거 위치 / 관련 계약:
발생 조건 / 현재 동작 / 기대 동작 / 영향:
읽기/주석 지적의 오해 가능한 내용 / 근거 규칙(해당 시):
생산자 → 소비자 / Writer / 공개 경계:
최소 수정 방향 / 확인 방법:
증거: 정적 분석 / 실행 재현 / 미확인 가정

지적이 없으면: 확인한 범위에서 지적 없음
추가로 필요한 정보 / 연결 검수 역할:
```

- P0: 광범위한 실행 불능 또는 심각한 데이터 파괴. P1: 핵심 흐름의 높은 영향도 오류/소유권 손실/중복/예약 누수. P2: 특정 지원 조건에서 발생하는 오류/회귀/계약 위반. P3: 현재 오동작 근거가 없는 국소 개선/가독성 문제.
- 등급과 증거 수준은 별개다. 추정만으로 높은 확신의 결함을 만들지 않는다. 재현 절차를 제안했을 뿐이면 실행 재현으로 표기하지 않는다.
- 완료는 할당 범위를 확인했다는 뜻이며 전체 게임 승인/무결함 보장이 아니다. 불완료와 해당 없음은 통과표가 아니다.

## 완료 판정

메인은 적용 대상 검수가 같은 코드 버전에 대해 끝났는지 확인한다. 확인된 필수 계약 위반은 해결하거나 사용자 지시에 따른 명시적 예외를 남긴다. 취향 수준 개선은 필수 수정과 분리한다. 중요한 미확정 오류, 필수 검수 누락, 무효화된 버전, 필요한 검증 실패가 남았으면 검수 완료/검증 통과라고 보고하지 않는다. 다수결/평균 점수로 판정하지 않는다.

실행 비용을 확인할 때는 역할별 지적/수용/기각 근거/놓친 결함/추가 재작업/전체 시간과 사용량을 기록할 수 있다. 기록을 위해 불필요한 보고 파일이나 테스트를 자동 생성하지 않는다.

## 설정과 로드 확인

공식 형식은 프로젝트 .codex/agents/ 아래의 독립 TOML이며 name, description, developer_instructions와 모델/effort를 명시한다. 부모 권한과 MCP 서버를 상속하며 프로필에 sandbox_mode 같은 가짜 격리 설정을 넣지 않는다.

- 프로필/규칙 변경 검증: TOML 파싱, 필수 필드/고유 이름/모델, 문서 경로, Codex의 실제 프로필 발견과 로드 오류를 확인한다.
- 실제 모델 추론 실행과 단순 로더 인식을 구분한다. 로더 확인만으로 검수 정확도나 모든 프로필의 실제 모델 실행을 확인했다고 보고하지 않는다.
- 기존 로컬 .codex/config.toml의 다른 설정은 보존한다. 공유 프로필만 Git에 포함하고 로컬 자격 증명/환경 설정을 포함하지 않는다.
- 공식 근거: https://learn.chatgpt.com/docs/agent-configuration/subagents
