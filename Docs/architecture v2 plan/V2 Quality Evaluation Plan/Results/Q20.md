## 3. 실제 채굴 동작과 경계

### Decision — 코드 확인

- query는 MinerDecision이 꺼져 있어도 다시 판단한다. 원본 MinerState/footprint/위치/방향/ProductItemElement/ProductResult가 모두 있어야 대상이다. MinerState 인자는 현재 계산에서 사용하지 않으며 진행도를 변경하지 않는다.
- ResourceSpatialIndex와 Fence가 모두 있어야 실행한다. 최신 ResourceNode lookup을 준비하고 Job이 **마지막 Map Writer + state.Dependency**를 기다리게 하며, 완료 handle을 AddReader로 돌려준다.
- anchor에서 effective footprint의 y→x 순으로 첫 번째 `ResourceNode.Amount>0`인 entity를 고른다. null·죽은/ResourceNode 없는 Map 항목은 건너뛴다. 첫 자원을 선택한 뒤 출력 품목을 검사하므로, 첫 품목이 기존 제품과 다르면 뒤 셀의 같은 품목으로 대체 탐색하지 않는다.
- 해당 품목의 MaxStack은 유효 Registry Blob에서 읽고, Registry가 없으면 50이다. 현재 품목별 실제 MaxStack을 쓰는 것과 테스트의 무설정 fallback=50을 구분한다. ProductItemElement의 **행 수**가 아이템 수이며 slot별로 나누지 않고 동일 품목 1스택으로 취급한다.
- ProductResult가 남아 있거나 기존 제품 중 다른 품목이 있거나 용량이 가득 차면 CanMine=false/Decision disabled. 자원은 찾았지만 막힌 경우 TargetResource는 그 자원을 남긴다. 선택된 TargetResource만 보고 채굴 허용으로 판단하면 안 된다.
- 같은 tick에 출고가 예정되어도 Decision은 현재 제품 수를 본다. 가득 찬 버퍼가 StateApply에서 비워지면 다음 Decision에서 재개한다. 출고 Decision보다 먼저/나중에 실행되어야 한다는 숨은 규칙은 없다.

### Execution — 코드 확인

- 활성 MinerDecision이 있는 채굴기만 query에 들어간다. CanMine=false/null target/미소비 ProductResult/ResourceNode 부재/Amount<=0이면 진행도와 자원량을 변경하지 않는다. 자원 무한 모드에서도 Amount>0인 노드가 필요하다.
- `dt=min(Time.DeltaTime,0.1)`로 상한을 적용하고 `Progress += MiningSpeed*dt`. Progress>=1이면 **한 번만** 1을 빼고 `ProductResult(ResourceType,1,0)`을 기록한다. while로 여러 개를 생산하지 않는다.
- ResourceConfig가 없으면 유한 자원이다. 유한일 때 Amount를 즉시 1 차감하고 0 이하가 되면 EndStateApply ECB에 DestroyEntity를 기록한다. 무한일 때 결과는 기록하지만 Amount를 차감하지 않는다. 실제 파괴와 공간 인덱스 제거는 뒤 경계다.
- Execution은 `.Schedule` 단일 Job이다. 여러 채굴기가 같은 자원을 선택했다면 각 Execute가 앞선 Amount 갱신을 다시 읽으므로 마지막 1개를 소비한 뒤 다음 채굴기는 Amount<=0에서 정지한다. **코드 확인이며 다중 채굴기 실행 재현은 미수행**이다. 실행 순서에 따른 승자/공정성은 별도 우선권 계약이 없다.
- Execution은 Decision enable을 끄지 않는다. 이는 다음 Decision에서 덮어쓰는 프레임 판단이며 일회성 IRequest와 다르다. 공개 정상 Phase 순서를 넘어 같은 Decision으로 Execution을 반복 호출하는 임의 시나리오까지 exactly-once로 보장하지 않는다.
- 중단 중의 잔여 Progress는 유지되고 대상 resource를 Progress와 묶는 별도 상태는 없다. 다음 판단에서 대상이 바뀌어도 잔여량이 이어진다. 이 동작을 새 버그로 단정하거나 초기화 규칙을 추가하지 않았다.

### ProductResult→실체화 — 코드 확인 및 선택 실행

Execution 시점에는 실제 아이템/출력 버퍼를 변경하지 않고 논리 결과만 남긴다. ItemLifecycle은 결과마다 Count개의 저장 아이템과 ProductItemElement Append를 **EndStateApply ECB**에 기록하고 결과 버퍼를 즉시 Clear한다. 실제 entity·Owner·출력 버퍼 참조는 Playback에서 확정된다. 채굴기는 prefab 초기화/렌더 태그/소유권 필드를 알 필요가 없다.

다음 Decision 전 EndStateApply Playback이 끝나므로 결과가 비워진 뒤에도 이전 프레임 생산품을 용량 검사에서 놓치지 않는 것이 정상 공개 경계다. 이를 ItemLifecycle 내부 Job의 상세 순서에 대한 의존으로 보지 않는다. Q15처럼 새 생산품의 출고 선택은 다음 Decision부터 가능하다.

DB가 없으면 ItemLifecycle의 테스트용 fallback을 사용한다. DB는 있으나 prefab이 누락되면 결과를 폐기할 수 있으며 이미 감소한 자원은 돌아오지 않는 기존 F-006이 적용된다. 자원 생성이 prefab 준비 전 전체 대기하는 Q18과 달리 **채굴 결과의 아이템 생성 실패 정책은 별개**다.

## 4. 상태 Reader/Writer·필요한 동기화

| 상태 | Owner / Writer → Reader | 계약·의존성 |
| --- | --- | --- |
| ResourceNode/GridPosition | Resource Generation ECB가 생성, MinerExecution이 Amount 감소/고갈 파괴 → MinerDecision/Execution·Sync | 현재 원본량 재확인이 경합 방지에 필요. 공간 위치 Map과 자원량은 같은 데이터가 아님 |
| ResourceSpatialIndex/Fence | ResourceSpatialSync의 Clear/Populate/Writer → MinerDecision read + AddReader | 이전 Sync 완료를 기다리며 독립 Job의 사용 기간을 반환. Generation의 내부 후보 알고리즘은 몰라도 됨 |
| MinerState | Spawn/Factory 초기화, MinerExecution 갱신 → 이후 Execution(Decision은 query 인자만 보유) | 진행의 단일 Writer. 다른 시스템을 호출해 진행도를 변경하지 않음 |
| MinerDecision | MinerDecisionSystem이 값/enable 작성 → MinerExecution | 공개된 이번 프레임 실행 후보. 대상량은 예약된 재고가 아니므로 Execution 재검사가 필요 |
| ProductResult | MinerExecution Append → ItemLifecycle Clear/ECB 기록 | 미소비 결과는 Decision과 Execution의 추가 생산을 막음. Count=1, slot=0 인계 |
| ProductItemElement | ItemLifecycle ECB Append, Q15 출고 Apply 제거 → MinerDecision/OutputDecision | 한 entity당 한 행, 품목/용량 및 소유권 계약. 채굴 Execution이 직접 추가하지 않음 |
| ItemRegistry | 초기화 게시 → MinerDecision | 불변 Blob의 MaxStack. Resource Map Fence와 다른 수명 계약 |
| EndStateApply ECB | MinerExecution 고갈 파괴, ItemLifecycle 아이템 생성/버퍼 기록 → ECB Playback | 각 producer handle 완료 후 재생. 현재 채굴 Job의 한 worker와 ECB producer 등록은 필요한 동기화 |

Q18의 새 자원은 EndCommand에서 entity가 생기지만 Resource Map에는 이후 Sync에서 들어온다. MinerDecision은 원본 entity의 존재만으로 신규 자원을 즉시 발견하지 않는다. 고갈도 Amount=0 재검사는 즉시 가능하지만 entity 파괴는 EndStateApply, Map 제거는 이후 Sync다. 이 두 시차를 같은 문제로 혼동하지 않는다.

## 5. V2 의존성·공개 계약 유지 시 변경 영향

| 관계 | 필요한 계약 / 개선할 결합 | 변경 전파 범위 |
| --- | --- | --- |
| MinerDecision → Resource Map/Fence + ResourceNode | 필요한 snapshot/원본량 조회. Sync Update를 직접 호출하지 않음 | Sync의 Job 분할을 바꿔도 Map 의미·최종 Writer를 유지하면 Miner 내부 수정 불필요 |
| Decision → Execution | 대상·허용 여부를 전달, Execution은 mutable 수량만 재확인 | 자원 탐색 루프를 같은 선택 결과로 최적화해도 Execution/ItemLifecycle 수정 불필요 |
| Execution → ProductResult → ItemLifecycle | 필요한 완료 결과 인계. prefab 생성 내부를 몰라도 됨 | 동일 Count/SlotIndex·성공/실패·Playback 계약을 유지한 Item 생성 내부 리팩터링은 Miner 변경 불필요 |
| Miner/Output → ProductItemElement | 같은 출력 원본 읽기, 쓰기는 Apply/ECB 경계 | 출고 탐색 구현이 바뀌어도 Miner는 현재 버퍼만 조회. 같은 tick 공간 확보를 선반영하는 변경은 공개 Phase 계약 변경 |
| 생산·철거 → 대기 생성물 | 기존 F-005의 대상 수명 충돌 | 다른 시스템의 deferred Append 세부 순서로 해결하려 하면 결합 확대. 공개 폐기/생산 접수 계약이 필요 |
| Spawn → footprint → MinerDecision | 기존 F-023의 base/effective 혼용 | 공개 base size가 지켜지면 Miner는 GetEffectiveSize 한 번이면 충분. 현재 Spawn이 회전된 값을 저장해 비정사각형 탐색 영역까지 영향 |

내부 변경 사례는 가상 영향 분석이며 코드를 바꿔 실험하지 않았다. 특히 Execution을 단순 ScheduleParallel로 바꾸는 것은 여러 채굴기의 ResourceNode 공통 쓰기와 ECB 안전성 계약을 바꾸므로 “내부 최적화라 다른 조건이 필요 없다”고 볼 수 없다. 병렬화가 필요하다면 자원별 중재/배치 방식과 승자 정책을 따로 정해야 한다.

국소 테스트에는 Resource Map/Fence·채굴기·결과 버퍼가 필요하다. 실제 아이템 인계를 검사할 때 ItemLifecycle/EndStateApply가 필요한 것은 필수 협력 계약이다. 다만 현재 fixture는 벨트/아이템 Sync·출고/Storage/Ownership까지 모든 사례에서 준비한다. 순수 Decision·진행도 테스트도 이 공통 준비를 공유하므로 테스트 독립성의 개선 여지는 있다. 불필요한 production 시스템 결합으로 확대하지 않는다.

## 6. 발견 문제와 기존 결과 연결

#### F-036 — MinerState의 Progress 0~1 설명이 고속 채굴의 잔여 진행도와 맞지 않음

- 발견 단계 / 유형 / 평가 축: Q20 / **문서 불일치** / 유지보수성.
- 우선순위와 이유: **P3**. 컴포넌트의 범위를 믿고 표시/정규화/상태 검사 코드를 추가하면 실제 유효 잔여량을 잘못 취급할 수 있다. 현재 기본 속도의 정상 생산 장애로 판정하지 않는다.
- 근거 수준: **코드 확인**. 고속 입력 실행 재현은 미수행.
- 위치: `MinerComponents.cs:7,13`, `MinerExecutionSystem.cs:54,106–113`, `BuildingConfigLoader.cs:128–154`, `BuildingLifecycleUtility.cs:128–129`.
- 기대 계약과 출처: MinerState summary/Progress 주석은 0.0~1.0 범위를 설명하지만 Execution summary는 초과분 보존을 설명한다. 공개 상태의 의미가 실제 Writer와 일치해야 한다.
- 확인한 코드 동작 / 발생 조건: 양수 MiningSpeed에 상한을 두지 않고, 한 Execute에서 최대 한 번만 Progress를 1 차감한다. 예를 들어 Progress=0, speed=30, dt=0.1, 유효 자원/출력 여유이면 산술상 Progress는 약 3에서 약 2로 남고 결과는 1개다. 이는 코드 계산 추적이며 Unity 실행 결과가 아니다.
- 영향 / 반대 근거: 실제 기본 Miner speed=0.1이며 일반 저속 구간에서는 잔여량이 1 미만이다. 현재 별도 UI consumer는 확인하지 않았고 즉각적인 아이템 유실을 주장하지 않는다. tick당 1개 제한 자체의 적합성은 게임 정책 확인 대상이다.
- 수정 방향 후보: 현 동작이 의도라면 Progress를 미처리 작업량으로 설명해 주석을 맞춘다. 고속에서도 정규화된 진행도만 지원하려는 의도라면 속도/처리량 계약부터 결정한다. 임의 clamp/while 생산은 용량/자원 경합에 영향을 주므로 이번에 변경하지 않는다.
- 필요한 추가 검증: 고속 입력의 Progress·결과 Count·자원량·다음 tick과 출력 막힘 후 재개를 함께 검사하는 테스트 제안. 현재 Test10은 speed=1에서 dt 상한만 검사하므로 이 경계를 보장하지 않는다.
- 처리 / 별도 수정 작업과 재검증 근거: **미결정 / 없음**. 코드·주석·테스트 수정 없음.
