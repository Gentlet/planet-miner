### 2.3 Item의 실제 계약 차이와 품목 커버리지

- **직렬화 확인:** 위 Item 8개에 `ItemAuthoring.cs.meta`의 GUID `7345044d23f333649a357d32e5ab3da6` 또는 다른 MonoBehaviour가 없다. 예를 들어 `Assets/Resources/Prefabs/Item/Iron_Ore Item.prefab:10–13`의 컴포넌트 목록은 Transform/MeshFilter/MeshRenderer뿐이다.
- **코드 확인:** `ItemAuthoring.cs:13–18`이 정적 `ItemIdentity`를 추가한다. Item DB Baker `:74–102`는 entity 참조 버퍼를 게시하며 identity를 대신 추가하지 않는다. Scripts/Editor의 직접 Baker·BakingSystem·ItemIdentity 작성 검색에서도 대체 정적 작성 경로를 찾지 못했다. `ItemLifecycleApplySystem.cs:181–185,319–323` 및 환급 경로는 prefab 복제 후 identity에 `SetComponent`한다.
- **추정:** 현재 저장된 입력을 새로 베이크하면 필요한 ItemIdentity가 없어 첫 prefab 기반 생성의 Set 전제가 깨질 가능성이 높다. **실제 baked archetype, Playback 예외와 부분 적용은 실행 미확인**이다. Dynamic transform 요청이 ItemIdentity까지 생성해 주지는 않는다. 기존 F-019의 실제 자산 사례로 연결한다.
- **차이:** Building과 Resource는 Spawn이 BuildingType/Footprint 또는 ResourceNode/GridPosition을 넣는 계약이므로 같은 단순 시각 prefab 구성 자체를 오류로 보지 않는다. LocalTransform의 실제 베이크 결과는 별도 확인 대상이다.
- **직접 Config 확인:** `CrafterRecipeConfig.json:52–65`의 id=5는 Drone을 출력하며 Iron_Stick/Copper_Stick을 요구한다. 실제 Item DB에는 Drone이 없다. `Assets/Resources/Prefabs/Drone.prefab` 파일이 별도로 존재해도 현재 InspectorList에 등록되어 있지 않으므로 이 DB의 출력 prefab으로 사용할 수 없다. 이 파일을 Item prefab으로 재사용할 수 있는지는 평가하지 않았다.
- **코드에 따른 조건부 영향:** 해당 레시피가 선택되어 ProductResult에 Drone이 기록되면 ItemLifecycle의 DB 조회는 누락 분기로 가고 결과는 Clear된다(`:168–176,230–231`). 레시피 선택·생산의 실제 도달 및 손실 재현은 미확인이다. 최초 F-006의 실패 정책 질문을 재사용한다.

기존 테스트의 국소 런타임 검증 가치는 유지된다. 누락된 부분은 실제 입력에서 그 국소 테스트가 전제하는 archetype까지 이어지는 별도 검증이다([F-021 최초 기록 Q08](Q08.md#f-021--authoringbaker-계약-이름의-테스트가-실제-baker-변경을-검출하지-못함)).

## 4. 상태 Owner·Reader/Writer와 변경 영향

| --- | --- | --- | --- |

**공개 계약을 유지한 내부 변경 사례:**

1. prefab의 GUID/root fileID·필수 baked 컴포넌트를 유지하며 mesh/material 표현만 교체하면 DB 장면 참조와 Spawn 코드를 함께 수정할 이유가 없다. 시각 결과 확인은 별도다. root를 child로 옮겨 ItemIdentity/transform이 다른 entity에 생기게 하는 변경은 공개 prefab 계약 변경이므로 이 사례에 포함하지 않는다.
2. DB Baker의 내부 helper를 정리하되 직렬화 필드/GUID/enum 값과 최종 DB·identity 계약을 유지하면 소비 시스템의 순서나 코드를 바꿀 필요가 없다. 현재 수동 ECS 테스트는 이 리팩터링이 베이크 출력을 깨뜨려도 잡지 못할 수 있다. 추가로 필요한 것은 실제 Bake 검증이며 다른 시스템 구현을 복제하는 것이 아니다.
3. Spawn 내부에서 새 진행/요청 상태를 초기화하되 외부 DB/Spawn 요청 계약을 유지하면 순수 시각 prefab·DB 목록 수정은 필요하지 않다. 다만 자체 archetype을 만든 테스트 fixture 및 별도 환급 초기화에는 영향이 있을 수 있다(Q08 F-020). 실제 생성 경로를 공통으로 검증해야 하는 이유다.
4. 파일 이동 시 `.meta`와 root ID를 보존하고 InspectorList 입력을 유지하면 장면 링크를 다시 작성할 필요가 없다. ResourcesAutoLoad의 경로/파일명 규칙을 바꾸는 것은 공개 입력 계약 변경이다. script GUID 재발급, enum 숫자 재배정 또는 직렬화 필드 이름 교체도 단순 내부 변경으로 취급할 수 없다. SampleScene의 오래된 데이터는 이 구분이 필요한 사례다.

현재 자료에서 개별 물류/채굴 시스템의 내부 Update 순서까지 알아야 prefab을 등록할 근거는 찾지 못했다. 필요한 지식은 정적 identity·root transform·타입 매핑·준비 완료·생성 확정 시점이다. 실제 World의 동시 SubScene 로드/언로드 때 DB 수명과 소비 중 참조 안전성은 이번 저장 파일 분석으로 확인하지 않았다.

## 5. 발견 문제와 기존 문제 연결

#### F-025 — 활성 빌드 장면의 세 DB가 현재 Authoring 스크립트와 연결되지 않는 참조를 유지함

- 발견 단계 / 유형 / 평가 축: Q11 / **안정성 결함·유지보수 위험** / 안정성·유지보수성·V2 연결 적합성.
- 우선순위와 이유: **P2**. 현재 활성 빌드 진입 경로에서 필요한 DB가 게시되지 않을 위험이 있으나 해당 장면의 유지 의도와 실제 빌드/로드 결과는 미확인이다.
- 근거 수준: **코드·직렬화 확인**. Editor의 Missing Script 표시, 실제 Bake 누락 및 빌드 중단 여부는 **미확인**, 아래 런타임 영향은 **추정**.
- 위치: `ProjectSettings/EditorBuildSettings.asset:8–10`; `Assets/Scenes/SampleScene.unity:580–585`; `Assets/Scenes/SampleScene/Sub.unity:269,322,386`; 현재 세 Authoring `.cs.meta`; §2.1의 GUID 대조.
- 기대 계약과 출처: 장면의 m_Script는 실제 MonoScript 참조로 해석되고 현재 Baker가 해당 Authoring 데이터를 읽어야 한다. 현재 Q08–Q10의 생성 시스템은 각각 도메인 DB 게시/부재 정책에 의존한다.
- 확인한 동작: 부모 SubScene 링크는 존재하지만 세 DB의 script GUID는 Assets의 어떤 `.meta`와도 일치하지 않으며 현재 같은 이름의 Authoring script GUID와 다르다. `m_EditorClassIdentifier`에 이름이 적혀 있다는 사실은 현재 MonoScript 참조 일치를 증명하지 않는다.
- 발생 조건과 영향: 활성 SampleScene 경로를 현재 소스 기준으로 새로 import/bake/load할 때 DB 게시가 누락될 가능성. Resource 준비 대기, Item/Building의 DB 부재 fallback, V2 테스트 경로와 빌드 경로의 차이로 이어질 수 있다. 실제 현상과 추가 구형 script 영향은 이번 범위에서 실행하지 않았다.
- 추가 근거: Sample SubScene은 `_entries`와 소문자 `type/prefab/size`를 저장한다. Building 현재 코드의 FormerlySerializedAs는 바깥 `_entries`에만 있고 entry는 Type/Prefab/Size다. Item/Resource도 현재 Prefabs 목록을 사용한다. Building 저장 숫자 0은 Belt 참조이나 현재 enum 0은 None이고, 1은 Miner 참조이나 현재 enum 1은 Storage다. **GUID만 교체하면 이관이 끝난다고 볼 수 없다.**
- 미확인 사항 / 반대 근거: V2 Test Scene/Sub의 현재 세 script 참조는 정상이다. SampleScene이 의도적으로 유지된 구버전 장면인지와 배포 진입점 결정은 미확인이다. 캐시나 저장되지 않은 Editor 상태를 읽지 않았다.
- 수정 방향 후보: 사용할 진입 장면을 결정한 후 그 경로의 DB를 현재 Authoring으로 검증·이관한다. GUID·직렬화 스키마·enum 타입 대응·실제 Bake를 함께 점검한다. 장면 교체나 GUID 텍스트 치환을 이번 평가에서 수행하지 않았다.
- 필요한 추가 검증: 선택한 실제 장면을 베이크하여 세 DB 개수/entry 개수·타입·prefab entity 존재와 필수 컴포넌트를 검증하는 사례. 현재 후보에는 이 검증이 없다.
- 처리 / 별도 수정 작업과 재검증: **미결정 / 없음**.

## 6. 검증 결과와 미실행 이유

- **코드·직렬화 확인:** 실제 장면/SubScene 메타데이터, 세 DB script 참조, 23개 prefab root/구성/직접 재질 링크, 관련 타입와 Config 출력 커버리지, 직접 Baker/Spawn 계약을 확인했다. 정적 조사 JSON은 Unity 테스트 결과 파일이 아니다.
- **이번 실행 확인:** 새 Unity 실행 증거 없음. Q08–Q10의 선택 테스트 결과는 해당 보고서의 제한된 보장 범위로만 참조했다.
- **미실행:** 새 컴파일, 전체/선택 EditMode, Play Mode, 실제 SubScene baking/import 강제 갱신, 빌드. 문서만 변경했고 이번 미확인 질문에 답하는 기존 후보 사례가 없어 관련 없는 테스트를 재실행하지 않았다. 검증 래퍼의 컴파일+테스트 경로도 호출하지 않았다.
- **최종 상태:** 제출된 Unity 비동기 작업 없음. 파일 보존과 계획의 제한된 갱신 범위는 최종 확인했다. 현재 Editor compile/play/test 상태를 조회했다고 주장하지 않는다.
- **추정과 미확인:** ItemIdentity 부재로 인한 ECB 실패, SampleScene의 실제 Missing Script/bake 결과, Drone 생산 손실의 실행 재현, 동시 장면 로드·언로드, 렌더 결과는 미확인이다. 평가 완료 표시는 이 항목들이 검증됐다는 의미가 아니다.

## 7. 남은 질문과 종료 범위

1. 현재 배포/사용 기준 진입 장면은 V2 Test Scene인가, SampleScene을 현재 V2로 이관할 것인가? 어느 쪽도 임의로 선택하지 않았다(F-025).
2. 실제 Item 8개에 ItemAuthoring의 타입을 부여하는 기존 계약을 유지할 것인가? 계약 유지 시 실제 베이킹에서 identity·transform·runtime mutable 상태 부재를 확인하는 검증이 필요하다(F-019/F-021).
3. Drone 레시피 출력을 Item 엔티티로 지원할 것인가? 지원한다면 Item DB용 prefab과 등록이 필요하며, 생산 실패 때 대기/명시적 거부/폐기 중 정책을 별도로 결정해야 한다(F-006). 별도의 Drone.prefab을 자동 등록하지 않았다.
4. 테스트 보강 후보는 실제 저장 SubScene에서 세 DB를 베이크한 결과의 entry 타입/참조/필수 컴포넌트 검사와 첫 Spawn 검증이다. 새 테스트 또는 테스트 자산 작성은 이번 요청 범위 밖이므로 제안만 기록했다. 렌더·실제 플레이 수동 확인은 사용자 수행 대상으로 남긴다.
