### 3.2 생성·Clear·재등록·용량·Dispose

| 작업 | 네 시스템의 확인한 계약 / 차이 |
| --- | --- |
| 생성 | OnCreate에서 Persistent Map 초기 용량 1024와 같은 엔티티의 Fence를 생성. 외부 주입 Map을 받아 소유하는 구조 아님 |
| 0개 | count==0이어도 ClearJob을 Fence.GetWriterDependency 뒤에 예약하고 SetWriter/state.Dependency에 등록. RequireForUpdate로 비어서 건너뛰지 않으므로 마지막 엔티티 제거 후 옛 키가 남지 않음 |
| 재구축 | 마지막 Writer+모든 Reader → Clear → `CombineDependencies(clearHandle, state.Dependency)` → PopulateParallel → SetWriter(populateHandle) 및 state.Dependency. Clear 중인 Map을 새 Reader에게 완성본으로 공개하지 않고 최종 Populate 핸들을 공개 |
| 용량 | Belt/Resource는 query entity 수, Item은 보관품을 포함한 query 수, Building은 각 축을 최소 1로 정규화한 **면적의 합**. 회전은 면적을 바꾸지 않음. 부족하면 Fence.Complete 뒤 `max(1024, 필요량*2)`로 확장. 매프레임 축소하지 않음 |
| 용량의 한계 | Item은 실제 월드 아이템 수보다 과다 예약할 수 있고 Building은 매번 메인 스레드 면적 합을 계산. 비용은 코드상 존재하나 병목/개선 효과는 미측정. 극단적 int 면적 합/배수의 overflow·메모리 부족은 이번 선택 테스트가 보장하지 않음 |
| 조회 | TryGet/Has/Count/AsReadOnly helper는 Map 접근만 수행. **읽기 전용 뷰는 불변 snapshot이나 완료된 snapshot을 뜻하지 않음**. 호출자가 올바른 Fence·가시 시점을 지켜야 함 |
| 해제 | OnDestroy는 해당 Fence.Complete 후 Map.IsCreated 검사·Dispose. 확인한 10개 Job Reader 등록이 Dispose의 대기 범위에 포함됨. 별도 Sync 간 UpdateAfter는 필요하지 않음 |
| 수명 전제 | OnUpdate는 Map/Fence 둘 중 하나가 없으면 건너뜀. OnDestroy는 singleton을 찾아 해제하며 별도로 singleton 엔티티를 제거하거나 컴포넌트를 default로 되돌리지 않음. 정상 World 전체 수명에서는 해제 주체가 명확함. 외부 singleton 제거/교체, 시스템만 파괴·재생성하는 hot restart의 지원은 미확인; 이를 정상 사용 경로의 확정 누수로 등록하지 않음 |
| 중복 셀 | Belt/Building/Resource의 TryAdd 반환을 소비하지 않음. 겹치는 두 Entity를 병합·예약 중재·오류로 처리하지 않고 한 값만 남김. 원본의 셀 유일성을 생산 경계가 보장해야 함. 실제 위반 가능한 배치 경로는 F-027 |

**Capacity 사전 조회 의문에 대한 결론:** 소스에는 getter 전에 명시적인 Fence.Complete가 없다. 하지만 현재 Sync는 유일한 Map Writer이며 이전 최종 Writer를 자기 state.Dependency에 보관한다. 현재 Entities의 `SystemState.BeforeOnUpdate:588`은 **그 시스템 자신의 이전 Job을 완료**한다. 따라서 재진입한 Sync의 이전 Clear/Populate는 끝나 있고 남은 타 시스템 Reader는 Capacity 읽기와 충돌하지 않는다. 재할당은 다시 전체 Fence를 완료한다. 선택한 반복 Sync 테스트도 통과했다. 이 조건에서 Capacity getter를 새 결함으로 등록하지 않는다. 이는 “Phase가 바뀌면 모든 Job이 완료된다”는 주장이 아니며, 별도 Writer를 추가하거나 writer 핸들을 자기 Dependency에서 누락하는 변경은 소유·동기화 계약 변경이다.

## 5. 동일 프레임 가시성과 필요한 동기화

**Fence는 안전한 접근 시점, Sync는 데이터의 갱신 시점**을 정한다. 완료 대기만으로 같은 프레임의 새 Entity/예약이 인덱스에 추가되지는 않는다. 반대로 다음 프레임에 읽는다는 사실만으로 이전 Job의 완료 대기를 생략할 수 없다.

공개 계약을 유지한 내부 변경 사례는 실제 수정 실험이 아닌 **현재 코드에 근거한 변경 영향 분석(추정)**이다.

1. **Clear/Populate의 Job 분할·수집 알고리즘 변경:** 동일 Map 의미·Sync 시점·최종 Writer/state.Dependency를 유지하면 Sync 내부만 바꿀 수 있다. 10개 Reader는 Job 이름·개수·순서를 알 필요가 없다. 지연 작업 시간의 변화로 Placement가 달라지면 F-026의 누락된 동기화가 드러난 것이다.
2. **Capacity 성장 계수 변경:** 최소 필요량과 안전한 재할당·Map 참조 수명을 유지하면 Sync 내부만 수정하면 된다. 소비자 수정은 불필요하고 Test05도 특정 2배 값이 아니라 필요 용량 이상과 모든 셀을 검사한다. 컨테이너를 Dispose하고 교체하는 변경은 기존 view 수명까지 지켜야 내부 변경이다.
3. **Validator 검사 주기/항목 변경:** 게임 데이터·Map/Fence 계약을 유지하므로 배치 로직을 함께 수정할 필요가 없어야 한다. 현재 Fence가 없는 Placement는 이 변경의 부수적 완료 차이에 영향을 받을 여지가 있다(F-026).
4. **BuildingInputDecision 내부 계산 최적화/Job 분할:** 결과 의미·최종 handle을 유지해 ProductOutput 코드를 고칠 필요는 없지만, Fence RW에 의해 ProductOutput까지 의존 체인에 묶인다(F-028). 이는 필요한 원본 데이터 충돌이 아닌 메타데이터 접근에서 발생한 추가 결합이다. 시간 단축량은 미측정이다.
5. **Footprint 처리 내부 정리:** Size의 base 의미를 유지한다면 Sync가 생산자가 Placement인지 Completion인지 구별할 이유가 없어야 한다. 현재 F-023을 생산자 판별 분기로 보정하면 불필요한 결합을 확대한다.

현재 Map 컨테이너 타입·iterator·BeltInfo/BuildingInfo 구조가 공개되어 있어 저장 방식 교체는 여러 Reader의 시그니처에 전파된다. 이는 **현재 공개 계약 변경**이며 “계약을 유지한 내부 변경도 모두 전파된다”는 증거로 섞지 않는다. Burst용 얇은 조회 view를 둘지의 선택은 별도 설계 사항이다. 공간 내용을 현재값으로 바꾸거나 Sync를 Command 직후로 옮기는 것도 관찰 시점이 달라지는 공개 계약 변경이다.

## 7. 발견 문제

#### F-026 — 배치의 메인 스레드 공간 조회가 세 인덱스의 Writer 완료를 기다리지 않음

- 발견 단계 / 유형 / 평가 축: Q12 / **안정성 결함·V2 설계 불일치** / 안정성·유지보수성·V2 적합성.
- 우선순위와 이유: **P2**. 배치 요청 처리 시 이전 Sync가 남아 있으면 조회 안전성이 다른 시스템의 완료 부수효과에 의존한다.
- 근거 수준: **코드 확인**. 경쟁 상태의 실제 예외·잘못된 배치 재현은 **미확인**.
- 위치: BuildingPlacementCommandSystem `:30–43,83–103,117`; BuildingPlacementValidationUtility `:73,91,97`; 세 Index Fence의 GetReaderDependency/Complete; WorldInvariantValidationSystem `:1,21,48–75`.
- 기대 계약과 출처: 각 Fence 주석·Q01b C06. 메인 스레드 Map Reader는 해당 최종 Writer 완료 뒤 조회해야 한다. AsReadOnly/IsCreated는 완료 대체가 아니다.
- 확인한 코드 동작: Command가 Map singleton만 요구하고 세 Map을 즉시 검증에 전달한다. 해당 Fence를 얻거나 Complete하는 코드가 없다. Query로 읽는 배치 요청/Config는 Spatial Populate의 NativeContainer 완료를 보장하는 계약이 아니다.
- 발생 조건과 영향: 이전 Sync Writer가 남은 상태에서 배치 검증을 수행하는 조건. Collections checks가 켜진 경우 안전성 오류, 검사 없는 실행에서 Clear/Populate 도중 관찰할 가능성이 있다. 잘못된 승인/거부로 이어질 가능성은 **조건부 추정**이며 Player 재현으로 확정하지 않는다.
- 근거 / 반대 근거: Editor 기본 Validator는 전 프레임 말에 Fence를 완료하여 조건을 가릴 수 있다. Placement 단위 테스트는 직접 Map을 채우거나 helper에서 Fence를 완료한다. `BeforeOnUpdate`는 **Placement 자신의** 이전 Job을 완료하므로 Sync의 Writer를 일반적으로 대신 기다리는 근거가 아니다.
- 수정 방향 후보: Command에서 세 인덱스의 준비와 메인 스레드 읽기 완료 경계를 명시하거나, 완료 계약을 포함한 조회 경계를 제공한다. Validator를 필수 게임 동기화 장치로 만들거나 Map을 강제 재구축하는 임시 대응은 피한다.
- 필요한 추가 검증: 미완료 Writer를 세 Fence 각각에 등록한 뒤 이미 존재하는 요청을 처리하는 EditMode 사례. Validator 없이 실행하고 오류 부재·정확한 검증 결과를 확인. 기존 관련 사례는 이 조건을 강제하지 않는다.
- 처리 / 별도 수정·재검증: **미결정 / 없음**. Q23에서 최초 기록을 이 문서로 연결한다.

#### F-027 — 같은 프레임의 별도 배치 요청이 동일 셀을 각각 승인하고 인덱스에서 한 현장을 가림

- 발견 단계 / 유형 / 평가 축: Q12 / **안정성 결함·V2 설계 불일치** / 세 축 모두.
- 우선순위와 이유: **P2**. 유효 요청을 여러 엔티티로 나눈 정상 입력으로 공사 현장 중복 점유가 가능하다. 우선순위 정책과 별개로 원본과 셀당 단일 인덱스가 불일치한다.
- 근거 수준: **코드 확인**, 아래 순차 추적. 실제 실행 재현은 **미확인**.
- 위치: PlacementCommand `:63–103,130–166`; PlacementValidationUtility의 overload별 claimedCells `:137–196,227–286,314–373`; BuildingSpatialSync `:153–160`.
- 기대 계약과 출처: BuildingSpatialIndex의 셀당 건물 조회, ValidateSinglePlacement의 기존 건물/현장 차단. Q01a/Q01b의 EndCommand와 Sync 경계 및 AGENTS의 “묶음 내부 선점” 범위.
- 확인한 코드 동작: 빈 (0,0)에 1×1 Storage 후보를 가진 요청 A/B를 같은 Command에 처리하면 A의 validation은 성공하고 현장 생성을 ECB에 기록한다. A의 claimedCells는 호출 종료 때 해제된다. B는 같은 옛 buildingMap과 새 claimedCells를 사용하여 역시 성공한다. EndCommand 후 두 현장이 존재하며 다음 Building Populate의 동일 key TryAdd는 하나만 보존한다.
- 발생 조건과 영향: 겹치는 후보가 서로 다른 요청 엔티티에 있음. Map이 어느 현장을 반환할지는 병렬 TryAdd의 선점 결과에 달리고 명시적 중재 순서는 없다. 후속 점유 조회가 다른 현장을 가리며 숨은 중복 원본을 고치지 못한다. 자재 유실·완공 이후 모든 결과까지 검증했다는 뜻은 아니다.
- 근거 / 반대 근거: Test07_BatchInternalContention은 **한 요청 안의 두 후보**만 검사한다. 정상 단일 요청/비중첩 요청은 해당 조건이 아니다. 새 Sync나 Fence 대기만으로 ECB 이전의 요청 간 예약 공백이 해소되지는 않는다.
- 수정 방향 후보: Command 처리 전체에서 승인 대기 점유를 전달하는 계약 또는 명시적 예약 owner를 마련한다. 어느 요청을 우선할지, strict 정책이 각 요청 단위로 어떻게 적용되는지는 사용자 설계 결정이 필요하다. Sync를 예약 중재자로 바꾸거나 Map을 제2 원본으로 쓰지 않는다.

#### F-028 — Fence 핸들 등록용 RW singleton이 Map Reader Job 사이에도 ECS 쓰기 의존을 추가함

- 발견 단계 / 유형 / 평가 축: Q12 / **유지보수 위험·V2 설계 불일치** / 유지보수성·V2 적합성. 현재 잘못된 게임 결과나 성능 병목으로 판정하지 않는다.
- 우선순위와 이유: **P2**. 메인 스레드에서만 수정하는 Fence 메타데이터의 접근 선언이 해당 시스템의 전체 예약 Job으로 전파되어, 독립적인 인덱스 Reader끼리도 추가 순서를 요구한다.
- 근거 수준: **코드 확인** — 현재 package/source-generator의 의존 구성. 실제 Job 타임라인·성능 영향은 **미확인**.
- 위치: 예시 BuildingItemInputDecision `:59–61,77–84`와 ProductItemOutputDecision `:55–58,71–79`; §2의 singleton query 생성·SystemState.GetEntityQuery/AddReaderWriters/Dependency/AfterOnUpdate 코드.
- 기대 계약과 출처: Fence.GetReaderDependency는 마지막 Map Writer만 반환하고 Reader들끼리는 AddReader로 묶어 다음 Writer에게 넘기는 모델. V2 §2.1의 불필요한 실행 결합 축소·병렬성 유지.
- 확인한 코드 동작: GetSingletonRW<BeltSpatialIndexFence>는 WithAllRW query를 생성한다. Build(ref state)는 해당 타입을 시스템 writer 목록에 등록한다. Reader는 state.Dependency와 Map Writer 핸들을 결합하고 최종 Job을 state.Dependency에 넣으므로 AfterOnUpdate가 이 Job을 Fence 타입 writer 의존에도 등록한다. 나중에 실행되는 다른 Reader의 state.Dependency가 이를 다시 받는다.
- 발생 조건과 영향: 같은 Fence를 RW로 취득하고 Job을 예약하는 두 Reader. BuildingInput과 ProductOutput은 Map과 상태를 읽고 서로 다른 decision을 쓰지만 Belt Fence 때문에 추가 선후 관계가 생긴다. 원래 ECS 데이터 충돌에서 필요한 의존까지 불필요하다고 주장하지 않는다. Job 순서/길이의 전파는 코드상 확인되나 실제 손실 시간은 측정하지 않았다.
- 근거 / 반대 근거: 수동 Fence의 Reader→Writer 안전성은 올바르게 유지되고 선택 통합 테스트도 통과했다. 현재의 보수적인 직렬화는 안전성 결함이 아니다. “Fence RW니까 항상 메인 스레드에서 모든 Job을 Complete한다”는 주장도 하지 않는다.
- 수정 방향 후보: 핸들 메타데이터 갱신과 ECS 게임 데이터 Job 접근 추적의 경계를 분리할지 검토한다. 대안도 현재 World 수명·Reader 등록·Writer 대기·Dispose 계약을 보존해야 한다. 단순히 GetSingletonRW를 없애거나 state.Dependency를 버리면 다른 의존이 깨질 수 있으므로 이번에 임의 변경하지 않는다.
- 필요한 추가 검증: 출력 상태가 독립적인 두 read-only Map Job의 dependency 포함 관계/프로파일 표본. 정상 결과만 검사하는 기존 테스트는 이 추가 결합을 판별하지 않는다. 목표 병렬성·측정 필요성은 별도 결정.
- 처리 / 별도 수정·재검증: **미결정 / 없음**.
