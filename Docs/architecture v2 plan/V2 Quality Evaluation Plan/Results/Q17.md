## 3. 상태 원본·Reader/Writer·프레임 경계

### 소유권과 실제 접근

| 상태 | Owner / 실제 Writer | 실제 Reader | 수명·동기화 계약 |
| --- | --- | --- | --- |
| ResourceGenerationSettings | 설정 게시 로더 | Bootstrap, ResourceGeneration | Bootstrap은 설정 singleton 존재를 요구. 설정의 저장 형식/파싱 순서를 모르고 값만 읽음 |
| Bootstrap 실행 여부 | 자기 SystemState.Enabled | ECS 그룹 실행 | 큐에 모두 추가한 뒤 false. 청크 생성 완료가 아니라 요청 발행 완료를 의미 |
| ChunkLoadRequestQueue + Element | Bootstrap이 없을 때 생성; Bootstrap Append, ChunkLoad Clear | ChunkLoad | 유일 tag 엔티티에 요청 버퍼가 있어야 함. 현재 Scripts에서 외부/카메라 Producer 구현은 발견되지 않음 |
| GeneratedChunkTracker.Map/Pending | **ChunkLoad**가 Persistent 집합 생성, 추가/제거, OnDestroy Dispose | 런타임 집합 내용은 ChunkLoad만 조회 | ECS 컴포넌트에 든 수명주기 상태. 공간 인덱스가 아님. ResourceGeneration은 marker/entity만 조회하고 두 집합을 읽거나 쓰지 않음 |
| GeneratedChunkReadyElement | ChunkLoad Append, ResourceGeneration Clear | ResourceGeneration | tracker 엔티티에 위치. 준비 전 보존, 준비 후 스폰/완료 기록을 마친 뒤 소비 |
| GeneratedChunkCompletedElement | ResourceGeneration의 **EndCommand ECB Append**, ChunkLoad Clear | 다음 Command의 ChunkLoad | 스폰 명령 뒤 같은 ECB에 기록. 완료 알림 반영 후 Map 추가/Pending 제거 |

`rg -n -F`로 Scripts의 Queue/Tracker/Ready/Completed 참조를 확인했다. 런타임 Native 집합 Reader/Writer는 ChunkLoad 하나이며 Job으로 넘기는 경로가 없다. 따라서 현재 이 집합에 공간 인덱스와 같은 별도 Fence가 없다는 것 자체는 결함이 아니다. 향후 Job reader를 추가한다면 그때 reader 완료·Dispose 계약을 새로 정의해야 한다. DynamicBuffer 협력은 메인 스레드의 명시적 Command 순서와 ECB 재생 경계를 사용한다. 관련 OnUpdate에는 버퍼 취득 후 즉시 구조 변경을 실행하면서 기존 버퍼를 계속 쓰는 구간이 없다.

### 처리 단계별 상태

| 시점 | 코드 확인한 상태 변화 | 중복/대기 의미 |
| --- | --- | --- |
| Initialization | 설정이 있어야 Bootstrap 실행. 큐를 준비해 `[-floor(N/2), -floor(N/2)+N-1]`의 두 축 Cartesian product를 추가하고 자기 비활성화 | 이미 있는 큐는 덮어쓰지 않고 Append. Bootstrap 자체는 중복 검사하지 않으며 접수 Owner가 처리 |
| Command의 ChunkLoad 시작 | Completed 각 좌표를 Map.Add하고 Pending.Remove한 후 Completed.Clear | 큐가 없거나 비어 있어도 완료 소비를 먼저 수행. 같은 완료 좌표 반복은 집합 연산상 멱등적 |
| 새 요청 접수 | Map 포함이면 drop. 아니면 Pending.Add 성공 시에만 Ready 추가. 원래 요청 버퍼 Clear | 같은 묶음·다음 호출의 중복 모두 병합. 원래 큐 삭제는 대기 인계가 확정된 뒤라 Consume-on-Apply에 맞음 |
| ResourceGeneration 준비 대기 | 설정/DB/버퍼/ECB/프리팹 준비 실패 시 return | Ready와 Pending 유지. 다음 호출에서 재검사. 불완전 준비를 완료로 표시하지 않음 |
| ResourceGeneration 기록 완료 | 각 Ready의 스폰과 Completed를 같은 EndCommand ECB에 기록하고 Ready.Clear | Ready=0은 완료가 아님. Pending이 여전히 중복 기록을 막음 |
| 같은 Command 끝 | EndCommand Playback에서 자원과 Completed가 반영됨 | 이 프레임의 ChunkLoad는 이미 끝나 Map은 아직 미확정. 자원 실체 존재와 Map 상태에 의도적 시차 |
| 다음 Command | 완료를 Map으로 확정한 뒤 새 요청 검사 | 완료와 같은 좌표의 재요청이 있으면 Map 검사에서 drop. Pending 제거가 재생 전 재생성 창을 만들지 않음 |

현재 정렬된 그룹의 tick을 기준으로 “다음 프레임”이다. 임의로 Load.Update를 다시 호출하는 테스트에서는 **다음 Load 호출**이 소비 시점이며, 렌더 프레임 번호를 저장하는 구현은 아니다. 준비가 끝난 정상 빈 청크도 완료 알림을 받는다. 설정 버퍼가 아예 비어 준비 조건에서 반환되는 상태와, 유효 설정의 weight=0 등으로 생성물이 0개인 상태를 혼동하지 않는다.

Bootstrap의 N<=0 fallback=3은 Settings 생성자와 겹치지만 필드 직접 설정도 가능하므로 독립 소비 경계의 방어로 볼 수 있다. 짝수 N은 좌표 중심이 -0.5에 위치한다. 현재 N=3 및 확인한 테스트 입력 1/3에는 영향이 없으며, 주석의 “원점 중심 대칭”을 근거로 짝수 크기 금지 규칙을 만들어 결함으로 등록하지 않았다.

## 4. 시스템 의존성과 공개 계약 유지 시 변경 영향

| 의존하는 시스템 → 대상 | 형태 / 공개 계약 또는 가정 | 필요한 이유 / 변경 전파 | 판정 |
| --- | --- | --- | --- |
| Bootstrap → ConfigLoad/Settings | UpdateAfter, RequireForUpdate, 값 읽기 | Init 내 게시 후 초기 요청. 다른 로더도 같은 singleton 계약을 충족하면 Bootstrap 알고리즘은 그대로 사용 가능 | **필요한 준비·데이터 계약**. 구체 타입 순서 참조는 있지만 파서 내부 의존은 없음 |
| Bootstrap → 요청 큐 → ChunkLoad | 큐 생성·Append / 큐 소비 | Producer는 좌표만 제출하며 Map/Pending/Ready를 직접 관리하지 않음 | **필요한 계약**. 큐 tag와 버퍼가 함께 존재해야 한다는 전제는 명시할 대상 |
| ChunkLoad → Ready → ResourceGeneration | 버퍼 게시·소비, UpdateAfter(ChunkLoad) | 동일 Command에서 접수한 작업 전달. ResourceGeneration은 생성 준비·계산만 수행 | **필요한 순서**. “바로 뒤” 주석과 달리 UpdateAfter는 인접 실행을 보장하지도 요구하지도 않음 |
| ResourceGeneration → EndCommand → Completed → ChunkLoad | ECB 호출·결과 전달·다음 호출 소비 | 실제 스폰 반영 이후 완료 확정. Pending을 Generation이 해제하지 않음 | **필요한 공개 왕복 계약**. 다른 시스템의 정리 함수/내부 집합에 기대는 순환 결합 아님 |
| ChunkLoad → Tracker의 두 집합/수명 | 자체 상태 직접 접근·Dispose | 중복 접수와 완료 추적의 단일 Owner | **국소 구현**. 기존 tracker를 채택할 때 부속 버퍼·유효 NativeContainer를 전제함. 현재 외부 production Writer는 없음 |

공개 계약을 유지한 내부 변경의 정적 영향 사례:

1. **광맥 계산/프리팹 해석 최적화**: Ready의 준비 대기 의미, 스폰 이후 Completed, EndCommand 경계를 유지하면 Bootstrap/ChunkLoad 수정은 필요 없다. 영향은 ResourceGeneration/Utility와 해당 생성 테스트에 머문다. 완료 순서를 뒤집거나 준비 전 Ready를 지우는 변경은 내부 최적화가 아니라 공개 수명주기 계약 위반이다.
2. **ChunkLoad의 중복 검사 루프 리팩터링**: Map/Pending 및 Ready/Completed 의미를 유지하면 ResourceGeneration이나 설정 로더의 내부를 수정할 이유가 없다. 다만 기존 테스트가 공개 Tracker 필드로 완료 상태를 검사하므로 자료구조 자체를 교체하는 것은 공개 데이터 형식 변경이다. 이 변경을 “계약 유지”라고 부르지 않는다.
3. **Config 파싱 구현 변경**: 같은 ResourceGenerationSettings를 같은 준비 경계에 게시하면 Bootstrap은 영향을 받지 않는다. 새로운 Init Producer를 도입할 때는 RequireForUpdate로 대기할 수 있으나 같은 tick 발행을 유지하려면 해당 Init 순서를 확인해야 한다. 현재 ConfigLoad 내부의 메서드 호출 순서를 알아야 하는 것은 아니다.

Load의 국소 테스트는 좌표 큐와 Tracker만으로 실행되며 자원 Config/DB·공간 인덱스·채굴 시스템을 기동할 필요가 없다. 완료의 실체 반영을 검증하는 통합 테스트에 Generation·EndCommand가 필요한 것은 실제 계약 검증이며 불필요한 준비 결합으로 보지 않는다. 실제 현재 V2의 경계를 평가했으며 V1 대비 개선량은 측정하지 않았다.

추가 관찰은 확정 신규 결함과 구분한다:

- Tracker/Queue의 singleton 유일성·부속 버퍼·NativeContainer가 유효하다는 내부 월드 구성 전제가 있다. 현재 production 생성 경로는 그 구성을 함께 만든다. 외부가 tag만 만들거나 tracker를 파괴/교체하는 지원 경로는 확인되지 않아, 그런 가정만으로 현재 충돌 결함을 등록하지 않았다.
- 완료 소비는 Pending 포함 여부를 검사하지 않고 Map.Add한다. 현재 유일 Producer는 Ready 처리 뒤 스폰과 같은 ECB에 완료를 기록하므로 정상 경로에는 출처가 맞는다. 임의의 완료 이벤트 주입·저장 복원·취소 후 늦은 완료까지 지원한다는 계약은 없다.
- Ready를 ECB 기록 뒤 지우므로 기록/재생 실패 시 자동 rollback·재시도는 없다. Q10의 prefab 준비 검사는 일반적인 미준비를 사전에 막지만 모든 ECB 실패를 보장하지는 않는다. 실패를 강제로 주입하지 않았고 정상 조건에서 실패하는 경로를 새로 입증한 것은 아니다. Q18의 직접 범위로 남긴다.
- Map은 생성 수명주기 기록이므로 자원이 채굴로 사라지더라도 재요청만으로 재생성하도록 지우지 않는다. unload/reset/재생성 기능이 없다는 사실 자체를 Q17 결함으로 취급하지 않는다.

## 7. 미확인 사항·제안·남은 질문

1. **초기 크기 계약**: 허용할 최대 N 또는 프레임당 발행량을 정할 필요가 있는가? F-017의 설계 질문에 연결한다. 한도·시간 분할을 임의로 구현하지 않는다. 과도한 맵을 실제 생성하는 부하 테스트 대신, 결정된 경계 입력을 검사하는 테스트를 제안한다.
2. **한 번 실행의 범위**: 현재는 SystemState.Enabled에 의한 해당 시스템 인스턴스의 1회 발행이다. 같은 World에서 새 게임/reset을 지원할 때 큐·Tracker·설정·Bootstrap을 어떻게 함께 초기화할지 별도 계약이 필요하다. 현재 지원 기능으로 가정하지 않는다.
3. **테스트 보강 후보**: 정렬된 Initialization 그룹에서 설정 부재→준비→반복 tick의 1회 발행, 기존 큐 내용 보존, N=1/0/짝수의 의도한 범위, 큐 부재 상태의 완료 소비, 중복 완료 멱등성을 직접 검사할 수 있다. 현재 Test02–06만으로 이 모든 경계를 실행 확인했다고 표현하지 않는다. 새 테스트는 작성하지 않았다.
4. **영구 준비 대기**: DB/필수 조건 누락이 계속되는 상태의 진단은 Q10의 기존 질문을 재사용한다. timeout/강제 완료/자동 fallback은 새 게임 규칙이므로 추가하지 않는다.
5. **미확인**: 실제 장면의 자동 초기화·프리팹 베이킹, 극단 크기 성능·메모리, ECB 부분 실패·취소/복원·tracker 외부 교체, 실제 플레이·입력·렌더·플랫폼·persistence. 사용자 수동 확인 결과는 전달받지 않았다.

필요한 선택 검증은 최종 통과했고, 이 범위의 미해결 사항은 추가 기능·경계 테스트 제안 또는 별도 설계 결정이다. Q17을 완료로 기록하되 코드 수정·테스트 보강·Q18 이후 평가를 자동 진행하지 않는다.
