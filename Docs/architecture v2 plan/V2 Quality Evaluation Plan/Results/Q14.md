### 3.2 판단→예약→적용

1. **Input Decision:** 입고 결정을 다시 켤 수 있도록 `IgnoreComponentEnabledState`로 조회한다. 이 옵션은 함께 필요한 BeltMovementState의 enable도 무시한다. 월드 Owner, 현재 셀 Belt 존재, progress≥0.999, 진행 방향 다음 셀 Building, Storage 존재를 확인한다. 필터 부재/AllowAll은 허용, Whitelist는 지정 비트만, Blacklist는 지정 비트 이외를 허용한다. FixedBitSet은 128비트이며 범위 밖 IsSet=false, 알 수 없는 filter Mode는 현재 허용 분기다. 정상 enum 범위 밖 입력 정책까지 안전하다는 뜻은 아니다.
2. **제작기 경계:** WaitingForByproductOutput이면 필터와 무관하게 거절한다. Command가 같은 프레임에 직접 필터/상태를 바꾸면 Phase·ECS 의존으로 Decision에서 읽는다. NoRecipe 자체를 별도 거절하지 않으며, 확인한 레시피 해제 경로는 빈 Blacklist다. 이 정책의 타당성은 Q22 질문으로 남기고 새 게임 규칙을 정하지 않았다.
3. **Reservation:** 활성 결정 중 CanDeposit=true/slot=-1만 처리한다. Storage/Stored 버퍼 부재 또는 SlotCount≤0이면 거절하고 disable. `safeSlotCount=min(SlotCount,120)`의 두 FixedList에 기존 수량·품목을 집계하고 pending 수량을 더한다. 같은 품목의 여유 슬롯 우선, 없으면 가장 낮은 빈 슬롯을 고른다. 상한을 넘는 슬롯·오염된 기존 버퍼를 복구하는 시스템은 아니다.
4. **동시 입고:** 단일 Schedule로 공유 pending Map을 직렬 수정한다. 기존 슬롯에는 `기존 수량+pending<MaxStack` 조건이 적용돼 정원 초과 승인을 막는다. 서로 다른 품목이 새 슬롯에 동시에 섞이는 것도 막지만, 같은 품목까지 새 슬롯을 공유하지 못하는 부작용이 F-031이다. 쿼리 순서는 명시적 공정성·설치 우선순위 계약이 아니다. 실패한 후보는 다음 Decision에서 다시 계산된다.
5. **Input Apply:** 활성 승인에 대상 Stored 버퍼가 있으면 append→movement disable→input decision disable→Transfer enable 순서로 처리한다. slot 범위·MaxStack·필터·기존 Owner를 다시 판단하지 않고 Reservation을 신뢰한다. 버퍼가 사라지면 결정 거절·소비. 비활성화가 소비 표식이며 성공 후 CanDeposit/slot 값 자체를 초기화하지 않는다.
6. **Ownership/ECB/Sync:** `UpdateBefore(ItemOwnershipApplySystem)`과 ECS Job 의존이 전달 순서를 보장한다. Ownership은 직접 바뀌고 Transfer는 disable, DisableRendering은 EndStateApply에서 확정된다. ItemSpatialSync는 그 후 Owner 기준으로 저장품을 월드 Map에서 제외한다. 입고는 Grid/Transform을 건물 좌표로 옮기지 않는다. 저장된 동안 위치가 이전 벨트 값이어도 Map 제외와 소유 버퍼가 표현을 담당한다.

Apply는 Transfer 컴포넌트가 없으면 버퍼 추가 후 요청 발행만 생략한다. 정상 Factory/ItemLifecycle 경로는 필요한 요청을 준비한다. 따라서 **성공 인계의 전제는 해당 컴포넌트 구성**이며 optional guard가 원자적 실패/롤백을 제공한다고 설명하지 않는다. 이번에는 비정상 프리팹 구성의 별도 실행 재현이나 신규 문제 등록을 하지 않았다.

입고 예약 뒤 Execution의 제작 재료 소비나 같은 StateApply의 출고가 공간을 비울 수 있다. 예약은 이 미래 여유를 선반영하지 않아 한 프레임 보수적으로 거절할 수 있다. 이는 새 슬롯의 품목 정보가 없는 F-031과 별개다. 예약 이후 다른 Writer가 같은 슬롯을 추가 점유하는 확장은 공통 승인 계약을 따라야 한다.

**변경 영향 사례 — 코드 변경 없이 현재 흐름으로 추론:**

- Reservation의 배열/반복 집계를 건물별 캐시로 바꾸거나 pending에 품목을 추가해도, 승인 slot·enable·CanDeposit와 실행 경계를 유지하면 Input/Apply/Ownership 수정은 필요 없다. 현재 처리 비용은 후보마다 Stored 버퍼와 슬롯을 다시 훑지만 측정 없이 병목으로 확정하지 않았다.
- 소유권 인계 결과·ECB 시점을 유지한 Ownership 내부 태그 코드 리팩터링은 Input이 알 필요 없다. 반면 Owner 반영을 다음 프레임으로 미루는 것은 공개 가시성 계약 변경이므로 Sync·Validator를 포함한 소비자 검토가 정상적인 변경 전파다.
- **비활성 아이템의 progress를 보존하던 철거 정리가 0으로 초기화하도록 내부 정리만 바뀌는 경우**, 비활성 아이템은 이동에 참여하지 않는다는 공개 계약 아래에서는 입고 결과가 달라질 이유가 없다. 현재 Input은 그 오래된 progress를 읽으므로 동일한 비활성 상태라도 입고 여부가 달라진다(F-032). 상대 도메인의 내부 잔여값 정리에 기대는 사례다.
- FixedBitSet 내부 비트 연산을 바꾸되 IsItemAllowed 결과를 유지하면 Input을 수정할 이유 없다. 반면 제작 상태를 세분화하면서 “잔여물 배출 중 입고 금지” 행동 계약만 유지하려 해도 Input의 구체 enum 비교가 변경 전파 지점이 된다. 별도 입력 가능 플래그/정책을 제공할지는 설계 선택이며 이번에 추가하지 않았다.

필요한 직렬 예약·공유 버퍼 쓰기 의존과 Phase/ECB는 제거 대상이 아니다. 시스템 수나 UpdateBefore 개수를 줄이는 것만으로 결합이 개선됐다고 판단하지 않았다.

#### F-031 — 새 슬롯의 예약 품목을 기록하지 않아 같은 품목의 동시 입고가 슬롯을 분산 점유하거나 거절됨

- 우선순위와 이유: **P2**. 아이템 유실이나 상한 초과의 확인은 없지만 유효한 동시 입고가 불필요하게 거절되거나 같은 품목이 여러 슬롯에 분산돼 다른 품목을 받을 공간을 줄인다.
- 근거 수준: **코드 확인**. 수치 사례는 분기 추적이며 실행 재현 결과가 아니다.

#### F-032 — 입고 판단이 movement enable을 무시해 비활성 월드 아이템의 잔여 progress로 입고를 승인함

- 발견 단계 / 유형 / 평가 축: Q14 / **안정성 결함·V2 설계 불일치·설계 판단 필요** / 대상 선정·수명주기 결합.
- 우선순위와 이유: **P2**. 비활성화된 바닥 아이템과 활성 벨트 아이템의 계약이 갈리고, 다른 시스템의 progress 정리 방식에 따라 원치 않는 수납이 가능하다.
- 근거 수준: **코드 확인**, 정상 수명주기로 이어지는 조건부 시나리오 추론. 실행 재현은 미수행.
- 위치: `BuildingItemInputDecisionSystem.cs:35–39,109–136,190–194`; `Components/Belt/BeltComponents.cs:21–46`; `BuildingLifecycleApplySystem.cs:198–218`.
- 기대 계약과 출처: BeltMovementState의 enableable 이동 참여 계약과 Q13의 활성 상태 검사. 벨트 철거 cleanup은 아이템을 “정적 바닥 아이템”으로 보존하기 위해 movement를 끈다. 바닥 수거를 일반 벨트 입고와 같은 기능으로 취급하는 명시적 재활성화 계약은 확인하지 못했다.
- 확인한 코드 동작: Input Decision의 IgnoreComponentEnabledState는 input decision을 다시 계산하는 데 필요하지만 BeltMovementState enable도 무시한다. Job은 EnabledRefRO나 IsComponentEnabled로 movement를 다시 확인하지 않는다. Owner Null·BeltMap 존재·progress≥0.999·대상/필터 조건만으로 입고를 켠다. Reservation/Apply도 movement enable을 승인 조건으로 사용하지 않는다.
- 발생 조건과 영향: 비활성 월드 아이템이 progress=1을 보존하고 해당 좌표에 벨트, 진행 방향에 Storage가 있으면 입고된다. 조건부 수명주기 사례는 **입고 대상이 없던 벨트 종단 아이템 → 벨트 철거(진행도 보존, enable=false) → 같은 셀 벨트 재설치와 인접 Storage 준비 → Sync 이후 Input**이다. Belt 이동은 이 아이템을 건너뛰지만 Input은 수납할 수 있다. 같은 비활성 아이템을 progress=0으로 정리한 경우에는 수납하지 않아 결과가 잔여값에 의존한다.
- 미확인 사항 / 반대 근거: 정상 Factory의 벨트 아이템은 enable=true이고 기존 테스트도 이 구성이다. 일반 신규 바닥 아이템은 progress=0이므로 모든 바닥 아이템이 자동 수납되는 것은 아니다. 재설치 후 자동 수거를 의도한 것인지 사용자 판단이 필요하며, 의도했더라도 progress 잔여값에 따른 선택 차이는 공개 규칙으로 정리해야 한다.
- 수정 방향 후보: Input Decision은 재계산하되 이동 활성 상태를 명시적으로 검사하거나, 바닥→벨트 복귀/수거를 별도 공개 전환 계약으로 정한다. 모든 enable 상태를 무시하지 않는 쿼리로 단순 교체하면 비활성 input decision을 다시 켜지 못할 수 있으므로 두 enable 의미를 구분해야 한다.
- 필요한 추가 검증: movement false/true × progress 0/1 × World/Stored의 후보 선정, disable 직전 활성 input decision의 정리, 철거·재설치 후 입고. 이번 후보 테스트에는 이 조건이 없다.
- 처리 / 별도 수정 작업과 재검증 근거: **미결정 / 코드·테스트 변경 없음**. 자동 수거 정책 결정 후 별도 수정·재검증.

기존 문제의 이번 경계 확인: **F-007**의 MaxStack≤0도 빈 슬롯 분기는 여전히 승인하며 Apply는 재검사하지 않는다. **F-004**의 같은 tick 입고·철거는 버퍼/Owner/렌더 태그가 서로 다른 시점에 바뀌는 문제로 남는다. **F-028**은 Input이 두 Fence singleton을 RW로 얻는 동일 패턴에 적용된다. 최초 결과를 대체하거나 신규 ID로 세지 않는다.

- **미실행 이유:** F-031/F-032의 정확한 반례 테스트는 없으며 테스트 추가는 금지 범위다. 후보의 MaxStack 초과 검사 테스트는 이미 오염된 버퍼를 주입해 Validator를 검증하므로 Reservation의 상한 승인 검증을 대신하지 않아 실행하지 않았다. 전체 EditMode·Play Mode·실제 장면·성능도 수행하지 않았다.

## 7. 남은 질문·완료 조건

1. **동시 입고 슬롯 정책:** 같은 품목은 이번 프레임에 새로 선점한 슬롯에도 남은 MaxStack까지 병합하는 것이 의도인가? 현재 기존 스택 병합 계약에 맞추는 F-031 수정안을 제안하며, 후보 간 우선순위/공정성은 별도로 정해야 한다.
2. **비활성 아이템 수거:** 벨트 철거 후 재설치한 바닥 아이템을 자동으로 벨트/입고에 참여시킬 것인가? 허용한다면 progress 잔여값이 아닌 명시적 전환 조건이 필요하다. 이번 평가에서 임의로 동작을 선택하지 않았다.
3. **제작기 입고 가능 계약:** generic Input이 특정 CrafterStatus를 직접 해석하는 방식을 유지할지, 제작 도메인이 공개 입고 가능 상태를 제공할지? NoRecipe와 빈 Blacklist의 허용 정책은 Q22에서 관련 범위만 확인할 질문이다.
4. **검증 보강:** F-031/F-032 사례 외에 품목별 Registry 상한 max-1/max, SlotCount 0/120/초과, 버퍼 소멸·필수 Transfer 컴포넌트 누락 시 인계 실패, 같은 tick 입고·철거의 최종 태그를 테스트 후보로 남긴다. 승인·구현은 별도 작업이다.

이번 범위의 코드 분석과 선택 실행은 완료됐고 필요한 검증의 차단은 없다. 신규 반례의 실행 재현·설계 결정·수정은 미완료로 구분했다. 계획상 다음 단계는 **Q15 — Storage/Product Output→예약→Apply**이며 별도 요청 전에는 진행하지 않는다.
