## 3. 상태 원본·알고리즘·소비 계약

### 3.1 Reader/Writer와 수명

| 상태 | Writer | Reader / 소비 | 확인한 계약과 경계 |
| --- | --- | --- | --- |
| `GridPosition`, `BeltMovementState.Progress`, `LocalTransform` | 일반 이동은 Belt Execution. 입출고·Routing Apply는 전달 위치/진행도 초기화. Lifecycle은 생성/철거 초기화 | Decision은 Grid/Progress, Execution은 세 필드, Sync는 위치를 인덱싱 | 원본은 ECS. Transform만 변경해서 이동시키는 계약이 아님. Apply의 Progress=0은 진행의 다른 Writer이며 전진 계산과 구분 |
| `BeltMovementState` enable | 생성/철거·저장 입고는 false, 출고/라우팅은 true | 두 Belt Job 모두 기본 enableable 쿼리로 활성 상태만 처리. 이웃 조회도 활성 여부 검사 | 컴포넌트 존재만으로 이동하지 않음. ownership과 별개이며 `Owner == Null`도 함께 필요 |
| `ItemOwnership.Owner` | Ownership Apply 및 생성/수명주기 경로 | 두 Belt Job과 이웃 간격 검사 | Belt는 world/stored 공개 구분만 필요. `StoredItemElement`/`ProductItemElement`의 제거·슬롯 정책을 알 필요 없음. 소유권 요청만으로 movement enable이 자동 정리되는 것은 아님(Q02) |
| `BeltMovementDecision.PlannedProgress` | Decision이 계산; Execution이 0으로 소비 | Execution; Validator가 잔류 검사 | 일반 컴포넌트이며 enable 요청이 아님. Reservation은 현재 이 필드를 읽거나 수정하지 않음. 공개 주석 범위 [0,1] |
| `IsBlocked` | Decision | 현재 runtime의 별도 행동 소비자 없음; 테스트/진단 | Execution이 값을 보존. true라도 승인된 부분 이동은 실행. 계획 소비는 PlannedProgress=0이며 IsBlocked=false가 아님 |
| Belt/Item Map + Fence | 해당 SpatialSync가 Map 내용, 각 Reader가 핸들 등록 | Decision은 두 Map, Execution은 Belt Map | Map은 파생 스냅샷. Decision은 Writer 핸들과 state.Dependency를 결합하고 양쪽에 AddReader; Execution도 Belt Fence를 인계. Map 내용과 컴포넌트 쓰기의 의존성은 별개 |

**enable 경계:** 저장품은 제외되고, 입력 전달이 movement를 끄며 출력 전달은 Progress=0과 함께 켠다. Execution의 non-world/missing-belt 분기는 계획만 0으로 지우며 enable까지 고치지 않는다. 누락 벨트 처리는 수명주기 책임이고 Validator가 orphan을 검출한다. 비활성 엔티티는 Execution과 계획 잔류 검사에서도 제외된다. “모든 엔티티의 계획이 무조건 매 프레임 0”이라는 강한 보증은 없다.

### 3.2 이동 승인과 적용

| 조건 | Decision 코드 동작 | 안정성 판단과 한계 |
| --- | --- | --- |
| dt/속도 | `min(DeltaTime,0.1)`; 원하는 전진량=현재 Belt speed×dt. dt≤0이면 시스템 반환, 원하는 양≤0이면 계획 0 | 긴 프레임 전체 시간을 따라잡는 로직이 아님. Config speed 10이면 dt=0.1에서 1칸 이동을 요청할 수 있음 |
| 같은 셀 선행 아이템 | 자신보다 progress가 epsilon 이상 큰 활성 월드 아이템 중 최솟값, `max(0,선행-progress-0.25)`로 제한 | 시작 스냅샷에 보수적으로 반응. 선행 아이템의 이번 프레임 이동 계획은 사용하지 않음. 이미 동일 progress인 두 아이템을 분리하는 복구 로직은 아님 |
| 다음 벨트 없음 | `max(0,1-progress)`까지만 이동 | 종단 progress=1에 머무를 수 있음. 입고 판단은 이 상태를 별도로 처리 |
| 다음 셀 비어 있음 | `min(원하는 양,1)` | 다음 셀 자체는 비어 있어도 그 너머 아이템까지의 간격은 보장하지 않음(F-030) |
| 다음 셀 점유 | `(1-progress)+다음 셀 최소 progress-0.25`를 양수 제한하고 최대 1로 제한 | 기존 점유와의 간격은 검사하지만 다른 출발점의 도착 계획은 보지 않음(F-029) |
| 다음 셀 4개 이상 | 위 간격 한도에 `max(0,(1-epsilon)-progress)`를 추가 적용 | 시작 시 가득 찬 셀에 들어가지 않는 방어. 현재 3개인 셀에 복수 도착할 때의 최종 수용량 계산과는 다름 |

Execution은 소유권/현재 벨트를 확인하고 **계획 값을 복사한 직후 0으로 소비**한다(94–97행). 양수인 계획만 진행도에 더하고, 다음 벨트가 있으면 셀을 옮겨 progress에서 1을 뺀다. 다음 벨트가 없으면 progress=1에서 멈춘다. 경계를 넘으면 새 Belt 방향으로 Transform을 계산한다. 최대 4회 hop·최종 progress 상한은 방어 장치이며, 점유·spacing·capacity 재검사는 아니다. 테스트의 수동 plan=1.4/2 사례는 정상 Decision의 [0,1] 계약을 넘긴 Execution 방어 테스트이지 정상 pipeline의 전방 안전성 증거가 아니다.

Decision/Execution 자체는 ECB를 쓰지 않는다. **Decision→Execution의 데이터 의존 완료, StateApply의 전달/소유권 적용과 EndStateApply ECB, 이후 Sync Map 갱신**을 구분해야 한다. Command ECB가 먼저 재생돼도 Map이 즉시 갱신된 것은 아니다(Q01a/Q01b/Q12). 현재 프레임의 topology 변경과 스냅샷 선택 문제는 Q12의 가시성 계약을 유지하며 여기서 별도 새 문제로 등록하지 않는다.

dt≤0 또는 필수 singleton 누락으로 Decision이 실행되지 않을 때를 표시하는 frame stamp는 없다. 정상 한 사이클에서 Execution이 계획을 지우므로 잔류를 확인하지 못했지만, 외부에서 오래된 계획을 주입하거나 시스템 일부만 실행해도 자동으로 무효화된다고 보장하지 않는다. 현행 정상 경로의 재현 결함으로 등록하지 않고 확장 계약 질문으로 남긴다.

## 4. 시스템 간 의존성과 변경 영향

| 의존하는 시스템 → 대상 시스템/데이터 | 의존 형태 | 공개 계약 또는 숨은 가정 | 필요한 이유 | 변경 전파 범위 | 근거·판정·문제 ID |
| --- | --- | --- | --- | --- | --- |

공개 계약을 유지한 내부 변경의 영향 사례(실제 코드를 수정한 실험이 아니라 호출·데이터 흐름 추론):

1. **Decision의 후보 검색 순서나 최소값 계산을 같은 승인량으로 리팩터링:** Execution·Storage·Routing 수정 불필요. 소비자는 최종 PlannedProgress만 읽는다. 특정 이웃 열거 순서를 공개 규칙으로 쓰지 않는다.
2. **Decision이 다다음 셀 간격까지 검사해 같은 [0,1]·안전한 승인량 계약을 지킴:** Execution의 경계 이동·소비 코드는 그대로 둘 수 있다. Decision 테스트와 통합 반례 검증만 보강하면 된다. 반대로 plan을 목적지/예약 토큰으로 확장하면 공개 계약 변경이므로 Reservation/Execution 소비자 수정은 정상 전파다.
3. **Storage 내부의 슬롯 탐색/버퍼 정리를 바꾸되 인계된 Owner·Grid·Progress·enable 결과와 Phase를 유지:** Belt 코드 수정 불필요. Belt가 알아야 할 것은 공개 인계 결과다. 단, 출고 대상 선정이 다른 유효 후보를 고르는 내부 변경만으로도 일반 이동과 같은 셀을 고를 확률이 달라져 잠재 F-029가 드러난다. 다른 시스템 내부 선택을 알아야 피할 수 있는 현재 상태는 명시적 경합 승인 계약으로 대체할 대상이다.
4. **Sync의 Clear/Populate를 동일 스냅샷·Fence를 보장하는 내부 재구축으로 교체:** Belt의 계산/적용 코드를 바꿀 이유 없음. 반대로 프레임 중 실시간 Map 갱신으로 바꾸는 것은 가시성 계약 변경이므로 단순 내부 변경으로 취급하지 않는다.

Job 의존성은 메모리 경쟁을 막고, 목적지 중재는 논리적 중복 승인을 막는다. 실행을 직렬화하거나 Fence를 더 Complete하는 것만으로 F-029/F-030이 해결되지는 않는다. Decision들은 같은 입력 스냅샷으로 승인하며 Execution에는 다른 승인과의 충돌 검사가 없기 때문이다.

## 5. 발견 문제

#### F-029 — 일반 벨트 이동이 목적지 중재에서 빠져 동시 진입의 간격·수용량을 보장하지 못함

- 발견 단계 / 유형 / 평가 축: Q13 / **구현 결함 + 문서 불일치**, 진입 우선순위는 설계 판단 필요 / 안정성·유지보수성·V2 적합성.
- 우선순위와 이유: **P1**. 유효한 벨트 배치와 정상 진행 상태에서 복수 아이템이 같은 목적지 진행도로 들어갈 수 있어 핵심 물류 상태가 겹친다.
- 근거 수준: **코드 확인**. 아래 수치 추적은 소스 분기의 분석이며 EditMode 재현 결과가 아니다.
- 위치: `BeltMovementDecisionSystem.cs:171–231`, `BeltMovementExecutionSystem.cs:94–130`, `BeltDestinationReservationSystem.cs:25–50,151–247,314–351`, `BuildingItemStorageApplySystem.cs:191–277`, `RoutingApplySystem.cs:97–131`.
- 기대 계약과 출처: `GameConstants.ItemSpacing=0.25`, `MaxItemsPerBeltTile=4`, `WorldInvariantValidationSystem.cs:315–426`의 간격·개수 검사. V2의 단계별 승인/적용 책임. 특정 합류 우선순위는 이 근거만으로 결정하지 않는다.
- 확인한 코드 동작: 일반 Belt Decision은 기존 ItemMap만 보고 계획을 확정한다. 목적지 Reservation은 **BuildingItemOutputDecision와 RoutingTransferDecision만** 후보로 삼고 일반 BeltMovementDecision을 조정하지 않는다. Execution은 점유 재검사 없이 승인량을 적용한다. Storage/Routing Apply도 예약 이후의 일반 이동 결과를 다시 점유 검사하지 않고 목적지 Progress=0으로 배치한다.
- 발생 조건과 영향: 출발 벨트 `(-1,0) Right`, `(0,-1) Up`, 공통 목적지 `(0,0) Right`가 있고 각 출발 아이템 progress=0.9, 목적지가 비어 있다고 하자. speed=2, dt=0.1(또는 현재 Config speed=10, dt=0.02)이면 양쪽 모두 0.2를 승인하고 목적지 progress=0.1로 들어가 **간격 0**이 된다. 일반 이동으로 progress=0.1에 도착한 뒤 승인된 출고/라우팅이 progress=0에 들어오는 경우도 간격 0.1이다. 목적지 기존 개수만 각각 검사하므로 복수 도착에 따른 최대 4개 초과도 막는 공통 절차가 없다.
- 근거 / 문서 차이: `CodeMemory/README.md:35`는 Reservation이 PlannedProgress의 경합을 제한한다고 설명하지만 현재 runtime의 정확한 심볼 참조에는 해당 Writer/Reader가 없다. 이 설명을 근거로 안전하다고 평가하지 않았다. Q12가 확인한 snapshot 가시성 자체와는 다른 승인 누락이다.
- 미확인 사항 / 반대 근거: 외부 출고와 Routing끼리는 현재 Reservation이 하나의 승자를 고른다. 일반 단일 직선 이동의 기존 테스트는 통과한다. 신규 수치 사례의 Unity 실행 재현과 실제 발생 빈도는 미확인이다. 방향을 꺾는 진입 자체는 현재 허용하며 기존 corner 테스트도 통과하므로 합류를 자동 불법으로 간주할 수 없다.
- 수정 방향 후보: 일반 경계 통과도 목적지 후보와 도착 progress/간격 예산에 포함하거나, 정상 경로에서 합류를 제한하는 명시적 topology 계약을 검토한다. 후자는 배치 검증·사용 규칙 변경이므로 임의 채택하지 않는다. 단순 실행 순서 변경이나 모든 Job 직렬화로 대체하지 않는다.
- 필요한 추가 검증: 두 일반 벨트→빈 한 셀, 일반 벨트+건물 출고, 일반 벨트+Routing, 기존 3개+복수 진입의 최종 Grid/Progress/enable/개수와 다음 Sync 이후 불변식을 검사하는 테스트 제안. 우선순위 결정 후 승인·거부 결과도 검증해야 한다.
- 처리: **미결정**. 코드·테스트 수정 없음.
- 별도 수정 작업과 재검증 근거: 수행하지 않음. 수정 승인과 우선순위 결정 후 별도 작업.

#### F-030 — 1칸 이동 상한만으로는 검사하지 않은 다다음 셀과의 간격 침범을 막지 못함

- 발견 단계 / 유형 / 평가 축: Q13 / **구현 결함** / 안정성·유지보수성·V2 적합성.
- 우선순위와 이유: **P1**. 현재 Config 속도와 허용 dt 범위 안에서 유효한 초기 간격이 한 번의 이동으로 깨질 수 있다.
- 근거 수준: **코드 확인**. 현재 Config의 도달성과 수치 분기를 확인했으며 반례 자체의 실행 재현은 미수행.
- 위치: `BeltMovementDecisionSystem.cs:49,128–131,171–231`, `BeltMovementExecutionSystem.cs:94–130`, `Assets/Resources/Config/BuildingConfig.json:4–5`, `Common/BuildingLifecycleUtility.cs:37–45,125`, `Phase2BeltExecutionTests.cs:220–237`.
- 기대 계약과 출처: 상기 ItemSpacing과 Validator의 cross-boundary 검사. PlannedProgress [0,1]은 이동량 범위이며 최종 간격의 별도 보장을 대체하지 않는다.
- 확인한 코드 동작: 다음 셀이 비면 `min(desired,1)`을 승인한다. 현재 progress를 고려한 도착 위치 너머의 spacing 구간은 검사하지 않는다. Execution은 해당 이동량을 그대로 적용한다.
- 발생 조건과 영향: 우향 3셀 `(0,0)→(1,0)→(2,0)`, 현재 Config speed=10, dt=0.1. A는 첫 셀 progress=0.9, 중간 셀은 비어 있다. 마지막 셀에 progress `0,0.25,0.5,0.75` 아이템을 두면 첫 아이템 B는 선행과의 간격이 이미 0.25여서 이번 계획이 0이다. A는 1을 승인받아 중간 셀 progress=0.9에 도착한다. B와 최종 경계 간격은 `(1-0.9)+0=0.1`로 0.25보다 작다. 시작 상태는 같은 셀·경계 간격 모두 유효하다.
- 근거: 빈 다음 셀 분기에는 그 다음 셀 조회가 없고, 마지막 셀 B는 same-tile 선행 검사로 정지한다. 전진량 상한 1을 지키고 hop도 한 번만 하는 사례이므로 Execution의 hop 상한으로 막을 수 없다.
- 미확인 사항 / 반대 근거: 선택 실행한 `Test08_DecisionSystem_LargeDeltaTime_ClampsDtAndPlannedProgress`는 progress=0, 다음 셀 빈 상태에서 **계획≤1**만 검사한다. 통과했지만 경계 너머 정체나 최종 간격을 검증하지 않는다. 낮은 속도·작은 dt의 직선 통합 통과도 이 반례를 부정하지 않는다. 실제 장면의 프레임 시간 분포는 측정하지 않았다.
- 수정 방향 후보: 도착 위치부터 spacing만큼의 전방까지 검사 범위를 확장하거나, 아직 검사하지 않은 경계 앞의 여유를 유지하도록 승인량을 제한한다. 고속·혼합 속도·회전에서의 throughput 정책을 먼저 명시하고 Execution의 승인량 적용 책임을 유지하는 방향을 검토한다.
- 필요한 추가 검증: 위 유효 초기 상태를 사용하는 Decision→Execution→Sync 간격 회귀 테스트, progress≈1과 종단 벨트 확장, 서로 다른 속도·회전 경로의 전방 간격 사례. 기존 Test08의 “터널링 방지” 주석과 실제 assertion 범위도 함께 정리할 것을 제안한다.
- 처리: **미결정**. 코드·테스트 수정 없음.
- 별도 수정 작업과 재검증 근거: 수행하지 않음. 승인된 별도 수정에서 확인할 사항이다.

- 기록: [verification.json](../../../../Logs/QualityEvaluation/Q13/verification.json), [시작 시각](../../../../Logs/QualityEvaluation/Q13/started.txt), [종료 시각](../../../../Logs/QualityEvaluation/Q13/finished.txt), [기존 invariant 로그 해시](../../../../Logs/QualityEvaluation/Q13/preserved-log-hashes.json). 기존 로그 1개 복원 후 SHA-256 일치 확인.
- 테스트 구조: 독립 World/Factory를 사용하고 Sync→Decision→Execution→Sync→Validator를 직접 호출한다. 명칭의 “Full”은 실제 Command·Reservation·StateApply를 포함한 정렬 그룹 실행을 뜻하지 않는다. 이번 테스트들에는 실제 Config 로드나 출고/라우팅과의 경쟁이 없다.
- 미실행: 전체 EditMode·Play Mode·실제 장면·성능·F-029/F-030 맞춤 실행 재현. 수용량 4개의 기존 Integration Test03은 정적인 4개 유지 사례이지 가득 찬 목적지에 외부 아이템이 진입하려는 분기의 충분한 검증이 아니므로 그 목적으로 추가 실행하지 않았다.

## 7. 남은 검증과 설계 질문

1. **공통 진입 승인 정책:** 일반 벨트 이동·건물 출고·Routing이 같은 목적지를 원하면 어떤 순서와 공정성 규칙을 적용할 것인가? 일반 벨트 간 합류를 허용할지와 함께 결정해야 한다. 현재 코드에 없는 우선순위를 임의로 도입하지 않았다.
2. **전방 검사와 고속 이동:** speed 10을 포함한 유효 속도에서 검사 범위를 늘릴지, 미검사 경계 앞에서 보수적으로 멈출지? F-030의 회귀 테스트와 실제 throughput 검증을 제안하며 성능 효과는 미확인으로 둔다.
3. **enable/계획 유효기간:** 향후 일시정지·시스템 부분 실행·외부 활성 전환이 추가되면 미실행 프레임의 오래된 계획을 어떤 경계에서 폐기할 것인가? 현재 정상 pipeline의 소비는 확인했지만 frame stamp나 비활성 계획 전량 초기화는 없다.
4. **추가 테스트 제안:** 동시 진입 네 종류(F-029), 다다음 셀 정체(F-030), 가득 찬 목적지 진입 차단, disable→enable 전환 후 계획 재작성/소비를 확인하는 통합 사례. 사용자 지시에 따라 파일은 추가·수정하지 않았다.
5. **사용자 수동 확인:** 필요 시 실제 장면에서 합류·정체·코너 표시를 확인할 수 있으나 이번 평가의 EditMode 통과와 같은 증거로 취급하지 않는다. 이 확인이 이미 이루어졌다고 기록하지 않는다.

선택 검증은 모두 종료됐고 필요한 실행의 차단은 없다. 신규 문제의 실행 재현·수정·설계 결정은 별도 미완료 항목으로 남긴 상태에서 **Q13 평가만 완료**한다. 다음 계획 단계는 **Q14 — Building Input→Storage Reservation→Apply**이며 별도 요청 전에는 진행하지 않는다.
