| 데이터 | Writer / Owner | Reader·소비자 | 수명·책임 |

### 3.2 준비·적용·소비

1. 요청이 없으면 return. RecipeRegistry가 없거나 Blob이 미생성이면 요청을 남긴 채 return한다. 이때 대상이 이미 무효여도 먼저 삭제하지 않으며, 0으로 레시피를 해제하는 요청도 Registry 준비를 기다린다.
2. EndCommand ECB가 있으면 버퍼를 얻는다. 없으면 Temp ECB를 만들어 함수 마지막에 즉시 Playback/Dispose한다. 기본 그룹에서는 **상태 변경은 Command OnUpdate 중 즉시**, 요청 엔티티 삭제만 EndCommand 시점이다. EndCommand가 없을 때의 fallback은 테스트/부분 World 경로이며 동일한 지연 삭제 시점이 아니다.
3. 요청 엔티티와 데이터 배열을 복사하고 query 순서대로 처리한다. 요청마다 존재하는 Target과 CrafterState를 확인한다. 무효 대상·CrafterState 부재는 적용 없이 요청 삭제. 다른 필수 버퍼/Filter 부재는 전체 거부 조건이 아니며 존재하는 부분만 처리한다(Q21 F-037과 연결).
4. 유효 대상이면 먼저 Progress=0, Active=false. 양쪽 버퍼가 있을 때 Stored의 각 Entity/ItemType을 Product에 append하고 Stored를 Clear한다. 완료 전까지 구조 변경을 Playback하지 않으므로 정상 흐름에서 버퍼 핸들을 구조 변경 뒤 재사용하지 않는다.
5. Product에 무엇이든 남으면 WaitingForByproductOutput. 비었거나 버퍼 조합이 없으면 새 ID의 부호에 따라 Idle/NoRecipe. 그 뒤 존재하는 Filter를 갱신하고 Selected/Active ID를 저장한다. 마지막으로 요청 삭제를 ECB에 기록한다.

‘원자적’이라는 summary는 정상 단일 Command 처리 구간의 관련 상태 전환을 뜻하는 수준으로만 해석했다. Registry 준비→정상 처리의 큰 경계는 명확하지만 잘못된 ID의 사전 거부, 예외 시 rollback, 모든 필수 구성의 검증, 외부에 전달할 성공/실패 응답을 제공하는 트랜잭션은 아니다. 메인 스레드 접근의 Job 동기화 전제는 F-039다.

### 3.3 잔여물의 슬롯·소유권·출력

- 기존 Product의 최대 SlotIndex를 읽고 `baseSlot=max(1,maxExistingSlot+1)`을 사용한다. Stored에서 처음 만난 품목 순서로 같은 품목은 같은 새 슬롯에 묶는다. 이전 주생산품 slot 0이나 기존 부산물 슬롯을 덮어쓰지 않고 기존 배열 뒤에 추가한다. 새 레시피의 Outputs 인덱스를 잔여물 슬롯에 재사용하지 않는다.
- 같은 Entity를 다른 버퍼로 옮기는 작업이다. Owner는 기존 Crafter, 렌더 비활성 상태도 그대로이며 Count만큼 엔티티를 만드는 생산 경로와 다르다. 정상 소유 버퍼의 Entity/ItemType 정합성을 신뢰하고 다시 검증하지 않는다.
- MaxStack/출력 슬롯 수를 검사하지 않는다. 여러 입력 슬롯의 같은 품목이 하나의 배출 슬롯에 모일 수 있다. **일시적인 잔여물 배출 버퍼와 정상 레시피 생산의 스택 용량 검사는 다른 경로**이며, 대기 중 신규 제작이 차단되므로 이것만으로 정상 생산의 용량 결함이라고 판정하지 않았다. 무조건 상한을 걸면 잔여물 보존/이동 완료 정책부터 정해야 한다.
- `FixedList32Bytes<byte>`가 품목 그룹 순서를 보관한다. 가득 찼을 때 새 품목은 typeIndex=-1인 채 첫 신규 슬롯으로 합쳐지는 분기다. 현재 유효 enum은 None 제외 9품목으로 이 한도를 넘지 않는다. 미래 품목 확장 또는 무효 enum 주입의 검토 사항이며 현재 정상 품목의 혼합 재현으로 등록하지 않는다.
- Product Output은 첫 slot 0을 우선하고 없으면 배열 첫 요소를 선택한다. 따라서 기존 완성품, 기존 부산물, 뒤에 추가된 잔여물이 배출될 수 있다. 숫자 슬롯 1→2→3 순회나 새 레시피 기반 우선순위가 아니다.
- 목적지 예약을 통과하면 Storage Apply가 Product에서 선택 Entity를 제거하고 위치/벨트 상태 및 TransferOwnershipRequest(null)을 갱신한다. Ownership Apply가 월드 소유권·렌더 태그를 반영한다. Command가 이 출고를 직접 호출하거나 벨트 예약 내부를 알아야 할 이유는 없다. 출구가 없거나 막혀 있으면 버퍼와 대기가 유지된다. 이것은 손실이 아니라 명시적인 배출 대기다.

### 3.4 진행 중 취소와 입고/제작 재개

**선소비 연결 [코드 확인]:** Q21의 Execution은 제작 시작 시 Stored에서 재료를 제거하고 Destroy 요청을 활성화한다. 이후 Recipe Command는 현재 Stored에 남은 것만 옮기므로 이미 선소비한 재료를 환급하지 않는다. Progress=1이어도 아직 ProductResult를 기록하지 않은 active 작업이면 같은 reset 경로다. 이미 실체화된 Product는 보존해 배출한다. 반환/취소 비용 정책은 소스 동작과 구분해 §7 질문으로 남긴다.

**대기 해제 [코드 확인·EditMode 확인]:** WaitingForByproductOutput 상태에서 Product.Length>0이면 CrafterDecision은 시작·진행·출력을 모두 막는다. 0이 되면 레시피 유효성과 현재 재료를 다시 판단하고 CrafterStateDecision을 발행한다. 재료가 없으면 **WaitingForInput**이며 무조건 Idle이 아니다. 같은 프레임 Input Decision은 아직 이전 Status를 읽으므로 계속 거절하고, StateApply가 새 Status를 반영한 뒤 다음 Input 판단에서 허용된다. 입력된 재료 자체도 StateApply에서 Stored에 들어가므로 새 제작 착수는 후속 CrafterDecision/Execution에서 이루어진다.

이는 일반 Input과 CrafterDecision의 같은 그룹 내 세부 순서를 정해 해결할 문제가 아니다. 두 판단은 이전 확정 상태를 읽고 이후 StateApply가 전이하는 공개 경계를 따른다. 강제로 Input을 CrafterDecision 뒤에 놓아도 NextStatus가 아직 원본 Status에 반영되지 않는다.

공개 계약 유지 시 내부 변경 사례(**정적 추정**):

1. **품목 그룹 탐색을 helper 또는 다른 지역 컨테이너로 교체하되 같은 Entity 순서·SlotIndex·Filter·Status를 유지:** Input, Execution, Output/예약/Ownership을 수정할 필요가 없다. Stored/제품 배열 재정렬은 출고 순서에도 영향을 줄 수 있으므로 같은 품목 총수만 보존했다고 계약 유지로 보지 않는다.
2. **Product Output의 출구 탐색을 같은 선택 Entity/목적지·동일 거부 결과를 내는 내부 구현으로 교체:** Command는 버퍼의 잔류 여부만 보므로 수정 불필요. 최종 아이템이 제거되는 Phase 자체를 바꾸면 대기 해제 시점의 공개 계약 변경이다.
3. **같은 NextStatus/enable 소비를 유지하며 StateApply의 구현을 helper로 분리:** Command와 Input 수정 불필요. 반대로 Status를 즉시 Decision에서 쓰도록 바꾸면 재개가 한 프레임 당겨지므로 단순 내부 정리가 아니다.
4. **Job을 더 늦게 완료하도록 계산 내부를 바꾸되 공개 상태·Phase 결과는 유지:** 관련 데이터를 Job dependency로 연결한 시스템은 핸들을 기다리면 된다. Command는 raw Lookup으로 main-thread 접근하므로 상위 호출자가 미리 Complete했는지까지 알아야 할 수 있다(F-039). 이는 필요한 Job 동기화를 지우자는 제안이 아니라 **동기화 책임을 해당 접근 경계에 두자는 제안**이다.
5. **레시피 파싱 구현만 바꾸고 ID 조회·재료 목록·수명은 유지:** Command 수정 불필요. 반면 유효 ID, None, 중복 ID, 레시피 해제 의미를 바꾸는 것은 공개 데이터/정책 변경으로 Q06과 관련 소비자 검토가 필요하다.

상태 조정이 여러 필드에 걸친다는 이유만으로 Command를 V2 위반으로 판정하지 않았다. 재료를 실제로 옮기면서 상태·필터를 함께 바꾸는 조정은 필요하다. 개선 후보는 불명확한 성공/취소 의미와 타 시스템의 동기화·정리 세부에 기대는 부분이며, 모든 책임을 단일 거대 시스템으로 합치는 방향은 제안하지 않는다.

## 5. 발견 사항

### F-039 — 레시피 Command의 메인 스레드 Lookup 접근에 관련 Job 완료 경계가 명시되지 않음

- 발견 단계 / 유형 / 평가 축: Q22 / **유지보수 위험·V2 설계 불일치** / 세 평가 축. 안정성 영향은 미완료 관련 Job이 존재하는 조건부 위험으로 구분한다.
- 우선순위와 이유: **P2**. 관련 Reader/Writer가 미완료인 조건에서는 main-thread 직접 접근의 안전성과 값 보존에 영향을 줄 수 있고, 소비자를 이해하려면 외부 동기화 지점까지 알아야 한다.
- 근거 수준: **프로젝트·설치 패키지 코드 확인**, 미완료 Job을 둔 실행 재현 및 현재 정상 그룹의 실제 발생 여부는 **미확인**. 선택 테스트 통과를 이 위험의 재현 또는 부정 증거로 사용하지 않는다.
- 위치: `CrafterRecipeCommandSystem.cs:75–81,90–184`; 아래 Entities 6.4.0 구현. 관련 공유 Writer는 Q21의 Execution/StateApply와 입출고 Apply.
- 기대 계약과 출처: 같은 ECS component/buffer를 main thread에서 직접 읽고 쓸 때 기존 Job과 동기화해야 한다는 설치 패키지의 Lookup safety 및 SystemState dependency API 계약. Phase 호출 순서와 Job 완료는 같은 의미가 아니다.
- 확인한 동작: Consumer는 Lookup.Update 후 CrafterState/Filter/Stored/Product를 바로 읽고 쓴다. `state.CompleteDependency()`나 해당 타입 dependency 완료, 또는 dependency를 받는 Job 실행을 사용하지 않는다. 요청 query 배열 추출은 대상 Crafter 데이터 전체를 완료하는 연산이 아니다.
- API 확인 근거: `Iterators/ComponentLookup.cs:104–116,265–293`과 `BufferLookup.cs:247–268,357–369`의 Update/indexer는 버전·safety handle 갱신과 접근 체크이며 대기 호출이 없다. `Iterators/EntityQuery.cs:967–985,1095–1112`는 query 필터/Entity 또는 **추출하는 요청 타입**의 write dependency를 기다린다. `SystemState.cs:433–451,582–590`에서 OnUpdate 진입은 자신의 이전 handle 완료 후 새 dependency 조회 필요를 표시하며, 별도 CompleteDependency가 등록된 타입들의 외부 의존을 완료한다.
- 외부 동기화와 반대 근거: request 엔티티를 EntityManager로 생성하는 구조 변경, 실제 명령이 담긴 ECB 재생, 직접 GetComponentData/GetBuffer를 통한 선행 접근 등이 Job을 먼저 끝내 위험을 가릴 수 있다. 현재 게임 입력 요청 producer는 소스에서 확인되지 않았고 기존 Test01도 미완료 Crafter Writer를 먼저 예약하지 않는다. **현재 정상 플레이에서 항상 race/예외가 난다는 판정이 아니다.**
- ECB를 무조건적인 보증으로 삼지 않은 이유: `EntityCommandBufferSystem.cs:186–220`은 자신의 dependency/등록 producer를 기다린다. `EntityCommandBuffer.cs:4184–4190`은 recorded chain이 있을 때만 BeginStructuralChanges를 시작하며, 그 경로의 `EntityDataAccess.cs:406–421`이 전체 Job을 완료한다. 따라서 ‘EndStateApply를 호출했음’만으로 모든 관련 Job이 항상 끝났다고 일반화하지 않는다. Command 자신의 요청 삭제 Playback은 직접 쓰기 **이후**이므로 선행 접근을 보호하지 못한다.
- 발생 조건·영향: 관련 상태/버퍼를 사용하는 Job이 아직 완료되지 않았는데 요청을 처리하는 부분 실행·호출/스케줄 변경. safety 예외 또는 검사 없는 환경의 경합 가능성을 정적으로 식별했으며 타이밍/손상은 측정하지 않았다.
- 수정 방향 후보: 등록된 관련 dependency를 main-thread 접근 전에 완료하거나, 처리 자체를 dependency에 연결하는 방식 검토. 공간 Fence 추가나 모든 World Job을 무조건 완료하는 방식은 요구하지 않는다. 실제 Type 접근 범위와 Blob 수명도 유지한다.
- 필요한 추가 검증: 요청을 준비한 뒤 관련 Writer/Reader Job을 등록하고 Consumer만 실행하는 기존 테스트 보강, 정상 그룹과 부하/안전성 검사 환경 비교. 현재 후보 2건에 해당 assertion이 없어서 추가 실행하지 않았다.
- 처리 / 별도 수정·재검증: **미결정**, 코드·테스트 변경 없음. NativeContainer 공간 Fence 누락인 Q12 F-026과는 상태/동기화 계약이 달라 별도 ID다.

## 7. 남은 질문·제안과 완료 범위

1. **취소 비용:** 이미 선소비한 작업을 레시피 변경으로 취소할 때 재료를 잃는 현재 동작이 의도인가? Progress=1이지만 아직 출력하지 않은 작업도 같은 정책인가? Q21의 질문을 이어받는다.
2. **요청 수용 의미:** F-040의 무효 양수 ID, 같은 레시피 재선택은 거부/no-op/재시작 중 무엇인가? 같은 tick의 복수 요청은 어느 순서를 보장해야 하는가? 현재 query 순서·요청 삭제를 사용자 의도의 마지막 선택 보장으로 설명하지 않는다.

4. **관련 테스트 보강:** active/부분 진행·선소비 상태에서 valid 변경, Entity/Owner 보존, 기존 slot0·다중 부산물과 잔여물 공존, 실제 출고→입고→새 제작, Registry 없음→준비 후 요청 소비, 무효 대상/누락 구성, F-039/F-040 조건을 제안한다. 같은 프레임의 재개 지연은 기존 Test02 계약을 유지하며 보강한다.
5. **잔여물 버퍼의 공개 의미:** 현재는 용량과 무관하게 남은 입력을 보존하는 임시 배출 경로다. 향후 별도 잔여물 상태나 입고 가능 계약으로 분리할 경우, 기존 아이템·slot0 우선·전체 배출 후 재개라는 의미가 바뀌는지 먼저 결정해야 한다.
