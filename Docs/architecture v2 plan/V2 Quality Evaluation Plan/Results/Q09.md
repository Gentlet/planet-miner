### 3.2 등록·중복·무효 값·누락 정책 — 코드 확인

- Populate는 목록을 Clear하고 다시 채우므로 반복 누적은 없다. 같은 수집 집합 내 중복 타입은 제거하지 않는다. Inspector 버튼은 Undo.RecordObject → Populate → SetDirty이고, 별도 검증/중복 진단 UI는 없다. ContextMenu 경로의 실제 Undo·저장과 multi-object 편집은 실행하지 않았다.
- AutoLoad/Populate는 None과 ConstructionSite를 제외하지만 **Count 및 정의되지 않은 숫자 enum 값은 명시적으로 제외하지 않는다**. List Baker는 Null prefab/None만 제외해 ConstructionSite도 게시할 수 있다. 공통 Spawn은 None/ConstructionSite만 거부한다. Count/범위 밖 요청의 실제 결과는 실행하지 않았으며 입력 유효성 공백은 기존 [F-019(Q08)](Q08.md#5-발견-문제)에 연결한다. Building에는 ItemAuthoring.Type 일치 계약을 그대로 적용하지 않는다.
- List Size는 각 축을 최소 1로 clamp한다. AutoLoad 크기는 타입별 정사각형 기본값(1×1/2×2/3×3)이다. Config 검증은 0 이하를 거부하지만 Authoring은 보정하므로 실패 의미가 같지 않다. 기본 크기 표는 Authoring과 Utility에 각각 있으며 현재 값은 같다.
- DB는 유효 행을 순서대로 Add하고 공통 lookup은 첫 일치에서 반환한다. 여러 GameObject의 DB는 DisallowMultipleComponent로 차단되지 않는다. **Building 소비자는 태그가 아닌 BuildingPrefabElement 버퍼만 query**하므로 버퍼만 가진 엔티티도 DB 후보다. 단일 후보면 사용하고 복수면 GetSingletonEntity 전제를 깨뜨릴 수 있다. 실제 복수 DB 구성은 미확인. 유일성 문제는 [F-018(Q08)](Q08.md#5-발견-문제)의 Building 추가 위치다.
- 빈 DB는 존재하는 DB다. 누락/Null prefab이면 오류와 Entity.Null 반환으로 거부한다. DB 자체가 query에 없으면 fallback archetype을 만든다. 이 분기는 테스트 플래그가 아니라 DB 존재 여부에 따른다. SubScene 로딩 전후의 실제 준비 상태는 Q11에서 확인할 일이다.
- **크기 선택**은 양수 request/현장 입력 → 일치 Config.Footprint → Utility 기본값 순서다. DB의 FootprintSize는 조회 시 `dbFootprint`로 받지만 사용하지 않는다(F-022). DB Size가 Spawn의 최우선 값이라고 해석하지 않는다.
- **타입 선택**은 DB key로 prefab을 고르고 targetType으로 인스턴스 BuildingType과 runtime state를 구성한다. DB Baker는 별도 BuildingType 컴포넌트를 prefab root에 미리 추가하지 않는다. Authoring 규약의 표를 근거로 실제로 bake한다고 설명하지 않는다.
- **방향**은 Direction과 라우팅 state에 전달된다. footprint는 Left/Right에서 swap한다. 이 Utility의 LocalTransform.FromPosition에는 방향 회전을 전달하지 않으므로 이 구간에서 quaternion 회전이나 원본 uniform scale 보존을 한다고 볼 수 없다. 필요한 시각 표현 정책·실제 화면은 별도 미확인 사항이며 논리 방향 오류로 단정하지 않는다.
- **Transform 반대 근거**: Renderable이라는 플래그만 보고 “정상 prefab에 LocalTransform이 없다”고 결함 등록하지 않았다. 로컬 Entities의 CreateEntityForPrefab은 root에 Dynamic을 추가한다(`BakedEntityData.cs:1165–1168`). 실제 project asset의 최종 베이킹 결과까지 확인한 것은 아니다.
- **공통 Spawn 실패 결과**는 즉시 Entity.Null이다. 직접 Spawn 요청의 Drop은 요청 문서에 명시되어 있다. 완공 caller는 반환값을 사용하지 않고 실패해도 현장·자재 파괴를 기록한다(F-024). non-Null 반환 역시 ECB에 성공 명령을 기록했다는 뜻이지 Playback 전체의 트랜잭션 성공 보장은 아니다.

| 직접 Spawn | Utility가 swap하여 Size=(3,2), SpatialSync가 GetEffectiveSize로 다시 swap | 점유 (2,3): 기대 (3,2)와 다름 |
| 배치→현장 | Validation/Placement가 (3,2)로 판단/기록, 현장 SpatialSync가 다시 swap | 검증 영역 (3,2)와 현장 인덱스 영역 (2,3)이 다름 |
| 그 현장→완공 | Completion이 Size=(3,2)를 Utility에 전달, Utility가 (2,3) 기록, Sync가 (3,2)로 계산 | 최종 영역은 원래 기대와 같아질 수 있지만 현장→완공 점유가 바뀜. 현장/완공의 Size 의미도 일관되지 않음 |

정사각형 입력은 swap해도 같아 결함을 가린다. 기존 단독 회전 테스트는 컴포넌트 Size=(3,2)만 assert하며 Sync를 호출하지 않는다. 이 assertion의 통과 여부와 전체 공간 계약의 정합성은 다른 질문이다.

## 4. 시스템 의존성과 변경 영향

| 관계 | 형태 / 공개 계약 | 필요한 이유·내부 가정 | 판정 |
| --- | --- | --- | --- |
| Inspector → Authoring.Populate | 같은 편집 대상의 직접 호출 | 목록 교체와 Undo 경계 | **필요한 계약**. 런타임 시스템 내부 지식 불필요 |
| DB Baker → DB 데이터 → 두 Lifecycle | read-only lookup, 준비/유일성 | 타입에 해당하는 유효 prefab 필요. 버퍼만 query하는 현재 DB 정의를 알아야 함 | **필요한 조회 + 검증 개선**, F-018/F-019 연결 |
| Spawn/Completion → BuildingLifecycleUtility | 공통 초기화 API 호출 | 타입·위치·방향·크기·stamp·DB/Config와 caller ECB 제공 | **필요한 공통 책임**. 두 caller가 타입별 buffer/decision을 각각 구성하지 않아 Item 환급의 F-020과 다름 |
| Authoring DB 크기 → Utility | 데이터 제공/조회 | 조회한 크기를 버리고 별도 Config/기본표로 결정 | **설계 판단/유지보수 개선**, F-022. Inspector Size를 이해하려면 Spawn의 내부 선택 분기까지 확인해야 함 |
| Placement/Utility → Footprint → Sync/Completion | 공유 상태 의미 | base와 effective 크기가 같은 필드로 전달되고 각자 회전 | **개선할 계약 불일치**, F-023. 필요한 방향 계산 자체가 아니라 적용 횟수·표현의 불일치가 문제 |
| Completion → Utility 반환값 → 자재/현장 수명 | 성공/실패 데이터 | 실패할 수 있는 호출인데 성공으로 간주하고 정리 | **개선할 결합**, F-024. Utility의 누락 정책/내부 실패 분기를 몰라도 반환값으로 처리할 수 있어야 함 |
| 조회/생성 Job → state.Dependency·ECB | 접근·기록 완료·실체 가시성 | read-only lookup 갱신, 최종 producer handle, EndStateApply Playback | **필요한 동기화**. Building DB는 ECS buffer이며 별도 공간 Fence를 추가할 이유는 확인되지 않음 |

**[추정: 공개 계약 유지 변경 영향 분석]** 실제 코드를 수정하는 실험은 하지 않았다.

1. 유효·유일한 Type→Prefab 및 base size 데이터를 유지하며 Baker의 수집 helper/임시 자료구조를 바꾸면 두 Lifecycle 시스템과 Inspector의 호출 코드는 수정할 필요가 없다. 중복 입력의 순서를 바꾸는 것은 현재 첫 선택 결과를 바꿀 수 있어, 결과까지 유지한 내부 변경과 구분한다(F-018).
2. 생성 컴포넌트·초기값·enable 상태·실패 반환·EndStateApply 가시성까지 유지한 채 AttachTypeSpecificComponents를 내부 helper로 재구성하면 두 caller는 바뀔 필요가 없다. **fallback archetype의 요구 컴포넌트 자체를 바꾸는 것은 API 서명이 같아도 공개 데이터 전제 변경**이므로 정상 caller 파급으로 분류한다.
3. 동일 DB 조회 결과와 Null 실패 계약을 유지하며 Utility 내부 검색을 바꾸면 정상 caller는 영향을 받지 않는다. F-024는 검색 알고리즘 결합이 아니라 **이미 공개된 실패를 무시하는 caller 결함**이다. 실패 반환을 없애 caller를 보호하는 방향으로 계약을 약화해서는 안 된다.
4. `BuildingFootprint.Size=base`와 GetEffectiveSize의 기존 의미를 보존하면서 공간 인덱스의 내부 저장 방식을 바꿔도 Writer 수정은 필요 없어야 한다. 현재 Writer가 effective를 저장하는 F-023은 이 전제가 깨진 상태다. Sync에서 “이 entity는 누가 만들었는가”를 구분해 보정하면 다른 시스템의 내부 구현 지식이 추가되므로 적절한 분리로 보지 않는다.
5. DB Size의 우선순위를 새로 올리는 것은 현재 Spawn의 관찰 가능한 크기를 바꾸는 **정책/공개 계약 변경**이다. 단순한 미사용 변수 정리와 구분해 F-022의 질문으로 남긴다.

검토 범위에서 도메인 간 Update/활성화/정리 직접 제어는 발견하지 않았다. 두 시스템이 공통 함수를 호출하는 것과 각각의 Cancel→Material→Completion, Demolish→Spawn Job 배열을 외부가 알아야 하는 것은 다르다. Baker/Inspector가 그 세부 배열을 알아야 할 이유는 없다. 문제는 순서 개수보다 상태 표현과 성공/실패 경계이며, 시스템 통합이나 동기화 제거를 개선으로 간주하지 않는다.

#### F-022 — Inspector/DB의 FootprintSize가 실제 Spawn 크기 선택에 사용되지 않음

- 발견 단계 / 유형 / 평가 축: Q09 / **유지보수 위험·설계 판단 필요** / 유지보수성·V2 적합성.
- 우선순위와 이유: **P2**. 편집 가능한 크기와 공개 DB 필드가 있어도 스폰에 영향을 주지 않아 설정 출처·변경 영향이 불명확하다. DB 크기가 반드시 최우선이어야 한다고 새 정책을 정하지 않는다.
- 근거 수준: **코드 확인**. 실제 Inspector 수정·스폰 비교는 **미실행**.
- 위치: BuildingPrefabDatabaseAuthoring `:27–37,48–71,126–145`; PrefabDatabaseComponents `:17–27,103–119`; BuildingLifecycleUtility `:36–60,68–74,190–213`; SpawnBuildingRequest `:32–35`.
- 기대 계약과 출처: Authoring/Prefab 규약의 Building DB는 prefab과 물리적 footprint를 제공한다. 현재 요청 문서는 Config/기본값 경로를 명시한다. 두 설명 중 DB Size의 역할·우선순위를 확정할 필요가 있다.
- 확인한 코드 동작: Baker는 크기를 buffer에 쓰고 lookup은 반환한다. Utility는 크기를 이미 입력/Config/기본값으로 결정한 뒤 `out dbFootprint`를 읽고 사용하지 않는다. 기본 규격 표도 Authoring과 Utility에 별도로 있다.
- 발생 조건과 영향: 사용자가 DB entry.Size를 비기본 크기로 바꾸어도 Spawn 입력/Config가 같으면 최종 footprint가 바뀌지 않는다. 수집 결과가 맞는 테스트와 실제 생성 크기가 맞는 테스트가 서로 다른 출처를 확인할 수 있다.
- 근거 / 반대 근거 / 미확인: 현재 두 기본표는 동일하고 기본 규격은 정사각형이다. 명시 요청이 DB보다 우선하는 것은 의도일 수 있으며 그 자체가 결함은 아니다. DB Size가 단지 메타데이터인지 실제 초기화 입력인지 미확정이다.
- 수정 방향 후보: DB Size를 사용할 조건·우선순위를 명시하거나, 의도적으로 사용하지 않는 필드라면 편집 UI/계약을 명확히 한다. 기본 규격 출처 공통화도 검토. 임의로 DB 우선으로 변경하지 않는다.
- 필요한 추가 검증: 서로 다른 request/Config/DB 크기를 가진 실제 Baker→Spawn 표본, 각 입력 부재·무효 조합과 회전 포함 우선순위 assertion 보강.
- 처리 / 별도 수정·재검증: **미결정**, 없음.

#### F-023 — BuildingFootprint의 base/effective 표현이 섞여 비정사각형 점유를 다시 회전함

- 발견 단계 / 유형 / 평가 축: Q09 / **안정성 결함·V2 설계 불일치** / 세 축 모두.
- 우선순위와 이유: **P2**. 공개 요청/Config가 허용하는 비정사각형을 Left/Right로 배치·스폰할 때 점유 영역이 달라진다. 현재 기본 정사각형은 영향을 가리므로 모든 건물의 현재 장애로 확대하지 않는다.
- 근거 수준: **코드 확인**, §3.3 수치 추적. 실제 배치→완공→인덱스 실행 재현은 **미확인**.
- 위치: BuildingComponents `:65–91`; BuildingPlacementValidationUtility `:21–26`; PlacementCommand `:136–139`; BuildingLifecycleUtility `:59–60,89,102`; ConstructionLifecycle `:439–444`; BuildingSpatialSync `:153–160`.
- 기대 계약과 출처: BuildingFootprint는 기본 크기로 설명되며 GetEffectiveSize가 방향을 적용한다. 배치 검증·현장·완공·공간 등록이 같은 점유 영역을 나타내야 한다.
- 확인한 코드 동작: Placement/Spawn Writer는 회전값을 Size에 저장하고 Sync Reader는 Size를 다시 회전한다. Completion도 회전된 현장 크기를 base 입력으로 전달한다. 이는 단순한 UpdateAfter 누락이 아니라 데이터 의미 불일치다.
- 발생 조건과 영향: `(2,3), Right` 직접 Spawn은 Size=(3,2) 뒤 Sync 점유=(2,3). 배치 검증 영역과 현장 등록 영역이 달라지고, 실제 Placement가 만든 현장의 완공 전후 점유도 바뀔 수 있다. 상이한 영역 때문에 후속 점유/자원 조회가 다른 셀을 보게 되는 영향은 조건부 추정이다.
- 근거 / 반대 근거 / 미확인: Phase7BuildingLifecycle Test09는 비정사각형을 쓰지만 Spawn 후 컴포넌트만 검사하며 Sync가 없다. Completion Test07은 `(2,2), Up`이고 직접 site를 만든다. 이번에는 이 두 테스트를 실행하지 않았다.
- 수정 방향 후보: Size를 base 또는 effective 중 하나로 명확히 하고 Writer/Reader 전체에서 한 번만 방향을 적용하도록 맞춘다. 기존 GetEffectiveSize와 공개 주석을 보존할지 포함하여 설계 선택을 기록한다. 생산자를 구별하는 임시 보정이나 순서 의존을 추가하지 않는다.
- 필요한 추가 검증: 비정사각형 4방향에 대해 직접 Spawn→Sync, 실제 Placement→site Sync→Completion→Sync의 정확한 셀 집합 비교. DB 크기 선택(F-022)과 분리하여 요청 크기로도 재현 가능.
- 처리 / 별도 수정·재검증: **미결정**, 없음. 후속 Q12/Q23/Q25/Q27에서는 이 최초 기록을 링크한다.

#### F-024 — 완공 Spawn이 prefab 누락으로 거부돼도 자재와 현장을 삭제함

- 발견 단계 / 유형 / 평가 축: Q09 / **안정성 결함·V2 설계 불일치** / 안정성·유지보수성·V2 적합성.
- 우선순위와 이유: **P1**. 완공 가능한 현장에서 DB 항목 하나가 누락되면 완공 건물 없이 현장과 도착 자재를 잃는 코드 경로다.
- 근거 수준: **코드 확인**. 오류 로그·ECB 결과의 실행 재현은 **미확인**.
- 위치: BuildingLifecycleUtility `:65–83`; ConstructionLifecycleApplySystem `:396–456`, 특히 `:418–427,439–456`.
- 기대 계약과 출처: 공통 Spawn은 Strict Fail에서 Entity.Null을 반환한다. 완공은 자재 충족 현장을 건물로 전환한다. 직접 Spawn 요청의 명시적 Drop과 달리, 현장·자재까지 실패 시 폐기한다는 공개 완공 계약은 확인하지 못했다.
- 확인한 코드 동작: 완료 flag·자재 충족 검사 후 stored item의 Destroy를 먼저 ECB에 기록한다. 공통 Spawn 반환값은 받지 않고 현장 Destroy도 기록한다. DB가 존재하지만 target prefab이 누락/Null이면 Utility는 오류와 Entity.Null을 반환하며 건물 생성 명령은 없다.
- 발생 조건과 영향: 정상 target의 완료 가능 현장 + 활성 Building DB의 해당 prefab 누락. 같은 ECB 재생 후 도착 자재·현장은 사라지고 건물은 생성되지 않는 경로다. 정상 등록이나 DB 자체 부재의 fallback은 이 조건이 아니다.
- 근거 / 반대 근거 / 미확인: 직접 Spawn의 누락 요청 소비는 명시 정책이어서 별도 결함으로 세지 않는다. 이 결함은 [F-006(Q03)](Q03.md#f-006--생산물-실체화-실패에도-productresult를-지워-재처리-근거가-사라짐)의 ProductResult Clear와 비슷한 실패 손실이지만, 다른 상태 Owner·완공 전환·반환값 무시가 원인이므로 별도 ID다. 현장 실패 보상 정책·실제 발생 빈도는 미확정.
- 수정 방향 후보: 즉시 거부 가능성을 자재 소비 이전에 처리하고, Spawn 기록의 성공/실패에 따라 현장/자재 처리 정책을 분기한다. 대기·취소/반환·명시적 실패 상태 중 정책을 결정해야 한다. non-Null만으로 이후 ECB Playback의 모든 오류까지 rollback된다고 보장하지 않는다.
- 필요한 추가 검증: 실제 prefab DB 누락/Null과 충족 현장·stored 자재를 준비하여 건물 수/현장 생존/자재 참조/오류를 확인하는 회귀 사례. 현재 후보에는 없으므로 보강 제안만 기록.
- 처리 / 별도 수정·재검증: **미결정**, 없음. Q25에서는 본 기록을 링크하고 완공 수명 전체를 평가한다.
