## 3. 흐름과 상태 Reader/Writer

### 3.1 요청부터 EndCommand까지

1. 세 공간 singleton과 Map.IsCreated가 준비되지 않으면 **return**한다. 이때 요청은 유지되며 `_currentTick`도 증가하지 않는다. Fence 완료나 건물 Config 준비를 요구하는 것은 아니다.
2. Config 태그가 있으면 같은 Entity의 건물/자재 버퍼를 `Allocator.Temp` NativeArray로 복사한다. Config가 없으면 해금 기본 true인 overload를 사용한다. 이 선택은 실제 로드 실패와 의도적 무설정을 구별하지 못한다([F-011 / Q05](Q05.md#f-011--설정-검증-실패가-의도적-무설정-world와-구분되지-않아-해금비용-제한이-빠짐)).
3. 헤더와 후보 버퍼를 **함께 가진** 요청만 순회한다. 빈 버퍼는 삭제를 기록한다. 후보를 복사하고 같은 길이의 임시 결과 배열을 만들어 묶음 검증을 완료한 뒤 적용한다.
4. 유효한 벨트 덮어쓰기는 원점의 같은 타입 Entity에 Direction SetComponent를 기록한다. 새 현장/자재/Stamp를 만들지 않는다. 현재 허용 분기는 **Belt 위 Belt**뿐이다. 주석의 ‘다른 벨트 업그레이드’는 별도 벨트 타입/교체 구현의 증거가 아니다.
5. 나머지 유효 후보는 새 Entity에 `BuildingType=ConstructionSite`, footprint·grid·direction, `ConstructionSite(Target,Progress=0,Flags)`, Stamp, LocalTransform, 요구/보관 버퍼를 기록한다. 자재는 해당 타입의 Config 행을 복사하며 Delivered/Reserved는 0이다. 기존 중복 자재 의미 문제는 [F-010 / Q05](Q05.md#f-010--같은-건물의-중복-자재-품목을-허용하지만-두-번째-요구-행을-충족할-수-없음)다.
6. 성공/거부 모두 요청 Destroy를 기록하고 임시 배열을 해제한다. **실제 현장 생성·방향 변경·요청 소멸은 EndCommand 재생 때** 확정된다. ‘즉시’ 주석을 OnUpdate 중 실체 변경으로 해석하지 않는다. 반환 결과/거부 이유를 외부 Entity나 이벤트로 게시하는 코드는 없다.

후보 버퍼가 아예 없는 헤더는 쿼리에서 제외되어 자동 소비되지 않는다. 이는 정상 producer가 지켜야 할 요청 형태이고, 무효 요청 복구 지원 여부는 미정이다. 예외/ECB 실패까지 Strict의 원자성을 보장하는 트랜잭션 구현은 없다. 여기서 Strict는 **검증 결과를 반영 전에 전부 취소**한다는 의미다.

## 4. 검증 조건·묶음 경합·회전

| 조건 | 코드 확인한 판정과 범위 |
| --- | --- |
| 크기·원점·방향 | 원점은 회전 결과의 좌하단. ValidateSingle은 비양수 크기를 거부한다. Left/Right면 x/y를 교환하고 Up/Down이면 유지한다. enum 범위, 최대 면적, 좌표 덧셈 overflow, 타입별 고정 크기는 검사하지 않는다 |
| 해금 | Config가 비어 있지 않으면 해당 타입 첫 행의 IsUnlocked, 미등록이면 false. Config 부재 또는 빈 배열은 전체 해금 취급. 해금 거부가 InvalidFootprint보다 먼저 반환된다 |
| 점유 | effective rectangle의 각 셀에서 기존 ConstructionSite와 일반 건물을 구분해 거부. Belt→Belt만 예외 승인. Map Entity의 실재/컴포넌트를 재검사하지 않으며 snapshot 계약을 신뢰 |
| 채굴 자원 | rectangle 안 ResourceMap key가 하나 이상이면 Miner 허용. 다른 건물은 자원 위에도 허용. 자원 품목/양·entity 생존을 별도 재조회하지 않는다. 광맥 생성 내부를 복제하지 않는 점은 적합 |
| 바닥 아이템 | 차단하지 않고 HasGroundItems 반환, 현장에 AwaitingItemClearance 기록. 회수/해제는 현재 연결되지 않았으므로 플래그 설정 테스트를 완공 가능성 근거로 쓰지 않음 |
| 묶음 내부 | 후보 버퍼 순서대로 검사하고 유효 후보만 claimedCells에 추가. 뒤 겹침은 BlockedByConstructionSite. 실패한 후보의 셀은 선점하지 않음 |
| Strict | 기본 0 플래그. 하나라도 실패하면 이전의 Success/BeltUpgradeAllowed도 BatchAllOrNothingRolledBack으로 변환. 적용 루프 전에 끝나므로 부분 방향 변경도 기록하지 않음 |
| Partial | 유효 후보만 적용. 내부 경합은 앞 후보 승리. candidate RequestTick은 Stamp에 쓰일 뿐 검증 정렬 기준은 아님 |
| 서로 다른 요청 | 요청마다 새 claimedCells, 동일한 이전 buildingMap, ECB 미재생. A/B가 같은 빈 셀을 각각 승인할 수 있음. F-027이며 Fence 대기만으로 해결되지 않음 |

**회전 수치 추적 — 코드 확인:** base `(2,3)`, Right, origin `(0,0)`은 검증에서 `[0..2]×[0..1]`을 검사한다. Placement는 `Size=(3,2)`를 저장하고 SpatialSync가 다시 교환해 `[0..1]×[0..2]`를 등록한다. 검증하지 않은 `(0,2)`를 점유하고 승인한 `(2,0)`을 누락하는 차이다. 정사각형/Up의 정상 테스트로 이 차이를 검증할 수 없다. 최초 문제는 [F-023 / Q09](Q09.md#f-023--buildingfootprint의-baseeffective-표현이-섞여-비정사각형-점유를-다시-회전함)이며 신규 ID를 만들지 않았다.

**현장 생성과 프리팹의 경계:** Placement는 candidate FootprintSize를 사용하고 Config/DB 크기를 읽지 않는다. 완공 단계 DB 누락 실패를 미리 보장하는 경로도 아니다. 이는 현장 생성이 완공 프리팹 내부 구성을 몰라도 되는 분리이며, 크기 출처의 권위는 [F-022 / Q09](Q09.md#f-022--inspectordb의-footprintsize가-실제-spawn-크기-선택에-사용되지-않음)와 함께 결정해야 한다. 신규 크기 정책을 이번에 정하지 않았다.

**공개 계약을 유지하는 내부 변경 사례:**

1. SpatialSync가 같은 snapshot·최종 Writer handle을 보존하며 Populate Job을 나누거나 작업량만 바꾸는 경우, 정상 Reader는 그대로여야 한다. Placement는 Fence를 기다리지 않아 완료 시간 차이가 안전성에 영향을 줄 여지가 있다(F-026). 실제 경쟁 재현/발생률은 미확인이다.
2. Config Loader가 같은 건물/자재 버퍼와 성공/실패 의미를 게시하면서 파싱 구현을 바꾸면 Placement·Utility·Completion을 함께 수정할 이유가 없다. Config 없음의 의미를 Ready/Failed로 새로 분리하는 것은 **공개 계약 변경**이며 내부 개선과 구분한다.
3. Placement의 승인 집합과 Tick/Order 의미를 유지하며 요청 순회·ECB 기록 순서를 최적화할 경우, 고유 순서 데이터가 있다면 후속 물류 내부를 알 필요가 없다. 현재 동일 Stamp는 Entity.Index나 방향 탐색 순서로 넘어가므로 생성/할당 이력 변화가 경합 선택에 영향을 줄 수 있다(F-041). 영향은 코드 경로에 따른 조건부 추정이다.
4. 동일 입력→동일 결과 계약을 보존한 claimedCells 자료구조 교체는 검증 Utility 내부에 한정할 수 있다. 현재 no-config / DynamicBuffer / NativeArray 세 overload가 선점·rollback 루프를 복제하므로 공통 수정 시 세 곳을 대조해야 한다. 이는 **국소 유지보수 위험**이며 다른 시스템의 세부 Job 순서를 알아야 하는 문제와 구분한다. 측정 없이 병목이라고 판정하지 않는다.
5. 완공 프리팹의 렌더/타입별 runtime 초기화 내부만 바꾸고 현장 입력·성공 의미를 보존하면 Placement 수정은 필요 없다. 반대로 Footprint.Size의 base/effective 의미를 바꾸는 것은 공개 계약 변경이다. 현재 F-023을 Sync에서 생산자에 따라 보정하는 해법은 채택하지 않는다.

개별 검증은 NativeContainer 입력만으로 분리 가능하며 Command 테스트도 다른 게임 시스템 전체 기동 없이 실행된다. 다만 테스트가 Map을 직접 채우고 Command→ECB를 수동 호출하기 때문에 실제 그룹 정렬·미완료 Writer·여러 요청 가시성까지 보장하는 것은 아니다. V1과 같은 범위의 비교를 하지 않았으므로 “V1보다 결합 감소”를 확정하지 않는다.
