### 3.2 Reader/Writer와 거부 시 보존

| 데이터 | Writer / Owner | Reader·소비 | 판정 |
| --- | --- | --- | --- |
| Stored/Product 버퍼 | 입고·출고 Apply, 생성/제작/레시피/철거 경로 | 해당 Output Decision은 read-only, Apply는 선택 Entity 하나 제거 | Decision/Reservation은 원본 버퍼를 수정하지 않음. Product 선택기는 Stored 재료 내부를 읽지 않음 |
| BuildingItemOutputDecision+enable | Storage/Product Decision 작성 → Reservation 거절 시 수정 → Apply 소비 | 예약과 Apply | enable=false가 후속 Apply를 제외. CanOutput=false인데 enable=true인 비정상 주입은 Apply 조기 반환으로 남을 수 있으며 정상 Producer는 둘을 함께 관리 |
| Belt/Item Map·Fence | 각 SpatialSync, Reader의 핸들 등록 | 두 Decision과 Reservation은 두 Map, Output Apply는 Belt Map | 마지막 Writer+state.Dependency 결합·AddReader. 메모리 동기화와 도착 승인 중재는 별개 |
| BeltMovementState·ItemOwnership | Belt Execution/전달/Ownership | Decision·Reservation이 현재 점유의 progress/enable/Owner 조회 | 인덱스 안의 후보를 추가 필터링. 일반 이동으로 새로 들어올 아이템을 선반영하지 않음(F-029) |
| PlacementStamp | 배치/생성 시 부착, 이후 불변 | Reservation | 출고 선택기가 경합 상대의 설치 시점이나 내부 처리 순서를 알 필요 없음 |
| GridPosition·Direction·LocalTransform·BeltMovementState | 성공 Output Apply | 다음 이동·Sync | 대상 입구 좌표, BeltMap 방향, progress=0, movement=true. 시각 좌표는 셀 중심에서 방향×0.5 뒤 |
| TransferOwnershipRequest·Owner·DisableRendering | Apply는 request, Ownership은 Owner 직접 쓰기+태그 ECB | Ownership→EndStateApply→Sync | 요청만으로 버퍼 제거가 일어나지 않음. Owner Null은 직접 적용, 표시 태그 제거는 ECB. 출고 ItemMap 등록은 후속 Sync |

- **Decision 거절(빈 버퍼/출구 없음/정체):** 결정값을 false/null/zero로 정리하고 disable. 버퍼·아이템 상태는 그대로다.
- **Reservation 거절(벨트 없음/공간 부족/경합 탈락):** CanOutput=false와 disable만 적용한다. 대상 Entity/좌표 값이 남아도 Apply는 비활성 쿼리에서 제외한다. 원본 버퍼·Owner·movement·위치를 쓰는 코드가 없다. 다음 Decision에서 재시도한다.
- **Apply에서 대상 Map 누락:** 버퍼를 만지기 전에 결정 false/null/disable로 소비한다. 원본 상태 보존은 코드 확인이다.
- **성공 Apply:** 원본 버퍼에서 한 Entity를 제거하고 상태를 복원한 뒤 결정을 false/null/disable. TargetBeltPosition 잔여값은 enable=false 하에서 사용되지 않는다.
- **오래된 선택/부분 구성:** 버퍼에서 찾지 못하거나 어느 버퍼도 없어도 월드 상태 변경을 계속한다. 각 컴포넌트 HasComponent guard는 예외를 줄일 뿐 원자적 실패/롤백을 보장하지 않는다. Transfer 누락 등 비정상 프리팹 구성까지 정상 출고라고 주장하지 않는다.

Q14와 같이 Input Job 뒤에 Output Job을 연결하므로 두 Job이 같은 버퍼를 동시에 쓰지 않는다. ItemOwnershipApply보다 먼저 요청을 쓰는 순서와 EndStateApply 이후 Sync는 필요하다. 이 순서가 모든 도메인의 임의 상태 변경을 자동으로 승인 계약에 포함하지는 않는다.

공개 계약을 유지한 내부 변경의 영향 사례(코드 수정 실험은 하지 않음):

1. **Reservation의 목적지 집계를 HashMap/List 대신 다른 방식으로 바꾸되 같은 승자·거절 enable을 유지:** Storage/Product 선택기와 Apply 수정은 필요 없다. 반면 승자 토큰/프레임 번호를 결정에 추가하면 공개 계약 변경이므로 소비자 수정은 정상적인 전파다.
2. **Product 선택의 첫 slot0 탐색을 같은 결과를 내는 helper로 교체:** 예약/Apply는 ItemToOutput Entity만 보므로 수정 불필요. 레시피의 재료 계산 내부가 달라져도 Product의 slot 의미와 생산 결과가 같다면 Output에는 영향 없다.
3. **버퍼 유지보수에서 요소 순서만 바꾸되 선택 Entity와 source membership을 유지:** Apply는 저장된 배열 인덱스가 아니라 Entity를 다시 검색하므로 안전하다. 이것은 좋은 분리다. 그러나 승인 후 다른 Writer가 해당 Entity를 제거/이관할 수 있게 변경하면 현재 공개 결정에는 무효화 결과가 없어 F-033이 드러난다. 이 경우 수명/취소 계약을 먼저 명시해야 하며, 무조건 ‘내부 변경’이라고 간주해서는 안 된다.
4. **동일한 active/world/spacing 결과를 내는 점유 계산 내부 최적화:** 순수 helper를 두 선택기와 예약에서 공유하면 계약을 유지한 계산 변경의 수정 지점을 줄일 수 있다. 현재의 세 구현을 같은 수치로 유지해야 하는 비용은 있지만 측정 없는 성능 개선 효과는 주장하지 않는다.

고정 출구 탐색과 PlacementStamp 우선순위는 현재 선택 정책이다. 경합에서 진 출고가 같은 프레임의 다른 빈 출구로 재탐색하지 않는 점, slot0이 계속 공급되면 부산물이 기다릴 수 있는 점은 확인했으나 공정성 요구가 없는 상태에서 곧바로 결함으로 등록하지 않았다.

3. **출구/경합 정책:** 고정 둘레 순서와 오래된 PlacementStamp 우선이 의도한 정책인지, 패자가 다른 빈 출구를 재시도할 필요가 있는지? 게임 규칙 결정 없이 불공정성 결함으로 확정하지 않았다.
4. **후속 검증 제안:** 거절 후 Apply까지 원본 상태 불변, Product 선택→예약→해당 buffer 제거→Ownership/ECB/Sync, 최대 정원/epsilon 경계, 동일 프레임 일반 이동+출고(F-029). 승인된 별도 테스트 보강에서 다룰 항목이다.
