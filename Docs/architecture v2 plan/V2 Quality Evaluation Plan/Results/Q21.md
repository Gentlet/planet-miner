### 3.2 착수·누적·용량·완료

1. **쿼리 진입:** Decision은 두 결정 컴포넌트의 enable은 무시하지만 존재 자체와 CrafterState/Stored/Product/ProductResult는 모두 요구한다. 레지스트리가 없거나 Blob이 미생성이면 시스템 전체가 return하며 이전 결정을 지우지 않는다. 필수 컴포넌트 누락은 대기 상태가 기록되는 경로가 아니라 쿼리에서 제외되는 경로다(F-037).
2. **착수 판단:** IsCraftingActive=false일 때 각 재료 행마다 Stored의 같은 품목 개수를 세어 Amount 이상인지 검사한다. 충분하면 CanStartCraft/CanAdvance=true, CanProduceOutput=false, NextStatus=Idle. 출력이 가득 차 있어도 착수를 막지 않는다. 즉 **재료 선소비→완료 후 출력 대기**가 현재 코드의 정책이다.
3. **선소비:** Execution은 현재 SelectedRecipeId로 레시피를 다시 찾는다. 재료별 뒤쪽 요소부터 RemoveAt 후 DestroyItemRequest enable을 켠다. 모든 행 반복 후 IsCraftingActive=true, Progress=0. 이어 같은 호출에서 진행도를 누적한다. 소비 중 구조 변경은 없으므로 제거 전 DynamicBuffer를 ECB 재생 뒤까지 보관하는 문제는 없다.
4. **전제와 실패:** Execution은 `remainingToConsume>0` 잔류를 실패로 처리하거나 rollback하지 않는다. 정상 동일 프레임에서 승인 재고가 유지된다는 전제는 필요하지만, 중복 재료 행에서는 Decision과 소비 계산이 이미 어긋난다([F-014 최초 Q06](Q06.md#f-014--중복-재료-행을-합산하지-않아-필요한-양보다-적은-재료로-제작이-시작됨)). DestroyItemRequest가 없는 malformed 아이템은 버퍼만 제거되며 정상 Item 생성이 요청을 제공한다는 Q03 계약에 의존한다. 후자는 새 정상 경로 결함으로 확대하지 않았다.
5. **누적:** `dt=min(Time.DeltaTime, GameConstants.MaxSimulationDeltaTime)`가 양수일 때 `(dt*Speed)/max(0.01,CraftTime)`을 더하고 상한 1로 clamp한다. 진행 중에는 출력 용량과 무관하게 누적하고 재료를 다시 요구/소비하지 않는다. 고속에서 넘친 진행도는 이월하지 않으며 한 호출에 여러 작업을 완료하지 않는다.
6. **전체 출력 용량:** 모든 유효 Outputs 행의 해당 슬롯에 대해 `기존 요소 수 + 이번 Amount <= 그 품목 MaxStack`이어야 한다. Registry 없음/Blob 미생성이면 50. 슬롯 하나라도 부족하면 **어떤 출력도 승인하지 않는다**. None/Amount≤0 행은 Decision·Execution 모두 건너뛴다. Storage.SlotCount, 기존 출력 품목/Owner/Entity 정합성, 임의 SpawnItemRequest의 향후 append는 검사하지 않는다. 이들은 정상 버퍼/저수준 생성 계약의 전제다.
7. **출력 시점:** Progress<1을 본 Decision은 CanProduceOutput=false이므로 Execution에서 이번에 1에 도달해도 출력하지 않는다. 다음 Decision의 재검사가 필요하다. 현재 프레임의 Output Apply가 공간을 비우더라도 이미 거절된 출력은 다음 Decision에서 재승인된다. 이는 공개 Phase 경계의 보수적인 지연이며 순서 결함으로 세지 않는다.
8. **결과와 실체화:** 완료 승인 시 Outputs의 모든 유효 행을 ProductResult로 기록하고 Active=false/Progress=0으로 reset한다. ItemLifecycle이 결과를 Clear하면서 아이템·소유 버퍼 append를 ECB에 기록한다. **용량 판단의 all-or-nothing과 실체화 실패의 원자성은 다르다**. 일부 prefab 누락 시 일부 출력만 생성될 수 있는 F-006은 재료 환급/재시도 보장이 없다는 기존 질문이다.

**Status 시점 [코드 확인 / 의미는 설계 질문]:** 착수 프레임 Decision은 NextStatus=Idle을 기록한다(`CrafterDecisionSystem:264–273`). Execution은 Active=true와 양수 Progress를 만들지만 StateApply는 앞서 기록된 Idle을 그대로 쓴다. 시작 직후에는 Status와 실행 상태가 같은 시점의 설명이 아니다. dt=0에서 출력 허가만 기록된 경우에도 StateApply는 NextStatus를 적용할 수 있다. 현재 Input은 WaitingForByproductOutput만 검사하므로 이 차이로 일반 입고가 즉시 잘못됨을 확인한 것은 아니다. Status가 ‘판단 시점의 표시’인지 ‘실행 완료 후 현재 상태’인지 결정이 필요하며 새 게임 동작은 정하지 않았다.

**프레임 계획 수명 [코드 확인]:** CrafterDecision은 IRequestComponent가 아니다. execution enable 잔류만으로 일회성 요청 미소비 결함이라고 판정하지 않는다. 다만 Execution만 반복하거나 Decision이 이전 계획을 갱신하지 못하는 부분 실행에서 안전한 멱등성을 보장하지 않는다. `CanCraft=false` 자체는 소비자의 최종 guard도 아니므로 세 동작 플래그의 일관성과 같은 프레임 유효성이 공개 계약에 포함돼야 한다.

## 4. 의존 관계와 공개 계약을 유지한 변경 영향

| 의존하는 시스템 → 대상 | 의존 형태 | 공개 계약 / 내부 가정 | 필요한 이유 | 변경 전파와 판정 |
| --- | --- | --- | --- | --- |
| Decision → Recipe/Item Registry·Stored/Product | 읽기·Job | 불변 레시피, 요소당 1개, 출력 배열 인덱스=슬롯, 품목별 상한 | 비용·전체 출력 판단 | **필요한 데이터 계약**. 중복 재료 의미의 불일치는 F-014 |
| Execution → Decision·CrafterState·Recipe | 읽기·상태 쓰기·Phase | 같은 프레임 실행 플래그, 승인한 재료가 Execution까지 유지됨. RecipeId/Index 대신 현재 SelectedRecipeId 재조회 | 판단과 실행 분리 | **필요한 승인 계약**, 프레임/취소 유효성의 문서화 개선 후보. 다른 도메인 내부 Update 호출 없음 |
| Execution → ItemLifecycle | 버퍼/enable 전달·ECS 의존·ECB | 참조를 먼저 제거한 삭제 요청, Count/SlotIndex 결과, EndStateApply 실체화 | 살아 있는 버퍼의 죽은 참조·구조 변경 경합 방지 | **필요한 동기화**. Product/Spawn/Destroy Job 내부 나열 순서를 Crafter가 알 필요는 없음. 실패 정책은 F-006 |
| StateApply → Decision·Execution 상태 | enable 소비·필드 쓰기 | NextStatus를 Status에 복사; Progress/Active는 Execution 소유 | 상태 결정 소비와 진행 상태 보존 | 공유 CrafterState의 ECS 의존은 필요. Status가 실제 실행 결과가 아닌 예측임을 알아야 하는 점은 의미 명확화 후보 |
| Input → CrafterState.Status | 다른 도메인 enum 읽기 | 특정 WaitingForByproductOutput일 때 일반 입고 차단 | 잔여물 배출 중 신규 재료 혼입 방지 | Q14와 같은 **결합 개선 후보**. 공개 입고 가능 계약으로 표현할지 질문. 차단 자체는 필요 |
| Recipe Command → 실행 상태·Stored/Product·Filter | 직접 쓰기·Command 선행 | 현재 작업 중단, 잔여물 이동, ID/필터 변경을 같은 Command 경계에 반영 | 레시피 변경의 일관성 | 필요한 교차 상태 조정. 전체 정책/동일 프레임 요청 처리는 Q22로 제한 |
| Spawn Utility / Factory → Crafter 3개 시스템·Input | 엔티티 구성·초기 enable | 필수 component/buffer 집합과 초기값 | 생성 직후 쿼리 진입과 입고 | **공개 구성 계약 자체는 필요**, 이를 두 구현이 불일치하게 유지하는 것이 F-037. 현재 테스트는 실행용 Factory 내부를 알아야 진입 전제를 얻음 |

**필요한 동기화:** Decision의 ScheduleParallel → Execution의 직렬 Schedule → StateApply의 ScheduleParallel은 각 `state.Dependency`와 동일 ECS 데이터의 읽기/쓰기 의존을 등록한다. Execution의 item별 DestroyItemRequest lookup 쓰기와 ItemLifecycle의 소비도 이 경계에 포함된다. 구조 변경은 EndStateApply(OrderLast)에서 확정한다. CrafterStateApply와 ItemLifecycle 사이에 별도 UpdateAfter가 없다는 사실만으로 오류라고 판정하지 않는다. 전자는 Status, 후자는 결과/아이템을 처리하며 정상 경로에서 상대의 private Job 순서에 의존하지 않는다. 이 분석은 실제 정렬 그룹을 새로 실행해 확인한 결과와 다르다.

공개 계약을 유지한 내부 변경 사례(**정적 영향 분석**, 수정 실험 없음):

1. **Decision의 슬롯별 계수를 반복 순회 대신 같은 수량을 내는 지역 집계로 교체:** 플래그·enable·동일 입력 결과를 유지하면 Execution/StateApply/출고 코드를 바꿀 필요가 없다. 중복 재료 합산으로 F-014를 고치는 것은 현재 동작과 허용 입력 의미를 바꾸므로 단순한 성능 리팩터링과 구분한다.
2. **Execution의 재료 탐색을 helper로 분리하되 같은 Entity 선택·선소비·삭제 요청·Progress·ProductResult를 유지:** ItemLifecycle은 원래 버퍼 탐색 방식에 의존하지 않으므로 수정 불필요. Entity 선택이나 소비 시점을 바꾸면 출력 요청 수명/소유권 계약 변경 여부를 별도로 검토해야 한다.
3. **ItemLifecycle의 내부 생성 코드를 나누거나 Job 구성을 바꾸되 같은 결과 소비·EndStateApply 생성·삭제 계약을 유지:** Crafter가 Product→Spawn→Destroy라는 현재 세부 순서를 따라 수정될 이유는 없다. 반대로 Clear 뒤 실체화를 다음 프레임으로 늦추면 ‘다음 Decision 전 Product에 보인다’는 공개 가시성 계약의 변경이다. 기존 미소비 가드만으로 그 변경에 안전하다고 주장하지 않는다.
4. **StateApply의 Status 복사/enable 해제 구현을 내부 helper로 이동:** 다른 소비자 영향 없음. 반면 `CrafterStateDecision` 같은 **필수 컴포넌트 추가**는 파일 내부 리팩터링처럼 보여도 엔티티 구성 계약 변경이다. Spawn·Factory 모두 갱신돼야 하며 현재 누락(F-037)은 바로 그 계약 불일치다. 필요한 소비자 갱신을 불필요한 결합으로 세지 않는다.
5. **제작의 내부 진행 알고리즘만 바꾸고 Product의 품목/슬롯/가시성과 공개 Status 의미를 유지:** Product Output은 레시피·진행 계산을 몰라도 된다. WaitingForByproductOutput의 이름/의미 자체를 바꾸면 Input도 검토해야 하는 것은 공개 enum 의존이며, 이 제작 정책 지식을 일반 물류가 가져야 하는지는 분리 설계 질문이다.

테스트는 CrafterStateApply/ItemLifecycle을 직접 협력자로 호출하므로 진정한 단일 함수 단위 테스트는 아니다. 이 정도의 공개 결과·ECB 협력은 합리적이다. 그러나 필수 구성 검증을 Factory로 우회하면 실제 Spawn이 쿼리 계약을 지키는지 독립적으로 보장하지 못한다. 시스템 수나 UpdateAfter 수를 줄이는 것을 개선 목표로 제안하지 않는다.

## 5. 발견 문제와 기존 문제 연결

### F-037 — 실제 Crafter 생성 구성에 필수 상태 결정과 입고 컴포넌트가 빠져 제작 흐름에 진입하지 못함

- 발견 단계 / 유형 / 평가 축: Q21 / **안정성 결함·V2 설계 불일치·검증 공백** / 안정성·유지보수성·V2 적합성.
- 우선순위와 이유: **P1**. 지원되는 DB 없는 fallback 생성 경로에서 생성된 Crafter의 Decision 진입과 정상 물류 입고가 차단된다. 단순 표시 오류가 아니라 핵심 제작 경로의 중단이다.
- 근거 수준: **코드 확인**. 해당 생성물로 제작을 실행한 재현은 **미확인**. 선택 EditMode 5건은 이 결함을 검증하지 않는다.
- 위치: `BuildingLifecycleUtility.cs:95,108,138–147`; `BuildingLifecycleApplySystem.cs:46–53`; `ConstructionLifecycleApplySystem.cs:63–70`; `CrafterDecisionSystem.cs:31–35`; `BuildingItemInputDecisionSystem.cs:150–158`; `CrafterRecipeCommandSystem.cs:159–179`; `TestEntityFactory.cs:174–204`; `Phase7BuildingLifecycleTests.cs:103–132`.
- 기대 계약과 출처: Utility의 ‘타입별 필수 컴포넌트 주입’ 책임, 실제 Decision 쿼리의 `CrafterStateDecision` 존재 요구, Input의 Storage 요구, Recipe Command의 기존 StorageFilter 갱신 계약. 현재 소비자가 요구하는 구성으로 판단하며 새 게임 규칙을 요구하지 않는다.
- 확인한 코드 동작: Crafter 분기는 CrafterState/CrafterDecision과 세 버퍼·출고 결정만 추가한다. CrafterStateDecision/Storage/StorageFilter는 추가하지 않는다. fallback 공통 archetype에도 없다. Decision은 엔티티를 제외하고, 초기 false인 CrafterDecision은 켜지지 않는다. 레시피를 지정하고 재료를 직접 넣어도 누락된 상태 결정 컴포넌트 때문에 판단이 시작되지 않는다. 정상 벨트 Input은 Storage 부재로 거절하며 Command는 Filter가 없으면 생성을 보충하지 않는다.
- 발생 조건과 영향: DB 없는 SpawnBuildingRequest 및 공사 완료가 사용하는 공통 fallback 생성. DB 경로도 같은 주입 누락은 있으나, prefab에 미리 해당 컴포넌트가 있다면 증상이 달라질 수 있다. **이번에는 실제 baked prefab을 확인하지 않았으므로 모든 DB 기반 실제 장면에서 재현됐다고 확정하지 않는다.**
- 근거 / 반대 근거: Factory는 세 컴포넌트를 모두 제공하여 선택 테스트 5건이 통과한다. 기존 `Test03_SpawnBuilding_Crafter_InitializesStateDecisionAndBuffers`는 이름과 달리 CrafterState·CrafterDecision·버퍼를 assert하고 **CrafterStateDecision·Storage·StorageFilter는 assert하지 않는다**. 이 테스트를 그대로 실행해도 누락 여부를 판정할 수 없어 추가 실행하지 않았다.
- 수정 방향 후보: 런타임 Spawn의 필수 구성·초기 enable 계약을 Factory 및 소비자와 맞추고, 실제 Spawn 결과로 Decision→Execution→StateApply를 연결한 회귀 검증을 추가한다. 공통 계약을 검사한다고 Factory와 런타임 구현을 무조건 같은 함수로 합칠 필요는 없다.
- 필요한 추가 검증: fallback과 최소 DB prefab의 생성/완공 후 필수 컴포넌트·초기 enable·NoRecipe, 레시피 선택 후 입고 승인·선소비·생산까지 확인. 잘못된 runtime 구성에서 기존 Factory 테스트와 결과가 달라지는지 확인한다.
- 미확인 / 설계 질문: Crafter 입력 슬롯 수의 제품 규칙은 Factory 기본 4를 그대로 런타임 정답으로 복사하지 않는다. 설정/레시피에 따른 슬롯 수를 어떤 공개 규칙으로 결정할지 별도 확인이 필요하다. 필수 `CrafterStateDecision` 누락 자체는 이 슬롯 정책 결정과 무관하다.

## 7. 남은 질문·제안과 완료 범위

1. **F-037의 별도 수정:** Crafter의 입력 슬롯 수와 초기 필터 정책은 무엇인가? Factory의 기본 4와 실제 게임 규칙을 동일시하지 않고 설정·레시피 계약을 확인해야 한다. 필요한 상태 결정 컴포넌트·초기 enable·생성 후 쿼리 진입은 함께 회귀 검증할 것을 제안한다.
2. **Status 의미:** Status는 판단 시점의 표시인가, 프레임 종료 시 실제 Progress/Active와 일치해야 하는가? 시작 프레임, 1에 도달하는 프레임, dt=0의 승인/실행 불일치를 직접 assert하는 테스트를 제안한다. 이번에는 전이 정책을 바꾸지 않았다.
3. **선소비 후 중단/실패:** 레시피 변경으로 중단된 작업의 이미 소비된 재료, prefab 실패로 누락된 출력의 환급·보존·영구 폐기 정책은 무엇인가? Q22 및 F-006 최초 질문에 연결한다. 필요하면 실패 결과나 작업 식별 계약을 설계하되 무조건 재시도를 추가하지 않는다.
4. **출력/비용 경계 검증:** 중복 재료의 정확한 총량(F-014), 품목별 MaxStack과 Amount가 다른 다중 출력, `count+amount==max`/초과, 처음부터 출력 만석일 때 선소비·완료 대기, ItemLifecycle 생략 시 잔류 ProductResult 차단을 보강할 것을 제안한다. 한 번의 출력 Amount가 MaxStack을 넘는 설정을 어디서 거부할지도 Q06의 미결 질문이다.
5. **프레임 계획 유효성:** 정상적으로 Decision→Execution이 매 tick 한 번씩 실행되는 공개 경계를 유지할 것인가? 부분 재실행/정지·레지스트리 준비 상태 전환까지 지원하려면 오래된 실행 결정의 처리 의미를 먼저 정해야 한다. 새 runtime 기능을 필수로 요구하지 않는다.

코드 확인·선택 실행 확인·정적 변경 영향 추정·미확인을 구분했고 필요한 선택 테스트는 최종 완료를 확인했다. 코드·테스트·Config·에셋 및 기존 설계 문서는 수정하지 않았다. **Q21에서 종료**하며 Q22나 F-037/F-038 수정은 자동 진행하지 않는다.
