## 3. 순수 계산이 보장하는 의미

### 좌표와 영역 — 코드 확인

- `ChunkSize=16`과 `CellCount=256`은 GameConstants에 연결된다. 셀→청크는 정수 나눗셈 후 음수 나머지가 있으면 몫을 1 낮춘다. 지역 셀은 `cell - chunk*16`이며 정상 셀 입력에서 각 축 0–15다. 예를 들어 (-1,-17)은 청크 (-1,-2), 지역 셀 (15,15), index 255에 해당한다. 이는 코드로 추적한 계산이며 이번에 별도 실행한 assertion이 아니다.
- `GetChunkBounds`는 청크 좌표의 16배부터 +15까지의 포함 범위다. `IsInsideChunk`가 양 축 경계를 검사하므로 정상 표현 범위에서 이웃 청크 영역은 겹치지 않는다. Q18의 생성/clip 검사 통과를 바닥 분포 자체의 근거로 사용하지 않는다.
- `ToCellIndex`는 유효 지역 셀, `FloorDiv`는 양수 divisor, 청크 경계 곱셈은 int 표현 범위를 전제로 한다. 현재 직접 사용은 상수 16을 넘긴다. 임의의 0 divisor나 무제한 청크 좌표를 지원하는 API라고 가정하지 않는다.

### 바이옴·전이·변형 — 코드 확인

1. `worldCell + boundaryWarp`를 regionSize(청크 수×16)로 나눈 뒤 **math.floor**하여 현재 영역을 고른다. 음수에서도 0 쪽 절삭이 아니라 아래쪽 영역을 택한다. 노이즈 amplitude<=0이면 warp는 0이며, 그 외에는 네 격자 hash 값에 smoothstep 보간한 value noise를 x/y 별도 salt로 계산한다.
2. 영역의 바이옴은 같은 시드·영역 좌표의 hash와 SelectionWeight 누적으로 선택한다. 청크 접수 여부·자원/건물 점유·이전 호출 순서·시간을 읽지 않는다. 불변 입력에 대한 함수이며 ECS 시스템이나 전역 random 상태를 호출하지 않는다.
3. 전이 폭=0이면 현재 바이옴을 유지한다. 그 외에는 warped 영역의 가장 가까운 x/y 경계를 고른다(x/y 동률이면 x). 거리>=전이 폭의 절반이면 전이 밖이며, 가까운 이웃 영역이 같은 바이옴이어도 전이를 만들지 않는다.
4. 다른 바이옴 경계 안에서는 거리 비율의 smoothstep과 exponent를 이용해 현재/이웃 바이옴을 선택한다. 현재 바이옴 확률은 경계에서 0.5, 전이 끝쪽에서 1에 가까워진다. 별도 hash로 전이용 변형을 쓸지 결정하며 확률은 `1-SmoothStep(distanceRatio)`다.
5. 전이용이면 variants prefix `[0, TransitionVariantCount)`, 아니면 선택된 바이옴의 `[VariantStart, VariantStart+VariantCount)`에서 weight 누적으로 변형을 고른다. 결과 `VariantIndex`는 **그 선택 목록 안의 로컬 인덱스**다. `GetVariant`가 같은 설정/버퍼와 결과로 실제 버퍼 위치를 해석해 `SpriteResourcePath`를 돌려준다.

서로 다른 단계는 구분된 salt를 사용하고 `HashToUnitFloat`는 하위 24비트를 [0,1) 값으로 바꾼다. 같은 설정·버퍼 순서·시드·셀에서 결과가 같다는 근거이지, 모든 시드가 다른 결과를 내거나 작은 유한 영역에서 가중치 비율이 정확히 일치한다는 보장은 아니다. 네 영역이 만나는 모서리에서는 모든 이웃을 혼합하지 않고 가장 가까운 경계 하나만 고려한다. 이것이 의도한 모서리 모양인지 시각 품질 판단은 별도로 남긴다.

입력 전제는 Q07의 검증된 설정이다. 목록 비어 있지 않음, 양의 유한 weight/합계, 유효 start/count와 전이 prefix, region>0, noise scale/exponent>0 및 Sprite 경로가 필요하다. Sampler/GetVariant는 매 호출마다 이를 다시 검증하지 않는다. `in DynamicBuffer` 형식 자체가 완전한 순수 타입이라는 주장이 아니라, **현재 본문에 쓰기/World 조회가 없다는 코드 근거**로 순수 계산이라 판단한다. 이전 설정에서 만든 selection을 변경된 버퍼에 적용하는 계약은 없다.

## 4. 진단 표시의 동작과 한계

Preview.Update는 기본 World가 존재하고 네 설정/버퍼를 **같은 엔티티**에서 찾을 수 있을 때까지 기다린다. 매번 만든 query는 finally에서 Dispose한다. 로더의 구체적인 실행 순서나 EndCommand/EndStateApply 시점을 알아야 할 필요가 없다. 설정이 갖춰진 다음 Update에서 읽으면 된다.

BuildPreview는 radius를 0–4로 clamp하고 한 변 `(2r+1)*16`셀을 원점 주변 청크 영역에서 샘플링한다. 현재 씬 r=1은 48×48 픽셀, 양 축 셀 -16…31이다. 실제로 로드된 청크 집합을 읽는 것이 아니므로 청크 로드/언로드의 시각화로 설명하면 안 된다.

| 표시 항목 | 코드가 하는 일 | 보장하지 않는 것 |
| --- | --- | --- |
| 색상 | UsesTransitionVariant면 transitionColor, 아니면 BiomeIndex=0에 grassColor, 나머지에 dirtColor | 임의 바이옴 ID마다 다른 색상/범례 제공. 현재 Grass/Dirt 순서 전제 밖의 일반 진단 |
| 밝기 | `0.88 + VariantIndex*0.06`, alpha=1 | 실제 Sprite의 픽셀/투명도/타일 모양, 여러 길이의 목록에서 충분한 구분 |
| 전이 색 | **전이용 변형이 선택된 셀**을 표시 | 전이 지대의 모든 셀 표시. 전이 안에서도 일반 바이옴 변형을 고를 수 있음 |
| Texture/Sprite | Point/Clamp RGBA32 텍스처, PPU=1인 Sprite 1개와 Renderer(order=-1000), child world position 설정 | 선택된 SpriteResourcePath로 개별 바닥 타일을 렌더링하는 기능 |
| 갱신 | previewObject가 있으면 즉시 return | 설정·색상·radius 변경, 기본 World 교체에 따른 자동 재생성/실시간 모니터링 |
| 정리 | OnDestroy에서 소유 Sprite/Texture/GameObject Destroy | OnDisable 시 표시 제거·오브젝트 풀/부분 재빌드 수명주기 |

Texture.Apply(false,true) 후 픽셀 CPU 수정 경로를 유지하지 않으며 리소스/child에 DontSave를 붙인다. 화면 생성은 ECS 엔티티나 바닥 점유를 생성하지 않는다. MonoBehaviour가 비활성화되더라도 기존 child Renderer가 자동 제거되는 코드는 없고, 정상 파괴 시 정리한다. 1회 진단이라는 현재 범위를 넘어 hot reload/disable 정책을 임의로 요구하지 않았다.

**실제 화면·색상·배율·셀 중심 정렬은 미확인**이다. Renderer 중심을 `minCell+size/2`, PPU=1로 배치한다는 코드 확인과 게임 오브젝트/카메라를 포함한 시각 정합성 확인은 다르다. 씬의 직렬화 radius/색상 조회도 화면 검증으로 취급하지 않는다.

| ChunkUtility | GameConstants의 크기 → Sampler/Preview 및 다른 좌표 소비자 | 공통 좌표 규칙 재사용. 크기 변경은 공개 월드 좌표 계약 변경이며 국소 내부 리팩터링과 다름 |
| Texture/Sprite/child | Preview 생성·정리 → SpriteRenderer | 표시 자원의 수명은 MonoBehaviour 소유, ECS 상태 Writer 아님 |
| 설정 준비 | 전체 게시 → Preview의 완전한 query | 필요할 때까지 기다리는 상태 조건. 자원 설정만으로 Init이 끝나는 F-016은 생산 측 준비 계약 누수이며 Preview가 수리할 책임은 아님 |

현재 바닥 버퍼를 runtime Job으로 수정하는 경로는 참조 검색에서 발견되지 않았다. 로더의 메인 스레드 초기 게시와 Preview의 동기 읽기에는 자원 공간 Map의 Fence를 끌어올 필요가 없다. 샘플링 결과는 좌표/설정에서 유도되므로 청크 완료 이벤트나 공간 인덱스 snapshot에도 의존하지 않는다. 향후 Job Writer/동적 설정 변경을 추가할 때는 그 새 데이터 계약의 의존성을 정의해야 한다.

공개 계약을 유지한 내부 변경 사례:

1. **가중 선택/노이즈 계산 최적화**: 같은 셀의 selection 및 Sprite 경로 의미를 유지하면 Preview/Loader/Chunk 시스템 수정이 필요 없다. salt·float 계산·행 순서 변경으로 분포가 바뀌는 것은 저장 형식만 유지했다고 계약 유지로 간주할 수 없다. 기존 월드 결과 호환성은 별도 요구 확인 대상이다.
2. **설정 파싱/검증 구현 변경**: 같은 엔티티와 prefix/start/count·준비 조건을 유지하면 Sampler/Preview는 영향받지 않는다. 전이 prefix를 옮기거나 VariantIndex를 전역 index로 바꾸면 공개 데이터 계약 변경이므로 소비자 수정은 정상적인 변경 영향이다.
3. **Preview의 SetPixel을 배열 업로드로 변경**: 같은 픽셀/표시 영역과 수명을 유지하면 Preview 내부 변경으로 제한되며 Sampler·게임 시뮬레이션은 바꿀 필요가 없다. 실제 Sprite renderer를 구현하는 것은 이런 내부 최적화와 달리 후속 기능이다.
4. **ChunkUtility의 음수 나눗셈 내부 구현 변경**: 같은 입력 범위·floor 의미를 유지하면 자원 생성/Preview의 코드 수정은 불필요하다. 크기나 inclusive bounds 의미를 바꾸는 것은 공개 계약 변경이다.

검증된 버퍼를 준비하면 Sampler의 국소 테스트에는 World 설정 로더·청크/자원 시스템 실행이 필수는 아니다. 현재 선택 테스트는 실제 Resources 로더를 쓰므로 설정 값/경로 변경에도 영향을 받는 통합 성격이 있다. 순수 기대값 테스트를 보강할 때 작은 고정 버퍼 fixture를 쓸 수 있지만 이번에는 테스트를 추가하지 않았다. V1 대비 의존성 감소량은 측정하지 않았다.

1. **진단 범위**: Preview를 계속 기본 두 바이옴의 고정 snapshot으로 둘 것인가, 바이옴 ID별 색상/범례·설정 변경/World 교체/OnDisable 갱신까지 지원할 것인가? 후자를 현재 요구로 가정하지 않았다.
