## 2. 입력·검증·게시의 실제 계약

### 2.1 초기화와 실패 경계

**[코드 확인]** 실제 로더는 managed `BuildingConfigInitSystem`이며 **OnCreate**에서 LoadAndPublish를 수행한다(`BuildingConfigLoadSystem.cs:31–35`). `OnUpdate`에서는 비활성화만 한다. 같은 파일의 unmanaged `BuildingConfigLoadSystem`은 BuildingConfig를 RequireForUpdate한 뒤 한 번 비활성화할 뿐 로드·게시·소비자 호출을 하지 않는다. 그 클래스의 로드 책임을 설명하는 상단 주석은 실제 구현과 다르다. 별도 로더 2개가 작동한다고 해석하지 않는다.

Init는 기존 BuildingConfig singleton이 있으면 읽기를 생략한다. 기존 엔티티의 세 버퍼·내용을 다시 검증하거나 보완하지 않는다. Resources 누락/검증 false이면 Loader와 Init의 오류 로그를 남기고 게시하지 않는다. fallback 설정, 실패 상태 컴포넌트, 재시도는 없다. 이 상태가 게임 전체의 작동 중지를 뜻하지는 않는다(F-011).

TryParseJson은 처음 두 out을 null로 두고 로컬 configList/materialList에 적재한다. 오류 분기에서는 false이며 마지막까지 성공해야 두 out을 반환한다(`:65–186`). 즉 후반 항목이 실패해도 앞서 쌓은 목록을 외부에 반환하지 않는다. TryParse는 ECS를 바꾸지 않고 Init가 success일 때만 Publish한다. 이 정상 오류 경계와 게시 중 예외에 대한 트랜잭션 보장은 구분한다.

현재 파일은 11종(ConstructionSite 제외), 자재 12행이며 각 건물 내 품목 중복은 없다. Storage=10, MainFacility=50 슬롯, Belt=10, Miner=0.1, Crafter/ResearchBuilding=1 speed다. Splitter/Merger/CoalGenerator/DroneStation은 잠겨 있고 연구 키는 모두 FixedString32Bytes 용량 안이다. 나머지 건물 종류의 enum·Config 존재가 해당 도메인 시뮬레이션 구현을 뜻하지 않는다.

speed=0은 파서에서 유효하지만 Belt/Miner/Crafter 생성 시 `speed > 0 ? speed : 2/1/1`로 대체된다(`BuildingLifecycleUtility.cs:125,129,139`). 0을 기본값 선택으로 쓰는지 정지 속도로 쓰는지 공개 의미가 필요하다. 현재 제공 파일에서 이 세 타입은 양수이므로 관찰된 장애로 기록하지 않는다.

### 2.3 게시 범위와 수명

PublishConfig는 검증된 목록을 받는 함수이며 null/빈 configs만 거부한다. **한 엔티티**에 BuildingConfig·BuildingRuntimeConfig 태그와 BuildingConfigElement·BuildingRuntimeConfigElement·BuildingConstructionMaterialElement 세 버퍼를 먼저 생성하고 채운다(`:194–234`). runtime 버퍼는 동일 루프에서 BuildingType/Speed/StorageCapacity를 통합 설정으로부터 복사한다. 자재는 BuildingType 키로 연결된 목록이다.

정상 호출은 메인 스레드에서 끝까지 실행되므로 후속 도메인이 완성된 세 버퍼를 읽는다. GetBuffer 이후 새 엔티티 생성 같은 구조 변경을 하지 않아 게시 루프에서 잡은 DynamicBuffer를 구조 변경 너머로 유지하는 문제는 확인되지 않았다. Persistent Blob/수동 Dispose는 없고 엔티티·버퍼 수명은 World/EntityManager가 관리한다. 이는 [Q04 F-008](Q04.md#f-008--공개-초기화의-교체-경로에-blob-소유권회수reader-종료-계약이-없음)의 Blob 소유 문제와 다르다.

공개 Publish는 항상 새 엔티티를 생성하며 재호출·기존 singleton·목록 간 교차 유효성을 재검증하지 않는다. 따라서 검증된 데이터, 단일 게시 주체, 빈 World에 대한 최초 게시가 전제다. 실제 runtime 호출은 Init 하나이고 테스트도 새 World에 한 번 게시한다. 정상 경로에서 중복 singleton이 생겼다고 주장하지 않는다. 직접 API를 다시 호출하면 singleton 소비와 충돌할 수 있으므로 일회성 전제를 명시할 개선 후보로 남긴다. 게시 도중 엔진 예외/메모리 할당 실패 rollback은 구현·검증하지 않았으며 정상 검증의 부분 반환 방지와 구분한다.

| 건물 런타임 상태 | BuildingLifecycleUtility가 Config 스펙을 컴포넌트로 초기화 | 해당 생산·물류 시스템 | 이후 작업 진행은 Config가 아니라 건물 상태 책임. 해당 전체 도메인 평가는 후속 단계 |

**필요한 동기화:** 초기 설정은 Init.OnCreate 완료 후 조회 가능하다. Placement는 두 DynamicBuffer를 `Allocator.Temp` NativeArray로 복사해 해당 OnUpdate에서 사용한다. 스폰·완료·철거는 read-only BufferLookup을 갱신해 Job으로 전달하고 state.Dependency 및 ECB producer 최종 핸들을 연결한다. 일반 ECS 버퍼이며, 매 프레임 수동 NativeContainer 맵처럼 별도 공간 Fence가 필요한 근거는 없다. Config 초기화에 EndCommand/EndStateApply를 추가할 필요도 확인되지 않았다.

현재 live 설정 Writer가 없으므로 reader끼리 구체 실행 순서를 강제할 필요는 없다. 향후 해금/스펙 변경을 추가하면 ECS 쓰기 의존성과 언제부터 새 값이 적용되는지 공개 계약이 필요하다. 특히 현장 요구량 snapshot과 철거 당시 환급값은 핫 리로드 시 함께 검토할 부분이며, 미구현 핫 리로드를 현재 결함으로 요구하지 않는다.

공개 계약을 유지하는 내부 변경 사례(**실제 수정 실험은 하지 않음**):

1. Loader의 JSON 역직렬화·목록 검증을 내부 helper로 분리하되 입력 허용 범위, false/null 정책, 게시 entity/buffer·시점을 유지하면 Init 외 소비자 변경은 필요 없다. Placement/Construction의 Job 이름이나 세부 순서를 알아야 할 이유도 없다.
2. Material Job의 품목 검색을 내부 index로 바꾸되 동일 요구 버퍼·수령/완료 의미를 유지하려면, 현재 유일성 미보장 상태에서 ‘첫 행만’인지 ‘모든 중복 행을 채움’인지 먼저 알아야 한다. 후자를 단순 최적화로 바꾸면 관찰 가능한 동작이 달라진다. 품목 유일성/합산을 공개 계약으로 확정하면 Loader와 Material이 동일 불변식을 따르고 내부 검색 구현을 독립적으로 바꾸기 쉬워진다(F-010).
3. Publish 안에서 config/runtime/material의 채움 순서를 재구성하되 동일 동기 호출 반환 시 완전한 동일 entity를 제공하면 소비자는 영향을 받지 않는다. 반대로 OnCreate 게시를 OnUpdate로 옮기거나 ‘실패 시 부재’ 의미를 바꾸는 것은 준비 시점/실패 공개 계약 변경이다. 기존 Test06과 부분 World 구성을 검토하는 것은 정상적인 계약 변경 영향이다.

V1과 동일 범위 비교를 하지 않았으므로 V1 대비 결합 감소는 판정하지 않는다. 시스템·파일 수를 줄이거나 필요한 Job 의존을 제거하는 것을 개선으로 간주하지 않는다.

## 5. 발견 문제

기존 F-001~F-009의 제목과 직접 관련 결과를 확인했다. F-010~F-012는 기존 문제와 원인·수정 경계가 달라 신규 등록한다. [Q00 F-001](Q00.md)의 공사 구현 설명 불일치는 최초 문서를 참조하고 재등록하지 않는다. 아래 소비 경로는 실제 존재하는 Completion/Material Job을 기준으로 분석했다.

#### F-010 — 같은 건물의 중복 자재 품목을 허용하지만 두 번째 요구 행을 충족할 수 없음

- 발견 단계 / 유형 / 평가 축: Q05 / 안정성 결함·V2 설계 불일치 / 안정성·유지보수성·V2 적합성.
- 우선순위: **P2**. 파서가 성공 처리한 설정에서 공사 완료가 막힐 수 있음. 현재 제공 Config에는 중복 없음.
- 근거 수준: **코드 확인**; 실행 재현 미확인.
- 위치: `BuildingConfigLoader.cs:161–180`; `BuildingConfigComponents.cs:150–167,192–209`; `ConstructionLifecycleApplySystem.cs:298–322,408–416`; 요구 컴포넌트 `ConstructionComponents.cs:169–171`.

- 발생 조건·영향: 해당 설정이 게시되고 그 건물 현장을 만든 경우. 다른 완료 조건이 충족되어도 두 번째 자재 행을 현재 수령 경로로 채울 수 없어 완공 대기 지속. 타 시스템에서 직접 버퍼를 수정하는 우회는 검토한 정상 경로가 아님.

- 수정 후보: Loader에서 building+item 중복을 거부하거나 합산하고 그 결과의 유일성 계약을 명시. 별개 행이 의도라면 수령 계약을 다중 행에 맞추는 설계 결정 필요.
- 추가 검증: 중복 2행 파싱/게시·Populate 결과, 공급 반복 후 완료 여부, 서로 다른 건물의 같은 자재는 허용, 합산 선택 시 overflow 검사. 계획 후보에 이 사례 없음.
- 처리 / 수정·재검증 근거: **미결정**, 코드·테스트 수정 및 문제 재현 실행 없음. Q24/Q25에서 동일 문제 발견 시 이 문서 참조.

#### F-011 — 설정 검증 실패가 의도적 무설정 World와 구분되지 않아 해금·비용 제한이 빠짐

- 근거 수준: **코드 확인**; 실제 장면의 실패→배치→완공 실행은 미확인.

- 추가 검증: 잘못된 후반 항목/리소스 누락→Init 실패→배치·완료의 정책별 결과, 의도적 무설정 테스트 모드와 실패 상태 구별. 기존 선택 Test05는 TryParse만 호출하므로 이 질문에 답하지 않음.

#### F-012 — 긴 requiredResearch가 TryParseJson의 실패 반환 경계를 벗어남

- 우선순위: **P2**. 특정 입력에서 정상 false/null 오류 반환 대신 예외 또는 손실된 키가 생길 수 있음.
- 근거 수준: **프로젝트 및 직접 의존 패키지 코드 확인**. 해당 입력의 Editor/Player 실행은 미확인.
- 위치: `BuildingConfigLoader.cs:75–84,146–150`; `FixedString.gen.cs:1550,1890–1907,2505–2510` (위 §1의 정확한 PackageCache 경로).
- 기대 계약과 출처: TryParseJson의 검증된 목록 반환/검증 실패 false 경계, BuildingConfigElement.RequiredResearch의 FixedString32Bytes 표현.
- 확인한 동작: requiredResearch를 길이 검사 없이 FixedString32Bytes로 바꾼다. 패키지의 UTF-8 용량은 29바이트, Initialize는 CopyFromTruncated를 호출하고 생성자의 CheckCopyError는 `ENABLE_UNITY_COLLECTIONS_CHECKS` 또는 `UNITY_DOTS_DEBUG` 조건에서 ArgumentException을 던진다. 이 변환은 FromJson의 try/catch 바깥이다. 검사 호출이 없는 빌드에서는 잘린 키가 남는 코드 경로다.

## 6. 검증 공백·공개 계약 판단
