- 평가일 / 평가 상태: **2026-09-29 (Asia/Seoul) / 평가 완료**. 코드 분석과 선택 EditMode 1개 범위이며, 실제 SubScene 베이킹·화면 검증이나 문제 수정 완료를 뜻하지 않는다.

- 안정성 판단 / 근거: 정상 정적/런타임 책임 분리는 확인. **등록 유일성과 prefab 적합성의 사전 검증은 부족**하다(F-018/F-019). 실제 현재 자산에 해당 오류가 있다는 판정은 아니다.

- 시스템 간 의존 관계 / 의존성 판정 / 변경 영향 사례: §3–4. 필요한 준비·Job·ECB 계약과 등록 순서/초기화 구현 결합을 구분했다.

### 등록·누락·무효 입력 — 코드 확인

- **ItemAuthoring**: DisallowMultipleComponent는 동일 GameObject의 중복 컴포넌트를 제한한다. Type의 None/정의 범위 검증은 없다. DB 유일성이나 월드 전체 singleton 보장은 이 특성의 역할이 아니다.
- **InspectorList Baker**: 목록 순서대로 등록하고, Null prefab과 None만 조용히 건너뛴다. 중복 타입, root ItemAuthoring 존재, DB Type과 authoring Type 일치, 전체 품목 등록 여부를 검사하지 않는다. 목록이 비거나 전부 제외돼도 DB 태그와 빈 버퍼는 먼저 만들어진다.
- **ResourcesAutoLoad Baker**: Prefabs 목록을 사용하지 않고 Resources를 다시 탐색한다. 따라서 AutoLoad 상태에서 Populate 버튼으로 보이는 목록을 수정해도 해당 목록이 bake 입력이 되는 것은 아니다. 두 경로의 이름 파싱 로직은 현재 같지만 별도로 구현되어 있다.
- **숫자/이름 검증**: Enum.TryParse 뒤 None만 제외하며 Enum.IsDefined 검사는 없다. Inspector 직렬화 값도 None 이외의 정의되지 않은 값이 별도 거부되지 않는다. 숫자 이름 등 잘못된 데이터의 실제 등록·베이킹은 이번에 재현하지 않았다.
- **중복 항목**: 모든 유효 행을 Add한다. ItemLifecycle의 두 수동 루프와 PrefabLookupUtility 모두 첫 번째 일치를 반환한다. 뒤의 정상 참조를 검색하여 대체하지 않는다. 현재 Baker는 Null 참조를 생략하므로 “Null이 먼저라 정상 행을 가림”은 외부에서 malformed 버퍼를 만든 경우에 한정한다.
- **DB 수**: 소비자는 DB 태그와 ItemPrefabElement를 함께 가진 엔티티가 있으면 GetSingletonEntity를 호출한다. 서로 다른 GameObject/SubScene에 여러 DB를 두는 구성을 사전에 검사하는 코드는 대상 범위에서 없다.
- **DB 부재와 빈 DB는 다름**: 소비자 쿼리에 DB가 없으면 fallback archetype을 사용한다. 빈 DB가 있으면 품목 누락으로 Strict Fail이다. 이 fallback은 실행 코드상 테스트 환경 플래그로 제한된 것이 아니라 DB 존재 여부로 선택된다. SubScene 로드 전후의 실제 요청 타이밍은 Q11 이후 미확인 사항이다.
- **품목 누락**: ItemLifecycle은 오류 로그 후 Spawn 요청을 소비/거부하고, ProductResult는 실패 행까지 Clear한다. 후자는 [F-006(Q03)](Q03.md#f-006--생산물-실체화-실패에도-productresult를-지워-재처리-근거가-사라짐)의 기존 정책 질문이다. 환급도 누락 품목은 오류 후 건너뛴다. 환급 손실 정책의 종합 평가는 Q28에 남긴다.
- **non-Null 참조만으로 적합성을 보장하지 않음**: DB Baker는 일반 GameObject도 GetEntity하여 등록할 수 있다. ItemIdentity를 붙이는 것은 별도 ItemAuthoringBaker이고, 런타임은 ItemIdentity/LocalTransform이 있다는 전제로 Set한다. 준비가 잘못된 prefab을 “미등록” 분기로 거부하는 구조가 아니다. 실제 예외·부분 재생 결과는 미재현이다.
- **Inspector**: 버튼 경로는 Undo.RecordObject → Populate → SetDirty로 구성되어 있다. 검증 메시지나 중복 표시, AutoLoad 시 목록의 역할 안내는 없다. ContextMenu는 Populate를 직접 호출하며 메서드 내부에 Undo/dirty 처리는 없다. 메뉴 호출 시 Unity가 추가로 제공하는 동작·저장 지속성·실제 Undo 결과는 미확인이고 결함으로 확정하지 않는다.

| ItemAuthoringBaker → prefab 식별·transform | 정적 상태 쓰기 | 런타임 Set에 필요한 ItemIdentity, 이동용 transform 준비 | **필요한 계약**. 두 Baker 중 어느 것이 먼저 실행되는지 게임 코드가 제어하지 않음. 다른 Baker가 식별 정보를 만든다는 전제의 검증 부족은 F-019 |
| DB Baker → Item DB → 생성/환급 | 데이터 게시/조회 | 단일 DB, 품목별 적합 prefab 매핑이 필요 | **필요한 계약 + 개선할 등록 검증**. 중복이면 목록/탐색 순서가 선택 의미를 갖게 됨(F-018) |
| Resources 수집 → enum·파일명·ItemAuthoring | 이름 규칙 / 서로 독립인 타입 출처 | 이름만으로 DB key를 정하고 별도 Type과 대조하지 않음 | **개선할 결합**. 이름 변경이 prefab 타입 변경 없이도 누락/오매핑으로 전파(F-019). 이름 규칙 자체 변경은 공개 입력 계약 변경이므로 순수 내부 변경과 구별 |
| ItemLifecycle ↔ BuildingLifecycle 환급 | Item archetype·초기 상태 규칙 중복 | 환급 도메인이 Item의 이동/입고/요청 세부 컴포넌트까지 알아야 함 | **개선할 결합**, F-020. 현재 서로 Update를 호출하거나 세부 Job 순서에 의존하는 관계는 없음 |
| 조회 Job → ECS lookup·state.Dependency | read-only buffer 접근 | buffer handle 갱신 및 Job 접근의 일관성이 필요 | **필요한 동기화**. ECS buffer이므로 별도 공간 NativeContainer/Fence를 요구하지 않음. 새 런타임 Writer를 추가한다면 읽기 의존·참조 수명 계약을 함께 검토해야 함 |
| 생성 Job → EndStateApply ECB | 기록 완료·재생 | 생성·초기화·참조 추가를 공개 Phase 종료 경계에서 확정 | **필요한 동기화**. Baker/Inspector가 Product→Spawn→Destroy의 내부 Job 배열을 알아야 할 이유는 없음 |
| 계약 테스트 → 수동 ECS prefab | 검증 독립성 | 모의 상태로 런타임 생성 계약을 국소 검사할 수 있음 | **유용한 분리이나 Baker 보증은 아님**, F-021. 실제 Baker 결함을 찾아내는 별도 검증이 필요 |

아래는 실제 코드 수정 실험이 아닌 **[추정: 현재 호출·데이터 흐름 기반 변경 영향 분석]**이다.

1. 유효하고 유일한 Type→Prefab 결과와 정적 prefab 구성을 유지하면서 Baker의 임시 수집 자료구조를 바꾸면 ItemLifecycle/환급/물류는 수정할 필요가 없다. 그러나 현재 중복 입력에서는 같은 행 집합이라도 순서가 달라지면 첫 선택이 바뀐다. 이를 해결하려면 유일성 또는 중복 선택 정책을 먼저 공개 계약으로 정해야 한다(F-018).
2. Populate의 내부 수집 helper를 추출하고 목록 교체·타입 매핑을 유지하면 Inspector의 Undo 호출은 그대로 유지할 수 있다. AutoLoad 쪽도 같은 결과가 필요하므로 두 복제 파서의 동작을 함께 확인해야 한다. 이 국소 중복은 다른 게임 시스템 내부를 알아야 하는 결합과 구분한다.
3. Spawn 요청·결과뿐 아니라 **생성되는 ECS 컴포넌트·값·enable 상태·가시 시점까지 유지**하면서 ItemLifecycle 초기화를 내부 helper로 추출하면 BuildingLifecycle을 반드시 수정해야 하는 것은 아니다. 현재 코드에서 완전한 공개 계약 유지 리팩터링이 환급의 동작을 깨뜨린다는 근거는 찾지 못했다. 다만 Item 생성 규칙의 구현은 환급에 계속 남아 두 경로의 일치 여부를 별도로 검토해야 한다(F-020). 이동 컴포넌트 표현이나 기본값을 바꾸는 사례는 Spawn 요청 서명이 같아도 **ECS 상태 계약 변경**이며, 이를 순수 내부 변경의 반례로 과장하지 않는다. 건물 도메인이 Item의 상세 상태 계약까지 알아야 하는 책임 분리가 적절한지는 별도 설계 판단이다.
4. ItemLifecycle 내부 Job을 재분할하더라도 최종 producer handle과 EndStateApply 가시성을 유지하면 DB Baker/Inspector 수정은 필요 없다. 반대로 ItemIdentity를 Baker에서 제거하거나 runtime state를 bake하기 시작하는 것은 정적/런타임 공개 계약 자체의 변경이며, 이런 변경의 파급을 불필요한 결합으로 세지 않는다.
5. 같은 prefab의 렌더 데이터만 바꾸고 정적 식별·transform 계약을 유지하면 본 검토의 런타임 초기화 코드는 수정할 필요가 없다. 다중 entity 렌더 계층·실제 화면 반영은 이번에 검증하지 않았으므로 시각 결과까지 보장하지 않는다.

현재 확인한 범위에는 도메인 간 Update·활성화·정리 직접 제어, Baker와 런타임의 순환 호출은 없다. 주요 부담은 **세부 실행 순서보다 등록 검증의 부재와 Item 초기 상태 구성의 교차 도메인 복제**다. V1과 동일 범위 비교를 하지 않았으므로 V1 대비 개선량은 판정하지 않는다.

## 5. 발견 문제

기존 결과의 F-001–F-017 제목과 Q03의 관련 본문을 대조했다. 아래는 신규 문제이며, F-005의 생성/철거 수명 충돌이나 F-006의 실패 결과 소비를 다시 등록한 것이 아니다.

#### F-018 — Item DB가 유일성을 검사하지 않아 등록 순서와 singleton 전제에 의존함

- 발견 단계 / 유형 / 평가 축: Q08 / **유지보수 위험·설계 판단 필요** / 안정성·유지보수성·V2 적합성.
- 우선순위와 이유: **P2**. 중복 타입은 조용히 앞 행만 사용하고, 복수 DB는 소비자의 단일 DB 전제를 깨뜨릴 수 있다. 정상 유일 등록에는 문제가 없다.
- 근거 수준: **코드 확인**. 현재 asset에 중복이 있는지와 실제 복수 DB 오류는 **미확인**.
- 위치: ItemPrefabDatabaseAuthoring `:18,54–67,74–104`; PrefabDatabaseComponents `:124–139`; ItemLifecycle `:82–83,158–164,298–304`; BuildingLifecycle `:133–134,349–365`.
- 기대 계약과 출처: Item DB는 품목에 해당하는 prefab을 조회하는 데이터 계약이다. 현재 소비자가 단일 DB·첫 일치를 요구하지만 생산 경계에서 유일성을 검증하거나 중복 정책을 명시하지 않는다.
- 확인한 코드 동작 또는 실행 결과: List/AutoLoad 모두 중복 key를 Add하고 조회는 첫 행에서 멈춘다. DisallowMultipleComponent는 여러 GameObject의 DB까지 막지 않는다. GetSingletonEntity 이전에 복수 개수 검사/정의된 거부 경로가 없다.
- 발생 조건과 영향: 동일 타입을 여러 prefab에 등록하거나 여러 DB가 동시에 존재하는 구성. 행/탐색 순서에 따른 선택 변경, 뒤 등록의 무시, 단일 DB 조회 전제 위반 가능. Resources.LoadAll 순서가 실제로 비결정적이라고 측정한 것은 아니다.
- 근거 / 미확인 사항 / 반대 근거: 유일 DB/유일 품목이면 현재 선형 조회는 충분하다. 기존 테스트는 그 정상 입력만 만든다. 복수 DB의 실제 예외·빈도는 재현하지 않았다.
- 수정 방향 후보: 중복을 bake/검증 시 오류로 거부할지, 명시적 우선순위를 지원할지 먼저 결정. 월드에 허용할 DB 수/병합 방식도 계약으로 고정. 정렬만 추가하여 우연한 우선순위를 정책으로 만들지 않는다.
- 필요한 추가 검증: List와 AutoLoad 중복 타입, 첫/뒤 행 순서 변경, 두 DB 동시 구성에 대한 진단·게시 결과 검사. 기존 테스트 보강 제안만 남김.
- 처리: **미결정**. 별도 수정 작업과 재검증 없음.

#### F-019 — 등록 경계가 prefab 식별 정보와 생성 전제의 적합성을 검증하지 않음

- 발견 단계 / 유형 / 평가 축: Q08 / **안정성 결함·유지보수 위험** / 안정성·유지보수성.
- 우선순위와 이유: **P2**. Inspector에서 허용되는 잘못된 참조가 사전 거부되지 않고 생성 시점으로 넘어갈 수 있다.
- 근거 수준: **코드 확인**. 잘못된 prefab의 실제 베이킹·ECB 실패·시각 불일치는 **미확인**, 아래 실행 영향은 **추정**.
- 위치: ItemAuthoring `:15–18`; ItemPrefabDatabaseAuthoring `:56–65,85–89,98–102`; ItemLifecycle `:181–185,319–323`; BuildingLifecycle `:387–393`.
- 기대 계약과 출처: Authoring/Prefab 규약의 정적 ItemIdentity·Dynamic transform과 Spawn Owner 초기화 경계. 런타임은 이미 존재하는 식별/transform에 Set하며, null 여부만으로 이를 충족했다고 볼 수 없다.
- 확인한 코드 동작: DB는 ItemAuthoring 존재/Type 일치를 확인하지 않는다. 자동 경로의 key는 파일명에서, 수동 경로는 entry.Type에서 온다. 원본 Type은 별도 Baker에서 작성되지만 인스턴스에서는 요청 타입으로 덮어쓴다. None 제외 외 enum 유효성 검사도 없다.
- 발생 조건과 영향: root에 ItemAuthoring이 없는 prefab, 이름/entry.Type과 ItemAuthoring.Type이 다른 prefab, 정의되지 않은 타입 등록. 전자는 ItemIdentity Set의 전제를 충족하지 못하고, 후자는 원본 시각 표현과 런타임 논리 타입의 불일치를 감출 수 있다. 누락 오류 로그 분기는 non-Null prefab의 적합성을 검사하지 않는다.
- 근거 / 미확인 사항 / 반대 근거: DB GetEntity의 Dynamic 요청은 transform 준비에 도움을 준다. 정상 ItemAuthoring prefab에서는 정적 식별이 준비된다. 실제 asset 상태는 Q11에서 확인할 일이며, 현재 모든 prefab이 잘못됐다는 주장은 아니다. 하나의 시각 prefab을 여러 타입에 재사용하는 것이 의도인지도 미정이다.
- 수정 방향 후보: root ItemAuthoring/유효 enum/필수 bake 결과를 검사하고, key와 Type의 단일 권위 또는 의도적 alias 정책을 정한다. Inspector 미리보기와 Baker의 진단이 같은 검증 규칙을 사용하도록 제안한다.
- 필요한 추가 검증: 실제 Baker로 ItemAuthoring 없음·Type 불일치·None/범위 밖 값·정상 prefab을 각각 준비하여 게시/거부·진단 확인. 렌더 계층과 transform 특수 구성은 별도 실제 자산 검증.
- 처리: **미결정**. 코드·에셋 수정 및 실패 재현 없음.

#### F-020 — 철거 환급이 Item 생성 내부 초기화 규칙을 별도로 복제함

- 발견 단계 / 유형 / 평가 축: Q08 / **유지보수 위험·V2 설계 불일치** / 유지보수성·V2 적합성.
- 우선순위와 이유: **P2**. Item 내부 컴포넌트 구성을 변경할 때 건물 도메인의 초기화 구현까지 동기화해야 한다.
- 근거 수준: **코드 확인**. 현재 두 경로의 주요 구성·false 초기값은 일치하며, 이미 발생한 초기화 불일치 버그를 주장하지 않는다.
- 위치: ItemLifecycle `:34–43,181–195,210–219,319–333,354–363`; BuildingLifecycle `:55–66,387–416`; 조회 복제는 ItemLifecycle `:158–165,298–305`와 PrefabDatabaseComponents `:124–140`.
- 기대 계약과 출처: V2 계획 §2.1·§14의 타 도메인 내부 구현 의존 축소, Authoring/Prefab 규약의 Spawn Owner 초기화 책임. Q03 DEP-Q03-06은 Lifecycle 내부 분기 중복을 언급했지만, 이번에는 별도 건물 도메인까지 복제된 직접 소비 경로를 확인했다.
- 확인한 코드 동작: 환급은 SpawnItemRequest를 내지 않고 DB를 직접 조회해 Instantiate/Create하고, ItemOwnership·GridPosition·이동 결정/상태·입고 결정·Destroy/Transfer 요청 초기화까지 구현한다. ItemLifecycle의 prefab/fallback 생성과 같은 규칙을 별도로 갖는다.
- 발생 조건과 영향: Item 생성 상태 계약 추가·기본값·초기화 정책 변경 시 BuildingLifecycle archetype과 두 helper도 함께 검토해야 함. 이는 공개 ECS 계약 변경의 정상 파급도 포함하므로, 계약 유지 내부 리팩터링에 무조건 외부 수정이 필요하다는 주장은 아니다. 유지보수 위험은 Item 생성 규칙이 두 도메인에 복제되어 단일 생성 경로 테스트만으로 환급 경로의 회귀를 보장할 수 없다는 점이다.
- 근거 / 미확인 사항 / 반대 근거: 직접 생성은 같은 ECB에서 환급과 철거를 기록할 수 있는 장점이 있다. 단순히 Spawn 요청으로 바꾸면 같은 Phase 요청 가시성과 소비 시점이 달라질 수 있으므로 자동 개선으로 판단하지 않는다. 현재 타 시스템 Update 직접 호출이나 Job 순서 결합은 확인되지 않았다.
- 수정 방향 후보: 품목/위치/소유 목적지만 받는 명시적인 item 생성 계약 또는 공통 초기화 함수를 검토. 현재 ECB 경계·실패 정책·환급 시점을 유지할 수 있는지 먼저 판단. 큰 시스템 통합이나 무조건 요청 전환은 제안하지 않는다.
- 필요한 추가 검증: 향후 수정 시 동일 입력의 일반 Spawn/Product/환급에서 prefab 및 fallback 구성·enable 상태·태그·결과를 비교. Q28에서 환급 수명과 실패 정책을 함께 확인하되 본 문제는 이 문서를 링크.
- 처리: **미결정**. 별도 수정·재검증 없음.

#### F-021 — Authoring/Baker 계약 이름의 테스트가 실제 Baker 변경을 검출하지 못함

- 발견 단계 / 유형 / 평가 축: Q08 / **검증 공백** / 안정성 검증·유지보수성.
- 우선순위와 이유: **P2**. 정적/런타임 책임 경계가 핵심인데 해당 Baker를 지우거나 runtime state를 추가해도 현재 모의 계약 테스트는 그 변경을 실행하지 않는다.
- 근거 수준: **코드 확인**. 테스트를 실제로 변형한 실험은 하지 않았다.
