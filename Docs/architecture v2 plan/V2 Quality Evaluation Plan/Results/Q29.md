Construction 요구/Delivered/Reserved/Progress, 생산 진행/레시피, DB/Config·필수 생성 구성도 범위 밖이다. 미구현 검사 전체를 새 게임 기능 결함으로 등록하지는 않았다.

진단은 `ReportViolation` 호출마다 TotalViolationCount를 증가시킨 뒤 파일 저장을 시도하고 Debug.Break를 호출한다. 콘솔 오류나 NUnit Assert를 발생시키는 코드가 아니므로 **Validator를 실행했다는 사실만으로 테스트 실패가 보장되지 않는다**. 검사 누락·쿼리 제외·위반 없는 무동작도 위반 0이 될 수 있다. 현재 동기식 managed 순회·임시 배열·정렬·파일 쓰기는 코드 특성이며 비용을 측정하지 않아 성능 병목을 확정하지 않는다.

## 3. Factory와 실제 Spawn/Baker의 차이

Fixture는 매 테스트 `new World`를 만들고 끝에서 Dispose한다. 실제 초기화 그룹·Config/DB·SubScene을 자동 구성하지 않는다. Factory는 EntityManager로 즉시 컴포넌트와 버퍼를 넣으며 Baker, Spawn 요청, prefab Instantiate 및 ECB 실패 경로를 실행하지 않는다.

| Factory 경로 | 실제 경계와의 차이 | 유효한 테스트 용도와 보장 한계 |
| --- | --- | --- |
| CreateResourceNode | ResourceNode/GridPosition만 생성 | 자원 계산/공간 fixture. DB 준비·prefab/렌더·생성 완료 인계 보장 아님 |
| CreateBelt / CreateBuilding | Belt는 Grid/Direction/Belt만, Building은 타입/크기/Grid/Direction만. 실제 건물 공통 Stamp/LocalTransform과 타입별 구성 생략 | 벨트/공간 단위 검사에 유효. 일반 건물 생성·설치 우선순위·철거 전체 검증으로 확대 불가 |
| CreateBeltItem | movement 활성, Direction 포함, DestroyItemRequest 없음. 실제 Item Spawn은 movement 비활성·Destroy 요청 보유로 시작 | 이미 벨트에서 이동 중이라는 특정 초기 조건. 실제 생성→벨트 진입·파괴 경계 대체 불가 |
| CreateStoredItem | Owner와 Stored 버퍼 참조를 함께 넣고 네 enableable 상태 false. **DisableRendering은 넣지 않음** | 수납 계산 fixture에는 유효. 실제 Lifecycle은 stored 생성에 태그를 추가하므로 렌더/ECB 검증용 동일 상태는 아님 |
| CreateStorage / CreateMiner | 실제 생성의 공통 Stamp/transform 등 생략. Storage는 기본 8슬롯·필터 선택적, Utility의 fallback은 20슬롯·필터 부착 | 테스트 입력값 차이 자체는 결함 아님. 기본값/구성 동등성 증거로 사용 불가 |
| CreateCrafter | StateDecision/Storage/StorageFilter를 제공하고 recipe=1·1×1·4슬롯으로 시작. BuildingItemOutputDecision은 없음 | 실제 Utility는 recipe=0·출고 결정을 제공하지만 앞의 세 component는 누락. **F-037**의 생산 진입 공백을 Factory가 가림. Factory 생성만으로 실제 출고까지 되는 완성 Crafter라고 볼 수도 없음 |

ItemAuthoring.Bake는 Identity만 추가한다. Phase0 Test04는 자신이 직접 만든 `(Prefab, ItemIdentity)`를 검사하므로 이 실제 Bake 메서드를 바꾸어도 검사 입력이 달라지지 않는다(**F-021**, 기존 등록). 격리용 Factory 자체를 없애거나 모든 테스트를 전체 World로 바꿀 이유는 없다. 필요한 보강은 **실제 생성 결과에 같은 공개 구성 계약을 적용하는 독립 검사**다. Factory의 임의 기본값을 게임 규칙의 정답으로 복사하지 않는다.

**공개 계약을 유지한 내부 변경의 영향 사례 [코드 기반 분석, 변경 실험 없음]:**

1. SpatialSync가 Clear/Populate Job을 합치거나 분할해도 동일 Map·Fence 완료 계약이면 Validator/Factory는 바뀔 필요가 없다. Validator의 검사 주기만 늘리는 변경도 게임 정확성에 영향을 주지 않아야 하지만 F-026은 완료 부수효과를 제거할 때 위험이 드러날 수 있다.
2. 공사/물류 내부 Job을 재배치하되 최종 Owner·버퍼·enable 및 EndStateApply 경계를 유지하면 Validator의 최종 상태 검사는 그대로여야 한다. 중간 상태·추가 Playback을 전제한 개별 테스트는 수정될 수 있다. 이를 런타임 공개 계약 변경으로 혼동하지 않는다.
3. ReportViolation의 파일명·보관 방식을 바꾸되 위반 보고/count 계약을 유지해도 두 CleanLogDirectory와 파일 패턴 assertion은 함께 바뀌어야 한다. 진단 내부 파일 형식에 테스트가 결합한 구체적 사례다.
4. 실제 Spawn/Baker의 공개 결과를 유지한 내부 리팩터링은 Factory를 바꿀 이유가 없다. 공개 결과를 잘못 깨뜨려도 Factory만 사용한 테스트는 입력이 그대로라 회귀를 놓친다(F-021/F-037). 반대로 Reader 필수 component가 바뀌면 생성 계약 변경이므로 Spawn·Baker/fixture의 영향을 함께 점검하는 것이 정상이다.
5. Input/Output 잔류 검사를 하나 제거하는 변경은 공개 검증 계약을 깨뜨리는 의도적 반례다. 현재 Test07은 다른 위반까지 합산해 이를 놓칠 수 있다(F-047). 이는 내부 변경 영향 사례와 별개인 assertion 강도 분석이다.

## 6. 신규 문제

### F-044 — 소유 버퍼 검사가 중복 참조와 공사 현장의 역방향 불일치를 놓침

- 발견 단계 / 유형 / 평가 축: **Q29 / 검증 공백 / 안정성·유지보수성**.
- 우선순위와 이유: **P2**. 현재 구현된 공사/소유권 경계의 잘못된 실물 참조가 위반 0으로 남을 수 있어 전체 불변식 보장으로 사용할 수 없다.
- 근거 수준 / 위치: **코드 확인 및 조건부 반례 추론, 실행 미확인**. `WorldInvariantValidationSystem.cs:447–563,579–722,725–848`; `BuildingPlacementCommandSystem.cs:145–157`.
- 기대 계약과 출처: ItemOwnership의 소유자와 소유 버퍼의 실물 참조 일치, Validator의 양방향 무결성 책임. 기존 [F-003](Q02.md#f-003--공사-수령이-동일-아이템-재사용과-기존-소유-버퍼를-검증하지-않음)은 잘못된 참조를 만드는 생산자 문제이며 본 건은 검사 누락이다.
- 확인한 동작 / 발생 조건: (A) 같은 Owner의 정상 아이템 한 개를 같은 유효 슬롯에 두 번 기록하면 정방향은 첫 일치에서 종료하고 역방향은 동일 Owner인 두 행을 단순 수량 2로 센다. MaxStack 이하·정상 필터/enable이면 중복 자체를 보고하지 않는다. Stored/Product 양쪽에 같은 아이템이 있어도 유일성 검사는 없다. (B) 실제 현장은 Storage 없이 Stored 버퍼를 가진다. 그 버퍼에 죽은 entity 또는 다른 Owner의 정상 아이템 참조가 남아 있어도 현장 역방향 쿼리에서 빠지고 정방향은 살아 있는 아이템의 현재 Owner만 검사하므로 해당 잘못된 행을 놓칠 수 있다.
- 영향 / 반대 근거: 일반 Storage의 죽은 참조·다른 Owner는 잡는다. 살아 있는 stored item의 자기 Owner 버퍼 누락도 잡는다. 모든 소유 오류를 놓친다는 뜻은 아니며 Validator가 중복을 생성한다는 주장도 아니다.
- 수정 방향 후보: Stored 버퍼의 공통 실존·Identity/Owner·유일성 검사를 Storage 용량 검사와 분리하고, 한 entity의 소유 버퍼 참조 수를 검증한다. 현장에 Storage를 억지로 붙여 검사 쿼리에 맞추지 않는다.
- 필요한 추가 검증: 동일 Stored 중복, 동일 Product 중복, Stored/Product 교차 중복, Storage 없는 현장의 dead/wrong-owner 참조와 정상 현장 대조. 새 테스트는 작성하지 않았다.
- 처리 / 별도 수정·재검증: **미결정 / 없음**.

StorageInvariant Test02~06의 결함 주입은 각각 소유 버퍼 누락·죽은 참조·슬롯/품목 혼합·fallback 50 상한·필터 검사의 유효한 코드상 후보다. 이번에는 새 실행 질문이 없어 실행하지 않았다. 정상 Test01의 이전 실행은 Q14에 기록돼 있으며, 이번 신규 Passed 수에 더하지 않았다. Test07을 실행해 현재 합계가 임계값을 넘는 것만 확인해도 F-047의 검출 공백을 해소하지 못한다.

신규 문제는 정적 분기·파일 경로·assertion으로 근거를 확보했다. 반례 테스트를 새로 만들거나 코드를 변형하지 말라는 범위에 따라 제안으로 남긴다. 필요한 실행을 요청해 놓고 수행하지 못한 상태는 아니므로 **코드 분석 평가 완료**이며, 실제 무결성·베이킹·비동기 경합 안전성의 실행 검증 완료는 아니다.

## 8. 남은 질문과 별도 작업 제안

- **검사 범위:** 공사 버퍼를 포함한 소유 참조의 유일성·역방향 검사를 보강할지? F-044의 최소 반례와 정상 대조군부터 제안한다. 현장 용량/자재 예약에 새 규칙을 추가하는 것과 구분한다.
- **생성 계약:** 실제 fallback·최소 DB prefab·실제 Baker를 각각 거친 구성 검사와 Factory 국소 테스트를 분리해 보강할지? Crafter 입력 슬롯 수는 기존 F-037의 설계 질문으로 유지한다.
- **동기화:** Validator 없는 부분 그룹에서 미완료 Fence Writer를 둔 배치 사례가 필요하다(F-026). 실제 그룹 검증에 추가 ECB 재생이나 무조건 Complete를 끼워 결함을 가리지 않아야 한다.
- **진단 보존:** 보고 저장 형식·테스트별 sink/경로와 실패 시 로그 보존 정책을 정할지? F-045/F-046의 수정 후보이며 이번에는 공용 파일을 건드리지 않았다.
- **assertion:** 위반 총합 대신 목표 불변식 종류·대상과 정상 상태를 확인할 관찰 계약을 마련할지? F-047 및 Q14의 무동작도 위반 0일 수 있는 한계를 대상으로 한다.
- **후속 연결 확인:** Q30a가 별도 요청되면 누적된 경계 질문에 답하는 기존 통합 사례만 선택한다. Q29에서 전체 EditMode·Play Mode·통합 시나리오 확대 또는 자동 수정은 하지 않는다.

결과 문서와 계획의 Q29 상태·결과 링크·현재 진행 상황·다음 후보만 갱신했다. 대상 두 문서를 제외한 기존 평가 폴더 31개 파일의 SHA-256이 변경 전후 일치함을 확인했고, 관련 코드·테스트·버전 파일의 기준선 diff도 비어 있다. 기존 삭제와 미추적 상태를 보존하며 여기서 멈춘다.
