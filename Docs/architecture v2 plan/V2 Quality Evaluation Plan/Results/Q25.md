## 3. 완료 조건과 상태 인계

### 3.1 무엇을 완료 대상으로 보는가

Completion 쿼리는 `ConstructionSite + GridPosition + Direction + BuildingFootprint + ConstructionMaterialRequirementElement`를 요구한다. **StoredItemElement와 PlacementStamp는 필수 쿼리 구성에 포함되지 않는다.** Q23 정상 Placement는 둘 다 붙인다. 반면 Q24 Material fixture의 축약 site는 위치/방향/크기가 없어 이 쿼리에서 빠진다.

| 조건 | 현재 처리 |
| --- | --- |
| AwaitingItemClearance 또는 Cancelled | 즉시 return. 자재/현장을 제거하지 않음 |
| TargetBuildingType None 또는 ConstructionSite | 즉시 return. Count나 임의 enum 값 전체를 검사하는 것은 아님 |
| 요구 행 중 하나라도 `DeliveredQuantity < RequiredQuantity` | 즉시 return. 모든 품목이 충족되어야 함 |
| 요구 버퍼가 비어 있음 | 검사 루프를 통과하여 즉시 완료 경로 진입 |
| Progress | 읽어 완료 조건으로 쓰지 않음. `Progress>=1`이나 건설 시간 누적 조건 없음 |
| ReservedQuantity | 완료 조건에 쓰지 않음. Delivered가 충족되면 남은 예약값 자체는 완료를 막지 않음 |
| 해금/자원/점유 재검증 | 완료 시 재검사 없음. 앞선 Placement와 현장 상태 계약을 신뢰 |
| 실제 보관품과 Delivered의 대조 | 개수·품목·Owner·중복 Entity 일치를 다시 검증하지 않음. Material의 정합성 보장에 의존 |

빈 요구 목록은 실제 기존 테스트가 정상 완료로 다룬다. 다만 Config 실패로 요구가 비어 버리는 경로는 별개의 [F-011 / Q05](Q05.md#f-011--설정-검증-실패가-의도적-무설정-world와-구분되지-않아-해금비용-제한이-빠짐)다. 이를 하나의 무료 건설 정책으로 합쳐 설명하지 않는다.

청소 플래그의 guard는 현재 구현이다. 이를 해제하는 runtime Writer는 Q23에서 발견되지 않았다. 이번 Test03은 **테스트 코드가 flag를 직접 지운 뒤** 완료를 확인하며 드론 회수·자동 clearance 구현을 증명하지 않는다. 미구현 회수 기능 자체를 새 결함으로 세지는 않는다.

### 3.2 자재·현장·새 건물의 적용 순서

1. Cancel Job은 Cancelled를 직접 쓰고, Material Job은 Delivered/Progress/Stored를 직접 쓴다. 명시적 Job dependency 뒤 Completion이 같은 update에서 그 결과를 읽는다.
2. Completion은 Stored 버퍼가 있으면 모든 non-Null ItemEntity에 `ECB.DestroyEntity`를 기록한다. 필요한 수량만큼 골라 지우거나 다른 Owner의 아이템을 걸러내지 않는다. 정상 수령 계약에서는 보관 목록 전체가 해당 현장의 자재다.
3. Stamp가 있으면 복사하고 없으면 default를 사용한다. TargetType·위치·방향·**footprint.Size**·Stamp·DB/Config 조회 context를 Utility에 전달한다.
4. `SpawnBuilding`의 반환값을 받지 않고 곧바로 `ECB.DestroyEntity(site)`를 기록한다.
5. EndStateApply가 기록을 재생한다. 정상 경로는 **기존 현장 Entity를 삭제하고 새로운 건물 Entity를 생성**한다. 현장에서 ConstructionSite만 제거해 같은 Entity를 건물로 바꾸는 방식이 아니다.

마지막 자재가 같은 update에서 수령되면 Material의 Owner/DisableRendering/요청 삭제 명령 뒤에 Completion의 실물 삭제·스폰·현장 삭제가 같은 ECB에 기록된다. 선정한 Test04/05는 이 인계를 실제로 통과했다. 이 순서는 필요한 완료 계약이며, 실패 시 임의 명령을 되돌리는 데이터베이스식 트랜잭션이나 자동 rollback을 뜻하지 않는다.

## 4. 공통 Spawn의 결과와 실패 상태

### 4.1 입력과 출력 계약

- Config의 첫 타입 일치 행에서 Speed/StorageCapacity를 읽는다. 입력 footprint가 비양수일 때만 Config.Footprint를 쓰고, 여전히 비양수면 기본 규격을 사용한다. 정상 site의 양수 크기는 완료 시 Config 크기보다 우선한다.
- Config의 IsUnlocked/건설 자재는 Spawn에서 재검사하지 않는다. 현장 요구량은 배치 시 복사본이며, 완료 시 조회하는 runtime 설정과 시점이 다르다.
- DB가 없으면 caller가 만든 6개 공통 컴포넌트의 fallback archetype으로 생성한다. DB가 있으면 prefab 조회를 사용하며 타입 누락/Null에서 오류를 기록하고 `Entity.Null`을 반환한다. **DB가 있지만 항목이 없는 경우 fallback하지 않는다.**
- prefab 조회에서 받아온 `dbFootprint`는 사용하지 않는다([F-022 / Q09](Q09.md#f-022--inspectordb의-footprintsize가-실제-spawn-크기-선택에-사용되지-않음)).
- 성공 경로는 공통 컴포넌트와 타입별 초기화를 ECB에 기록하고 deferred Entity를 반환한다. non-Null은 **생성 명령을 기록했다는 결과**이며, 뒤의 ECB Playback·실제 prefab 구성 전체가 성공했다는 확인값은 아니다.

### 4.2 조건별 상태 표

| 입력/결과 | 스폰 기록 | 자재·현장 처리 | 근거 수준 |
| --- | --- | --- | --- |
| 정상 요구 충족 + DB 없음 | fallback 생성 | Stored 실물 모두 삭제, site 삭제 | **코드 + 선택 EditMode 확인** |
| 정상 요구 충족 + 유효 DB 항목 | Instantiate와 초기화 기록 | 동일한 실물/site 삭제 | **코드 확인**. 이번에는 실제 DB 완료 테스트 미실행 |
| 요구 미충족/clearance/Cancelled | Utility 호출 전 return | 보존 | 요구 미충족/clearance는 **선택 EditMode 확인**, Cancelled는 코드 확인 |
| DB 있음 + 목표 항목 누락/Null | 오류 + Entity.Null, 새 건물 생성 기록 없음 | 이미 기록한 자재 삭제와 이후 site 삭제는 그대로 | **F-024 코드 확인**. 직접 Spawn 거부만 별도 EditMode 확인 |
| 잘못된 prefab 구성으로 나중 Playback 실패 | non-Null 기록 후 실패할 가능성을 함수 반환만으로 배제할 수 없음 | 기존 명령의 자동 rollback/보상 경로 없음 | **미확인**. 잘못된 prefab을 새로 만들거나 실행하지 않음 |

**F-024 순차 추적:** 충족 현장 S, Stored 자재 I1/I2, 활성 DB에 목표 Miner 없음 → `Destroy(I1), Destroy(I2)` 기록 → Utility에서 `Missing prefab...Spawn rejected`와 `Entity.Null` → 반환값 무시 → `Destroy(S)` 기록. 정상 ECB 재생을 가정하면 건물 생성 없이 세 원본이 제거된다. 오류 로그를 남기는 것과 원본을 보존하는 것은 다르다. 최초 문제·우선순위 **P1**은 [Q09 F-024](Q09.md#f-024--완공-spawn이-prefab-누락으로-거부돼도-자재와-현장을-삭제함)를 유지한다.

직접 Spawn 요청은 공개 계약에 Strict Fail/Drop이 명시되어 있고 caller가 요청만 소비한다. 완료 caller는 이미 존재하는 site와 도착 자재를 함께 제거한다. 같은 Utility를 쓰더라도 **실패 시 잃는 원본과 책임이 다르므로**, 직접 요청 소비 정책을 현장·자재 폐기의 근거로 쓰지 않는다.

**공개 계약을 유지한 내부 변경 사례:**

1. Material이 품목 검색/진행도 계산 내부를 최적화하면서 직접 Delivered/Stored와 최종 handle을 유지하면 Completion을 수정할 필요가 없다. Stored 쓰기만 ECB로 늦추는 것은 같은 update의 소비 가능 시점을 바꾸므로 계약 유지 변경이 아니다.
2. Utility의 타입별 초기화 내부를 정리하되 같은 컴포넌트/enable/버퍼·Null 실패 결과·ECB 기록 의미를 유지하면 두 caller는 그대로여야 한다. Completion은 원래 공개된 실패 결과조차 처리하지 않아 “대상 prefab이 반드시 존재한다”는 내부 성공 조건에 기대고 있다(F-024). 오류 원인을 caller가 다시 조회해 추측하기보다 공통 함수 결과로 결정하는 경계가 필요하다.
3. Prefab lookup의 검색 알고리즘이 같은 첫 일치/Null 결과를 유지하거나 Config 파서가 같은 게시 내용을 유지하면 Completion의 조건 코드는 영향받지 않는다. DB 누락을 fallback으로 바꾸거나 자재 비용을 완료 때 재조회하는 것은 공개 정책 변경이다.
4. SpatialSync가 동일 snapshot·Writer handle·셀→Entity 의미를 보존하며 Job 구성을 바꾸면 Completion은 수정하지 않는다. Map 갱신을 완료 Job에서 직접 수행하는 대안은 원본/파생 상태 Owner를 중복시키므로 필요한 동기화 제거의 해결책으로 제시하지 않는다.
5. footprint.Size 의미나 필수 Crafter 구성을 변경하는 것은 타입별 공개 데이터 계약의 정합성을 맞추는 작업이다. caller마다 회전 횟수/누락 컴포넌트를 보충하도록 만드는 것은 다른 생성 경로의 내부 지식을 늘린다. 공통 Utility 계약과 consumer 쿼리를 함께 정렬해야 한다.

V1과 같은 범위의 비교 근거가 없으므로 “V1보다 의존성이 감소했다”는 결론은 내리지 않는다.
