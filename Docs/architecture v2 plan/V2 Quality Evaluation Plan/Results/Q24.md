## 3. 요청 수명과 실제 수령 분기

### 3.1 필요한 실행 순서

OnUpdate는 Cancel/Supply 요청 또는 완전한 site 쿼리 대상이 하나라도 있을 때 실행한다. 하나의 EndStateApply ECB를 만들고 `state.Dependency`에서 시작해 **Cancel.Schedule → Material.Schedule → Completion.Schedule**로 연결한다. 세 Job은 `ScheduleParallel`이 아닌 단일 워커 예약이며 마지막 handle을 `state.Dependency`와 `AddJobHandleForProducer`에 전달한다.

Cancel이 `ConstructionSite.Flags.Cancelled`를 **직접** 써야 이어지는 Material/Completion이 같은 프레임에 취소를 관찰한다. Material도 요구량과 보관 버퍼를 직접 써서 뒤 요청과 Completion이 최신 결과를 읽는다. 이 순서는 “Cancel Wins, 수령 후 완료 판정”이라는 현재 lifecycle 계약을 위한 동기화다. 외부 도메인의 Update 순서를 알아야 하는 결합과 구분한다.

Strict Rejection은 **이 요청이 거부 분기에서 추가 집계/소유권 변경을 하지 않는 것**이다. 이미 승인된 다른 요청의 변경까지 되돌리는 묶음 트랜잭션이 아니다. Job이 직접 쓴 수량·보관은 ECB 재생보다 먼저 관찰되며, ECB 실패 시 전체를 rollback하는 구현은 없다. 시스템 주석의 ‘단일 ECB 트랜잭션’을 이 이상의 원자성 보장으로 사용하지 않는다.

**같은 프레임 다중 공급:** 요구량 2에 서로 다른 아이템 3개면 앞서 처리된 2개가 즉시 Delivered/Stored를 변경하고 마지막은 거부된다. 이번 Test08에서 이 결과를 확인했다. 그러나 요청 쿼리 순회를 공개 FIFO/요청 시각 우선순위로 정의한 코드는 없다. 테스트의 item1/item2 승리를 모든 archetype/생성 이력에 대한 보장으로 일반화하지 않는다.

**동일 실물 재사용:** 요구량 3 이상인 미완료 현장에 같은 ItemEntity 요청 두 개를 보내면 두 번 Delivered/Stored를 증가시킬 수 있다. 같은 아이템을 두 현장에 공급하면 양쪽 버퍼에 참조를 추가하고 ECB의 마지막 Owner만 남는 경로도 있다. 다음 프레임 재요청·기존 창고 보관품도 현재 Owner 검사로 차단하지 않는다. 모두 [F-003 / Q02](Q02.md#f-003--공사-수령이-동일-아이템-재사용과-기존-소유-버퍼를-검증하지-않음)의 같은 누락이며 **코드 확인**, 신규 실행 재현은 아니다.

**중복 품목 요구 행:** 첫 Iron 행이 이미 만족되면 두 번째 Iron 행의 RemainingRequired가 남아도 첫 행에서 거부한다. [F-010 / Q05](Q05.md#f-010--같은-건물의-중복-자재-품목을-허용하지만-두-번째-요구-행을-충족할-수-없음)를 재확인했다. Loader/Placement가 중복 행을 어떻게 표현할지 함께 결정해야 하며 수령에서 임의 합산하지 않았다.

| Supply producer → 기존 소유 버퍼/아이템 선점 | 소비자에게 명시된 인계/중복 거부가 없어 외부 보증 필요 | 원래 Owner가 누구인지와 ECB 전 ownership이 아직 바뀌지 않는다는 내부 사정을 알아야 중복을 막음 | **개선할 결합 F-003** |
| Material ↔ 일반 소유권/아이템 수명 Writer | 같은 raw 상태를 서로 다른 경로로 변경 | 정상적으로 분리된 아이템이면 독립 가능. 동일 아이템에 Supply와 Transfer/Destroy가 겹칠 때 승자 계약은 확인 못함 | **판단 보류**. 다중 Writer라는 이유만으로 새 결함을 등록하지 않음 |
| ItemSpatialSync/Validation → Owner·소유 버퍼 | EndStateApply 이후 공개 상태 조회 | Stored는 공간에서 제외, Owner/버퍼 존재 검사 | **필요**. 보관 누락을 소비자에서 복구하도록 의존시키지 않음 |

**공개 계약을 유지한 내부 변경 사례:**

1. 정상 도착 producer가 경로 탐색·작업 큐 자료구조를 바꾸되 유일한 실제 아이템과 완전한 site를 같은 시점의 Supply 요청으로 넘기면 Material 수정은 필요 없다. 반대로 재시도 시 중복 요청이 허용되는지, 기존 창고/드론 소유 상태로 넘기는지는 공개 인계 계약에 포함되어야 한다. 지금은 이 조건을 producer가 수령 내부를 보고 추측해야 한다(F-003).
2. Cancel Job의 반환 위치 계산 내부를 바꾸면서 Cancelled의 직접 쓰기와 완료 handle을 유지하면 Material은 그대로다. Cancelled를 ECB로 늦추는 것은 **같은 프레임 Cancel Wins 가시성 변경**이므로 공개 계약을 유지한 내부 변경으로 취급하지 않는다.
3. Material의 합계 계산을 최적화하되 같은 즉시 Delivered/Reserved/Progress/Stored와 최종 ECB 결과를 유지하면 Cancel/Completion/ItemOwnershipApply 수정은 필요 없다. 단순히 Stored.Add만 ECB로 옮기면 뒤 Completion이 새 실물을 못 보므로 **현재 Job 인계 시점 계약을 바꾸는 변경**이다. 필요한 의존을 불필요한 결합으로 세지 않는다.
4. 일반 ItemOwnershipApply가 동일한 직접 Owner·렌더 태그 결과와 공개 시점을 보존하며 내부 분기를 정리하면 독립 Supply 경로를 바꿀 필요는 없다. 같은 아이템에 요청이 겹치는 경우는 별도 승자/인계 계약이 필요하며, 도메인별 내부 버퍼를 읽는 임시 보정으로 해결하지 않는다.
5. Placement가 같은 필수 site 구성·요구 의미를 유지하며 검증/ECB 기록 순서를 바꾸면 Material에 영향이 없어야 한다. Stored 버퍼를 생략하거나 늦게 추가하는 것은 **공개 현장 구성 변경**이다. F-042는 그 전제 위반을 검출하지 않고 부분 적용하는 현재 소비 경계의 문제다.

독립 수령 검증에는 Config 로더·배치·공간 인덱스·일반 OwnershipApply 전체가 필요하지 않다. 반면 현재 테스트가 완료 쿼리에서 빠지는 축약 site를 써야 완료 후 사라지지 않는다는 점은 국소 검증의 범위를 제한한다. 이는 실제 현장의 수령→완공 연결을 검증했다는 근거가 아니며 Q25에서 구분해야 한다. V1과 같은 범위의 비교를 하지 않아 결합 감소량은 주장하지 않는다.
