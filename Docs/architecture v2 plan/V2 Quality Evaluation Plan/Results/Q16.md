## 3. 포트·상태·승인·적용 계약

### 3.1 포트와 기준 벨트

포트는 건물 자신의 Direction을 직접 기준으로 계산하지 않는다. Splitter는 **선택된 입력 벨트 방향**, Merger는 **선택된 출력 벨트 방향**을 forward로 사용한다. 초기 건물 direction은 상태의 초기값이지만 기준 벨트가 Null이면 실제 연결 탐색으로 forward를 정한다. 1칸 인접 포트 규칙이며 footprint 전체 둘레를 탐색하는 Q15의 건물 출고와 다르다.

| Forward | Splitter 포트 0→1→2 | Merger 입력 위치 0→1→2 |
| --- | --- | --- |
| Up | Up→Right→Left | Down→Left→Right |
| Right | Right→Down→Up | Left→Up→Down |
| Down | Down→Left→Right | Up→Right→Left |
| Left | Left→Up→Down | Right→Down→Up |

입력은 `beltPosition+beltDirection==routerPosition`, 출력은 `routerPosition+beltDirection==beltPosition`이다. Merger 표의 방향은 **입력 벨트가 놓인 상대 위치**이며 벨트의 이동 방향은 라우터를 향해야 한다. DirectionEnum의 Up/Right/Down/Left 순서로 회전·반대 방향을 계산한다.

- **기준 연결 선택:** 캐시된 InputBelt/OutputBelt가 없거나 GridPosition이 없거나 Map/입출력 방향 검사를 통과하지 못하면 인접 네 셀을 다시 탐색한다. 유효한 캐시는 유지하며 매 프레임 최우선 Stamp로 다시 바꾸지 않는다.
- **선택 우선순위:** Stamp가 있는 연결이 없는 연결보다 우선하고 Tick→Order가 더 이른 연결을 선택한다. Stamp 동률 또는 모두 없음에서는 탐색 순서 **Up→Right→Down→Left**의 먼저 본 벨트를 유지한다. 이는 공통 목적지 중재의 SourceEntity.Index 동률 처리와 다른 역할/정책이다.
- **변경 후 탐색 시작:** 기준 Entity가 달라졌다면 해당 결정에서만 startCursor=0으로 탐색한다. 실제 전달에 성공해야 Apply가 새 기준 벨트·forward·다음 커서를 영속 상태에 쓴다. 기준 연결이 사라졌다는 이유만으로 상태를 즉시 Null/0으로 정규화하지 않는다.
- **Splitter:** 기준 입력의 끝에 있는 후보 한 개를 고른 뒤 OutputCursor에서 시작해 최대 3포트를 검사한다. 막힘/누락 포트를 건너뛰어 첫 사용 가능한 출구를 선택한다.
- **Merger:** 기준 출력의 공간을 먼저 확인하고 InputCursor부터 최대 3개의 입력을 검사한다. 비어 있거나 누락된 입력을 건너뛴다. 기준 출력이 막혔다고 다른 기준 출력을 임의로 선택하지 않는다.

### 3.2 Reader/Writer와 동일 프레임 가시성

| 상태 | Writer / Owner | Reader·소비 | 확인한 계약 |
| --- | --- | --- | --- |
| SplitterRoutingState / MergerRoutingState | 생성 시 초기화, 정상 프레임은 RoutingApply | 각 Decision은 read-only | 기준 벨트·forward·커서. 후보 산출/거절만으로 커서를 바꾸지 않음 |
| RoutingTransferDecision+enable | Decision 작성 → Reservation 탈락 disable → Apply 전체 필드 Null 및 disable | 예약/적용 | 별도 승인 토큰 없이 활성 상태 유지가 승인 표현. IRequest/ECB 사건이 아닌 프레임 결정 |
| GridPosition·Direction·BeltMovementState·LocalTransform | 일반 이동·각 전달 Apply·Lifecycle | Routing Decision은 소스/목적지 상태, Apply는 목적지 현재 위치/방향 | RoutingApply는 직렬 Job으로 원본을 직접 쓰며 ECB나 Map은 쓰지 않음 |
| ItemOwnership | 일반 Ownership/Lifecycle 경로 | 두 Routing Decision의 소스/목적지 조회 | 라우팅은 월드→월드이므로 Owner/렌더 태그/소유 버퍼/TransferOwnershipRequest를 변경하지 않음 |
| Belt/Item Map·Fence | SpatialSync 및 각 Reader 등록 | 두 Routing Decision·공통 Reservation | 마지막 Writer+state.Dependency 대기 및 양쪽 AddReader. Apply는 Map을 읽지 않으므로 Map Fence 추가가 필요하지 않음 |
| PlacementStamp | 배치/생성 시 부착 후 불변 | 기준 연결 탐색은 **벨트** Stamp, 공통 목적지 중재는 **라우터/건물** Stamp | 서로 다른 Entity의 우선순위를 같은 ‘설치 우선순위’로 뭉뚱그리지 않음 |

소스 선택은 ItemMap 후보 중 Owner Null, BeltMovementState 존재, progress≥0.999에서 최대 progress를 고른다. **movement enable은 검사하지 않는다.** 동률 progress이면 순회 중 마지막 후보를 택하므로 ItemMap 열거 순서를 별도의 공정성 계약으로 보장하지 않는다. 비활성 소스의 잔여 progress에 따른 선택은 [F-032](Q14.md#5-발견-문제)의 같은 계약 위반이며, 라우팅에서는 Apply가 movement를 다시 true로 만들어 이동 참여까지 재개시킨다. 새 ID를 부여하지 않았다.

### 3.3 실제 목적지 예약의 범위

| 경로 | 공통 BeltDestinationReservation 후보인가? | 적용 시점·대상 |
| --- | --- | --- |
| Splitter / Merger 전달 | **예** — RoutingTransferDecision.TargetBelt의 GridPosition을 목적지 키로 사용 | StateApply의 RoutingApply |
| Storage / Product 출고 | **예** — BuildingItemOutputDecision.TargetBeltPosition | StateApply의 BuildingItemStorageApply |
| 일반 벨트 경계 이동 | **아니오** — BeltMovementDecision을 읽거나 수정하지 않음 | Execution에서 원본 위치·진행도 변경. 기존 F-029 |
| 건물 입고 | **아니오** — 건물 슬롯을 다른 Reservation에서 배정 | Q14의 Storage Input Apply/Ownership 인계 |

공통 중재는 목적지의 기존 활성 월드 벨트 아이템 count<4와 입구 progress≥0.249를 확인하고, 외부 후보 중 Stamp/Index 기준 한 개만 유지한다. Routing Decision의 선검사는 모든 월드 아이템을 세고 progress≥0.25를 요구하여 다르다(F-034). **공통 중재가 후보를 거절하는 것은 가능하지만 선검사에서 사라진 후보를 복구하지는 못한다.** 또한 일반 벨트가 Execution에서 새로 도착하는 것은 중재에 포함되지 않는다. Q15의 Routing 대 Building 경합 통과를 모든 도착 경합의 보증으로 확대하지 않는다.

### 3.4 적용·커서·실패 소비

Apply의 필수 guard는 Item/TargetBelt가 Null이 아니고 양쪽 GridPosition과 대상 Direction이 존재하는지다. 통과하면 아이템을 대상의 현재 셀·방향·progress=0으로 옮기고 movement를 켜며 Transform을 입구에 맞춘다. 이어 기준 벨트·forward를 쓰고 **실제로 사용한 포트를 역산해 `(port+1)%3`**으로 커서를 전진시킨다. 단순히 이전 cursor+1을 하는 방식이 아니므로 우회 후에도 다음 포트가 맞는다.

Decision 단계 막힘이나 Reservation 탈락이면 Apply 쿼리에서 제외돼 원본 아이템·커서는 유지된다. Apply의 필수 guard 실패도 이동/커서 갱신 없이 결정의 세 Entity 필드를 Null로 정리하고 disable한다. 반면 결정 단계 거절은 enable만 끄므로 이전 필드 값이 남을 수 있다. 소비자는 enable을 따라야 한다.

Apply는 현재 Owner, source 위치/끝 진행도/enable, source 존재·입출력 방향, 목적지 BeltComponent, 최종 공간을 다시 검증하지 않는다. 정상 Decision/Reservation·컴포넌트 구성과 승인 후 수명을 전제로 한다. Q15 F-033의 버퍼 제거 실패와 동일 코드 문제로 재등록하지 않고 **라우팅의 승인 수명 계약 질문**으로 남긴다. 대상/아이템이 완전히 파괴된 경우와 다른 상태로 바뀌었지만 엔티티는 살아 있는 경우를 구분한다.

Decision은 Map 방향·캐시 forward를 사용하고 Apply는 현재 ECS 방향/위치로 포트를 다시 계산한다. 따라서 포트 결정 이후 topology가 바뀌어도 같은 승인이라고 가정하려면 별도 일관성 계약이 필요하다. 기본 Phase에서는 Command가 Decision보다 먼저, 건물 철거는 RoutingApply 이후이며 구조 변경/Sync가 별도 경계다. Map이 현재 원본과 항상 같다고 가정하거나 Fence 추가만으로 의미 차이를 해결할 수는 없다.

문서 차이: RoutingComponents.cs:54–55의 ‘예약은 별도 데이터’, ‘ExecutionGroup에서 이동’ 주석과 달리 현재는 같은 결정의 enable을 유지/해제하고 **StateApply**에서 이동한다. CodeMemory README의 routing runtime 미구현 문장도 현재 소스와 다르다. 코드·실행 근거를 우선했으며 이번에 기존 문서를 수정하지 않았다.

공개 계약 유지 시 내부 변경의 영향 사례(실제 수정 실험은 하지 않음):

1. **포트 유틸리티를 enum 산술에서 표 조회로 교체하되 같은 방향/인덱스를 반환:** Decision·Apply의 동작이나 예약 인터페이스를 바꿀 필요 없다. 네 방향 테스트는 이 공개 결과를 검증한다.
2. **목적지 중재의 HashMap/List를 다른 집계 방식으로 교체하되 같은 승자·enable 결과 유지:** Splitter/Merger의 탐색과 커서 갱신은 변경 불필요. 다른 시스템의 내부 자료구조를 알 필요가 없는 좋은 경계다.
3. **허용된 target/source/Item을 그대로 유지하며 후보 검색을 최적화:** Apply는 source/target Entity로 실제 포트를 알아내므로 반복문의 내부 순서를 알 필요 없다. 다만 ‘동일 결과’가 아니라 포트 우선순위를 바꾸는 것은 공개 정책 변경이다.
4. **비활성 바닥 아이템의 progress만 내부 정리에서 1→0으로 바뀜:** 공개적으로 이동에 참여하지 않는 상태는 같아도 현재 source 선택 여부와 target 차단 여부가 바뀔 수 있다(F-032/F-034). 타 도메인의 비활성 잔여값 정리에 기대는 불필요한 결합이다.
5. **승인 후 벨트 위치·방향 변경을 허용:** 이는 단순 내부 최적화가 아니라 승인 가시성/수명 계약 변경이다. 현재 Apply가 live 데이터로 포트를 역산하므로 경로 snapshot 또는 무효화 검토가 필요하다. 메모리 접근이 안전해도 의미상 승인이 유지된다는 뜻은 아니다.

Work-conserving은 현재 후보 탐색에서 막힘/빈 포트를 건너뛴다는 범위다. 이후 공통 중재에서 진 Splitter가 그 프레임의 다른 빈 포트를 재탐색하지는 않으며, Merger의 기준 출력 변경 정책과도 다르다. 이 한계를 공정성 요구 없이 곧바로 별도 결함으로 등록하지 않았다.

## 5. 발견 문제

#### F-034 — 라우팅 목적지 선검사와 공통 예약의 점유·간격 기준이 달라 후보가 일관되게 중재되지 않음

- 발견 단계 / 유형 / 평가 축: Q16 / **유지보수 위험·조건부 안정성 결함·설계 판단 필요** / 목적지 용량·경합 승인 계약.
- 우선순위와 이유: **P2**. 같은 목적지 상태에서 공통 예약/건물 출고가 허용하는 진입을 라우팅만 사전에 막을 수 있다. 불필요한 대기와 포트 선택 차이를 만들며 규칙 변경이 복제된 구현에 전파된다.
- 근거 수준: **코드 확인**. 아래 비교 사례의 Unity 실행 재현은 미수행.
- 위치: `SplitterDecisionSystem.cs:264–297`, `MergerDecisionSystem.cs:265–298`, `BeltDestinationReservationSystem.cs:314–351`; 비교 대상 `StorageItemOutputDecisionSystem.cs:194–216`, `ProductItemOutputDecisionSystem.cs:197–218`는 Q15 근거.
- 기대 계약과 출처: 공통 목적지 예약의 최대 4개·입구 spacing 검사, Q13/Q15의 활성 월드 벨트 아이템 정의, GameConstants의 ItemSpacing/AlignmentEpsilon. 바닥 아이템까지 막는 별도 routing 정책을 의도했다면 명시가 필요하며 이번에 임의 결정하지 않는다.
- 확인한 코드 동작: 라우팅은 Owner Null이면 movement 유무/enable과 무관하게 count를 올리고, movement가 존재하면 disable이어도 progress를 읽는다. 최소 간격은 0.25다. 공통 예약은 movement 존재+enable=true인 월드 아이템만 세고 0.249를 적용한다. 선검사 실패는 결정 disable로 끝나므로 공통 예약까지 전달되지 않는다.
- 발생 조건과 영향: 유효한 출력 벨트 셀에 **비활성 월드 아이템 하나(progress=0)**가 있으면 두 라우팅 Decision은 출구를 차단한다. 공통 예약/건물 출고는 이를 활성 벨트 점유로 세지 않아 공간을 허용할 수 있다. movement 없는 월드 아이템 네 개도 라우팅의 정원 검사만 막을 수 있다. 활성 아이템 하나의 progress=0.2495 사례는 상태 정의가 같아도 epsilon 차이로 라우팅만 거절한다.
- 근거 / 중복 구분: F-032는 입력/source의 비활성 아이템을 **이동 대상으로 선택**하는 문제다. 여기서는 destination에 대한 **공통 용량 판정과 후보 선필터 불일치**가 문제이며 별도 ID를 부여한다. 일반 벨트의 신규 도착 중재 누락 F-029와도 다른 경계다.
- 미확인 사항 / 반대 근거: 활성 아이템의 progress=0.1/0.9 같은 일반 사례에서는 판정이 일치한다. 정확히 0.25를 요구하는 보수 정책이나 바닥 점유 차단이 의도일 가능성은 사용자 판단이 필요하다. 최종 예약이 과다 승인을 만든다는 주장이 아니라 도달 가능한 후보가 서로 다르다는 확인이다. 실제 정체 빈도·성능 영향은 미측정.
- 수정 방향 후보: 목적지에 세는 아이템과 epsilon 계약을 먼저 명시하고 순수 공간 판정 helper 또는 공통 조회 계약으로 공유한다. Decision의 포트 탐색과 Reservation의 여러 신규 후보 중재는 서로 필요한 책임이므로 두 단계를 무조건 합치거나 검사를 제거하지 않는다.
- 필요한 추가 검증: enabled/disabled/movement 없음 × world/stored × progress 0/0.249/0.2495/0.25, 정원 3/4의 표로 선검사와 예약을 대조. 불허 대상은 양쪽 거절, 허용 대상은 예약 도달 여부까지 검사. F-032의 source 비활성 사례와는 별도 assertion을 둔다.
- 처리 / 별도 수정 작업과 재검증 근거: **미결정 / 코드·테스트 변경 없음**. 점유 정책 결정과 테스트 보강은 별도 작업이다.

기존 문제 적용: **F-029**는 Routing→목적지 예약에도 그대로 적용된다. **F-032**는 두 FindItemAtBeltEnd의 enable 누락으로 같은 비활성 잔여 progress 의존을 보인다. **F-028**은 두 Decision과 공통 예약의 Fence singleton RW 패턴에 남아 있다. 최초 발견 결과의 판정을 이번 통과로 해결됨으로 변경하지 않았다.

- 기록: [verification.json](../../../../Logs/QualityEvaluation/Q16/verification.json), [시작](../../../../Logs/QualityEvaluation/Q16/started.txt), [종료](../../../../Logs/QualityEvaluation/Q16/finished.txt), [기존 로그 해시](../../../../Logs/QualityEvaluation/Q16/initial-log-hashes.json). 기존 로그 1개는 동일했다.
- 재사용: Q15에서 실행한 `Phase6BeltDestinationReservationTests.Test03_BuildingOutput_Vs_RoutingTransfer_PlacementStampArbitration`은 외부 후보의 Stamp 중재 근거로 연결하고 재실행하지 않았다. Q13의 일반 이동과의 경합 누락은 여전히 코드 확인이다.

**검증 한계:** 독립 World/Factory에서 Sync→해당 Routing Decision→Reservation→RoutingApply→Sync를 직접 호출한다. 일반 Belt Decision/Execution·건물 입출고·실제 전체 정렬 그룹·ECB 기반 철거를 함께 실행하지 않는다. 연결 테스트는 EntityManager로 벨트를 직접 파괴한다. 따라서 실제 동시 이동/입출고/철거의 전체 프레임 보증은 아니다. 네 방향 단위 테스트는 수치 계약이며 장면 회전/렌더 검증이 아니다.

TargetOrItemDestroyed라는 이름만으로 아이템 파괴까지 실행 확인했다고 기록하지 않았다. source 벨트만 파괴되거나 item Owner/위치가 바뀐 경우, live 방향과 Map 방향 불일치, Stamp 동률/누락, 예약 패자의 cursor 동결, F-034/F-032 반례는 이번 assertion 밖이다. 테스트 추가 금지와 범위 제한에 따라 제안으로 남겼다. 전체 EditMode·Play Mode·성능 검증은 수행하지 않았다.

## 7. 남은 질문·완료 조건

1. **공통 목적지 점유 정책:** 정적 바닥 아이템·movement 없는 아이템을 라우팅과 건물 출고에서 같게 취급할 것인가? ItemSpacing의 epsilon도 같은 경계를 사용할지 결정해야 한다(F-034).
2. **활성화 정책:** 비활성 source를 라우팅이 자동 회수·재활성화하는 것이 의도인가? 의도한다면 잔여 progress 대신 명시적 전환 계약이 필요하다. 최초 문제는 F-032로 유지한다.
3. **기준 연결·공정성:** 유효한 기준 벨트의 고정, 동률/무 Stamp 시 방향 순서, 공통 중재의 Index fallback, 예약 패자의 대체 포트 재탐색 여부가 의도한 규칙인지? 명시되지 않은 새 우선순위를 도입하지 않았다.
4. **승인 수명:** Apply 전 source/target 이동·회전·재소유가 생길 때 무효화할지, 결정 시 경로를 보존할지? 현재 소스·대상·Owner 재검사와 커서 갱신의 최소 성공 조건을 함께 정의할 필요가 있다.
5. **테스트 제안:** F-034 판정 표, 비활성 source, 예약 패자 원본/커서 보존, source 또는 item 파괴, 기준 연결 변경 후 전달 실패 시 상태 유지, 실제 일반 벨트 이동+라우팅 경합(F-029). 이번에 작성·수정하지 않았다.

이번 코드 분석과 선택 실행은 완료됐고 필요한 실행에 차단은 없다. 신규 반례의 실행 재현·정책 결정·수정은 미완료로 구분했다. 계획상 다음 단계는 **Q17 — 초기 청크 Bootstrap→Load Command**이며 별도 요청 전에는 진행하지 않는다.
