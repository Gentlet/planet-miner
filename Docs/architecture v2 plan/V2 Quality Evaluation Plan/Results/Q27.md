## 2. 직접 Spawn과 실패 정책

1. 요청이 존재하면 시스템이 EndStateApply ECB를 만들고 Building DB·Config context와 lookup을 준비한다. 건물 DB는 `BuildingPrefabElement` 버퍼 존재로 찾고, Config는 `BuildingConfig + BuildingConfigElement`로 찾는다. 하나라는 전제에서 `GetSingletonEntity()`를 사용한다.
2. Spawn Job은 요청 값을 Utility에 전달한다. 같은 시스템에 철거 요청도 있으면 철거→벨트 정리→Spawn의 단일 워커 Job 체인을 따른다. 여기서는 철거 내부의 타당성을 평가하지 않았다.
3. Utility는 None/ConstructionSite를 거부한다. 크기는 양수 요청값 우선, 그렇지 않으면 해당 Config 행, 여전히 잘못됐으면 타입 기본값이다. Config 행이 있으면 속도/슬롯 수를 읽고 타입별 적용 단계에서 기본값을 보충한다.
4. DB가 없으면 공통 6개 컴포넌트의 fallback 엔티티를 기록한다. DB가 있으면 첫 타입 일치 prefab을 조회하며 누락/Null일 때 오류와 `Entity.Null`을 반환한다. 존재하는 DB의 누락을 fallback으로 덮지 않는다.
5. 공통 위치·방향·타입·footprint·Stamp·LocalTransform과 타입별 구성을 기록한다. 직접 Spawn Job은 반환값과 관계없이 **요청만 Destroy**한다. 이는 요청에 문서화된 Strict Fail/단발 소비 정책에 맞는다.
6. 마지막 Job handle은 `state.Dependency`와 ECB producer에 등록한다. 구조 변경은 EndStateApply Playback에서 확정되고 이후 Synchronization에서 맵이 갱신된다. 새 건물의 Decision 참여는 그 후의 Decision 단계다. Utility의 non-Null 반환은 생성 명령 기록이며, Playback 성공 확인이나 rollback 보증이 아니다.

| 입력 조건 | 확인한 결과 | 근거 수준 / 한계 |
| --- | --- | --- |
| DB 부재 + 정상 타입 | fallback 생성 | Belt/Miner/routing 사례 EditMode 확인 |
| DB 존재 + 정상 prefab | Instantiate 후 공통/타입별 주입 | 모의 Miner prefab 사례 EditMode 확인. 실제 Baker/렌더링 보장 아님 |
| DB 존재 + 타입 누락 또는 Null | 오류·Entity.Null, 요청 소비 | 누락은 Q25 Test08 근거 재사용. Null 행의 실제 Spawn 재현은 미수행 |
| Config/해당 타입 행 없음 | 속도 Belt 2 / 기타 1, 기본 용량 20, 타입 기본 크기 경로 | 코드 확인. 전체 누락 조합을 실행한 것은 아님 |
| Config 행 존재 | 속도·용량 적용, 요청 크기가 무효일 때만 Config 크기 사용 | speed 3.5 / Storage 64는 이번 Test06 확인. 전체 우선순위 행렬은 미검증 |
| MainFacility Config 용량 ≤ 0 | Indestructible만 추가, 저장 구성 생략 | 코드 확인. 일반 Storage의 ≤0→20 보충과 다름 |
| None / ConstructionSite | 생성 없이 요청 소비 | 코드 확인. 기존 Test10은 이번 미실행 |
| Count / 정의 밖 enum, 잘못된 Direction, 점유 중 좌표 | 포괄적인 입력/배치 검증 없음 | 코드 확인. 신뢰된 내부 명령의 허용 범위는 설계 질문으로 남김 |

Config 게시 실패와 의도적인 Config 부재를 이 소비자는 구분하지 않는다. 그 원래 정책 질문은 [Q05 F-011](Q05.md)에 연결한다. Spawn 자체에는 해금/자재/점유 검사가 없으며, 이를 Placement 검증을 수행하는 사용자 입력 경로라고 해석하지 않는다. PlacementStamp도 입력을 그대로 복사할 뿐 새 우선순위를 발급하지 않는다.

## 3. 타입별 초기화와 직접 소비 계약

공통 구성은 `BuildingType`, `BuildingFootprint`, `GridPosition`, `Direction`, `PlacementStamp`, `LocalTransform`이다. LocalTransform은 격자 `(x,y,0)`의 `FromPosition` 값으로 설정한다. DB 경로 역시 초기 위치를 덮어쓰므로 prefab transform을 그대로 보존하는 정책은 아니다. 실제 시각 결과는 확인하지 않았다.

| 타입 | Utility가 주입하는 초기 구성 | 직접 소비 / 판정 |
| --- | --- | --- |
| Belt | BeltComponent, speed>0 아니면 2 | BeltSpatialSync가 Belt/Grid/Direction을 읽음. 공통 상태·기본 속도는 Test01 확인 |
| Miner | speed>0 아니면 1, Progress=0; MinerDecision/출고 결정 비활성; Product/Result 버퍼 | MinerDecision 쿼리 및 Product 출고 구성에 맞음. Test02 확인. 채굴 실행 자체는 이번 범위 아님 |
| Crafter | recipe/activeRecipe=0, Progress=0, NoRecipe, active=false; CrafterDecision/출고 결정 비활성; Stored/Product/Result 버퍼 | **CrafterStateDecision·Storage·StorageFilter 없음(F-037)**. Decision 진입·정상 입고 계약을 만족하지 않음. 실제 prefab이 보충하는지는 미확인 |
| Storage | 슬롯 양수 또는20; Stored, 기본 AllowAll/빈 mask 필터, 출고 결정 비활성 | 입고는 Storage 필요. Stored 출고 쿼리는 Product 없는 대상을 선택. Config 슬롯64는 Test06 확인 |
| Splitter / Merger | 기준 Belt=Null, forward=요청 방향, cursor=0; RoutingTransferDecision 비활성 | 각각의 RoutingState/Grid/BuildingType 쿼리와 맞음. Test05는 방향·결정 비활성을 확인하지만 Null/cursor까지 assert하지 않음 |
| MainFacility | Indestructible; 용량>0이면 Storage/Stored/AllowAll/비활성 출고 결정 | 코드 확인. Config 부재 기본20, Config의0은 저장 기능 생략. 실제 Spawn 사례 미실행 |
| PowerPole / CoalGenerator / DroneStation / ResearchBuilding | 공통 구성만 | 해당 미래 도메인 동작 구현으로 확대하지 않음. 존재하지 않는 기능을 이번 Spawn 결함으로 등록하지 않음 |

기본 크기는 Belt/Storage/Splitter/Merger/PowerPole 1×1, Miner/Crafter 2×2, 나머지 위 유효 타입 3×3이다. DB lookup이 돌려준 `dbFootprint`는 사용하지 않는다(**F-022**). Utility가 방향 적용 값을 Size에 저장하는 반면 BuildingSpatialSync는 Size를 base로 해석하여 다시 회전한다(**F-023**). 요청 `(2,3), Right`는 저장 `(3,2)`→인덱스 `(2,3)`이 된다. 정사각형 정상 테스트 통과는 이 문제를 검증하지 않는다.

## 4. Reader/Writer·순서·공개 계약과 결합

| 상태 / 경계 | Writer → Reader | 필요한 계약 / 개선할 결합 |
| --- | --- | --- |
| SpawnBuildingRequest | 현재 테스트 등 외부 생산자 → Spawn Job, ECB 소비 | 생성 입력과 단발 소비는 필요. 현재 런타임 생산자와 성공 응답 계약은 없음 |
| Building DB / Config | Baker/초기화 게시 → system context → Utility RO lookup | 외형 prefab/정적 설정 제공은 필요. lookup 내부 탐색을 caller가 알 필요는 없음. DB 유일성·필수 schema 전제는 별도 진단 경계 |
| 초기 Grid/Direction/Stamp/Footprint | Utility ECB → 물류·공간·생산 Reader | 필드 의미와 초기 구성은 공개 계약. F-023은 다른 Writer가 무엇을 회전했는지 알아야 하는 불필요한 결합 |
| 타입별 state/decision/buffer | Utility ECB 초기화 → 각 도메인 소유 시스템 | 실제 Reader가 요구하는 구성까지 제공할 책임. F-037은 Factory 또는 prefab 내부 구성이 결손을 보충해 주리라는 전제 |
| 구조 변경 | 단일 Spawn Job → EndStateApply Playback → Sync | producer handle과 단계 경계는 필요. Spawn이 직접 맵을 고치거나 Sync의 Update를 호출하지 않아 Fence 접근은 추가로 필요 없음 |
| 물류 Apply → BuildingLifecycle | 명시적 UpdateAfter + system Job dependency | 기존 건물 철거 전에 최신 물류를 반영하는 경계. Spawn만의 필요조건으로 설명하지 않으며 상세 철거 검증은 Q28 |
| Construction Completion → Utility | 동기 함수 호출로 같은 생성 규칙 재사용 | 두 caller가 같은 공개 초기화/실패 결과를 공유하는 것은 적합. 완료 caller의 실패 반환 무시는 F-024 |
| Item DB → Spawn만 있는 BuildingLifecycle update | 시스템은 철거 여부 분기 전에 Item DB singleton을 조회 | Spawn Job/Utility는 Item DB를 쓰지 않음. 철거 context의 무조건 조회는 **개선할 결합**. 복수 Item DB 시 영향을 Spawn까지 넓히는 F-018의 관련 지점이며 별도 ID로 중복 등록하지 않음 |

Component/BufferLookup은 Update 후 Job 필드에 전달하고 RO 의도를 명시한다. Spawn은 기존 건물 버퍼를 직접 수정하지 않으며 ECB로 새 실체의 상태를 기록한다. 구조 변경 너머에 기존 DynamicBuffer를 보관하는 Spawn 코드도 없다. 단, DB/Config가 복수인 잘못된 월드, prefab entity의 생존·LocalTransform 등 필수 schema, ECB Playback 실패의 전체 복구는 이 Utility가 보증하지 않는다.

공개 계약을 유지하는 내부 변경의 영향은 다음과 같다.

1. DB 조회를 선형 검색에서 다른 내부 표현으로 바꾸어도 선택 규칙·실패 결과·입력/출력 계약이 같으면 두 caller와 Decision 시스템은 바뀔 이유가 없다. DB footprint의 권위를 바꾸는 것은 내부 리팩터링이 아니라 F-022의 계약 결정이다.
2. 초기화 함수를 타입별 작은 함수로 나누되 동일 컴포넌트·값·enable·버퍼·ECB 의미를 유지하면 두 caller는 그대로여야 한다. Crafter 필수 구성을 추가하는 수정은 실제 생성 결과와 소비자 계약을 맞추는 별도 수정/회귀 검증이다. 슬롯 수를 Factory 기본값으로 임의 확정하지 않는다.
3. Decision의 계산 내부가 바뀌어도 필요한 컴포넌트 계약이 같으면 Spawn은 그대로다. Reader가 필수 컴포넌트를 새로 요구하면 이는 공개 구성 계약의 변경이므로 Spawn/Baker/Factory의 관련 구성을 함께 확인해야 한다. 파일 수가 많다는 이유만으로 부적절한 결합이라 판정하지 않는다.
4. 철거용 Item DB 조회를 철거 요청 경계로 제한하는 후보는 Spawn의 공개 출력·정상 순서를 바꾸지 않고 불필요한 준비 전제를 줄일 수 있다. 실제 수정과 복수 DB 회귀 검증은 하지 않았다.
5. footprint를 base로 일관되게 유지하려면 Utility뿐 아니라 Placement·Completion 입력·Sync Reader와 관련 테스트를 함께 확인해야 한다. 생성자를 구별하는 사후 보정이나 새로운 순서 의존을 추가하는 방향은 F-023을 해결하지 못한다.
