## 3. 정적/런타임 계약과 준비 경계

### 3.1 상태 Owner·Reader/Writer

| 상태 | Writer / Owner | Reader | 적용·소비 경계 |
| --- | --- | --- | --- |
| LoadMode, Prefabs(Type, Prefab) | 사용자 / PopulateFromResources | DB Baker | List는 직렬화 목록, AutoLoad는 Resources를 다시 읽음 |
| Resource prefab 이름 | asset 작성자 | Populate와 AutoLoad의 별도 파서 | Trim → 공백을 `_`로 치환 → 대소문자 무시 ItemTypeEnum.TryParse. 이름으로 DB key를 만듦 |
| ResourcePrefabDatabase / ResourcePrefabElement | Resource DB Baker | ResourceGenerationCommand → lookup/resolve | holder는 TransformUsageFlags.None, 참조 prefab은 Renderable. 타입-참조 매핑을 게시하며 노드의 런타임 매장량·Grid를 bake하지 않음 |
| ResourceGenerationSettings / Config buffer | 설정 로더(직접 관련 이전 평가 Q07) | Command·Utility | 동일 설정 엔티티의 버퍼. seed·품목·반경·확률·양을 읽으며 DB 준비와 별도 전제 |
| `resolvedPrefabs[i]` | TryResolvePrefabs | Command의 엔티티 검사, Generate의 configs[i] 처리 | configs.Length 크기의 Temp 배열, 같은 인덱스의 설정과 참조를 대응. 해당 update 안에서만 사용/Dispose |
| GeneratedChunkTracker.Map/Pending | **ChunkLoadCommandSystem** | ChunkLoad 자신의 재접수 판정 | Generation은 NativeHashSet을 직접 쓰지 않음. Pending은 준비 대기와 ECB 반영 대기를 모두 포함 |
| Ready buffer | ChunkLoad 게시, ResourceGeneration 소비 | ResourceGeneration | 미준비면 그대로 유지. 모든 준비 검사 후 전체 ready에 스폰·완료 기록을 마치고 Clear |
| Completed buffer | ResourceGeneration의 EndCommand ECB | 다음 Command의 ChunkLoad | spawn 명령 뒤에 Append, Playback 전에는 없음. 다음 ChunkLoad가 Map 추가/Pending 제거 후 Clear |
| 새 ResourceNode / GridPosition / LocalTransform | ResourceGenerationUtility의 ECB | 공간 Sync, 이후 자원 소비자 | Instantiate 뒤 위치와 ResourceType/Amount 초기화, EndCommand에서 확정. 원본 prefab의 런타임 state를 수정하지 않음 |
| ResourceSpatialIndex | ResourceSpatialSync | 후속 조회자 | ECS 실체의 파생 인덱스. Sync에서 Grid로 등록하고 Fence로 NativeContainer 의존을 관리 |

자원 타입이 DB에 기록되는 것과 개별 ResourceNode의 타입/양이 runtime에 초기화되는 것은 다른 책임이다. 별도 ResourceNode Authoring이 꼭 있어야 한다는 조건은 없다. 선택 테스트의 AddPrefab은 **Prefab+LocalTransform만** 만들고, 생성 뒤 ResourceNode+GridPosition 쿼리와 공간 인덱스에 들어가는 것을 확인한다.

### 3.2 Authoring·등록 정책 — 코드 확인

- Populate는 Clear 후 `Resources/Prefabs/Resource`를 수집한다. 재호출이 목록을 누적하지 않지만, 수집 집합의 동일 타입 중복은 제거하지 않는다. 이름 파싱 실패와 None은 조용히 제외한다.
- AutoLoad Baker는 목록을 무시하고 같은 경로를 다시 탐색한다. Populate와 Baker에 파서가 각각 있어 같은 이름 규칙을 유지해야 한다. 목록을 수정해 AutoLoad 결과를 제어할 수 있다고 설명하지 않는다.
- List Baker는 Null prefab/None만 제외한다. enum 정의 범위, 중복 key, 실제 prefab asset인지, 전체 자원 Config와 매핑이 일치하는지 자체 검증하지 않는다. `DisallowMultipleComponent`는 한 GameObject 내부 제한이며 월드의 단일 DB를 보장하지 않는다.
- DB가 비어 있어도 태그와 버퍼는 게시한다. 소비자는 ResourcePrefabDatabase 태그 singleton을 얻은 뒤 **그 엔티티**의 ResourcePrefabElement를 검사한다. Item/Building과 query 방식이 다르므로 하나의 공통 누락 규칙으로 설명하지 않는다.
- lookup은 첫 일치를 선택하고 Null이면 false다. 정상 Baker는 Null 참조를 건너뛰지만 외부 변조/언로드 등으로 dead/null 행이 먼저 있고 정상 중복 행이 뒤에 있는 상황을 자동 대체하지 않는다. 실제 현재 asset의 중복/잘못된 참조는 미확인이다.
- **보완되는 점:** 런타임 Command는 resolve된 각 non-Null entity의 Exists와 LocalTransform을 검사한다. Item/Building의 등록 검증 공백을 근거로 Resource도 malformed 참조를 곧바로 Instantiate한다고 판정하지 않는다. 무효 참조는 생성 이전 대기로 전환된다.
- 정상 prefab root는 Unity Entities가 Dynamic을 자동 부여한다는 [Q09의 엔진 코드 근거](Q09.md#3-타입크기방향dbspawn의-실제-계약)가 있다. Renderable 플래그 하나만으로 LocalTransform 누락 결함을 등록하지 않는다. 실제 scene-object 참조나 특수 transform 베이킹은 미검증이고 Command의 guard 대상이다.

### 3.3 준비→생성→완료 — 코드 확인 및 선택 실행 확인

1. RequireForUpdate는 ResourceGenerationSettings, GeneratedChunkTracker, ResourcePrefabDatabase 존재를 요구한다. DB가 없으면 생성 update가 실행되지 않고 ChunkLoad가 이미 보관한 Ready/Pending은 유지된다.
2. ready 없음, DB에 prefab buffer 없음, 설정 엔티티에 config buffer 없음, configs.IsEmpty, EndCommand ECB 시스템 없음이면 기록/Ready 소비 전에 반환한다. 일부 조건은 test case로 실행했고 나머지는 소스 분기로만 확인했다.
3. TryResolvePrefabs는 `configs[i]`에 대응하는 entity를 만든다. **IsValidConfig는 Type>None, Weight>0, MaxPatchRadius>=0, MaxAmount>0**를 요구한다. 해당 조건을 통과하지 않는 행은 배열에 Null로 남기고 generation에서도 건너뛴다. 이는 Q07 로더의 모든 유효성 검사를 대체하는 함수가 아니다.
4. 필요한 행 하나라도 lookup에 실패하면 전체 update가 대기한다. 나머지 품목만 먼저 생성하지 않는다. 그 뒤 Exists/LocalTransform 검사를 모든 non-Null 참조에 적용하며, 하나가 잘못돼도 ECB 생성 전에 반환한다.
5. 검사 통과 후 CreateCommandBuffer하고 각 Ready 청크에 Generate 호출 및 Completed Append를 같은 ECB에 기록한다. 그 후 Ready만 Clear하고 Pending은 건드리지 않는다. 스폰/알림을 기록하는 작업은 메인 스레드에서 동기 실행되므로 이 코드에 별도 생성 Job producer handle은 필요하지 않다.
6. EndCommand Playback 후 entity와 완료 알림이 존재한다. 다음 ChunkLoad가 알림을 받아 Pending→Map으로 확정한다. 이전/다음 프레임의 재요청은 Pending/Map으로 중복 제거된다. Ready가 비었다는 사실을 생성 완료와 동일시하지 않는다.
7. 자원 실체는 Command 종료에 생기지만 공간 인덱스는 Synchronization 이후에 갱신된다. 따라서 “같은 프레임 entity가 존재”와 “해당 프레임 앞선 Decision의 인덱스 조회로 발견”을 구분한다. 이번 테스트는 채굴을 실행하지 않았다.

**입력·실패 정책의 세부 한계:**

- 비어 있는 config buffer는 대기지만 **행이 있고 모두 Weight=0**이면 prefab이 필요 없는 빈 청크로 완료될 수 있다. 다만 이때도 DB 태그/버퍼와 ECB는 필요하다. 빈 청크의 기존 실행 근거는 Q01a에 있다.
- FillChance=0이어도 위 IsValidConfig를 통과하면 prefab을 요구한다. 대상 청크에서 실제 광맥이 나올지 계산하기 전에 설정상 필요한 전체 품목을 준비시키는 정책이다. 이를 불필요한 결함으로 임의 변경하지 않는다.
- Utility의 bool Generate overload는 lookup 완료만 확인한다. **Exists/LocalTransform 검사는 Command가 소유**한다. 해석된 NativeArray overload는 길이·순서·entity 유효성이 이미 준비됐다고 전제한다. 정상 Command는 이 전제를 만족한다. Utility를 범용 안전 스폰 API로 확장해 설명하지 않는다.
- 대기 분기에는 timeout·사유 상태·로그가 없다. 일시 지연 시 매 프레임 오류를 내지 않는 장점이 있지만 영구 누락 진단은 어렵다. 게임의 실패 정책을 임의로 정하지 않고 §7의 진단 질문으로 남긴다.
- 사전 검사는 알려진 무효 참조 때문에 부분 ECB 기록/재생에 들어가는 것을 피한다. 메모리 실패·외부의 DB/prefab 파괴·ECB 전체 예외에 대한 일반 트랜잭션 rollback까지 보장하지 않는다. 생성 기록과 Playback 사이의 prefab 언로드 경합은 미검증이다.

1. 같은 유효·유일 Type→Prefab 매핑을 내면서 Baker의 목록 수집 구현을 바꾸면 Command/Utility/ChunkLoad 수정은 불필요하다. 중복 행의 순서를 바꿔 첫 선택이 달라지면 관찰 결과가 바뀌므로 계약 유지 변경이 아니다.
2. 같은 Config·동일 품목 entity 배열·실패 bool을 유지하며 TryResolvePrefabs의 검색 내부를 바꾸면 Command의 Exists/LocalTransform 검사나 ChunkLoad는 수정할 필요가 없다. 배열의 순서/길이를 바꾸는 것은 공개 중간 데이터 계약 변경이다.
3. 동일 seed·청크에서 같은 자원 셀·타입·양과 ECB 확정 시점을 유지하면서 Utility의 후보 계산을 재구성하면 Baker/ChunkLoad는 영향을 받지 않는다. 분포 알고리즘이나 겹친 품목 선택 결과가 달라지면 결정론 결과 계약까지 별도로 검토해야 하며 Q10에서 변경하지 않는다.
4. Ready/Completed 의미·가시 시점·중복 제거 결과를 유지하며 ChunkLoad의 Map/Pending 내부 구현을 바꾸면 ResourceGeneration은 그 container를 읽거나 쓰지 않으므로 수정할 필요가 없다. 컴포넌트의 공개 표현을 바꾸면 해당 component를 직접 보는 테스트는 정상적으로 영향을 받는다.
5. 생성 기록을 Job으로 옮기되 같은 EndCommand 결과를 유지하려면 Command 내부에서 최종 Job handle과 ECB producer 등록, 준비 데이터의 수명을 맞춰야 한다. 이는 필요한 동기화 변경이며 Baker가 Job 내부 순서를 알아야 한다는 뜻이 아니다. 기계적으로 병렬화 가능하다는 성능 판정은 하지 않는다.

따라서 정상 준비·생성 경계를 이해하는 데 필요한 것은 단일 DB/Config, Ready 보존, Completed 가시성, prefab transform 전제다. 다른 시스템의 전체 실행 배열이나 정리 구현까지 알아야 하는 숨은 결합은 이번 정상 경로에서 확인하지 못했다. 시스템 수·UpdateAfter 개수만으로 적합성을 판정하거나 V1보다 결합이 감소했다고 단정하지 않는다.

## 7. 남은 질문·완료 범위·다음 단계

1. 영구 DB 누락·잘못된 참조와 정상 로딩 지연을 구별할 진단 상태가 필요한가? 현재는 모두 조용히 대기한다. 원인 상태/최초 1회 진단 등의 후보를 남기며 timeout·자동 fallback을 임의로 추가하지 않는다.

4. Utility를 외부 caller도 쓰는 API로 유지한다면, configs/resolvedPrefabs의 길이·순서·유효 entity 전제를 명시할 필요가 있다. 이번에 일반 생성 API로 확대하거나 새 경계를 구현하지 않았다.
5. 실제 Resources 이름·프리팹·SubScene 연결 및 베이킹 출력은 Q11의 대상이다. Renderable/transform·실제 노드 렌더, ContextMenu 편집·저장·증분 베이킹은 미확인이다.

완료 범위는 Q10 Authoring/Baker, 직접 준비·생성/완료 인계, 기준선 차이, 상태 Reader/Writer·의존/변경 영향, 기존 문제 연결과 선택 5건의 최종 검증 기록이다. 필요한 검증이 환경에 막힌 상태는 아니다. **Q11 — DB의 실제 프리팹·SubScene·장면 연결**은 다음 후보로만 남기고 이번 작업에서 진행하지 않는다. 수정·테스트 보강도 자동 진행하지 않는다.
