## 1. 기준선, 실제 확인 범위와 보존

### 기준선과 변경

Q00의 Git HEAD와 이번 HEAD는 같다. `git diff <Q00 HEAD> -- Assets Packages ProjectSettings Tools` 및 staged 변경 목록은 비어 있다. 기존 ` D PROJECT_EVALUATION_PLAN.md`와 미추적 평가 문서 폴더 상태를 보존했다. 삭제 복구·stage·commit은 하지 않았다.

이번 수정 대상은 이 결과 파일과 계획 문서의 Q31 상태·결과 링크·진행 상황·다음 작업뿐이다. 기존 결과 문서를 다시 쓰거나 문제를 해결됨으로 바꾸지 않았다. 두 대상 문서를 제외한 기존 평가 폴더 **34개 파일**은 시작/종료 SHA-256 비교로 보존을 확인했다.

Git 기준선 일치는 추적 소스 변경이 없다는 근거다. ignored 캐시, 실제 baked 데이터, Editor/World의 실행 상태와 과거 실행 환경의 동일성을 증명하지 않는다. 따라서 과거 EditMode 통과를 이번 현재 환경에서 다시 검증한 것으로 표시하지 않는다.

## 2. 세 축의 최종 판단

| 평가 축 | 판정 | 근거와 판단 범위 |
| --- | --- | --- |
| 안정성 | **일부 불일치** | 정상 채굴→수납, 일부 정체 복구, 취소/반환·정리 후 재건축에는 기존 선택 EditMode 근거가 있다. 그러나 실제 fallback Crafter 생성 누락(F-037), 완료 실패 후 자재/현장 폐기(F-024), 생산 대기와 철거(F-005), 일반 벨트 경합·전방 간격(F-029/F-030)은 핵심 계약을 깨는 코드 경로다. 이 반례들을 실행 재현한 것으로 보고하지 않는다 |
| 유지보수성 | **일부 불일치** | 설정 Registry, 순수 생성/좌표 계산, 프레임 결정/결과, 인덱스 소유자는 책임을 찾기 쉽게 한다. 반면 Item 초기화 복제(F-020), base/effective 혼용(F-023), 입력 행 의미와 소비자 가정(F-010/F-014), Blob 교체 수명(F-008), Factory/실제 Spawn 차이 및 좁은 assertion(F-021/F-037/F-044~F-048)이 변경과 회귀 판단을 어렵게 한다 |
| V2 설계 적합성 | **일부 불일치** | ECS 원본 상태와 `Command → Decision → Reservation → Execution → StateApply → Synchronization`, 두 ECB, 요청·결정·결과의 인계가 존재한다. 하지만 모든 목적지 경쟁이 Reservation에서 승인되지 않으며, 폐기 시 아직 실체화되지 않은 결과와 실패 반환을 조정하는 계약이 부족하다. 파일의 단계별 분리만으로 목표 달성을 판정할 수 없다 |

이는 현재 구현의 평가다. 미구현 전력·드론·연구·UI·바닥 표시 등을 결함 수에 추가하거나 출시 준비도를 매기지 않는다. 필요한 동기화가 많은 사실 자체도 결함으로 세지 않는다. 미검토 조건까지 포함하는 무결함·무순환·독립성 보장이나 백분율 점수는 제시하지 않는다.

## 3. 의존성 목표와 변경 영향

상세 관계도, 상태별 Writer, 직접 제어 검색 범위는 [Q30b](Q30b.md)에 있다. 공통 흐름은 설정/프리팹 게시 → 명령/결정 → 예약/실행 → 상태 적용/ECB → 공간 Sync → 다음 판단이다. 청크 Ready/Completed, 재고와 백프레셔, 레시피 잔여물 배출은 공개 데이터의 피드백으로 이해할 수 있다.

| 구분 | 종합 판단 |
| --- | --- |
| 유지할 공개 계약 | Component/Buffer의 원본 상태, 요청 소비와 enable 의미, 결정 승인·적용, 두 ECB의 가시 시점, 공간 Map 소유자·Fence Reader/Writer·Dispose 경계, Config/Blob 읽기 수명 |
| 필요한 순서 | Cancel→Material→Completion의 Job 인계, 물류 반영 후 철거, 구조 변경 후 Sync는 행동을 위한 협력이다. 즉시 변경한 flag/버퍼를 ECB로 옮기면 관찰 시점이 달라지므로 같은 계약의 단순 정리로 볼 수 없다 |
| 개선할 결합 | F-004/F-005의 최종 Owner/표시/대기 생성과 폐기, F-024의 실패 반환과 원본 소비, F-010/F-014의 행 의미, F-023/F-037의 생산자·소비자 표현/schema, F-008의 교체 수명, F-020의 Item 초기화 복제 |
| 조건부 동기화 위험 | Placement의 직접 Map 조회(F-026), Recipe Command의 main-thread Lookup(F-039)은 외부 완료 부수효과에 기대는 조건이 있다. Validator나 테스트 helper의 강제 완료를 정상 런타임의 보장으로 삼지 않는다. 의도적으로 미완료 Job을 만든 실행 재현은 없다 |
| 직접 제어·순환 | Q30b의 명시된 검색/확인 범위에서는 게임플레이 시스템끼리 Update를 직접 호출·제어하는 경로를 찾지 못했다. ECB 시스템 획득, 자기 초기화 비활성화, 정적 Loader/Utility 호출은 구분했다. 청크 생성 완료가 다시 Load로 오는 관계는 공개 결과 소비이며 그 자체가 순환 제어 결함은 아니다 |
| 구조 후보와 측정 한계 | 일반 Input의 Crafter 상태 enum 해석, 작업 종류와 무관한 DB 준비 context, Fence 메타데이터 접근 선언(F-028)은 분리 검토 후보다. 새로운 가용성 Component나 통합 거대 시스템이 반드시 필요하다고 결론내리지 않는다. F-028의 의존 추가는 분석 근거이며 실제 병목/개선량은 측정하지 않았다 |

공개 계약을 유지하는 변경과 계약 자체를 바꾸는 변경을 구분해야 한다.

| 변경 예 | 현재 예상되는 영향과 분리 후보 |
| --- | --- |
| Item의 공개 생성 요청 의미는 유지하며 내부 초기화 구성을 바꿈 | ItemLifecycle뿐 아니라 건물 철거 환급의 별도 초기화도 맞춰야 한다(F-020). Item 생성 책임 경계를 공유하는 후보가 있으나, 환급 시점·ECB·오류 정책까지 보존해야 한다 |
| 잔여물 배출 중 입고 차단 행동은 유지하며 Crafter 내부 상태를 정리함 | 일반 BuildingItemInput도 Crafter 상태 enum을 해석하므로 영향이 전파된다. 입고 가능 여부의 공개 계약으로 줄일 가치가 있는지 검토할 수 있다. 공개 enum이라는 이유만으로 무조건 잘못된 private 접근이라고 판정하지 않는다 |
| `BuildingFootprint.Size`의 기본 크기 계약을 일관되게 적용함 | Placement와 공통 Spawn의 저장 표현, BuildingSpatialSync의 회전 적용을 함께 확인해야 한다(F-023). DB/Config/request 중 크기 권위를 바꾸는 선택(F-022)은 별도 정책 변경이다 |
| 중복 자재/레시피 행을 합산하거나 거부함 | 입력 의미를 확정하는 공개 계약 변경이다. Loader와 수령/완료·Decision/Execution의 assertion을 함께 맞추어야 하며 국소 리팩터링으로 숨기지 않는다 |

같은 범위의 V1 코드·동등 실행·측정과 비교하지 않았으므로 **“V1보다 의존성이 감소했다”는 결론은 내리지 않는다.** 현재 V2의 필수 협력과 개선할 결합을 구분한 것이 이번 목표 적합성 평가의 범위다.

| 실제 제작·레시피 변경의 전체 물류 | Factory 내부 제작 및 일부 상태 전환의 기존 선택 근거. 실제 Spawn→잔여물 출고→재입고→새 제작, 실패 생산물 처리와 출력 슬롯 전체의 종단 결과는 미확인 |
| 공사 바닥 정리·운송 예약·입력 생산자 | 플래그/필드와 소비자 분석. 자동 clearance, 운송 예약 전 수명과 입력 중복 방지는 구현·검증 근거가 부족하며 임의 규칙으로 보충하지 않음 |
| Validator·테스트 증명 범위 | 소유 참조 유일성/현장 역방향, 모든 요청/결과, 렌더와 건물 점유 전체를 검사하지 않음. 진단 격리와 목표별 assertion 보강 필요 |
| 실제 플레이·UI/입력·시각·성능·플랫폼·영속화 | 사용자 수동 확인 자료 없음. Play Mode·WebGL/Player·장시간 성능·저장/로드를 검증하지 않음. 전력·드론·연구·실제 바닥 렌더 등 미구현 영역의 완성도는 평가하지 않음 |
| V1 대비 개선 | 동일 범위 비교와 측정이 없어 결합 감소·성능 향상·정량 점수는 판단 보류 |

이 공백을 채우는 실행/수정은 별도 작업이다. 이번 요청 안에서 테스트 추가·전체 실행·실제 플레이로 범위를 확대하지 않았다.

## 8. 수정 전 사용자 결정 사항

아래는 후속 작업에서 행동이 달라지는 질문이다. **답변을 받거나 정책을 선택한 상태가 아니다.** 알려진 필수 Component 누락, 공통 실패 반환 확인, base/effective 계약 정합성, 진단 격리를 다루는 데 모든 질문의 답이 먼저 필요한 것은 아니다. 해당 수정 범위에 영향을 주는 결정만 확인하면 된다.

| 결정할 질문 | 관련 근거 / 선택의 영향 |
| --- | --- |
| 같은 틱 생산/저장 Spawn과 철거가 겹칠 때 새 실물은 반환할지, 생산/요청을 거부할지, 보상할지? 일반 인계·공급·Destroy 중 누가 최종 소유/표시를 확정할지? | F-003~F-005. 생성 대기 결과와 폐기 접수의 성공/실패 계약을 결정한다. 죽은 Owner/버퍼를 남기지 않는 정합성은 어느 정책에서도 필요 |
| 생산물 실체화 실패와 공사 Spawn 실패는 각각 대기/재시도, 취소/반환, 명시적 실패 중 어떻게 처리할지? | F-006은 판단 보류, F-024는 실패 반환을 무시하는 확인된 P1. 도메인별 기존 DB 부재 fallback/등록 누락 거부 차이를 유지할지 함께 명시. 전체 ECB rollback을 당연한 기능으로 가정하지 않음 |

## 9. 종료 기록

Q31 결과와 계획의 허용된 진행 항목만 갱신했다. 기존 평가 문서 34개 보존, HEAD·staged/작업 트리 상태, 관련 코드·에셋·패키지·도구의 기준선 이후 변경 없음, 새 결과/계획의 로컬 링크를 확인했다.

**평가는 완료했으며 결함 수정은 수행하지 않았다.** 최종 결론은 현재 V2의 유효한 데이터·실행 경계를 유지하면서 P1의 생성/실물 보존/이동 승인을 우선 수정 후보로 삼고, 필요한 정책과 미확인 실행을 별도 작업으로 명확히 하는 것이다. 다음 단계 자동 진행, 테스트 범위 확대, 코드 수정은 하지 않는다.
