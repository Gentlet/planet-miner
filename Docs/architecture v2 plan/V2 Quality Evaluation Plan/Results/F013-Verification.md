# F-013 레시피 품목 검증과 필수 주생산품

작업일: 2026-10-08. 현재 코드 분석·.NET 빌드와 Unity 컴파일/실행 검증을 구분한다. 최초 Q06의 무효 품목 반례는 코드 분석이며 실제 실행 재현 기록이 아니다.

> 2026-10-09 현재 상태: F-015의 동일 원본 Unity 컴파일과 최신 어셈블리에 현재 품목/출력 검증이 포함돼 당시 남은 필수 컴파일 확인을 충족했다. F-013은 구현·컴파일 완료로 반영하며 아래 대기/실패와 집계는 당시 기록으로 보존한다. 무효 품목의 실행 재현은 미수행이다. [공유 컴파일 확인](#2026-10-09-f-015-공유-컴파일-확인).

## 확정 정책

- JSON 재료·주생산품·작성한 부산물에는 정식 품목명만 허용한다. 대소문자 무시와 앞뒤 공백 허용은 유지하며 오타·빈/누락 이름·숫자 문자열·None·미정의 품목을 거부한다.
- 실제 주생산품은 출력 슬롯 0에 필수다. 주생산품 없는 부산물 전용 레시피나 재료만 소각하는 무출력 레시피는 허용하지 않는다.
- 없는 부산물은 목록 생략/null/빈 목록으로 표현한다. 작성한 부산물은 실제 품목이어야 하며 None 행을 빈 슬롯으로 사용하지 않는다.
- 초기화 오류는 해당 레시피 설정 전체 미게시·로그·즉시 SimulationFatalError와 기존 GameSimulationGroup 차단을 사용한다. 항목 제외·자동 fallback·재시도·앱 종료는 추가하지 않는다.

## 구현과 책임

- RecipeConfigLoader.ParseItemType은 빈 값 검사, Enum.TryParse 성공, Enum.IsDefined, 정식 이름과의 대소문자 무시 일치를 확인한다. 재료·주생산품·부산물이 같은 파싱을 사용한다. 숫자/복합 enum 문자열도 정식 이름 일치에서 거부한다.
- ParseJson과 PublishConfig는 같은 ValidateConfig를 사용한다. 버퍼 범위·중복 재료·필수 출력·슬롯 0 주생산품/후속 부산물 역할을 검사하고 모든 원본 재료/출력 행의 실제 품목을 확인한다. 원본 목록의 참조 범위 밖 행도 품목 검사를 우회하지 않는다. 출력량은 양수여야 하므로 직접 구성한 0수량/음수 출력도 게시되지 않는다.
- JSON의 기존 비양수 재료/출력 수량과 제작 시간 보정은 유지한다. 파싱된 출력은 기존처럼 최소 1이고 직접 구성한 설정의 양수 출력 검사는 무출력 우회 방지다. 재료 long→int 범위, F-014 중복 거부와 전체 재료 선검사, F-015의 별도 추가 ID 정책은 변경하지 않았다.
- PublishConfig는 기존 Registry 중복을 입력 처리 전에 거부하고 전체 검증 후에만 새 엔티티를 만든다. 뒤쪽 부산물이 잘못돼도 새 부분 Registry를 만들지 않는다. 복사 중 실패하면 이번 호출이 만든 미완성 엔티티만 회수한다.
- RecipeInitSystem의 사전 등록은 원본 세 버퍼를 ValidateRegisteredConfig로 검사한 뒤 필수 ID 1~5를 확인한다. 같은 하위 품목·범위·출력·중복 검사 함수를 재사용하며 원본을 복사하거나 수정하지 않는다. 실패한 사전 등록 원본은 보존하고 기존 ReportFailure로 Fatal을 게시한 뒤 자동 Init을 비활성화한다.
- 공개 Loader는 예외를 전달하고 실제 제품 호출자인 InitializeRecipeRegistry가 기존 로그/Fatal로 변환한다. 직접 PublishConfig 호출의 검증 거부를 그 함수 자체의 Fatal 게시로 바꾸지 않았다.
- Runtime Reader는 기존 ECS 설정 버퍼와 RecipeConfigLookupUtility를 계속 사용한다. Init 내부 참조·새 시스템/컴포넌트/Utility/영속 캐시·partial 분리는 추가하지 않았다. Command/Building/Drone/Commit 순서·소유권·생산 결과/실물 인계도 변경하지 않았다.

## 코드로 확인한 보존 경계

- 오타·빈/누락·None·숫자 이름·후반 부산물 오류는 파싱 성공 결과를 반환하지 않는다. 공개 게시의 무효 enum·출력 0개·양수가 아닌 출력량·출력 역할 오류도 Registry 생성 전에 거부한다.

- 정상 JSON은 실제 주생산품을 지정하고 부산물을 생략하므로 새 품목 계약과 일치한다. 기존 다중 부산물 테스트의 JSON도 슬롯 0 주생산품과 후속 부산물로 변환된다. 테스트를 새로 실행한 근거는 아니다.
- F-037의 입력 슬롯 계산과 실패 시 제작 진행도·보관/출력 버퍼·Owner·필터 보존, F-014의 소비 가능 실물 전체 선검사, F-008의 World 수명 1회 게시 경계는 변경하지 않았다. F-006의 실행 중 생산물 생성 실패/결과 Clear 정책도 이번 작업 범위가 아니다.

## 2026-10-08 관련 이슈 후속 정리

사용자의 문서 정리 요청에 따라 현재 Task와 직접 관련 소스/후속 기록을 대조했다. 이번 후속은 문서만 변경하며 F-013 구현 소스·기존 테스트·Config는 보존하고 새 컴파일·테스트를 실행하지 않는다. 위 .NET 통과와 Unity 대기는 이전 구현 단계의 결과다.

- **F-008 — 게시 전 거부와 기존 원본 보존 강화:** PublishConfig는 기존 Registry 확인을 새 입력 검증보다 먼저 수행한다. 전체 검증 뒤에만 새 엔티티를 만들고 복사 실패 시 이번 호출의 엔티티만 회수한다. 사전 등록 실패는 원본을 삭제/보충/교체하지 않는다. World 소유·읽기 전용·1회 게시·Reader 의존성의 기존 완료를 유지한다. 원본 48/48는 새 품목 오류/사전 등록 실패의 실행 근거가 아니다.
- **F-009 — 선택 검증의 대상 경계만 갱신:** 품목 이름/None/출력 누락·후반 부산물·직접 게시/사전 등록 오류가 기존 초기화 실패 전달에 연결됐다. 무효 품목의 실행 재현이나 파일 부재·읽기/일반 파싱 실패의 검증 공백을 해소한 것은 아니다. 기존 선택 검증 분리/추적 종료를 유지하고 새 테스트·assertion을 필수로 되살리지 않는다.
