## 3. 실제 코드가 보장하는 정렬

`GameSimulationGroup`은 `SimulationSystemGroup`의 자식이다(`Phases/GameSimulationGroup.cs:7`). 나머지 여섯 그룹은 모두 `GameSimulationGroup`의 자식이고, 연속된 다섯 `UpdateAfter`가 아래 순서를 만든다. 그룹은 빈 기반 클래스 확장으로 별도 갱신·정렬 비활성화 코드가 없다.

```text
SimulationSystemGroup
└─ GameSimulationGroup
   Command → Decision → Reservation → Execution → StateApply → Synchronization
      └─ EndCommand ECB (마지막)                    └─ EndStateApply ECB (마지막)
```

두 ECB 위치는 아래 표가 기준이다. 도식의 가로 간격은 런타임 시간이나 Job 완료 시점을 뜻하지 않는다.

| 단계 | 정렬 근거 | 내부에 명시된 선후 관계 |
| --- | --- | --- |
| Command | `CommandGroup.cs:8`; EndCommand `:12`의 OrderLast | ChunkLoadCommand → ResourceGenerationCommand (`ResourceGenerationCommandSystem.cs:17`). BuildingPlacementCommand·CrafterRecipeCommand와 이 두 시스템 사이의 추가 순서는 지정되지 않음. 네 일반 시스템 뒤에 EndCommand |
| Decision | `DecisionGroup.cs:8–9` | BeltMovement·BuildingItemInput·StorageItemOutput·ProductItemOutput·Miner·Crafter·Splitter·Merger Decision 8개 사이에 추가 UpdateBefore/After 없음 |
| Reservation | `ReservationGroup.cs:7–8` | BuildingStorageInputReservation·BeltDestinationReservation 사이에 추가 순서 없음 |
| Execution | `ExecutionGroup.cs:8–9` | BeltMovement·Miner·Crafter Execution 사이에 추가 순서 없음 |
| StateApply | `StateApplyGroup.cs:8–9`; EndStateApply `:12`의 OrderLast | BuildingItemStorageApply → ItemOwnershipApply; RoutingApply → ItemOwnershipApply; BuildingItemStorageApply·RoutingApply·ConstructionLifecycleApply → BuildingLifecycleApply. 그 외 추가 선후 관계는 지정되지 않음. 일반 시스템 7개 뒤에 EndStateApply |
| Synchronization | `SynchronizationGroup.cs:8–9` | Belt·Building·Item·Resource SpatialSync 사이에 추가 순서 없음. WorldInvariantValidationSystem은 `:15`의 OrderLast로 그 뒤에 실행(개발용 조건부 코드) |

이는 **정렬 제약이 보장하는 부분 순서**다. 관계가 없는 형제 시스템에도 실행 시점의 구체적 배열은 생기지만, 그 배열을 게임 계약으로 삼거나 파일명·등록 순서로 고정하지 않는다. 예를 들어 BuildingLifecycleApply와 ItemOwnershipApply의 상호 순서는 현재 속성으로 지정되지 않는다. 이 사실만으로 결함으로 판정하지 않으며 도메인 경합은 Q02/Q28에서 확인한다.

로컬 Entities는 OrderFirst/일반/OrderLast bucket을 나누고 각 bucket의 제약을 정렬한다. 같은 그룹의 일반 시스템과 ECB 사이에 개별 UpdateAfter를 반복하지 않아도 두 End ECB는 마지막 bucket에 놓인다. 프로젝트가 정의한 해당 그룹에서 다른 OrderLast 멤버는 발견되지 않았다. 기본 World 초기화는 그룹 등록 후 정렬하며, 선택한 통합 테스트도 직접 그룹을 구성하고 SortSystems를 호출한다. 테스트는 실제 기본 World의 자동 등록 전체를 대신하지 않는다.

그룹 순서는 시스템의 갱신·Job 예약 순서다. 그룹 하나가 끝날 때 그 그룹의 모든 Job을 무조건 Complete한다는 뜻은 아니다. 데이터 작업 순서는 ECS Dependency와 공간 Fence, ECB 생산자 핸들로 이어진다. 상위 Simulation의 다른 Unity 시스템과 GameSimulationGroup의 상대 순서, 고정 시간 간격·프레임당 정확히 1회 실행까지 이번 선언이 보장하지는 않는다.

두 ECB 클래스는 별도 OnUpdate를 구현하지 않는다. 기반 `EntityCommandBufferSystem.OnUpdate`가 등록된 버퍼를 생성 순서대로 처리하며, 재생 전에 자신의 의존성과 등록된 producer handle을 완료한다. 이 범위에서 확인한 비동기 ECB 생산자 5개는 모두 최종 핸들을 등록한다. Command의 세 ECB 생산자는 메인 스레드에서 기록한다.

**하나의 ECB 시스템은 하나의 명령 버퍼와 같지 않다.** 여러 생산자가 각각 만든 버퍼가 같은 재생 시점에 순차 처리된다. Job 실행 완료 순서가 버퍼 재생 순서를 바꾸지 않는다. 같은 ECB에 기록했다는 이유만으로 오류 발생 시 전체 롤백되는 트랜잭션이라고 해석해서도 안 된다. 도메인별 실패 복구·부분 적용 정합성은 후속 평가 대상이다.

BuildingItemStorageApply·RoutingApply·CrafterStateApply는 이 검색 범위에서 독립 ECB를 만들지 않는다. 기존 상태·버퍼·enable 상태를 Job으로 쓰고 의존성을 전달한다. 따라서 “상태 변경은 전부 EndStateApply에서만 보인다”는 설명은 부정확하다.

### 경계의 예외와 조건

- **레시피 fallback:** `CrafterRecipeCommandSystem.cs:62–73,194–198`은 EndCommand 시스템이 없으면 Temp ECB를 만들고 같은 OnUpdate 끝에서 직접 Playback/Dispose한다. 전체 Scripts의 명시적 `new EntityCommandBuffer`·`.Playback(` 검색에서 이 경로가 확인됐다. 정상 자동 구성과 선택한 건설 통합 테스트에는 EndCommand가 있다. fallback이 잘못됐다고 단정하지 않고, 부분 World 구성에 따라 요청 삭제 시점이 달라지는 계약으로 기록한다. 필요성·일관성은 Q01b/Q22로 넘긴다.
- **ECB 시스템 부재 정책은 동일하지 않다:** ResourceGeneration은 EndCommand가 없으면 대기하며 Ready를 유지한다. BuildingPlacement와 StateApply의 네 생산자는 GetOrCreate를 사용하고, MinerExecution은 기존 EndStateApply를 전제로 한다. GetOrCreate로 객체를 얻는 것과 수동 World의 그룹 update list에 등록하는 것은 구분해야 한다. 부분 구성에서의 정책 통일 여부는 이번에 결정하지 않는다.
- **두 경계는 전체 Unity 실행의 Sync Point 총수가 아니다:** ChunkLoad의 OnCreate와 SpatialSync의 OnCreate는 싱글톤을 직접 만들고, InitialChunkLoadBootstrap의 Initialization OnUpdate도 큐 엔티티·버퍼를 직접 만든다. 초기화·설정 게시까지 “오직 두 ECB만 구조 변경 가능”으로 일반화하지 않는다. 실제 성능상 동기화 횟수는 측정하지 않았다.
- **실체 생성과 인덱스 반영은 별개:** EndCommand 뒤에 새 자원·현장 엔티티는 존재하지만 SpatialSync는 여전히 Phase 6이다. MinerDecision은 ResourceSpatialIndex를 읽으므로 EndCommand 생성만으로 새 자원을 같은 프레임에 채굴 대상으로 고른다고 보장할 수 없다. ResourceSpatialSync가 갱신한 인덱스는 다음 Decision이 Fence를 통해 읽는다. 두 End ECB 주석의 “동일 프레임 상호작용” 또는 “모든 상태 반영”은 이 제한을 함께 적용해야 한다.

| 유지보수성 | 여섯 그룹과 두 얇은 ECB 클래스로 공통 실행 순서를 찾기 쉽다. 다만 기존 F-002의 오래된 재생 시점 설명과 recipe의 별도 fallback을 모르면 실제 경계를 잘못 이해할 수 있다. 부분 World 구성 정책과 주석 정리는 후속 판단으로 남김 |
| V2 적합성 | **공통 Phase/ECB 배치에 한해 적합.** 각 생산자가 후속 소비자 시스템을 직접 Update하는 대신 그룹·ECB의 공개 기능으로 협력한다. 단, 도메인별 직접 상태 쓰기와 형제 순서 의존이 적절한지는 Q01b 및 각 도메인 단계에서 검토해야 한다. V1 대비 결합 감소나 V2 전체 적합성은 판단하지 않음 |

Q01a에서 필요한 최소 관계만 기록한다. 전체 관계표·도메인 내부 의존성 평가는 Q01b 이후 범위다.

| 관계 | 의존 형태 / 판정 | 변경 영향 |
| --- | --- | --- |
| 여섯 Phase → GameSimulationGroup 및 앞 Phase | 공개 그룹·순서 계약 / 필요한 계약 | 그룹 연결 자체가 바뀌면 모든 후속 데이터 가시성 전제를 재검토해야 함 |
| Command 생산자 → EndCommand | ECB 기록·수명주기 / 필요한 계약 | producer는 소비자 내부 구현보다 정해진 재생 경계에 의존. recipe fallback은 별도 구성 조건 |
| MinerExecution·StateApply 생산자 → EndStateApply | ECB 기록·producer 완료 핸들 / 필요한 계약 | Phase 4에서 기록하더라도 Phase 5 끝까지 구조 변경이 지연됨. 핸들 등록·재생 시점을 유지해야 함 |
| ResourceSpatialSync → 인덱스, MinerDecision → 인덱스/Fence | Writer/Reader 계약 / 필요한 계약 | ECB 시점만 앞당겨도 이 인덱스의 갱신 시점은 따라 바뀌지 않음 |
| StateApply의 명시적 형제 순서 | 공개 속성은 확인, 해당 도메인의 필요성·충분성은 판단 보류 | 단순 속성 개수로 결합 개선·악화를 판정하지 않음 |

변경 영향 사례(수정 실험 아님): 두 ECB 클래스에 내부 진단을 추가하되 버퍼 생성 API·생산자 대기·OrderLast·재생 의미를 유지한다면, 이번에 추적한 생산자 코드를 함께 수정할 필요는 확인되지 않았다. 반대로 자원 생성 기록을 EndStateApply로 옮기면 공개 가시성 계약이 바뀌므로 ResourceGeneration·경계 Probe·그룹 통합 assertion을 재검토해야 한다. 후자는 정상적인 계약 변경 영향이며 내부 구현만 바뀌어도 전파되는 불필요한 결합과 구분한다.

## 7. 발견 사항·미확인·다음 단계

- 기존 [F-002 — 재생 경계 문서 불일치](Q00.md#84-문서와-구현의-차이)를 현재 ResourceGeneration의 EndCommand 호출과 선택한 테스트로 재확인했다. 추가로 `ChunkLoadCommandSystem.cs:7`과 위 빈 청크 테스트 이름도 과거 StateApply 표현을 유지한다. 같은 불일치의 추가 위치이므로 새 문제 ID를 부여하지 않았다. 수정 여부는 미결정이며 이번에는 주석·테스트명을 고치지 않았다.
- F-001은 Q00의 범위 근거로만 사용했다. 건설 시스템의 내부 Job 예약 체인은 ECB 핸들 확인에 필요한 만큼만 검토했고, 완료·취소·철거 도메인 평가를 수행하지 않았다.
- 새 확정 구현 결함은 이번 범위에서 등록하지 않았다. recipe fallback과 부분 World의 ECB 등록 조건은 경계 예외로 남겼으며 Q01b/Q22에서 필요성을 판단한다. “발견 없음”은 전체 구현의 안전성 보증이 아니다.
- 미확인: 실제 기본 World 전체의 구체적 시스템 배열, 같은 그룹에서 순서가 없는 시스템 사이의 모든 데이터 경합, 전체 공간 Fence 안전성, 실패 시 부분 적용, 실제 플레이·입력·화면·성능·빌드·지속성. 이 단계에 수동 플레이 결과는 없다.
- 완료 조건: 범위·기준선 비교·정렬 근거·기록/재생 표·세 축 판단·최소 의존 관계·변경 영향 사례·선택 테스트 최종 결과·예외와 미확인을 기록하여 Q01a 완료.
