## 2. 입력 → 검증 → 게시 및 수명

1. **[코드 확인]** `TryLoadConfigFromResources`는 TextAsset을 읽고 전체 검증으로 넘긴다. 파일 부재·빈 JSON·파싱 실패에는 실패를 반환한다. 자원만 받는 옛 Load/Parse overload도 전체 바닥 검증을 수행한 뒤 floor 출력을 버린다.
2. seed는 0을 금지하고 initialChunkSize는 음수를 거부하며 0이면 3이다. 자원 목록은 비어 있을 수 없고, null 행·정의되지 않은/None 품목·중복 품목을 거부한다. weight/fillChance는 0..1, 반경은 `0 <= min <= max`, 양은 `1 <= min <= max < int.MaxValue`를 검사한다. 자원 weight는 각 후보의 발생 확률이다. 현재 합계 1.2를 정규화 누락 결함으로 보지 않는다.
3. 바닥은 양의 region, `0 <= transition <= region`, 유한한 양의 scale/exponent 및 유한한 0 이상 amplitude를 요구한다. 바이옴/전이 목록 필수, 바이옴 ID는 공백·Ordinal 중복·FixedString UTF-8 초과를 거부한다. variant 경로도 UTF-8 길이, 양의 유한 weight, `Resources.Load<Sprite>` 성공을 확인한다. 목록별 가중치 합도 유한 양수여야 한다. 이 경계는 문자열 변환 전에 길이를 검사한다.
4. **[코드 확인·EditMode 확인]** 임시 자원 목록과 바닥 목록을 전부 검증한 뒤에만 out seed/size/list/floor를 설정한다. 바닥 오류로 실패해도 이미 검사한 자원 목록은 외부로 반환하지 않는다. Init은 false일 때 게시 함수를 호출하지 않으며 로그 후 비활성화한다. 자동 fallback·자동 재시도는 없다.
5. 정상 Init은 전체 Publish overload를 호출하여 ResourceGenerationSettings, ResourceGenerationConfigElement, FloorGenerationSettings, FloorBiomeElement, FloorVariantElement를 같은 엔티티에 만든다. 메인 스레드의 동기 호출 안에서 완성하며 중간에 다른 시스템을 실행하지 않는다. 각 버퍼는 채운 후 다음 구조 변경으로 넘어가고 앞 버퍼를 다시 사용하지 않는다.
6. **경계:** 정상 입력 검증에 대한 all-or-nothing이지 공개 Publish의 일반적인 트랜잭션/예외 롤백 보장은 아니다. Publish는 검증된 인자를 전제하고 직접 CreateEntity 후 추가하며, null list·변조된 floor·중복 호출을 자체 방어하지 않는다. 정상 Init에서 그런 입력을 만드는 경로는 확인되지 않았다. 호환 overload가 의도적으로 floor 없이 게시하는 경우는 F-016으로 분리한다.
7. ECS 데이터의 소유자는 해당 World의 설정 엔티티다. Blob/별도 Persistent NativeContainer가 없어 사용자 코드의 Dispose 대상이 아니다. 로컬 managed 목록은 게시 시 버퍼로 복사된다. Sprite는 로드 시 존재/타입을 검사하고 경로만 저장하며, Sprite 객체를 ECS가 소유·복제하는 구조가 아니다. 설정 엔티티 삭제/World 종료 이후 버퍼를 보관해 읽는 계약은 없다. 실행 중 교체·재시작 정책은 구현/검증하지 않았다.

## 3. 상태 Reader/Writer와 의존 관계

| 상태 / Owner | Writer | Reader와 필요 시점 | 계약·결합 판단 |
| --- | --- | --- | --- |
| JSON 및 Resources Sprite | 프로젝트 입력 자산 | Loader의 메인 스레드 검증 | 엔진 자산 조회가 검증에 포함됨. 순수 JSON 검증도 Resources 환경 필요; 테스트 독립성/다른 공급원 도입 시 경계 분리 후보 |
| 검증된 managed 목록 | Loader 로컬 | PublishConfig가 동기 복사 | 공개 mutable DTO이므로 호출자가 검증 후 변경하지 않는 전제. runtime Init에서는 즉시 전달 |
| ResourceGenerationSettings / 설정 엔티티 | 정상 Init → PublishConfig | Init의 존재 가드, Bootstrap의 N×N 큐, Resource Command의 seed, Preview의 공유 seed | 같은 seed 공유는 필요한 계약. 설정 하나의 존재로 전체 완료를 판정하는 가정은 F-016 |
| ResourceGenerationConfigElement / 같은 엔티티 | PublishConfig | Resource Command → Utility, prefab 활성 목록·발생량/반경 계산 | 읽기만 수행. 자원 프리팹은 별도 DB 준비 계약이며 Sprite 검사로 보증되지 않음 |
| FloorGenerationSettings·Biome/Variant 버퍼 / 같은 엔티티 | PublishConfig | Preview query → FloorBiomeSampler | 전이 prefix와 바이옴별 연속 start/count는 컴포넌트 주석으로 공개된 데이터 배치 계약. Loader의 내부 foreach 순서 자체에 의존해야 하는 것은 아님 |
| InitialChunkLoad 큐 / 큐 엔티티 | Bootstrap | 후속 Chunk Command | `UpdateAfter(WorldGenerationConfigLoadSystem)`와 Resource 설정 RequireForUpdate가 게시 후 큐 작성 보장. 상세 큐 수명은 Q17 범위 |

**필요한 동기화:** Resources 조회와 ECS 구조 변경은 초기화 메인 스레드에서 끝내고, Bootstrap은 명시적 UpdateAfter로 기다린다. 자원 생성은 후속 Command에서 필요한 설정/DB/ECB 준비 조건을 확인한다. Preview는 같은 엔티티에 바닥 전체가 있음을 query로 확인한다. 설정은 게시 후 읽기 전용으로 사용하며 별도 공유 NativeContainer가 없으므로 이 범위에 공간 인덱스 Fence를 추가할 이유가 없다.

**불필요하거나 개선할 결합:** 소비자가 정상 전체 Publish와 자원 전용 Publish의 차이, 초기화의 가드 필드 하나까지 알아야 하는 것은 준비 완료 계약의 누수다. Loader의 반경 검증을 고치려면 Resource Utility의 `max + 1`·제곱 계산, 바닥 검증을 고치려면 Sampler의 int 곱셈까지 읽어야 하는 숫자 전제도 F-017이다. Resource Command의 실제 스폰은 **EndCommand**이며 EndStateApply라는 이전 주석은 [Q00 F-002](Q00.md)와 동일 문제다. 게시 자체에는 그 ECB의 세부 재생 순서를 알아야 할 이유가 없다.

- 우선순위와 이유: **P2**. 지원되는 호환 API 조합에서 불완전 설정을 완성된 상태와 구분하지 못한다. 현재 정상 Init 경로에서 항상 발생하는 결함은 아니다.
- 근거 수준 / 위치: **코드 확인**, Loader `:379–420` PublishConfig overload, LoadSystem `:20–24`, Bootstrap `:9–23`, Preview `:26–35`.
- 기대 계약과 출처: LoadSystem summary와 컴포넌트 계약은 자원·바닥을 같은 엔티티에 1회 게시한다. 준비가 끝났다면 해당 전체 데이터를 조회할 수 있어야 한다.
- 확인한 코드 동작 / 근거: 옛 Publish overload는 floor=null로 전달하여 자원만 만든다. 그 뒤 Init은 ResourceGenerationSettings singleton만 보고 비활성화한다. Bootstrap은 자원 설정만으로 진행할 수 있지만 Preview는 바닥 전체 query를 충족하지 못한다.
- 발생 조건과 영향: 테스트/다른 초기화 호출자가 기존 공개 overload로 미리 게시한 World를 정상 Init과 함께 사용할 때, 바닥 없이 자원 초기화만 가능한 상태가 계속 남는다.
- 미확인 사항 / 반대 근거: 현재 production 호출은 전체 overload 하나이고 호환 호출은 Phase4WorldGenerationConfigTests Test02에서 발견했다. 해당 테스트는 자원만 검사한다. 호환 게시 후 Init 조합은 실행하지 않았고, 자원 전용 World가 의도된 외부 지원 계약인지 미확인.
- 수정 방향 후보: 전체 설정의 준비 완료 판정을 명시하고 불완전 기존 엔티티의 거부/보충 정책 결정. 자원 전용 overload를 명시적 테스트/호환 전용 API로 분리하거나 전체 게시와 다른 상태로 표현. 단순히 또 생성하면 singleton 중복이 되므로 정책 없이 수정하지 않음.

- 처리 / 별도 수정 작업과 재검증 근거: **미결정**, 구현·테스트 변경 없음. 승인된 별도 수정 시 위 계약과 재검증 필요.

#### F-017 — 검증된 설정의 반경·전이 폭이 소비자의 정수 연산 한계를 넘을 수 있음

- 발견 단계 / 유형 / 평가 축: Q07 / 안정성 결함·유지보수 위험 / 안정성·유지보수성.
- 우선순위와 이유: **P2**. 정상 기본값은 안전하지만 허용 입력의 극단 값에서 생성 연산 오류·과도한 순회·잘못된 전이 판정이 가능하다.
- 근거 수준 / 위치: **코드 확인**, Loader `:223–227,267–272`, ResourceGenerationUtility `:104–110,151–166`, FloorBiomeSampler `:86–87`, GameConstants `:6`.
- 기대 계약과 출처: 검증된 설정을 게시하고 소비자는 이를 사용한다. 이미 maxAmount는 난수 exclusive upper bound를 고려하여 int.MaxValue를 거부하는 반면 반경·셀 변환에는 대응 경계가 없다.
- 확인한 코드 동작: `minRadius=1, maxRadius=int.MaxValue`는 반경 조건을 통과하지만 소비자의 `maxRadius + 1`은 int 표현 범위를 벗어난다. 제곱 거리에도 int 곱셈/합산을 사용하며 큰 반경에 안전하지 않다. 후보 청크 순회도 반경에 따라 급증한다.
- 발생 조건과 영향: 다른 필드가 유효한 큰 반경 설정. 오류의 정확한 예외/지연 양상은 실행하지 않았다. 바닥의 `region=transition=134217728`도 검증 조건을 만족하지만 `transition * 16 * 0.5f`는 float 변환 전에 int 곱셈을 한다. unchecked 정수 결과는 음수가 되어 양수 경계 거리와 비교 시 전이 처리를 건너뛸 수 있다. checked 환경이면 오버플로 예외 가능성이 있으며 Unity 실행 양상은 미확인이다.
- 근거 / 반대 근거: 실제 JSON은 반경 1–2, region 3, transition 2라 이 조건을 만들지 않는다. 문제는 입력 허용 범위와 소비 산술 전제의 불일치이며 현재 기본 맵이 잘못됐다는 판정이 아니다.
- 수정 방향 후보: 실용적인 최대 반경/초기 크기/region·transition 범위를 설계 계약으로 결정하고, 소비자의 덧셈·제곱·셀 변환도 안전한 자료형/연산 순서로 검토. 계산 방식의 숨은 한계를 Loader 여러 곳에 임의 숫자로 복제하지 않음.
- 필요한 추가 검증: 큰 맵을 실제 생성하지 않는 경계 입력 거부 테스트, 허용 최대값의 산술 안전성 테스트, 전이 폭 변환 단위 테스트 제안. 기존 후보에 이 문제를 겨냥한 사례는 확인되지 않아 새 테스트를 작성/실행하지 않음.
- 처리 / 별도 수정 작업과 재검증 근거: **미결정**, 코드·Config 변경 없음. 제한값은 사용자 설계 결정 후 별도 수정/검증.

## 7. 남은 질문·제안과 완료 확인

- **설계 질문:** 자원 전용 World와 Publish overload를 계속 지원할 것인가? 지원한다면 전체 초기화와 다른 준비 상태로 구별할 것인가, Init이 바닥을 보충할 것인가?
