## 2. 입력→검증→게시·조회 흐름

**[코드 확인]** `InitializationSystemGroup`의 managed Init가 메인 스레드에서 동기적으로 입력을 읽고 Persistent Blob을 완성한 후 EntityManager로 ItemRegistry를 직접 게시한다. ECB 요청/재생 경로는 없다. 게시 후 `Enabled=false`이며 자동 재시도·핫 리로드는 구현되지 않았다.

1. `OnUpdate:36–44`는 Registry singleton이 있으면 그 Value의 유효성을 검사하지 않고 비활성화한다. 없으면 공개 Initialize 함수를 부르고 반환 Blob을 private 필드에 보관한다.
2. `InitializeItemRegistry:60–76`의 null/빈 override는 파일 읽기로 이어진다. 첫 경로는 `Application.streamingAssetsPath/ItemConfig.json`, 다음은 `Application.dataPath/StreamingAssets/ItemConfig.json`이다. 파일 부재/빈 내용은 기본 빌더, 파일 접근 예외는 warning 후 기본값으로 간다. 공백 문자열은 JSON 파싱 경로다.
3. `BuildBlobAssetFromJson:98–126`은 DefaultMaxStack만 양수인지 검사하여 아니면 50을 쓴다. Items가 없으면 개별 override 없이 진행한다. 품목 이름 파싱은 대소문자를 구분하지 않고, 실패한 이름은 경고 없이 무시한다. Enum.TryParse 뒤 정의된 enum인지 확인하는 검사는 없다. 중복 품목은 Dictionary의 마지막 값이 남는다. 개별 MaxStack의 0·음수·None 재정의는 검증하지 않는다(F-007).
4. 파싱 예외는 warning을 남기고 빌더를 계속 호출한다. catch에서 defaultMaxStack/customStacks를 초기 상태로 되돌리지는 않는다. 따라서 루프 중 예외가 생기는 경우 앞서 읽은 값이 남는 코드 구조다. Unity JsonUtility가 null 배열 원소를 실제로 어떻게 복원하는지와 그 예외 경로는 **미확인**이며, 부분 게시가 실행 재현됐다고 판정하지 않는다.
5. `BuildBlobAsset:137–165`는 현재 enum 개수 10만큼 배열을 만들고 `(ItemTypeEnum)i`에 대응시킨다. 각 원소는 override 또는 품목별 기본값이다. Blob 작성 완료 전에는 Registry를 바꾸지 않는다. 공개 Initialize는 기존 singleton이 있으면 Value를 교체하고, 없으면 엔티티를 생성한다. 빌드 뒤 게시 예외 시 Blob을 해제하는 rollback은 없다.
6. `GetMaxStack`은 배열 범위 안이면 저장값, 범위 밖이면 DefaultMaxStack 또는 명시 fallback을 반환한다. 기본값 조회를 통한 enum 유효성 검증 기능은 없다. 현재 enum은 연속 값이어서 배열 인덱스 계약과 일치한다. 값에 구멍/별칭을 추가하는 변경은 이 계약을 재검토해야 하며 현재 결함으로 등록하지 않는다.

### 기본값은 세 가지 상황을 구분해야 함

| 상황 | 실제 값 [코드 확인] |
| --- | --- |
| 현재 JSON 파일 | None=0, 광석 4종=50, Iron/Copper/Stick 4종=100, Drone=1, DefaultMaxStack=50 |
| 파일 없음 / 품목 override 없음 | GetDefaultMaxStackFor가 위 품목별 값을 사용. DefaultMaxStack=64로 설정해도 현재 enum의 알려진 품목들은 0/50/100/1을 유지 |
| 범위 밖 enum 조회 | 기본 overload는 Blob.DefaultMaxStack, 다른 overload는 전달된 fallbackMaxStack. byte enum이므로 실제 범위 밖 예는 250 |
| Registry 자체가 없거나 Value가 생성되지 않음 | Reservation/Miner/Crafter/Validation이 각각 50으로 처리. 품목별 기본 Blob의 Iron=100, Drone=1과는 다름 |
| BuildDefaultFallbackBlobAsset에 직접 인자 전달 | 인자의 양수 검사 없음. 현재 런타임 호출은 기본 50만 사용하므로 임의 음수 인자 문제를 실제 런타임 발생으로 확대하지 않음 |

`DefaultMaxStack`은 기존 모든 품목의 기본값을 일괄 변경하는 설정이 아니다. 현재 Test03도 이 구분을 assertion으로 표현한다. Registry 부재 시 50은 모든 소비자에서 동일하지만 각 위치에 복제돼 있다. 품목별 기본값과 다른 부재 정책을 의도했는지 질문으로 남기며, 현재 정상 초기화 경로에서 부재 상태가 계속된다고 주장하지 않는다.

## 3. 상태 Owner·Reader/Writer·수명

| 상태 / Owner | Writer·해제 책임 | Reader | 가시성·필요한 동기화 |
| --- | --- | --- | --- |
| DTO·Dictionary·BlobBuilder / Init 호출 | 호출 안에서 작성, Temp builder는 using으로 해제 | 같은 빌드 호출 | 외부 시스템이 파싱 순서·Dictionary 내부를 알 필요 없음 |
| Persistent ItemRegistryBlob / 생성 호출 | 빌더가 작성, 게시 후 정상 코드에는 내용 Writer 없음 | Reservation/Miner/Crafter Job, Validation | 최초 게시 완료 후 불변 읽기. 매 프레임 쓰는 공간 맵과 달라 별도 Reader/Writer Fence가 필요한 상황은 확인되지 않음 |
| ItemRegistry.Value / 게시 주체 | Initialize가 Create/Set. OnUpdate는 기존 값이면 소유권 인수 없이 종료 | 소비 시스템이 매 OnUpdate 값을 복사해 Job에 전달 | Initialization→Simulation의 준비 경계. singleton 존재와 Blob.IsCreated는 별도 조건 |
| `_blobReference` / ItemConfigInitSystem | 자동 초기화 반환값만 저장, OnDestroy에서 Dispose | Init 자신의 해제 코드만 | 다른 시스템은 private 필드를 모르고 읽을 수 있음. 살아 있는 Job보다 Blob 수명이 길어야 함 |
| 공개 빌더/Initialize 반환 Blob / 외부 호출자 | 테스트가 보관하고 직접 Dispose | 테스트 및 해당 World의 Registry | 자동 Init 소유와 별개. Initialize 재호출 시 교체·이전 Blob 회수·reader 완료 책임은 API 주석에 명시되지 않음(F-008) |
| 슬롯 수 / Storage 소유 도메인 | 건물 구성 측이 SlotCount 작성 | Reservation | MaxStack은 슬롯당 같은 품목의 개별 엔티티 수 제한. SlotCount·MaxStorageSlots와 다른 축 |

자동 초기화→World 종료라는 정상 경로는 소유 핸들이 한 곳에 모여 있다. 테스트의 static 초기화 경로는 `_blobRef.Dispose()` 후 World.Dispose하며, Test06은 Job.Complete를 먼저 수행한다. 테스트가 Init 시스템을 생성해도 Test05 외에는 Init.Update를 호출하지 않으므로 자동 소유와 테스트 소유를 중복 취득하지 않는다.

**[미확인]** 실제 World 종료에서의 reader 완료와 메모리 해제, Init만 중도 제거한 뒤 소비자가 남는 경우, 외부 singleton의 수명은 이번에 실행 검증하지 않았다. OnDestroy에 명시적인 전체 reader 완료 코드가 없다는 사실만으로 기본 World 종료가 unsafe라고 단정하지 않는다. Registry를 런타임 교체/해제할 때는 복사된 Blob 참조를 들고 있는 Job까지 종료를 보장해야 하며, 단순 SetComponentData만으로 그 수명 계약이 완성되지는 않는다.

| Init 내부 파일 읽기·JSON 파싱·Blob 구성 메서드를 재구성 | 입력 해석·fallback 결과, ItemRegistry/배열 모양·GetMaxStack 결과·초기 게시 시점·수명 유지 | Init 내부와 해당 단위 테스트만 검토. Reservation/Miner/Crafter/Validation의 내부 순서·Job 코드는 수정할 필요 없음 |
| Miner의 생산 여유 검사 Job을 내부 분할 | 같은 Registry 값을 읽고 같은 결정을 내림 | Miner의 핸들 결합만 변경. Init나 다른 Reader를 함께 수정할 이유 없음 |
| Init의 할당 관리 방식을 바꾸되 1회 게시·반환 API를 유지 | 외부 호출자의 소유권 의미까지 유지해야 함 | Reader는 영향 없음. 공개 Initialize의 교체 경로는 기존 `_blobReference` 소유와 분리돼 있어 테스트·호출자 해제 책임을 먼저 명시해야 함(F-008) |

반대로 핫 리로드 추가, 부재 시 50을 품목별 기본값으로 변경, DefaultMaxStack이 모든 품목에 적용되도록 변경, 배열 표현 제거는 공개 수명·동작·데이터 계약 변경이다. 그때 소비자를 검토하는 것을 숨은 내부 결합의 증거로 세지 않는다. V1과 동일 범위를 비교하지 않았으므로 V1 대비 결합 감소도 확정하지 않는다.

## 5. 발견 문제

기존 F-001~F-006의 제목과 관련 내용을 확인했다. 이번 세 문제는 기존 문제와 원인·수정 경계가 달라 F-007~F-009로 등록한다. [Q03의 생성 경계 MaxStack 미검사](Q03.md)는 같은 품목 용량의 관련 경계이며 신규 중복 문제로 등록하지 않는다. Lifecycle이 모든 용량 검증을 대신할지 여부는 Q03의 원래 질문을 유지한다.

#### F-007 — 검증되지 않은 MaxStack을 게시하여 생산·입고의 용량 판단이 엇갈림

- 발견 단계 / 유형 / 평가 축: Q04 / 안정성 결함·설계 판단 필요 / 안정성·V2 적합성.
- 우선순위와 이유: **P2**. 잘못된 설정 하나가 생산을 막고 저장 슬롯의 상한 위반을 허용할 수 있다. 현재 제공 JSON은 유효하여 정상 설정의 장애로 확대하지 않는다.
- 근거 수준: **코드 확인**. 무효 JSON 값에 대한 실행 재현은 미확인.
- 위치: `ItemConfigInitSystem.cs:108–115,152–160`; `ItemConfigComponents.cs:31–38`; `BuildingStorageInputReservationSystem.cs:125–130,165–190`; `MinerDecisionSystem.cs:132–149`; `CrafterDecisionSystem.cs:187–195`; `WorldInvariantValidationSystem.cs:707–715`.

Reservation은 빈 슬롯을 고를 때 MaxStack을 비교하지 않아 다른 입고 조건을 만족하면 첫 1개를 배정한다. 직접 후속 `BuildingItemStorageApplySystem.cs:131–162`도 MaxStack 재검사 없이 승인 슬롯에 StoredItemElement를 추가하므로 Validator 기준으로는 1개가 상한 초과다.
- 발생 조건과 영향: 해당 무효 설정이 게시되고 정상 입고/생산 경로가 그 품목을 사용할 때. 생산 정체와 슬롯 제한 불일치. ItemType 오타·중복·None override도 별도 오류 없이 처리되지만 허용 정책 자체는 결정이 필요하다.
- 미확인 사항 / 반대 근거: 0을 품목 비활성화 의미로 의도했는지 불명확. 그렇게 의도했더라도 빈 슬롯 경로와 같은 의미를 공유하지 않는다. 현재 파일의 실제 품목은 모두 양수다.

- 필요한 추가 검증: 실제 품목 0·음수·누락 MaxStack, None 재정의·잘못된 이름·중복의 게시 정책, 빈 슬롯 예약과 생산 판단의 동일 계약 검사. 기존 Phase3ItemConfigTests에는 해당 assertion 없음.
- 처리 / 별도 수정 작업과 재검증 근거: 미결정 / 수정·테스트 추가 없음.

#### F-008 — 공개 초기화의 교체 경로에 Blob 소유권·회수·reader 종료 계약이 없음

- 발견 단계 / 유형 / 평가 축: Q04 / 유지보수 위험 / 안정성·유지보수성·V2 적합성.
- 우선순위와 이유: **P2**. 공개 함수는 기존 singleton 교체를 허용하지만, 안전하게 재사용하려면 시스템의 private 소유 필드와 reader 수명을 알아야 한다. 정상 1회 초기화의 현재 메모리 누수로 단정하지 않는다.
- 근거 수준: **코드 확인**, 재호출·해제 후 접근의 실행 증상은 미확인.
- 위치: `ItemConfigInitSystem.cs:32–53,56–92`; `Phase3ItemConfigTests.cs:23–30,140–156`.
- 기대 계약과 출처: Persistent Blob의 명확한 할당/해제 소유자, V2 §14의 공개 계약을 통한 협력. 현재 주석은 초기화·입력 설명만 있고 반환값 Dispose 책임·재호출 조건을 설명하지 않는다.
- 확인한 동작: 자동 경로는 반환값을 `_blobReference`에 넣어 OnDestroy에서 해제한다. static Initialize는 새 Blob을 만들고 기존 Value를 교체하지만 이전 참조를 반환/해제하지 않으며 private 필드도 갱신하지 않는다. 사전 등록된 Registry를 보면 OnUpdate는 소유권 인수 없이 종료한다.
- 발생 조건과 영향: 자동 초기화 뒤 static Initialize를 다시 호출하면 시스템은 옛 Blob을 계속 소유하고 새 Blob은 caller 관리가 필요하다. caller가 반환 참조를 잃으면 새 할당이 회수되지 않을 수 있고, 외부 소유 옛 Blob을 저장하지 않고 덮으면 회수 경로를 잃을 수 있다. caller가 임의로 이전 Blob을 Dispose하면 기존 Job snapshot이나 자동 owner의 해제와 충돌할 수 있다.
- 미확인 사항 / 반대 근거: 런타임의 외부 재호출자는 검색 범위에서 없음. 현재 테스트들은 반환 Blob을 직접 해제하고 Test06은 읽기 Job을 완료한다. 지원되지 않은 핫 리로드 기능 자체를 결함으로 요구하지 않는다.
- 수정 방향 후보: 초기화 전용 API로 제한할지, 교체를 지원할지 명시. Blob 생성과 게시·소유를 분리하거나 단일 소유 경계를 제공. 단순히 기존 Blob을 무조건 Dispose하는 수정은 제안하지 않는다.
- 필요한 추가 검증: 사전 등록 singleton, 반복 호출, automatic→static 교체, World 종료·시스템 중도 제거, 게시 실패 때 생성 Blob 회수, 진행 중 reader가 있을 때 교체 금지/완료 규칙.
- 처리 / 별도 수정 작업과 재검증 근거: 미결정 / 수정·실행 재현 없음.

- 발견 단계 / 유형 / 평가 축: Q04 / 검증 공백·유지보수 위험 / 유지보수성.

### 7.1 최초 시도 — 연결 차단 기록

**[CLI 확인] 2026-09-29 10시대 KST**에 설치된 Unity CLI 스킬과 AGENTS 절차로 연결부터 확인했다. 아래는 최초 시도의 기록이다. 당시 명령의 최종 프로세스 종료와 JSON을 확인했으며 비동기 컴파일·테스트 제출은 없었다.

| 명령·환경 | 최종 결과 |
| --- | --- |
| `unity.exe status --project-path <프로젝트> --format json` / 제한 계정 | exit 1, success=false, `STATUS_NO_INSTANCES`, count=0. 실행 Editor 조회 실패로 누락 가능하다는 warning 1개 |
| 같은 `status` / 승인된 권한 상승 진단 | exit 1, success=false, `STATUS_NO_INSTANCES`, count=0, warnings=[] |

`pipeline list`가 실행 중 Editor를 확인했으므로 Editor가 꺼져 있다고 결론내리지 않는다. safeMode=null 및 summary=0은 Safe Mode 확정 근거가 아니며 접속 불가의 근본 원인은 미확인이다. 같은 응답의 `updateAvailable=true`는 연결 실패 원인으로 단정하지 않았다. 패키지 업데이트·설치·Editor 재시작·별도 headless 인스턴스로 우회하지 않았다. 자동 승인 검토의 거절은 없었다.

- 예정 검증: `Tools/Codex/Verify-Unity.ps1 -TestFilter @(<위 3개 메서드>)`. 래퍼는 ready Editor를 먼저 요구하므로 현재 연결 진단에서 멈췄다. 래퍼와 그 내부 recompile/run_tests를 호출하지 않았다.
- 컴파일 최종 상태: **미실행**. 읽기 전용 분석을 위한 별도 재컴파일 없음; 어셈블리 최신성·컴파일 오류 유무는 미확인.
- 테스트 최종 상태: **미제출 / 연결 차단**. Passed / Failed / Skipped / Inconclusive 모두 **해당 없음**. 0건 통과로 기록하지 않는다.
