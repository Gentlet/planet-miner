## 2. 철거 수명과 참조 처리

### 2.1 검증과 중복 요청

| 대상 조건 | 처리 |
| --- | --- |
| Entity.Null 또는 BuildingType 없음 | 요청만 ECB Destroy. 이미 파괴된 Entity도 이 경로 |
| Type=None 또는 ConstructionSite | 요청만 소비. None은 같은 Job의 선행 철거 마킹에도 사용; 현장은 Cancel 요청의 책임 |
| IndestructibleBuilding 보유 또는 Type=MainFacility | 요청만 소비, 건물 보존. 태그와 타입은 독립 거부 조건 |
| 나머지 대상 | 원래 buildingType을 지역 변수로 보존하고 실제 BuildingType.Type을 **즉시 None**으로 변경한 후 반환·환급 기록 |

철거 Job은 `.Schedule` 단일 워커다. 첫 요청의 None 쓰기는 ECB가 아니라 ComponentLookup 직접 쓰기이므로 후속 동일 대상 요청이 즉시 관찰한다. 건물/요청의 실제 Destroy는 뒤의 Playback까지 지연된다. 원래 타입을 지역 변수에 보존하여 None 마킹 뒤에도 환급 Config 행과 Belt 여부를 판별한다.

따라서 정상 처리에서는 한 대상의 반환/환급 명령이 한 번만 기록된다(**코드 확인**). Test06은 두 요청 모두 소비되고 건물이 사라지는 사실을 실행 확인하지만, 재료·내용물이 없는 PowerPole이므로 **중복 환급 수량을 직접 확인하지는 않는다**. None 마킹 뒤 ECB 실패 시 원상복구도 없다. 주석의 “단일 ECB 트랜잭션”을 rollback 보증으로 해석하지 않는다. Count/정의 밖 enum 전체를 검사하는 거부 로직은 없다.

### 2.2 기존 Stored/Product 아이템

- 대상의 GridPosition이 있으면 그 좌하단 좌표, 없으면 `(0,0)`을 반환 위치로 사용한다. footprint 안의 분산 배치나 타일 용량 검사는 하지 않는다.
- StoredItemElement와 ProductItemElement를 각각 순회하며 non-Null ItemEntity에 `Owner=WorldItem`, `DisableRendering` 제거, GridPosition/LocalTransform의 건물 좌표 설정을 ECB에 기록한다. 기존 엔티티를 보존하는 반환이며 새 엔티티를 만드는 환급과 다르다.
- 원래 버퍼를 Clear하거나 각 요소를 제거하지는 않는다. 최종 건물 Destroy가 소유 버퍼 자체를 제거하므로 정상 경로에서 그 버퍼의 참조가 남지 않는다. 기존 반환품의 이동/Destroy/Transfer/입고 결정 상태는 여기서 초기화하지 않는다. 정상 저장품은 입고/생성 경계에서 이동이 비활성화된다는 계약에 의존한다.
- 아이템의 생존·현재 Owner·다른 버퍼의 중복 참조를 다시 검사하지 않는다. 잘못된 죽은 참조 또는 다른 Owner 버퍼에 남은 참조까지 철거가 정리하는 기능은 아니다. 이 전제 위반은 기존 [Q02 F-003](Q02.md#f-003--공사-수령이-동일-아이템-재사용과-기존-소유-버퍼를-검증하지-않음) 같은 상류 경로와 구분한다. 현재 정상 철거가 자체적으로 복제한다고 주장하지 않는다.

일반 물류 Apply 뒤 실행하므로 같은 틱 입고로 **실제 buffer.Add된** 항목은 철거 순회에 포함되고, 출고로 제거된 항목은 다시 반환하지 않는다. 그러나 Owner/렌더 태그의 최종 합의와 **ECB에만 Append가 대기 중인 새 아이템**은 이 순서만으로 해결되지 않는다(§5).

### 2.3 벨트와 외부 참조

철거된 Belt의 기준 좌표를 TempJob NativeList에 모으고, 이어지는 Cleanup Job이 **활성 BeltMovementState + GridPosition** 대상의 최신 GridPosition과 대조한다. 일치하면 이동 enable을 false로 기록한다. 현재 ECS 좌표를 읽으므로 이전 Synchronization의 ItemSpatialIndex가 이동 전 셀을 가리키는 문제를 피한다. 철거가 맵을 직접 수정하거나 Fence를 추가로 사용하지 않는다.

Cleanup은 아이템을 Destroy하거나 Owner/위치/진행도/시각 위치를 다시 쓰지 않는다. 정상 월드 아이템이 그 자리에 남는 계약이다. 비활성 이동 상태의 잔여 progress가 후속 입고에 사용되는 문제는 이미 [Q14 F-032](Q14.md#f-032--입고-판단이-movement-enable을-무시해-비활성-월드-아이템의-잔여-progress로-입고를-승인함)에서 다뤘다. 이를 이번 철거의 새 결함으로 세지 않는다.

EndStateApply 후 Building/Belt/Item 공간 Sync가 원본을 다시 등록한다. 건물/벨트 엔티티가 제거돼 점유는 빠지고 반환품은 Owner=Null로 Item 맵 대상이 된다. **BuildingSpatialIndex의 점유 해제만 Test07에서 실행 확인**했으며 세 맵을 모두 실행 검증한 것은 아니다.

다른 라우터의 InputBelt/OutputBelt 필드를 철거가 전역 검색해 지우지는 않는다. 다음 Splitter/Merger Decision은 `GridPositionLookup.HasComponent`로 파괴된 Entity를 검출하여 맵에서 기준 벨트를 다시 찾고, 대안이 없으면 결정을 비활성화한다. 영속 참조 자체는 성공한 RoutingApply 전까지 남을 수 있지만 이를 즉시 무효 역참조하는 코드는 아니다. 이 재선정의 실제 철거 연속 프레임 실행은 미확인이다.

## 3. 건축 비용 환급과 생성 계약

환급은 건물에 보관한 과거 지불 내역이 아니라 **철거 시점 Config의 BuildingConstructionMaterialElement** 중 원래 타입이 같은 모든 행을 읽는다. Quantity마다 새 아이템 하나를 건물 좌표에 만든다. 기존 Stored/Product 반환량과 별개다. 동일 품목의 여러 행도 합쳐져 모두 처리된다. Config에는 BuildingConfig와 BuildingConfigElement가 있어야 시스템 query에 잡히며, 재료 버퍼가 없으면 환급 기록이 없다.

| 환급 입력 | 확인한 동작 | 근거 / 한계 |
| --- | --- | --- |
| Config/재료 버퍼/해당 타입 행 부재 | 기존 내용물 반환·건물 파괴, 신규 비용 환급 없음 | 코드 확인. 게시 실패와 의도적 없음 구분은 기존 Q05 정책 질문 |
| 정상 비용 + Item DB 없음 | fallback archetype으로 Quantity개 생성 | Test03 Iron3개 월드/좌표/표시 확인 |
| 정상 비용 + DB에 정상 prefab | Instantiate하여 타입·소유·위치·상태 주입 | Test09 모의 prefab Iron2개 확인. 실제 Baker/렌더링 보장 아님 |
| Item DB 있음 + 해당 prefab 누락/Null | 오류를 기록하고 **해당 행만 continue**, 다른 행은 계속 처리; 건물/요청 파괴 진행 | Test10은 누락 Iron5개에 대해 건물 소멸·아이템0·예상 오류 확인. 혼합 정상/누락 행은 미실행 |

환급 prefab helper는 ItemIdentity/LocalTransform에 Set하고 Grid/Owner와 Destroy·Transfer·BeltMovementState·BeltMovementDecision·입고 결정을 Add한다. enableable 네 상태를 false로 만든다. fallback은 같은 구성의 archetype에 Set하고 같은 enable 상태를 초기화한다. Owner는 WorldItem이며 DisableRendering은 새로 추가하지 않는다. prefab에 원래 있는 해당 태그를 제거하는 명령도 없으므로 prefab schema/표시 전제는 기존 [Q08 F-019](Q08.md#f-019--등록-경계가-prefab-식별-정보와-생성-전제의-적합성을-검증하지-않음) 범위다.

환급은 ItemLifecycle에 SpawnItemRequest를 전달하지 않고 BuildingLifecycle 내부의 두 helper에서 Item 초기화 규칙을 복제한다(**F-020**). 같은 ECB로 환급/철거를 기록하는 이점이 있어 요청 전환이 자동으로 더 낫다고 결론 내리지 않는다. DB 단일성 전제(**F-018**)와 Q27에서 확인한 무조건 context 조회도 남는다. 반대로 철거만 있어도 사용하지 않는 Building DB singleton을 미리 조회하므로 Spawn/철거의 준비 전제가 불필요하게 엮여 있다.

“100% 환급”은 현재 비용 행이 정상적으로 스폰되는 경우의 동작이다. 미등록 prefab에 대해 환급을 영구 생략하는 현재 Test10 정책과 완료 손실 **F-024**는 다른 경계다. 이 의도적으로 검사된 철거 정책을 자동으로 F-024와 같은 결함으로 등록하지 않고, 제품 정책 질문으로 남겼다. 현재/과거 비용 변경이나 제작 진행 중 선소비 재료의 보상 규칙도 임의로 추가하지 않았다.

## 4. 상태 Reader/Writer와 의존성 판정

| 상태 / 경계 | Writer → Reader / 가시성 | 판정 |
| --- | --- | --- |
| DemolishBuildingRequest | 외부 생산자 → 단일 Demolish Job → ECB Destroy | 단발 소비 필요. 현재 runtime producer는 발견 안 됨 |
| BuildingType | Spawn 초기화 → Demolish None 직접 쓰기 → 같은 Job 후속 요청 | 중복 방지에 필요한 live 상태. ItemLifecycle이 이 내부 마커를 알아서 회피한다고 가정하면 안 됨 |
| Stored/Product 참조 | StorageApply 직접 Add/Remove → 철거 RO 순회 | 물류 후 실행과 ECS Job 의존은 필요. 아직 재생되지 않은 Append까지 읽는 경계는 아님 |
| Owner / DisableRendering | OwnershipApply는 Owner 직접/태그 ECB; 철거는 둘 다 ECB | 같은 최종 상태의 Writer 간 합의 부족. **F-004** |
| GridPosition / movement enable | Execution·Routing·StorageApply 즉시 쓰기 → Cleanup RO query → disable ECB | 최신 위치를 읽기 위한 명시 선행·Job 연결은 필요. 공간 맵의 내부 재등록 순서를 몰라도 됨 |
| ProductResult / 새 아이템 참조 | Execution 결과 → ItemLifecycle ECB 생성/Append → 소유 건물 | 건물 폐기와 대기 생성 인계 미정. **F-005**, 단순 Job 완료로 해결 안 됨 |
| 비용/Item DB | 설정/Baker 게시 → Refund 읽기·Item 생성 | 타입/수량/prefab 공개 계약은 필요. Item 세부 초기화 복제는 **F-020** |
| DemolishedBeltPositions | Demolish Add → Cleanup 읽기 → 의존 Dispose | 같은 시스템 내부 임시 전달이며 외부 도메인이 목록을 알 필요 없음 |
| 건물/아이템 원본 → 공간 맵 | EndStateApply 적용 → Sync Clear/Populate | 파생 인덱스 Owner 유지. 철거가 동기화 시스템 Update를 호출하지 않음 |
| 라우터의 기준 벨트 참조 | RoutingApply 저장 → Decision 유효성 검사·재선정 | 공개 Entity 생존/맵 계약으로 대응. 철거의 라우터 전역 순회는 현재 필요 없음 |

시스템의 순서는 `RoutingApply/BuildingItemStorageApply → BuildingLifecycle`로 명시돼 있다. 내부는 `state.Dependency → Demolish → Cleanup → (Spawn)`이고 마지막 handle을 ECB producer와 state.Dependency에 등록한다. 이 동기화는 제거할 대상이 아니다. ItemOwnership/ItemLifecycle과 BuildingLifecycle 사이의 상대 시스템 순서는 명시돼 있지 않다. Job 데이터 접근의 안전한 완료와 **서로 다른 ECB 명령의 최종 의미**는 별개다.

공개 계약을 유지하는 내부 변경의 영향 사례:

1. Cleanup의 좌표 탐색을 다른 내부 자료구조로 바꾸되 같은 최신 위치·최종 이동 비활성 결과와 수명을 유지하면 물류 시스템은 바뀔 필요가 없다. 현재 아이템×철거 좌표 순회의 실제 비용은 측정하지 않아 성능 결함으로 등록하지 않는다.
2. StorageApply의 내부 탐색을 바꾸어도 같은 시점에 source membership/목적지 buffer/위치를 확정하면 철거는 그대로다. 그러나 최종 StateApply 결과만 같게 하면서 buffer 갱신을 지연 ECB로 옮기면 현재 철거 순회가 새 항목을 놓칠 수 있다. 이는 공개 중간 가시성 계약을 먼저 명시할 필요가 있는 F-005 계열 결합이다.
3. Item의 공개 생성 결과를 유지한 초기화 helper 리팩터링은 건물 도메인이 몰라도 되어야 한다. 현재 환급 구현은 별도 경로여서 같은 생성 규칙 변경 시 archetype과 두 helper의 동기화 점검이 필요하다(F-020). 다만 새 필수 ECS 컴포넌트 자체를 추가하는 것은 공개 구성 계약 변경이며 정상적인 변경 전파도 포함한다.
4. 철거 반환 결과를 같게 유지하려는 내부 스케줄 변경도 Ownership의 Add/Remove 태그와 ECB 생성 순서를 알아야 안전하다(F-004). 명시적인 최종 소유/표시 인계가 필요하며 모든 시스템을 합치거나 임의의 순서 속성 하나를 해결책으로 확정하지 않는다.
5. 생산품 생성을 철거보다 먼저 스케줄해도 deferred Append는 반환 목록에 나타나지 않는다(F-005). 순서를 바꾸는 대신 생산/스폰 접수와 소유자 폐기를 조정하는 공개 수명 계약이 필요하다.
