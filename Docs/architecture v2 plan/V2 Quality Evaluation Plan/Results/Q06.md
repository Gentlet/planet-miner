## 2. 입력→Blob→게시와 실패 정책

### 2.1 입력과 변환

**[코드 확인]** `InitializeRecipeRegistry`의 null/빈 override는 Resources 경로 `Config/CrafterRecipeConfig`를 사용한다. 파일이 없거나 TextAsset.text가 null/빈 값이면 warning 후 기본 5종 Blob을 만든다. 직접 JSON 빌더에서 역직렬화 결과/recipes가 null 또는 빈 목록이면 기본 Blob으로 간다. 명시적으로 빈 recipes를 주어 빈 Registry를 만드는 기능은 없다.

JSON 빌더는 FromJson 예외를 catch하지 않는다. 따라서 ‘입력 부재 fallback’이 ‘모든 잘못된 JSON의 fallback’을 뜻하지 않는다. malformed JSON·null 행을 실제 Unity가 어떻게 처리하는지는 이번 후보 테스트가 검증하지 않는다. 빌드 실패 시 Init의 `_blobReference = ...; Enabled=false`까지 도달하지 못할 수 있으며, Unity의 시스템 예외 후 갱신 정책까지 추정하지 않는다.

| 데이터 | 현재 변환 계약 | 검증/기본값의 한계 |
| --- | --- | --- |
| id | 입력 int 그대로 RecipeBlob.Id에 기록 | 0/음수/중복 검사 없음(F-015) |
| craftTime | `>0`이면 그대로, 아니면 1초 | 양의 Infinity 같은 비유한 값은 별도 검사 없음. Execution은 추가로 최소 0.01초를 적용하므로 Blob 값과 실제 시간 계산은 같은 개념이 아님 |
| ingredients | null이면 길이 0, 입력 순서대로 행 생성 | 품목 TryParse 성공 여부/정의된 enum/None 검사 없음(F-013), 품목 중복 유지(F-014). amount≤0는 1로 보정 |
| 주생산품 | Outputs[0], IsByproduct=false, 항상 한 행 할당 | 무효/누락 이름도 None 등으로 게시 가능. outputAmount≤0는 1로 보정 |
| byproducts | 입력 순서대로 Outputs[1..N], IsByproduct=true | 품목 검증 없음. amount≤0는 1. 같은 품목의 다른 출력 행은 다른 슬롯으로 처리되므로 재료 중복과 같은 결함으로 취급하지 않음 |
| conditions | DTO에서 받을 수 있지만 사용하지 않고 ConditionFlags=0 | 컴포넌트는 예약 필드라고 명시. 현재 조건 판정 Reader 없음. 미구현 조건 시스템 자체를 결함으로 등록하지 않되 비어 있지 않은 입력의 정책은 질문 |

현재 JSON은 양의 고유 ID 1~5, 유효 재료 6행, 레시피당 주생산품 1종이며 부산물 없음·conditions 빈 목록이다. outputAmount 생략은 현재 빌더의 양수 보정과 결합되어 1이 된다. 구성은 Iron_Ore→Iron(1초), Copper_Ore→Copper(1초), Iron 2→Iron_Stick(1.5초), Copper 2→Copper_Stick(1.5초), Iron_Stick 2+Copper_Stick 2→Drone(4초)다. 기본 빌더도 같은 5개 매핑을 직접 구성한다. 두 정의의 자동 동기화나 동일성 테스트는 없다.

### 2.2 원자성·게시·조회

Temp BlobBuilder의 using 안에서 전체 Recipes/Ingredients/Outputs를 구성한 뒤 마지막에 Persistent Blob을 반환한다. 게시 전 실패면 이 함수가 Registry를 부분 갱신하는 경로는 없다. 다만 유효성 검증이 부족해 ‘완성된 Blob’과 ‘제작 가능한 레시피’는 다르다.

Init의 OnCreate는 base 호출뿐이며 **OnUpdate**에서 최초 게시한다. 기존 RecipeRegistry singleton이면 Value.IsCreated를 확인하지 않고 비활성화한다. 공개 Initialize는 EntityManager로 기존 Value를 교체하거나 새 singleton을 직접 생성한다. ECB를 통하지 않는다. 빌드 뒤 게시 예외 때 새 Persistent Blob을 회수하는 try/finally는 없다.

Registry의 ID/주생산품 검색, Recipe의 재료 검색은 모두 선형 첫 일치 반환이다. 첫 일치 반환 자체는 명확한 구현이며 성능 병목으로 판정하지 않는다. 유일성 보장 없는 ID는 뒤 레시피 접근을 가리며(F-015), TryFindIngredient도 중복 수량을 합산하지 않는다(F-014). runtime 제작은 TryFindIngredient를 호출하지 않고 직접 행 순회를 한다는 점을 구분한다.

## 3. 주생산품·부산물 계약과 Reader/Writer

**[코드 확인]** JSON 빌더는 slot 0에 주생산품, 나머지에 부산물을 배치한다. TryGetPrimaryOutput은 IsByproduct=false인 첫 행을 찾고 없으면 Outputs[0]을 반환한다. 그러나 실제 Decision/Execution은 IsByproduct를 읽지 않고 **출력 배열 인덱스를 슬롯 번호로 사용**한다. ProductItemOutputDecision도 SlotIndex=0을 우선한다. 따라서 런타임 계약에는 bool의 의미뿐 아니라 **0=주생산품, 1..N=부산물의 안정적인 순서**가 포함돼야 한다. 플래그만 유지하고 배열을 재정렬하는 것은 공개 슬롯 계약 변경이다.

| 상태 / Owner | Writer·해제 | Reader | 필요한 경계 |
| --- | --- | --- | --- |
| DTO·Temp Builder / 빌드 호출 | Loader 작성, using 해제 | 같은 호출 | 내부 JSON/할당 순서를 소비자가 알 필요 없음 |
| Persistent RecipeRegistryBlob / 생성 주체 | 게시 전 Loader 작성, 정상 게시 후 내용 Writer 없음 | Command, CrafterDecision/Execution, 테스트 Job | 불변 값의 reader끼리 별도 순서 불필요; 모든 reader보다 긴 할당 수명 필요 |
| RecipeRegistry.Value / 게시 주체 | Initialize에서 Create/Set | 세 시스템이 매 갱신 Value 확인·snapshot | 초기화 후 Simulation 준비. Config 없거나 Value 미생성이면 소비자는 return; 무조건 기본 레시피로 직접 대체하지 않음 |
| Init._blobReference / RecipeInitSystem | 자동 초기화의 반환값을 보관, OnDestroy Dispose | 해당 시스템의 수명 코드 | 외부 reader는 private 필드를 읽지 않음. 공개 재초기화와 자동 소유 필드의 불일치는 F-008 재사용 |
| 공개 빌더/Initialize 반환 참조 / 호출자 | 테스트가 필드 보관·TearDown Dispose; 자동 소유와 별개 | 테스트 및 Registry 조회 | 호출자가 Job 종료 후 해제해야 함. Test07은 Complete 뒤 TearDown 해제 |
| 선택 ID·필터 / 제작 상태 | RecipeCommand가 SelectedRecipeId/ActiveRecipeId와 재료 whitelist 작성 | Decision/Execution | Recipe ID와 유효 재료 enum이 공개 연결 키; Loader의 private 자료구조 참조 없음 |
| 프레임 결정·저장 재료·ProductResult | Decision은 계획, Execution은 선소비/진행/생산 결과 | Execution, 이후 ItemLifecycle | Decision/Execution 모두 현재 Registry에서 ID로 조회. decision.RecipeIndex는 있지만 Execution이 그것으로 Blob을 인덱싱하지 않음 |

Decision과 Execution은 `[ReadOnly] RecipeRegistry` snapshot을 Job에 전달하고 각 state.Dependency를 등록한다. Registry 초기화에 공간 인덱스 Fence나 EndStateApply ECB를 추가해야 할 근거는 없다. 기존 상태/버퍼 쓰기의 ECS 의존성과 Blob을 아직 읽는 Job이 있을 때의 해제 금지는 필요한 동기화이며, 시스템 결합을 줄이려고 제거할 대상이 아니다.

**수명 한계 [코드 확인/미확인]:** automatic OnUpdate→OnDestroy의 소유 필드는 단일하다. static 함수로 기존 singleton을 교체하면 이전 Blob은 자동 해제되지 않고 private 소유 필드도 갱신되지 않는다. pre-existing singleton은 소유권을 인수하지 않는다. 이 형태는 Q04의 **F-008과 동일**하며 `RecipeInitSystem.cs:11,18–37,44–70`에 적용된다. 테스트의 수동 교체 사례는 기존 Blob을 명시 Dispose한 뒤 새 값을 받는다. runtime 외부 재호출은 검색 범위에서 없고 정상 초기화에 현재 누수가 발생했다고 단정하지 않는다.

자동 Init.OnDestroy의 실제 reader 종료 순서, Init만 중도 제거한 뒤 살아 있는 singleton, 무효/복수 singleton, 게시 예외와 반복 초기화의 전체 해제는 실행 미확인이다. 정상 World 파괴가 unsafe라고 OnDestroy 본문만으로 단정하지 않으며, hot reload가 구현돼야 한다고 요구하지 않는다.

## 4. 의존 관계와 내부 변경 영향

| ID / 관계 | 형태·공개 계약 | 내부 구현 의존·영향 | 판정 |
| --- | --- | --- | --- |
| DEP-Q06-01 / Init → Loader → Registry | 호출·게시·할당 수명 | 다른 gameplay 시스템 Update/정리 호출 없음 | 필요한 계약 |
| DEP-Q06-02 / Command·Decision·Execution → Registry | 읽기, ID·재료·출력·시간 | 정상 소비자는 Resources나 빌더 임시 구조를 몰라도 됨. 품목/ID 검증은 소비자의 건너뛰기·NoRecipe 규칙에 맡겨짐 | 정상 데이터 의존 적합, F-013/F-015 검증 경계 보완 |
| DEP-Q06-03 / Loader 재료 목록 → Decision→Execution | 같은 품목의 수량 의미 | Decision은 행별 같은 재고 재사용, Execution은 행별 순차 차감. 제작 가능한 입력을 정의하려면 두 알고리즘의 차이를 알아야 함(F-014) | 개선할 숨은 불변식 |

| DEP-Q06-05 / 외부 초기화 호출자 → Init 소유 및 Job reader | 교체·해제 | old/new Blob 소유자와 진행 중 reader를 알아야 안전한 교체 가능 | 개선할 결합, [F-008 최초 문서](Q04.md#f-008--공개-초기화의-교체-경로에-blob-소유권회수reader-종료-계약이-없음) |

공개 계약 유지 시 내부 변경 사례(**실제 수정 실험 아님**):

- Resources 읽기와 JSON 변환을 별도 내부 helper로 나누고 같은 fallback·ID 조회 결과·배열/슬롯 순서·게시 시점·수명을 유지하면 Loader/Init 및 단위 테스트 내부 변경에 한정된다. Crafter 시스템의 구체 Job 순서나 내부 플래그를 함께 수정할 이유는 확인되지 않았다.
- Decision의 재료 개수 집계를 내부 맵으로 최적화하더라도 현재 중복 행을 독립 비교하는 관찰 결과를 유지해야 ‘계약 유지’ 변경이다. 합산 비교로 고치면 현재 F-014의 입력에서 동작이 달라지므로 단순 성능 리팩터링으로 숨길 수 없다. 품목 유일성 또는 합산 의미를 공개 계약으로 정하면 Decision과 Execution의 내부 알고리즘 선택을 분리하기 쉬워진다.
- 출력 배열을 정렬하면서 IsByproduct만 유지하는 것, 동일 ID의 첫 일치 규칙을 바꾸는 것, Blob 교체를 런타임에 허용하는 것은 슬롯/조회/수명의 공개 의미 변경이다. 관련 시스템·테스트 검토가 필요하다는 사실 자체를 불필요한 결합으로 세지 않는다.

특정 생산/수령 시스템의 세부 순서를 Loader가 직접 호출하거나 활성화하는 순환 제어는 확인되지 않았다. 반면 단일 데이터 계약이 명시하지 않은 유일성·유효성·해제 책임은 다른 도메인의 코드를 알아야 하는 실제 이해 비용이다. V1과 동일 범위 비교는 하지 않았으므로 V1 대비 감소를 확정하지 않는다.

## 5. 발견 문제

#### F-013 — 무효 재료·출력 품목을 게시하여 제작 정체 또는 산출물 누락이 가능함

- 발견 단계 / 유형 / 평가 축: Q06 / 안정성 결함 / 안정성·유지보수성·V2 적합성.
- 우선순위: **P2**. 입력 오타 하나가 게시 성공 후 재료 소비·출력 결과를 바꿀 수 있음. 현재 파일의 품목들은 유효함.
- 근거 수준: **코드 확인**; 오류 입력 실행 재현은 미확인.
- 위치: `RecipeConfigLoader.cs:89–111`; `CrafterDecisionSystem.cs:170–195,244–260`; `CrafterExecutionSystem.cs:118–141,166–178`; `CrafterRecipeCommandSystem.cs:163–170`.
- 기대 계약과 출처: RecipeIngredientBlob/RecipeOutputBlob의 품목 의미, 기존 ItemTypeEnum의 None sentinel, Execution의 실제 출력 기록 조건.
- 확인한 동작: Enum.TryParse 반환 bool을 무시하고 결과를 저장한다. 오타/빈 이름의 파싱 실패는 None 값으로 이어지며 정의되지 않은 숫자 enum도 별도 IsDefined로 거부하지 않는다. Decision은 None 출력의 용량 검사를 생략하고 Execution은 해당 출력을 기록하지 않는다.
- 발생 조건·영향: 재료는 유효하지만 주생산품 이름이 오타이고 부산물이 없으면, 재료 완비 시 선소비·제작 진행 후 결과를 만들지 않고 사이클을 초기화하는 경로가 있다. 잘못된 부산물만 누락되는 경로도 있다. 잘못된 재료는 정상 아이템으로 만족하지 못해 대기할 수 있음. 모든 무효 숫자 입력의 세부 결과를 실행 확정하지 않음.
- 반대 근거/미확인: 정상 Config 및 기존 테스트의 이름은 모두 유효. None을 의도적 무출력 표기로 허용할지 정책은 확인되지 않음. 그래도 입력 오타와 의도적 무출력은 현재 구분되지 않음.
- 수정 후보: 재료·주생산품·부산물의 파싱 성공/정의 여부/None 정책을 입력 경계에서 검증. 실패 시 전체 거부·항목 제외·fallback 중 정책 확정 후 적용.
- 필요한 추가 검증: 잘못된 이름·누락/None·정의되지 않은 숫자 품목, 후반 부산물 오류의 전체 게시 범위, 유효 재료가 소비되지 않는 실패 정책. 기존 후보에는 없음.
- 처리 / 수정·재검증 근거: **미결정**, 코드/테스트 수정 없음. [Q03 F-006](Q03.md)의 prefab 실패 후 결과 소비와는 원인/경계가 달라 신규 등록.

#### F-014 — 중복 재료 행을 합산하지 않아 필요한 양보다 적은 재료로 제작이 시작됨

- 발견 단계 / 유형 / 평가 축: Q06 / 안정성 결함·V2 설계 불일치 / 안정성·유지보수성·V2 적합성.
- 우선순위: **P2**. 특정 레시피 입력에서 비용 계산과 선소비가 일치하지 않음.
- 근거 수준: **코드 확인**; 실행 재현 미확인.
- 위치: `RecipeConfigLoader.cs:87–95`; `RecipeConfigComponents.cs:74–87`; `CrafterDecisionSystem.cs:244–273`; `CrafterExecutionSystem.cs:118–141`.
- 기대 계약과 출처: 레시피의 Ingredients.Amount와 ‘재료 완비 후 선소비’ 계약. 같은 재고를 서로 다른 요구량에 이중 계상하지 않아야 함.
- 확인한 동작: 같은 품목 행을 그대로 허용한다. 예를 들어 Iron_Ore 1 행 두 개, 실제 StoredItem 1개면 Decision은 각 행에 대해 foundCount=1로 모두 통과한다. Execution은 첫 행에서 1개를 제거하고 두 번째 행은 소비 부족이어도 remainingToConsume을 검사/롤백하지 않은 채 IsCraftingActive=true로 설정한다. TryFindIngredient helper도 첫 행 수량만 반환한다.
- 발생 조건·영향: 해당 중복 레시피와 합계보다 적고 각 행 요구량 이상인 재고. 다른 정상 조건을 충족하면 부족한 비용으로 제작을 진행할 수 있음. 현재 JSON에는 레시피 내부 중복 재료가 없음.
- 반대 근거/미확인: 같은 품목의 여러 출력은 다른 슬롯으로 처리되므로 이 문제를 출력 중복에 일반화하지 않는다. 다른 producer의 버퍼 손상/동시 수량 변경 전체는 이번 범위 밖.
- 수정 후보: Loader에서 품목 중복 거부 또는 수량 합산 및 overflow 확인. 중복 행을 유지한다면 Decision의 총 요구량 검증과 Execution의 선소비 계약을 함께 설계해야 함.
- 추가 검증: 중복 [1,1]/[2,3]과 재고 1/3/5 비교, 정확한 비용·부족 시 무소비, 서로 다른 품목, helper의 공개 수량 의미. 기존 후보에는 없음.
- 처리 / 수정·재검증 근거: **미결정**, 수정·재현 실행 없음. [Q05 F-010](Q05.md#f-010--같은-건물의-중복-자재-품목을-허용하지만-두-번째-요구-행을-충족할-수-없음)과 유일성 문제는 유사하나 Recipe Loader와 Decision/Execution이라는 별도 상태/수정 경계이며 증상도 비용 부족 제작이므로 별도 ID. Q21에서 재발견 시 이 문서 참조.

#### F-015 — 0·음수·중복 레시피 ID를 허용하여 선택할 수 없거나 앞 정의에 가려지는 레시피가 게시됨

- 발견 단계 / 유형 / 평가 축: Q06 / 안정성 결함·유지보수 위험 / 안정성·V2 적합성.
- 우선순위: **P2**. 게시 목록과 ID 기반 제작 선택의 의미가 불일치함.
- 근거 수준: **코드 확인**; 무효/중복 ID 실행 재현은 미확인.
- 위치: `RecipeConfigLoader.cs:83`; `RecipeConfigComponents.cs:100–114`; `CrafterDecisionSystem.cs:117–145`; `CrafterExecutionSystem.cs:104–108`; `CrafterRecipeCommandSystem.cs:151–176`.
- 기대 계약과 출처: ID로 Recipe를 선택하는 Registry helper와 Crafter의 `SelectedRecipeId <= 0` NoRecipe 계약.
- 확인한 동작: 파서는 ID를 그대로 복사하며 생략 시 DTO int 기본값 0이다. Decision/Execution은 0 이하를 레시피 없음으로 처리한다. 같은 양의 ID 두 행은 TryGetRecipeIndex의 첫 일치만 접근하므로 뒤 정의는 일반 ID 선택 경로에서 가려진다.

- 반대 근거/미확인: 현재 파일 ID 1~5는 유일·양수. 같은 주생산품의 다른 고유 ID까지 금지해야 한다고 요구하지 않으며, primary-output 검색의 첫 일치 우선 정책은 별도 질문.

### 기존 F-008 적용 및 추가 검증 공백

- **F-008 재사용:** RecipeInitSystem의 old/new Blob 교체와 private 소유 필드 분리는 [최초 Q04 기록](Q04.md#f-008--공개-초기화의-교체-경로에-blob-소유권회수reader-종료-계약이-없음)과 같은 문제다. Recipe의 추가 위치와 실제 호출 범위는 §3에 기록했다. 이전 결과는 수정하지 않았다.
- 기본 레시피와 실제 JSON이 같아서 Test01의 길이 5 통과만으로 실제 파일을 읽었는지 fallback을 탔는지 구별하지 못한다. 현재 Test03/07도 실제 Resources 값에 의존하는 연동 테스트이며 순수 fallback 검증으로 설명하지 않는다. Q04 F-009의 테스트 독립성 경고를 참조하되 파일 연동 테스트라는 이유만으로 새 결함을 만들지 않는다.
- 테스트 후보에는 자동 Init.OnUpdate/OnDestroy, 재초기화/외부 Blob 소유·해제 경합, malformed JSON, 빈 목록의 fallback, 무효 품목/중복 재료/ID 거부가 없다. 신규 검증 제안으로 남기며 정상 테스트로 대체 검증했다고 주장하지 않는다.
