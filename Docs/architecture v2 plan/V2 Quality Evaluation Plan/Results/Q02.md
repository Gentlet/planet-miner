## 3. 상태 Owner와 Reader/Writer

**[코드 확인] ItemOwnership은 소유권의 원본 데이터지만, ItemOwnershipApplySystem이 모든 경로의 단일 Writer인 것은 아니다.** 일반 물류 이전, 스폰, 공사, 철거가 작성 책임을 나누고 있다.

| 데이터 | 현재 Writer / 변경 책임 | Reader·계약과 경계 |
| --- | --- | --- |
| ItemIdentity.Type | 생성 경로에서 초기화. Q02에서는 정적 타입과 버퍼 타입 캐시의 관계 확인 | 버퍼 등록·생산/물류·검증에서 사용. 타입 변경 기능 자체는 이번 범위가 아님 |
| ItemOwnership.Owner | 일반 이전은 ItemOwnershipApply Job의 직접 쓰기. ItemLifecycle·공사 수령/취소·건물 철거/환급은 ECB로 직접 초기화/변경 | Null이면 월드, 그 외 수납. ItemSpatialSync·벨트 이동·입고 판단·Validation 등이 읽음. Owner 존재와 소유 버퍼 등록은 별도 정합성 조건 |
| TransferOwnershipRequest + enable | 일반 입출고 Apply가 TargetOwner를 쓰고 enable. 스폰 경로는 컴포넌트를 준비하고 disable. ItemOwnershipApply가 읽고 disable | 아이템당 한 컴포넌트의 요청 상태이며 복수 요청을 보관하는 큐가 아님. 동일 아이템에 대한 복수 생산자의 승자 정책은 별도 계약이 필요 |

| ProductItemElement | ItemLifecycle 생산 결과/스폰 Append, 물류 출고 RemoveAt, 레시피 변경 Add | 생산품 출력 대기. 같은 Owner 안의 Stored→Product 이동은 ownership을 바꾸지 않음 |

공사 완료/취소와 철거는 현장·건물 자체를 삭제하면서 해당 버퍼도 소멸시킨다. 반면 살아 있는 창고·제작기에서 아이템만 삭제할 때는 요청 생산자가 소유 버퍼를 먼저 정리해야 한다. 서로 다른 수명주기 조건을 같은 “버퍼 자동 정리”로 설명하지 않는다.

## 4. 요청 소비와 적용 흐름

### 일반 입고·출고

```text
입고: Stored 버퍼 Add → 벨트 이동 disable → Transfer(target=건물) enable
출고: Stored/Product 버퍼 Remove → 위치·벨트 상태 복원 → Transfer(target=Null) enable
    → ItemOwnershipApply: ownership 직접 쓰기 + 렌더 태그 ECB 기록 + Transfer disable
    → EndStateApply: 태그 구조 변경 재생
    → ItemSpatialSync: ownership 기준 월드 인덱스 갱신
```

**[코드 확인]** BuildingItemStorageApply의 UpdateBefore(ItemOwnershipApplySystem)와 Job Dependency가 같은 Phase의 요청 작성·소비를 연결한다. ECB 기록 Job은 AddJobHandleForProducer로 완료 핸들을 전달한다. 이 순서는 필요한 동기화다. 소유 버퍼·ownership·렌더 태그가 한 번의 즉시 쓰기로 원자적으로 바뀌는 것은 아니다.

### ItemOwnershipApply의 분기

| 입력 상태 | 결과 [코드 확인] |
| --- | --- |
| TargetOwner == Null | 기존 ownership이 Stored이면 DisableRendering Remove 기록. ownership을 WorldItem으로 변경. 요청 disable |
| TargetOwner가 존재함 | 기존 ownership이 WorldItem이면 DisableRendering Add 기록. ownership을 Stored(target)로 변경. 요청 disable |
| TargetOwner가 존재하지 않음 | ownership·태그를 바꾸지 않고 요청 disable |
| 기존 Stored → 다른 Stored | Owner만 변경하고 태그 명령은 추가하지 않음. 기존/새 소유 버퍼 정리는 호출 측 책임 |
| 요청 disable | 정상 enableable 쿼리에서 제외. 컴포넌트 존재만으로 처리하지 않음 |

대상 존재 검사는 `EntityStorageInfoLookup.Exists`다. 대상의 Storage/버퍼·슬롯·수용 능력, 기존 버퍼 제거, 대상이 ECB에서 곧 파괴될지까지 검증하지 않는다. 이는 일반 요청의 제한된 역할이다. 호출자가 소유 버퍼를 먼저 바꾼 뒤 거부되는 경우의 롤백까지 이 소비자에서 제공한다고 가정하면 안 된다.

태그 명령은 현재 ownership의 전환 여부로 결정한다. 이미 WorldItem인데 DisableRendering이 남아 있거나 이미 Stored인데 태그가 없는 불일치를 매번 복구하는 정규화 시스템은 아니다. 따라서 다른 Writer도 일관된 ownership/태그 상태를 유지해야 한다.

### 다른 Item 요청과 직접 작성 경로

- SpawnItemRequest는 독립 요청 엔티티이며 ItemLifecycle이 목적지에 맞는 ownership·태그·버퍼 등록을 ECB로 함께 기록하고 요청 엔티티를 삭제한다. 필드 계약과 작성 경계만 확인했고 전체 생성 실패 정책은 Q03으로 남겼다.
- DestroyItemRequest는 enableable이다. ItemLifecycle의 해당 Job은 ECB.DestroyEntity만 수행한다. 살아 있는 소유 버퍼에서 먼저 제거하는 규칙은 ItemRequests의 주석과 CrafterExecution의 실제 RemoveAt→enable 호출에서 확인했다.
- ProductResult는 생산 결과 데이터이며 ItemLifecycle이 아이템 생성 명령으로 바꾸고 Clear한다. 일반 Transfer 요청을 거치지 않는 생성 경로다.
- 공사 수령·반환과 철거 반환도 일반 Transfer를 거치지 않는다. 이 경로들이 같은 ItemOwnership·DisableRendering을 쓰므로 일반 요청 경로만 통과해도 전체 소유권 일관성이 보장되지는 않는다(F-003/F-004).

## 5. 의존 관계와 변경 영향

| 관계 | 공개 계약 / 실제 알아야 하는 내용 | 필요한 동기화와 결합 판정 |
| --- | --- | --- |
| StorageApply → TransferOwnershipRequest → OwnershipApply | TargetOwner, enable 소비, 버퍼·위치는 생산자 책임. 같은 Phase에서 소비자보다 먼저 실행해야 함 | 명시된 요청 계약과 UpdateBefore는 필요. 소비자 private Job 구성은 알 필요 없음 |
| OwnershipApply → EndStateApply | 직접 ownership 변경과 지연 태그 변경, producer 핸들 전달 | 필요한 인프라 계약. ECB 내부 큐 구현에 의존하지 않음 |
| 제작 재료 소비 → DestroyItemRequest → ItemLifecycle | 소유 버퍼 선제거 및 요청 enable | 필요한 소유권 경계. 삭제 시스템이 각 생산 건물의 버퍼 내부를 뒤져 정리하지 않아도 됨 |
| 레시피 변경 → Stored/Product 버퍼 | 같은 Owner 유지, 버퍼만 이동 | 공유 버퍼 계약 의존. 아이템 소유권 소비자의 실행 순서까지 알 필요는 없음 |
| 공사 수령 → 기존 소유 상태·현장 버퍼 | 현재 소비자는 ItemIdentity·요구량만으로 수령하고 기존 Owner/동일 아이템 선점은 확인하지 않음 | 생산자가 중복·기존 보관품을 절대 보내지 않는다는 외부 보증이 필요하지만 확인한 요청 계약에는 없음. **F-003: 개선할 결합/검증 누락** |
| 철거 반환 ↔ OwnershipApply | 같은 태그를 반대 명령으로 기록하며 ownership의 직접 쓰기와 ECB 쓰기를 혼용 | 정상 최종 상태를 이해하려면 상대 시스템의 태그 조건·버퍼 생성 순서까지 알아야 함. **F-004: 숨은 순서 의존** |
| ItemSpatialSync·물류 판단 → ItemOwnership | 월드/수납 여부 | 원본 데이터에 의존하는 필요한 계약. 렌더 태그를 상태 원본으로 취급하지 않음 |

**[추정: 현재 호출 관계에 근거한 변경 영향 사례]**

1. OwnershipApply의 유효성 검사 구현·Job 분할을 바꾸되 기존 요청 의미·같은 Phase 소비·ownership 결과·EndStateApply 태그 결과·시스템 타입을 유지하면 StorageApply는 수정할 필요가 확인되지 않는다. 이 경계는 내부 변경 영향을 제한한다.
2. StoredItemElement를 찾는 내부 검색을 유틸리티로 옮기되 같은 요소를 같은 시점에 제거하고 Transfer/Destroy 요청을 발행한다면 OwnershipApply·ItemLifecycle의 내부 구현은 변경할 필요가 없다. 버퍼 형식이나 소비 시점까지 바꾸면 공개 계약 변경이므로 별도다.
3. 철거 내부 스케줄링을 바꿀 때 같은 입력·반환 결과를 의도하더라도 OwnershipApply와의 태그 ECB 순서를 재검토해야 한다(F-004). 이는 공개된 최종 WorldItem/태그 제거 계약을 유지하기 위해 다른 Writer의 세부 명령을 알아야 하는 변경 영향이다. 필요한 전체 순서 계약이 명시되지 않아 단순 내부 리팩터링의 독립성을 제한한다.

ownership/태그 작성이 여러 파일에 있다는 사실만으로 모든 경로를 한 시스템에 합치라고 결론내리지 않는다. 공사·철거의 책임은 유지하면서 아이템 인계·중복 방지·최종 표시 상태의 계약을 명확히 하는 방향을 별도 검토할 수 있다.

## 6. 발견 문제

기존 결과 Q00·Q01a·Q01b의 ID를 검색했다. 등록된 F-001/F-002와 아래 문제는 원인이 다르므로 **F-003/F-004**를 신규 등록한다. F-001의 공사 구현 설명은 [Q00 최초 기록](Q00.md#84-문서와-구현의-차이)에 연결하며 중복 등록하지 않는다. F-004는 Q01b에서 미확인으로 남긴 형제 Writer 경합을 현재 소스로 구체화한 것이다.

### F-003 — 공사 수령이 동일 아이템 재사용과 기존 소유 버퍼를 검증하지 않음

- 발견 단계 / 유형 / 평가 축: Q02 / 안정성 결함·유지보수 위험 / 안정성·V2 적합성.
- 우선순위: **P2**. 특정 요청 입력에서 한 실물 아이템이 여러 자재로 집계되거나 서로 다른 소유 버퍼에 남을 수 있다. 실제 사용자 입력·드론 경로에서의 발생 빈도는 미확인이다.
- 근거 수준: **코드 확인**. 아래 조건으로 새 테스트를 작성하거나 실행 재현하지 않았다.
- 위치: `ConstructionLifecycleApplySystem.cs:259,261–359`, `BuildingLifecycleComponents.cs:57–91`.
- 기대 계약: 아이템 하나의 Owner와 소유 버퍼 참조가 일치해야 한다. Supply 요청은 실제 자재 ItemEntity를 인계하는 요청이다. 일반 Transfer는 버퍼 정리를 생산자에게 맡기지만 Supply 계약에는 이미 수납된 아이템·동일 아이템 중복의 인계/거부 정책이 명시되지 않았다.
- 확인 동작: 수령 Job은 현장·취소 플래그·ItemIdentity·품목·잔여 요구량을 확인한 뒤 DeliveredQuantity 증가와 현장 Stored 버퍼 Add를 즉시 수행한다. ownership은 ECB.SetComponent로 나중에 바꾼다. 전달받은 `ItemOwnershipLookup`을 Execute에서 사용하지 않으며, 기존 현장 버퍼의 동일 ItemEntity 검색·다른 Owner 버퍼 정리·동일 프레임 아이템 선점도 없다.
- 발생 조건 A: 요구량 3 이상인 미완료 현장에 동일 월드 아이템을 가리키는 Supply 요청 2개. 두 요청 모두 잔여량 조건을 통과해 Delivered가 2 증가하고 같은 엔티티 참조가 2번 추가된다. 요구 미충족 상태를 유지하면 완료 Job의 삭제와 분리해 이 상태를 관찰할 수 있다.
- 발생 조건 B: 정상 기존 창고 버퍼에 들어 있는 품목 일치 아이템을 다른 미완료 현장으로 공급. 새 현장에 참조가 추가되고 Owner는 현장으로 바뀌지만 기존 창고 참조를 제거하는 코드가 없다. 최종 소유 버퍼·Owner 계약을 깨뜨린다.
- 영향: 자재 실물 수와 도착 집계 불일치, 복수 버퍼 참조, 이후 소비/반환에서 무효 참조·중복 처리 위험. 후속 실패의 구체적 런타임 형태는 미확인이다.
- 반대 근거·한계: 정상적으로 서로 다른 월드 아이템만 공급하는 경로는 통과한다. 선택한 기존 Material Test02도 이 정상 사례다. 기존 다중 공급 테스트는 서로 다른 item1/item2/item3를 사용해 위 조건을 검증하지 않는다.
- 수정 방향 후보: 기존 소유자에게서의 명시적 인계 또는 거부 정책과 동일 ItemEntity 재수령 방지를 정한다. 단순히 ECB 재생 전 IsWorldItem만 검사하는 것으로 동일 프레임 중복까지 해결된다고 보지 않는다. 새 게임 규칙·구현은 추가하지 않았다.
- 추가 검증 제안: 동일 현장 중복, 서로 다른 현장 간 동일 아이템 경합, 기존 Stored/Product 아이템의 인계, 이미 수령된 아이템 재요청. 소유 버퍼 유일성·Owner·Delivered·렌더 태그를 함께 검사한다.
- 처리: **미결정 / 코드·테스트 수정 없음**. Q24는 이 최초 기록을 연결해 인계 정책·검증을 이어간다.

### F-004 — 같은 프레임 입고·철거의 렌더 태그가 ECB 생성 순서에 의존

- 발견 단계 / 유형 / 평가 축: Q02 / 유지보수 위험·V2 설계 불일치 / 안정성·유지보수성·V2 적합성.
- 우선순위: **P2**. 허용된 실행 순서에서 반환된 월드 아이템에 DisableRendering이 남을 수 있다. 현재 자동 World의 구체적 배열에서 실제로 재현되는지는 미확인이다.
- 근거 수준: **코드 확인 + 조건부 경로 추론**, 실행 재현 없음.
- 위치: `BuildingItemStorageApplySystem.cs:24,145–161`, `BuildingLifecycleApplySystem.cs:18–20,117–118,286–308,381`, `ItemOwnershipApplySystem.cs:43–54,69–98`. ECB 생성 순서대로 재생되는 공통 계약은 [Q01a §4](Q01a.md#4-구조-변경-기록재생-경계) 참조.
- 기대 계약: 성공 입고 이후 같은 tick 철거로 반환된 아이템은 Owner==Null이고 DisableRendering이 없어야 한다. 철거의 정상 반환 코드와 기존 Demolish Test02의 assertion이 이 결과를 명시한다.
- 발생 조건과 경로: 월드 아이템이 입고되어 Stored 버퍼에 들어가고 Transfer가 활성화된 tick에 대상 건물 철거 요청도 존재한다. 현재 속성은 StorageApply→OwnershipApply와 StorageApply→BuildingLifecycle을 보장하지만 두 소비자 사이 순서는 없다.
- 허용 순서 `StorageApply → BuildingLifecycle → OwnershipApply → EndStateApply`에서: (1) 철거가 아이템의 WorldItem 쓰기·태그 Remove·건물 Destroy를 먼저 만든 ECB에 기록한다. (2) 건물은 아직 ECS에 존재하며, 아이템의 ownership도 아직 WorldItem이므로 OwnershipApply는 Stored 쓰기를 즉시 하고 태그 Add를 나중 ECB에 기록한다. (3) 재생 시 철거 ECB가 Owner를 WorldItem으로 돌리고 태그를 제거한 뒤 Ownership ECB가 태그를 다시 추가한다. 최종적으로 Owner는 Null인데 DisableRendering이 남는 경로가 된다.
- 반대 순서에서는 Ownership의 Add 뒤 철거 Remove가 적용될 수 있다. 이 차이가 필요한 선후 관계를 공개하지 않은 상태에서 상대 Writer의 세부 명령을 알아야 하는 이유다. Job 완료 핸들이 있어도 ECB 사이의 생성 순서 의미를 대신 해결하지 않는다.
- 영향: ownership·공간 인덱스와 표시 태그 불일치. 실제 화면에서의 증상은 Play Mode로 확인하지 않았으며, 여기서는 태그 상태의 위험만 판정한다.
- 반대 근거·한계: 선택한 Demolish Test02는 이미 저장된 아이템 반환이고 동시 입고를 만들지 않는다. 기존 Demolish Test12는 벨트·라우팅 경합이며 해당 그룹에 OwnershipApply를 넣지 않는다. Q01a의 정상 건설 통합 통과도 이 조건의 증거가 아니다. 특정 기본 정렬의 관측 없이 항상 발생한다고 주장하지 않는다.
- 수정 방향 후보: 최종 소유권·표시 상태의 적용 우선순위/완료 경계를 명시하여 일반 이전과 철거 반환이 충돌하지 않도록 한다. 명시적 최소 순서 또는 인계 결과 통합을 검토할 수 있으나, 다른 공사·철거 경합까지 검토하지 않고 속성 하나가 전체 해결책이라고 단정하지 않는다. OwnershipApply가 건물의 내부 철거 마커를 임의로 읽는 방식으로 결합을 늘리지 않는다.
- 추가 검증 제안: 같은 tick 입고+대상 철거, ECB 전후 Owner·Stored 버퍼·요청 enable·DisableRendering·ItemSpatialIndex를 함께 확인. 의도한 공개 순서에 독립적으로 구성 순서를 바꿔도 결과가 유지되는지 검사한다.
- 처리: **미결정 / 코드·테스트 수정 없음**. Q28에서 같은 문제를 재등록하지 말고 이 기록을 연결한다.

## 8. 세 평가 축·남은 질문·완료 조건

| 축 | 판단 / 근거 |
| --- | --- |
| 안정성 | 정상 요청·입출고·단일 수령/반환은 선택 테스트에서 확인. F-003의 중복/기존 Owner 검증 누락, F-004의 조건부 태그 경합은 개선 대상이다. 전체 수명주기 안전성은 미보장 |
| 유지보수성 | 일반 요청은 버퍼·위치 책임과 소유권 반영을 구분하여 국소 이해가 가능하다. 반면 여러 직접 Writer가 같은 상태·태그 규칙을 따로 유지하므로 변경 시 공사·철거까지 확인해야 한다. 테스트의 논리 상태 검증과 렌더 태그 검증 범위도 다름 |
| V2 적합성 | **일부 불일치**. 일반 Transfer/Destroy의 데이터 계약과 producer 핸들은 적합한 협력 경계다. F-003의 외부 중복 방지 가정과 F-004의 상대 Writer 내부 태그·ECB 순서 지식 요구는 직접 결합·변경 영향 축소 목표를 제한한다. 여러 Writer가 존재한다는 이유만으로 불일치 판정한 것은 아님 |

남은 설계 질문: 공사 자재는 월드 아이템만 수령하는가, 기존 소유자에게서의 인계를 지원하는가? 이미 확인된 하나의 실물을 중복 집계하지 않아야 한다는 정합성 요구와, 이 지원 범위 선택을 구분한다. 같은 tick 일반 입고와 철거의 최종 결과 계약을 어떻게 명시할지는 Q28의 관련 경합 검토와 함께 결정해야 한다. 이번에는 어느 정책도 새로 구현하지 않았다.

완료 범위는 요청·상태 계약, 소유권/버퍼/렌더 Writer 지도, 대표 Reader, 요청 소비·ECB 시점, 의존 관계와 내부 변경 영향, 관련 기존 테스트 최종 상태, 문제·미확인·보강 제안의 기록이다. 결함 수정이나 새 재현 테스트까지 완료 조건으로 바꾸지 않았다.
