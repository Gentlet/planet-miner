## 3. 결정론·청크 경계·준비 대기

### 생성 계산 — 코드 확인

1. 난수 상태는 `HashSeed(worldSeed, candidateChunk, ResourceType)`마다 새로 만든다. target 청크나 이전 청크 호출의 난수 상태를 입력으로 사용하지 않는다. 0 hash는 1로 바꾼다. 이는 같은 입력 재현성의 근거이며 **서로 다른 모든 seed/좌표의 무충돌 보증은 아니다**.
2. 활성 설정의 최대 반경으로 `neighborRange = maxRadius / 16 + 1`을 정하고 target 주변 후보를 y→x→config 순서로 순회한다. 정상적인 int 범위에서는 청크 밖 중심의 광맥도 대상 셀까지 도달할 수 있는 후보 범위를 포함한다. 최대 반경에 따른 여유 후보가 생기는 것은 누락과 다르다. 극단 산술 한계는 F-017을 따른다.
3. 후보의 발생 여부·반경·중심과 원 내부 offset을 순회하며 fill/amount 난수를 뽑는다. **대상 청크 clip 및 occupied 검사는 그 뒤**다. 같은 후보를 이웃 target에서 다시 계산할 때 target별로 난수 소비 횟수가 달라지지 않도록 하는 핵심 순서다.
4. `occupied`는 Generate 호출마다 생기는 target 청크의 임시 집합이다. 대상 내부 셀에만 Add하므로 최대 256셀이고, 중첩 광맥/품목에서는 먼저 도달한 후보가 해당 셀을 차지한다. 등록 순서는 고정된 후보·config 순서에 의존하며 ECB entity ID나 전역 공간 맵을 읽지 않는다.
5. 정상 좌표 범위에서 청크의 `[chunk*16, chunk*16+15]` 영역은 겹치지 않는다. 각 target은 자기 셀만 스폰하므로 이웃 청크를 어느 순서로 생성해도 대상 간 셀 충돌을 만들지 않는다. **같은 target을 Utility에 두 번 직접 호출할 때의 멱등성은 없다**. 그것은 Q17의 Pending/Map 접수 Owner 책임이다.

생성물의 좌표·종류·매장량이 결정론의 비교 대상이다. ECB entity index, 병렬 HashMap 열거 순서, 플랫폼/Mathematics 버전 변경까지 같은 결과라는 보장은 이번 근거에 없다. 설정 행의 재정렬은 겹치는 후보의 승자를 바꿀 수 있으므로 단순 저장 형식 정리라고 가정하면 안 된다. 현재 로더는 설정 품목 중복을 거부하고 입력 순서를 유지한다.

### 준비와 빈 청크 — 코드 확인 + 기존 실행 재사용

- Command는 Settings/Tracker/Resource DB를 요구하고 Ready가 없으면 종료한다. 설정/DB의 부속 버퍼, 유효 설정 목록, EndCommand, 활성 품목의 prefab 전체를 확인한다. 존재하지 않는 prefab entity 또는 LocalTransform 누락도 기록 전에 return한다.
- `IsValidConfig`는 이름과 달리 로더의 전체 입력 검증을 대체하지 않는다. `ResourceType>None`, Weight>0, MaxPatchRadius>=0, MaxAmount>0인 생성 대상 필터다. 로더가 검증한 일반 입력을 전제로 하고, arbitrary enum·잘못된 min/max를 가진 외부 직접 게시를 전부 검증하지 않는다. 두 역할의 차이는 공개 Utility를 호출할 때 알아야 할 전제다.
- prefab resolve 배열은 configs 길이·순서와 일치해야 하며 inactive 행은 Entity.Null이다. Command가 배열을 같은 길이로 만들고 같은 순서로 전달한다. **생성 도메인 내부 협력 전제**이며 Sync/Load가 배열 구조를 알아야 하는 결합은 아니다.
- 미준비면 Ready/Pending을 유지한다. 모든 대상이 준비되면 각 청크의 spawn 명령 뒤 Completed를 같은 EndCommand ECB에 넣고 Ready를 비운다. Pending은 다음 Load까지 유지한다.
- weight=0 등으로 생성물이 없는 **준비된 빈 청크**도 Completed를 게시한다. 반대로 configs 버퍼 자체가 없거나 비어 있으면 준비 미완료로 반환한다. 활성 prefab이 없더라도 ResourcePrefabDatabase marker와 부속 버퍼의 존재는 현재 요구한다.
- 이 사전 검사는 일반적인 missing/dead/transform 오류의 부분 기록을 막는다. 기록 뒤 다른 Command가 prefab/tracker를 파괴하는 조건이나 임의 ECB 예외까지 rollback하는 트랜잭션은 아니다. 현재 그런 production 충돌 경로를 새로 입증하지 않았으며 실패 강제 주입은 미수행이다.

| EndStateApply 이후 Synchronization | 고갈 파괴까지 반영한 ResourceNode+GridPosition 원본을 대상으로 Clear→Populate. 최종 Writer 핸들을 게시하며, 그룹 Update 반환 자체가 Job 완료를 의미하지 않음 |
| 다음 Command / Decision | Load가 Completed를 Map으로 확정. MinerDecision은 최종 Map Writer에 의존하여 조회. Placement의 별도 완료 누락은 기존 F-026 |

Sync의 비어 있지 않은 경로는 Writer fence→Clear→(Clear+state.Dependency)→Populate 순서다. 용량 부족 시 모든 Map 사용 완료 후 `max(1024,count*2)`로 확장한다. 자원이 0개여도 Clear Job을 예약해 이전 항목을 제거한다. Dispose 역시 Fence 완료 뒤 수행한다. 이 구조는 원본 상태의 ECS 의존성과 NativeContainer 의존성을 구분하며 생성 시스템의 개별 Job/프리팹 초기화 순서를 요구하지 않는다.

채굴의 EndStateApply 파괴는 자원 **생성** ECB 경계가 아니다. [F-002 최초 기록](Q00.md#84-문서와-구현의-차이)의 EndStateApply 잔존 주석과 실제 EndCommand 호출을 구분했다. Completed를 공간 맵 준비 신호로 사용하는 새 경로는 이번 소스에서 찾지 못했다.

## 5. 시스템 의존성과 변경 영향

| 의존 관계 | 공개 계약 / 필요한 이유 | 내부 변경의 전파·판정 |
| --- | --- | --- |
| Generation → Config/DB | 검증된 설정, 활성 품목의 준비된 prefab | 파서·DB 작성 방식이 바뀌어도 같은 게시 계약이면 Generation/Sync 내부 수정 불필요. **필요한 데이터 계약** |
| ChunkLoad ↔ Generation | Ready 인계, 실제 반영 뒤 Completed, 다음 Load 소비 | 서로의 Update를 직접 호출하거나 Tracker 집합을 교차 변경하지 않음. **필요한 요청/결과 왕복** |
| Generation → Utility | prefab 배열의 설정 인덱스 대응, 결정론적 생성 API | 같은 도메인 내부 준비/계산 협력. Sync가 이 배열 또는 후보 순서를 아는 의존은 없음 |
| Generation → EndCommand → Sync | 원본을 Command 끝에 생성, 이후 최종 원본으로 인덱스 재구축 | 정확성에 필요한 Phase/ECB 경계. Sync는 Generation 구체 타입을 참조하지 않음 |
| MinerDecision → Map/Fence | Writer 기다림과 Reader 반환, ResourceNode lookup | Clear/Populate Job 이름·개수와 독립적. **필요한 동기화** |
| Placement → Map | 메인 스레드 조회 전 Fence 완료가 없음 | Validator 또는 다른 완료 부수효과를 기대할 여지가 있는 **불필요한 결합, 기존 F-026** |

공개 계약을 유지한 내부 변경 사례:

1. **생성의 후보 탐색 최적화**: 같은 셀별 결과·ECB/완료 경계·준비 정책을 보존하면 ChunkLoad/Sync/MinerDecision 변경은 필요 없다. 후보 병렬화가 occupied의 승자나 RNG 소비를 바꾸면 출력 계약 유지가 아니므로 별도 결정론 검증이 필요하다.
2. **Sync의 Clear/Populate를 다른 수집 방식으로 교체**: 같은 Map 의미·Sync 시점·최종 Writer 및 ECS 의존성을 유지하면 Generation과 MinerDecision은 변경할 필요가 없다. 반면 실행 시간 변화만으로 Placement가 영향을 받는다면 기존 F-026의 숨은 완료 의존이 드러난 것이다. 필요한 Fence를 없애서 이를 해결할 수 없다.
3. **프리팹 조회를 캐시로 변경**: configs와 resolve 결과의 대응 및 준비 대기 의미를 유지하면 Generation 도메인 내부로 변경을 제한할 수 있다. Load가 prefab 목록을 다시 검사하거나 Sync가 prefab 타입을 알아야 할 이유는 없다.

생성 Utility 단독 테스트는 ECB·설정·mock prefab만 필요하며 Sync/채굴을 기동하지 않는다. 그룹 통합 테스트에는 완료·공간 등록이라는 실제 계약 때문에 Load/Generation/ECB/Sync가 필요하다. 직접 Map 값을 비교하려면 Fence 완료가 필요하며 이는 테스트 편의용 우회가 아니다. Q12의 F-028은 여러 Job Reader 사이의 추가 의존 사례로, Resource의 현재 단일 MinerDecision Job Reader에 같은 경합을 새로 입증한 것으로 확대하지 않았다.

## 8. 남은 질문·완료 범위

1. **광맥 결과의 호환 범위**: 겹치는 후보의 config 순서 우선권을 장기적으로 고정할 것인가? RNG/hash/순회 최적화나 설정 재정렬 때 이전 월드 분포까지 보존해야 하는가? 현재 고정 입력의 재현성과 저장 파일/버전 간 호환 요구는 구분해야 한다. 새 우선권 규칙을 만들지 않았다.
2. **F-035 보강**: 경계를 넘는 후보를 독립 기준값으로 검증하고, 음수 청크 및 실제 seam의 amount까지 비교하는 테스트를 제안한다. 선택 테스트의 통과만으로 이 공백이 해소되지는 않는다.
3. **F-017 허용 범위**: 반경·좌표·초기 청크 수의 실용적인 상한이나 계산 예산은 별도 결정이 필요하다. 극단 입력을 실제로 대량 생성하는 부하 실험은 하지 않았다.
4. **미확인 실행 경계**: ECB 기록/부분 Playback 실패 복구, 다른 producer가 같은 셀 자원을 생성할 때의 정책, Sync 빈 맵/용량 확장/Dispose의 강제 경합, F-026 재현, 각 Map key→Entity 대응, 실제 Baker·씬·플랫폼 간 결정론·성능·메모리·persistence는 이번 새 실행의 보장 범위 밖이다.
5. 영구 준비 대기 진단과 reset/취소 정책은 Q10/Q17의 기존 질문을 유지한다. 임의 timeout·fallback·재생성 기능을 추가하지 않았다. 사용자 수동 플레이 결과도 없다.

원본/파생 상태, Reader/Writer, 실제 ECB·다음 소비 경계, 결정론의 의미와 한계, 필요한 의존/숨은 결합, 새 실행 및 재사용 근거를 기록해 Q18을 완료한다. 테스트 보강·설계 결정·수정과 **Q19 이후 평가는 자동 진행하지 않는다**.
