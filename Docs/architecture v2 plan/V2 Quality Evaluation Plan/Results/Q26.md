## 3. 취소 처리와 동일 update의 경합

### 3.1 취소 요청 한 개의 수명

| 단계 | 현재 동작과 범위 |
| --- | --- |
| 대상 확인 `:190–195` | TargetSite Null 또는 ConstructionSite 부재이면 요청만 ECB Destroy. 이미 사라진 site/완공 건물을 구별하는 기준은 이 컴포넌트 존재 |
| 중복 확인 `:198–203` | 이미 Cancelled이면 요청만 삭제 기록. 실물 반환·site 삭제를 두 번 기록하지 않음 |

취소에는 요구량/Delivered/Reserved/Progress 값이 필요하지 않다. 정상 현장의 **실제로 도착해 보관된 Entity 목록**을 반환하며, 아직 운송 중인 자재나 건설 비용에 대한 별도 환급 Entity를 생성하지 않는다.

### 3.2 같은 update에 존재하는 취소·공급·완료

`ConstructionLifecycleApplySystem.OnUpdate`가 요청을 조회하는 시점에 취소와 공급이 함께 존재하는 경우의 계약이다. lifecycle 실행 뒤에 같은 프레임의 다른 producer가 새로 요청을 만드는 경우까지 현재 update가 처리한다고 보장하지 않는다.

```text
Cancel: Cancelled를 직접 쓰고, 이미 보관된 자재 반환/site 삭제를 ECB에 기록
    ↓ 같은 dependency 체인
Material: Cancelled를 읽고 새 Supply를 거부, 공급 요청만 삭제 기록
    ↓
Completion: Cancelled를 읽고 return, 소비/스폰하지 않음
    ↓
EndStateApply: 반환·site/요청 삭제 재생
```

- Cancel/Material/Completion은 단일 워커 `Schedule`을 순차 연결한다. 마지막 handle을 `state.Dependency`와 ECB `AddJobHandleForProducer`에 등록한다.
- **완료 가능한 현장도 Cancel Wins**다. 취소 전 이미 충족된 자재는 반환하고 건물을 생성하지 않는다.
- **같이 들어온 새 공급품은 수령 후 반환되는 것이 아니라 수령 전에 거부된다.** Cancel이 먼저 목록을 읽으므로 그 목록에는 이 Supply의 새 아이템이 추가되지 않는다. 이 요청에 의한 아이템 Owner/태그/위치 변경도 없다.
- 두 번째 Cancel은 첫 Cancel이 직접 쓴 flag를 읽는다. site Entity가 ECB 전까지 살아 있어도 다시 반환하지 않는다. 멱등성은 **취소 요청의 중복**에 대한 것이며, Stored 안의 중복 실물 참조를 정규화하는 것은 아니다.

`UpdateBefore(BuildingLifecycleApplySystem)`도 선언되어 있으나, 위 세 Job의 Cancel Wins는 외부 시스템 정렬이 아니라 명시적 handle 체인으로 성립한다. 이 속성 하나로 일반 Transfer·철거 등 모든 교차 도메인 경합이 해결됐다고 해석하지 않는다.

## 4. Reader/Writer·반환과 참조 정리

| 상태 | Writer/Owner | Reader와 관찰 경계 | 판정 |
| --- | --- | --- | --- |
| Cancel request | 현재 테스트 producer; 게임 입력 producer는 미구현 | Cancel Job→EndStateApply 삭제 | 공개 요청 계약. 타 도메인 Update 호출 없음 |
| ConstructionSite.Flags | Cancel 직접 OR, Placement 초기 flags | 뒤 Cancel·Material·Completion | 같은 update의 중복/경합 차단에 필요한 즉시 상태 |
| StoredItemElement | Material이 직접 Add, Placement가 빈 버퍼 생성 | Cancel이 ReadOnly로 순회 | 정상 실물 목록에 의존. Cancel은 버퍼를 수정하거나 수량을 재산정하지 않음 |
| ItemOwnership | Cancel이 ECB WorldItem 기록; 일반 OwnershipApply 등 별도 Writer 존재 | EndStateApply 후 ItemSpatialSync/물류/Validation | 정상 반환은 같은 Entity의 Owner를 Null로 변경 |
| DisableRendering | Cancel ECB Remove | 렌더링 | 테스트는 태그 존재 여부 확인, 실제 화면 검증 아님 |
| GridPosition·LocalTransform | Cancel ECB로 site 원점에 재설정 | 공간/표시 | 다중 자재도 같은 원점으로 반환. Test02는 두 GridPosition, 첫 실물의 Transform.Position 확인 |
| site·요구/Stored 버퍼 | Cancel ECB Destroy(site) | 재생 후 접근 불가 | Owner 자체를 없애므로 현장 버퍼를 별도 Clear하지 않아도 참조가 함께 사라짐 |
| BuildingSpatialIndex / ItemSpatialIndex | 각 SpatialSync | 다음 재구축에서 site 제외/정상 WorldItem 등록 | 취소 Job이 Map을 직접 수정하지 않는 것은 적합. 이번 실행은 Building 점유 해제만 확인 |
| Reserved·외부 운송/요청 참조 | 취소가 별도 정리하지 않음 | 향후 도착/운송 producer의 계약 필요 | 현재 운송·예약 증가 producer 미구현. 후속 공급은 죽은 site guard로 Drop하는 코드 경로 |

현장 버퍼를 Clear하지 않는 것을 곧바로 참조 누수로 판단하지 않는다. 성공적인 EndStateApply 후 site와 그 버퍼는 함께 소멸하고, 실제 아이템은 WorldItem으로 남는다. 다만 **다른 살아 있는 Owner 버퍼**나 외부 운송 참조까지 자동으로 정리되는 것은 아니다. [F-003 / Q02](Q02.md#f-003--공사-수령이-동일-아이템-재사용과-기존-소유-버퍼를-검증하지-않음)로 기존 다른 Owner의 참조가 남은 상태라면 취소도 이를 찾아 제거하지 않는다.

Cancel은 Stored 요소가 Null인지만 검사하고 Item Entity 생존·현재 Owner==site·ItemIdentity·Owner/GridPosition/LocalTransform 구성은 다시 확인하지 않는다. 정상 목록/아이템 스키마는 필요한 인계 전제이며, stale 참조·구성 누락 때의 실제 ECB 오류/복구는 미확인이다. [F-042 / Q24](Q24.md#f-042--보관-버퍼가-없는-현장도-자재-수령을-승인하여-집계소유권과-실물-보관이-분리됨)처럼 목록 자체가 누락되면 반환 대상도 알 수 없다. 이 기존 공급 경계 문제를 새 취소 문제 ID로 중복 등록하지 않는다.

BeltMovementState·이동/입고 결정·TransferOwnershipRequest는 이 Job이 초기화하거나 소비하지 않는다. 확인한 Belt Decision은 Stored 또는 현재 셀에 벨트가 없으면 이동 계획 0으로 막으므로, 이동 상태 미초기화만으로 이번 정상 반환의 잘못된 이동을 단정하지 않았다. 기존 Cancel fixture는 이 컴포넌트들이 없는 축약 item을 쓰며, 이후 재수거/벨트 진입의 동작은 검증 공백이다.

| 동일 실물의 Cancel 반환 ↔ 일반 Transfer/Destroy | 최종 결과를 조정하는 공개 승자 계약 미확인 | 상대 Writer의 ECB 기록 순서에 임의로 기대면 결합 증가 | **판단 보류**. 이번 지원 경합은 Cancel/Supply/Completion으로 한정 |
| 테스트/유지보수자 → 내부 Job 순서 설명 | Test04 주석은 Material→Cancel이라고 설명 | 실제 거부와 위치 반환의 차이를 놓칠 수 있음 | **개선할 문서·검증 공백 F-043** |

**공개 계약 유지 변경 사례:**

1. Material의 품목 lookup/진행도 계산 내부를 바꾸되 Cancelled guard와 live Stored 계약을 보존하면 Cancel은 수정하지 않는다. 취소 코드가 수령의 matchedIndex나 예약량 계산을 알 필요가 없다.
2. Completion이 prefab 조회/초기화 내부를 바꾸더라도 Cancelled에서 아무 소비/스폰 없이 return하는 계약이 유지되면 Cancel과 독립적이다. 취소가 F-024의 실패 스폰 분기를 직접 알아서 보상할 이유는 없다.
3. Cancel의 실물 순회 방식을 바꾸면서 한 실물의 최종 WorldItem·표시·위치와 site/요청 삭제, Cancelled 가시성을 보존하면 Material/Completion을 바꿀 필요가 없다. 반면 Cancelled만 ECB로 늦추면 동시 Supply/Completion이 아직 미취소로 보므로 **공개 인계 시점 변경**이다. 필요한 순서를 불필요한 결합으로 세지 않는다.
4. SpatialSync가 같은 snapshot·Writer handle·Map 의미를 보존하며 Clear/Populate를 재구성해도 Cancel 수정은 필요 없다. 반환 Job에 Map 변경을 추가하면 책임을 중복시키므로 개선책으로 제시하지 않는다.
5. 외부 producer가 UI 처리나 요청 큐 내부를 바꾸면서 같은 lifecycle 관찰 시점에 같은 Cancel 요청을 게시하면 소비자는 그대로다. 게시가 lifecycle 이후로 이동하거나 이미 수납된 실물을 다른 경로가 같은 update에서 가져가는 것은 **가시성/배타성 계약 변경**이며 단순 내부 최적화와 구분한다.

선택 테스트의 네 helper 이름은 Cancel/Material/FullPipeline 등으로 다르지만 실제로는 모두 같은 lifecycle system 한 번과 ECB 한 번을 실행한다. 테스트 이름을 별도 게임 시스템 간 호출로 오해할 필요가 없고, 유일한 실제 스케줄 책임은 lifecycle system에 있다. V1 비교 근거가 없어 결합 감소량은 주장하지 않는다.
