**[코드 확인] 내부 Job 순서**는 ProductResult→Spawn→Destroy다(`:85–117`). 같은 단일 ECB를 공유하므로 각 Job을 직렬 의존으로 연결하고 마지막 핸들을 ECB producer로 등록한다. 이 핸들은 기록 완료를 보장하며, 다른 시스템에서 대기 중인 구조 변경을 미리 보이게 하지는 않는다. 공개 계약에 필요한 것은 Execution 결과를 StateApply에서 소비하고 종료 시 실체화한다는 경계이지, 다른 도메인이 이 세 Job의 세부 순서를 알아야 한다는 조건이 아니다.

### 생성·무효 입력·중복 처리

- **ProductResult (`:144–231`)**: None 또는 Count≤0는 건너뛰고 최종 Clear한다. 양수 Count만큼 서로 다른 아이템을 만들며 ItemType·SlotIndex를 ProductItemElement에 전달한다. 생산자에 ProductResult와 ProductItemElement 두 버퍼가 모두 있어야 query에 들어간다. 출력 버퍼가 없으면 처리·Clear 자체가 이루어지지 않는다.
- **Spawn (`:255–382`)**: World는 Owner를 Null로 고정한다. Storage/Product는 TargetOwner가 Null이 아니고 대응 버퍼가 있을 때만 허용한다. 존재하지 않는 대상·버퍼 부재·알 수 없는 Destination은 생성 없이 요청을 소비한다. 두 버퍼가 함께 있어도 Destination이 지정한 하나에만 Append한다.
- **검증의 한계**: Spawn은 ItemType None/범위, SlotIndex, Storage.SlotCount, MaxStack, 필터·용량을 검사하지 않는다. DB 없는 World 요청에 None을 주면 fallback 아이템 생성 경로에 들어간다. ProductResult도 SlotIndex·용량을 검사하지 않는다. 이를 고수준 입고 예약 API로 사용하면 안 된다. 호출자 검증을 전제로 하는 저수준 생성 계약인지, 경계 자체가 거부해야 하는지는 설계 질문으로 남긴다. 새로운 게임 규칙을 임의로 요구하지 않는다.
- **Prefab 정책**: DB가 없으면 fallback archetype. DB가 있으면 첫 일치 prefab을 사용하고, 미등록/Null은 오류 로그 후 거부한다. non-Null이지만 죽은 prefab, 필수 컴포넌트 누락, DB 복수 singleton은 별도 방어가 없다. 실제 등록 자산의 유효성은 미평가다. 파일 상단 `:16`의 “미등록 시 fallback” 주석은 이 실제 분기와 다르므로 평가 근거로 사용하지 않았다.
- **초기 상태**: Destroy/Transfer/BeltMovementState/BuildingItemInputDecision은 false로 초기화한다. 새 엔티티는 Playback에 생성되므로 같은 OnUpdate의 Destroy query가 새 엔티티를 다시 잡지 않는다. prefab 경로는 Identity·LocalTransform 존재를 전제로 Set하고 나머지 런타임 상태를 Add한다. fallback은 같은 역할의 archetype에 Set한다.
- **중복 의미**: 같은 데이터를 가진 별도 Spawn 요청 둘은 아이템 둘을 만드는 요청이다. request ID 기반 중복 제거 계약은 없다. ProductResult의 동일 행 둘도 수량 합산이며, Execution은 이미 남은 ProductResult가 있으면 중복 생산 기록을 막는다. Destroy의 bool 활성은 동일 아이템에 반복 설정해도 요청 개수를 늘리지 않는다. 이것을 별도 시스템의 중복 ECB Destroy나 동일 시스템을 Playback 전에 재호출하는 상황까지 보장하는 멱등성으로 확대하지 않는다. Spawn 요청은 Playback 전까지 남아 있어 수동 재호출 시 다시 기록될 수 있다.

### 삭제와 소유 버퍼

**[코드 확인]** DestroyItemApplyJob(`:390–396`)은 요청이 활성인 엔티티에 Destroy만 기록한다. ItemIdentity/Owner 검증, Stored/Product 역참조 정리, 다른 Transfer 요청과의 우선순위 중재는 없다. 요청은 별도 대상 필드가 없는 대상 부착형이므로 이미 죽은 아이템을 가리키는 독립 Destroy 요청을 소비하는 모델이 아니다. 아이템 외 엔티티에 잘못 붙이면 그 엔티티도 삭제 대상이 된다.

정상 producer인 CrafterExecution은 버퍼 `RemoveAt` 후 요청을 활성화한다(`:128–132`). 이때 Owner 값은 파괴 전까지 기존 소유자를 가리키지만, 프레임 끝에는 엔티티가 없어져야 한다. 요청 컴포넌트가 없는 malformed 아이템은 버퍼만 제거되는 코드 경로이므로 초기 archetype 계약도 중요하다. 정상 Lifecycle 생성은 해당 요청을 항상 제공한다. 이 malformed 사례의 실행 여부는 미확인이다.

공사 완공은 자재와 현장 소유자 자체를 같은 ECB로 파괴한다. 살아남는 버퍼의 참조만 남기는 일반 소비와 다르며, ItemLifecycle만이 모든 item Destroy의 전역 작성자라고 설명하지 않는다. 별도 삭제 경로 전체는 Q24 이후 범위다.

공개 계약을 유지한 내부 변경 사례:

1. 생산 계산을 바꾸되 ProductResult의 품목·수량·슬롯과 게시 시점을 유지하면 ItemLifecycle 수정은 필요 없다. 반대로 내부 순회를 변경해도 ECB 종료 시 동일한 상태·버퍼를 제공한다면 정상 출고/Sync 수정은 필요 없다.
2. Lifecycle의 네 초기화 분기를 공통 함수로 정리해 같은 구성·enable 상태·렌더 정책을 유지하면 외부 호출자는 바뀔 필요가 없다. 검토 범위는 해당 분기와 생성 테스트로 제한할 수 있다. 이 제안은 실행하지 않았다.
3. “StateApply 끝에 신규 제품을 버퍼에 넣는다”는 외부 약속을 유지하면서 버퍼 작성 시점을 Job 즉시 반영에서 ECB Append로 바꾸면, 중간에 버퍼를 순회하는 철거는 결과가 달라질 수 있다. 현재가 ECB Append 형태다. 공개 종료 경계만으로 협력하지 못하고 상대의 내부 작성 시점을 알아야 하는 사례이며 F-005의 핵심이다.
4. BuildingLifecycle의 다른 책임 때문에 시스템 생성/정렬 순서를 바꾸어도 공개 Phase는 동일하다. 하지만 F-005는 결과가 고아 item에서 잘못된 Append로 달라질 수 있다. 단순 순서 고정은 양쪽 모두의 안전성을 해결하지 않는다. 생성 접수·취소/반환·대상 폐기 사이의 데이터 계약이 필요하다.
5. Destroy 이전 버퍼 선제거 순서를 유지한 채 Crafter의 재료 선택 자료구조를 바꾸는 것은 Lifecycle에 영향을 주지 않는다. 선제거를 Destroy 이후로 미루는 것은 내부 변경이 아니라 공개 삭제 계약 위반이다. 필요한 동기화를 불필요한 결합으로 분류하지 않는다.

## 5. 발견 문제

기존 F-001/F-002는 [최초 기록 Q00 §8.4](Q00.md#84-문서와-구현의-차이)에 둔다. 기존 F-003 공사 중복 수령과 F-004 입고·철거 태그 경합은 [최초 기록 Q02 §6](Q02.md#6-발견-문제)에 둔다. F-005는 F-004와 철거 접점은 같지만, **이미 존재하는 입고 아이템의 태그 순서가 아니라 새 실체·버퍼 Append와 소유자 수명 충돌**이므로 별도 등록했다.

### F-005 — 생성 대기 아이템을 놓친 채 소유 건물을 철거할 수 있음

- 발견 단계 / 유형 / 평가 축: Q03 / **안정성 결함·유지보수 위험·V2 설계 불일치** / 세 축 모두.
- 우선순위와 이유: **P1**. 정상 생산과 철거가 같은 tick에 접수되면 아이템 소유 정합성 손상 또는 ECB 오류 가능성이 있다.
- 근거 수준: **코드 확인**. 아래 두 실행 순서의 결과는 소스에서 도출한 경로 분석이며, 현재 실제 그룹 순서·실행 재현은 **미확인**.
- 위치: ItemLifecycle `:19,50–53,181–225,261–284,343–376`; BuildingLifecycle `:18–20,117–118,286–329,381`; 로컬 Entities ECB `:4482–4485,5314–5318`.
- 기대 계약과 출처: 생성된 저장품의 Owner는 살아 있고 대응 버퍼에 참조가 있어야 한다(Q02/Validation). 철거는 기존 저장·출력품을 world로 반환한다(BuildingLifecycle, Phase7 Test02). 새 제품도 저장품으로 생성하는 이상 이 정합성에서 제외할 수 없다.
- 확인한 코드 동작: Lifecycle은 ProductResult를 읽고 신규 실체/Append를 ECB에 기록한다. 철거는 Playback 전의 Stored/Product 버퍼만 순회하여 반환 명령을 기록한 뒤 건물을 Destroy한다. Lifecycle은 철거의 `BuildingType.None` 마킹을 읽지 않으며 서로의 상대 순서 선언도 없다.
- 발생 조건과 영향: 같은 건물에 유효한 ProductResult(또는 Storage/Product Spawn 요청)와 유효한 철거 요청이 동시에 처리되는 경우. **Lifecycle ECB가 먼저** 재생되면 새 아이템·참조는 생기지만 철거의 반환 목록에는 없고, 건물 파괴 후 죽은 Owner를 가리키는 숨겨진 저장품이 남는 경로다. **철거 ECB가 먼저**면 이후 생성 ECB가 이미 사라진 버퍼에 Append한다. 로컬 Entities의 safety/debug 검사에는 이 경우 예외를 던지는 코드가 있다. 검사 없는 빌드의 구체적 결과는 판정하지 않는다.
- 근거: 기록 시 존재 검사는 Playback 시 생존을 보장하지 않음. 모든 Job을 완료해도 deferred Append는 재생 전 버퍼에 보이지 않는다. 두 순서 모두 문제가 있어 UpdateAfter 추가만으로 해결되지 않는다.
- 미확인 사항 / 반대 근거: 기존 Phase7 Test02는 이미 실체화된 아이템만 준비하고 ItemLifecycle을 함께 돌리지 않는다. 그 정상 반환은 Q02에서 통과했다. 이 사실은 새 생성 경합을 반증하지 않는다. 실제 씬에서 요청이 겹치는 빈도·실제 오류 메시지·부분 재생 상태는 미측정.
- 수정 방향 후보: 대상 폐기와 생산/스폰 접수를 함께 판정하는 수명 계약, 대기 결과의 반환 또는 명시적 거부/보상 정책을 정한다. 다른 시스템의 내부 버퍼 기록 순서를 하드코딩하는 방식은 피한다. 코드 변경 없음.
- 필요한 추가 검증: 한 건물에 ProductResult Count>0 + Demolish, Storage/Product Spawn + Demolish를 각각 준비하고 두 ECB 생성 순서 및 실제 정렬 그룹에서 Owner/버퍼/아이템 수·태그·오류를 확인하는 회귀 사례. 기존 테스트 수정·추가는 별도 승인 범위.
- 처리: **미결정**. 별도 수정·재검증 없음. 후속 Q28에서는 이 문서를 링크하고 중복 ID를 만들지 않는다.

### F-006 — 생산물 실체화 실패에도 ProductResult를 지워 재처리 근거가 사라짐

- 발견 단계 / 유형 / 평가 축: Q03 / **설계 판단 필요·검증 공백** / 안정성·유지보수성.
- 우선순위와 이유: **판단 보류**. 생산 실패 시 손실을 허용하는 정책인지 확인되지 않았다. 현재 소스의 Strict Fail을 임의로 결함으로 단정하지 않는다.
- 근거 수준: **코드 확인**, 실패 생산 파이프라인 실행·정책 의도는 **미확인**.
- 위치: ItemLifecycle `:168–176,230–231`; MinerExecution `:109–123`; CrafterExecution `:117–135,155–178`; ProductComponent의 결과 전달 계약.
- 기대 계약과 출처: ProductResult는 완료된 생산 결과를 실제 아이템으로 바꾸는 전달 데이터다. SpawnItemRequest에는 실패 Drop 정책이 명시되어 있으나, 소비된 자원/재료가 있는 생산 결과를 실패 시 영구 폐기하는 정책은 해당 컴포넌트 계약에 명시되지 않았다.
- 확인한 코드 동작: DB가 있고 해당 품목 prefab이 없으면 생산 item은 만들지 않고 로그를 남긴다. 루프 끝에서는 실패 행도 포함해 전체 결과를 Clear한다. Miner는 이미 자원을 차감했고 Crafter는 재료를 선소비하고 완료 상태를 초기화하므로 Lifecycle에 재시도·반환 기록이 남지 않는다. 여러 결과 중 일부 prefab만 없으면 다른 출력은 생성되고 누락 출력만 손실될 수 있다.
- 발생 조건과 영향: 생산 가능한 품목의 prefab 등록 누락/Null. 입력 소비 대비 출력 감소, 복구 뒤 자동 재처리 불가. 프리팹이 정상 등록된 정상 경로에는 이 조건이 없다.
- 근거 / 반대 근거: 코드에는 “Strict Fail”과 “Consume-on-Apply” 의도가 있고 SpawnItemRequest의 기존 Test06은 거부·요청 삭제를 기대한다. 다만 이 테스트는 ProductResult, 투입 재료, 자원 차감, 복수 출력의 부분 실패를 검사하지 않는다.
- 수정 방향 후보: 영구 폐기가 의도라면 생산 실패 계약과 진단을 명시한다. 보존이 필요하다면 대기/거부 결과/보상 중 정책을 정한 뒤 producer의 중복 생산 가드와 함께 설계한다. 무조건 재시도나 fallback을 추가하지 않는다.
- 필요한 추가 검증: 일부 품목 prefab 누락 상태에서 Count·SlotIndex별 생산 결과와 재료/자원·결과 잔류량을 확인하고, DB 복구 후 재시도 정책을 검증하는 기존 테스트 보강 제안.
- 처리: **미결정**. 별도 수정·재검증 없음.

Phase1 helper는 Lifecycle→Ownership→EndStateApply를 직접 호출한다. 실제 그룹 정렬, 다른 sibling 조합, 실제 렌더 화면까지 검증하는 테스트가 아니다. Test11의 근거는 살아남는 Stored 버퍼 선제거이고, Product 버퍼 선제거의 동일한 런타임 사례까지 통과했다고 확대하지 않는다.

## 8. 남은 질문·완료 범위·다음 단계

- 생산 완료와 철거가 같은 tick이면 대기 생산물을 월드로 반환할지, 생산을 취소/보상할지 정책 결정이 필요하다. 어느 선택이든 죽은 Owner·없는 버퍼 Append를 남기지 않는 것은 공통 정합성 요구다(F-005).
- 생산 prefab 누락 시 결과를 영구 폐기할지, 대기/실패 결과를 남길지 확인이 필요하다(F-006). 이번 평가에서 새 정책을 구현하지 않았다.
- Spawn은 유효 품목·슬롯·수용량을 보장받는 내부 명령인가? 범용 요청 경계라면 거부 조건과 실패 결과를 어디서 보장할지 명시할 필요가 있다. 현재는 대응 버퍼 존재 이상의 수납 검증을 수행하지 않는다.
- 같은 아이템에 Transfer와 Destroy를 동시에 활성화하는 규칙, Playback 전 수동 재호출, malformed prefab/복수 DB, 실제 정렬 그룹의 F-005 재현은 미확인이다. 광범위 경합 평가는 후속 단계에 남긴다.
- 수동 확인: 실제 장면의 생성·삭제·가시성은 이번 평가에서 보장하지 않는다. 실행 재현/수정 검증 없이 시각적 정상 여부를 주장하지 않는다.
