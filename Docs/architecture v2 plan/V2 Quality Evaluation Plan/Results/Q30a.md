## 2. 네 가지 통합 질문과 확인 범위

### A. 자원 고갈 → 생산 실체 → 벨트 → 최종 소유자

**코드 확인:** Miner Execution은 ProductResult를 추가하고 유한 자원 Amount를 줄인 뒤 고갈 Destroy를 EndStateApply에 기록한다. ItemLifecycle은 실제 item 생성·ProductItemElement Append를 ECB에 기록하고 ProductResult를 비운다. 이 제품은 다음 Decision에서 출고 후보가 된다. StorageApply는 버퍼 membership/위치/이동을 반영하고 Transfer를 발행하며, OwnershipApply는 Owner를 즉시·렌더 태그를 ECB로 반영한다. Sync는 확정된 world item만 Map에 넣는다.

**EditMode 확인:** `Phase4EndToEndPipelineTests.Test01_SingleItem_MiningToStorage_CompleteLoop` 통과. 초기 Sync 1틱 뒤 60틱(0.05s)에서 자원 entity 소멸, Miner 제품 버퍼 0, 창고 Iron_Ore 정확히 1, 해당 item의 stored Owner=창고, 경로 세 벨트 셀의 Map 비어 있음, 누적 Validator 0을 assert한다. Q20의 추가 Playback helper와 달리 등록된 그룹이 EndStateApply를 실행한다.

**한계:** 자원·Miner·Belt·Storage는 Factory, Item은 DB 없는 fallback이다. 물량 1·직선·단일 수신자이며 일반 이동과 라우팅/출고의 동시 목적지 경합, 실패 prefab, 렌더 태그 직접 assertion, 전역 item 총수/동일 entity의 전체 경로 추적은 없다. ResourceGenerationCommand·초기 청크와의 연결은 이 테스트 대상이 아니다. 이 통과로 F-005/F-006/F-029/F-030을 부정하지 않는다.

### B. 막힌 목적지 → 라우팅 거절·상태 유지 → 공간 확보 후 재개

**코드 확인:** Merger는 직전 Sync의 ItemMap으로 count/minProgress를 읽어 포화를 거절한다. 목적지 중재가 유지한 RoutingTransferDecision만 RoutingApply에서 실제 Grid/진행도로 반영되고 성공 시 커서가 바뀐다. Sync가 다음 프레임 조회를 갱신한다. Map 준비/Fence와 승인 enable 소비는 필요한 공개 경계다.

**EditMode 확인:** `Phase6EndToEndPipelineTests.Test03_Backpressure_PropagatesToMergerSplitterAndRecovers` 통과. 목적지 네 아이템으로 5틱 정체 후 입력 item 위치 `(10,10)`과 Merger cursor=0을 확인하고, 테스트가 네 장애물을 직접 Destroy한 뒤 5틱 후 같은 입력 entity가 `(12,10)`에 도착했으며 Validator 누적 0임을 확인한다.

**한계:** 이름에 Splitter가 있지만 이 사례는 Merger 한 개다. 목적지 확보는 정상 하류 출고가 아닌 직접 Destroy이며, 5틱 후 도착을 검사하므로 다음 한 틱의 즉시 재개 시간을 증명하지 않는다. 재개 후 커서 값은 직접 assert하지 않는다. 한 셀로 들어오는 일반 벨트 이동 후보와의 경합(F-029), 비활성 아이템의 잔여 progress 기준 차이(F-034), 실제 벨트 철거 후 연결 재탐색은 별도다.

### C. 부분 수령 → 같은 틱 추가 공급·취소 → 소유권·점유 해제

**코드 확인:** ConstructionLifecycle은 Cancel→Material→Completion을 Job 핸들로 연결한다. Cancel은 Cancelled를 직접 쓰고 기존 Stored 참조를 WorldItem/태그 제거/위치 변경 ECB로 반환한다. 후속 Material은 취소 현장을 거절하고 Completion도 취소 flag에서 return한다. site Destroy 재생 후 BuildingSpatialSync가 원본 소멸을 반영한다.

**EditMode 확인:** `Phase7EndToEndConstructionPipelineTests.Test02_CancelWins_PartialSupply_ToCancellation_RefundsWorldItemsAndReleasesSpatial` 통과. 실제 Placement로 만든 Storage 현장에 첫 자재를 공급하고 buffer 길이 1·Owner=site를 확인한다. 다음 틱의 추가 자재 공급+취소 후 site 소멸, 두 자재 Owner=WorldItem, 건물 Map에서 위치 해제, Validator 0을 확인한다.

**한계:** 요구 3 중 기존 1+새 1이므로 동시 완료 가능 상태를 강제하지 않는다. 두 item을 처음부터 같은 현장 좌표에 만들고 최종 위치/태그를 직접 assert하지 않아 추가 공급의 ‘거절’과 ‘수령 후 반환’을 결과 위치로 구별하지 못한다. 이는 Q26 F-043의 구별 공백과 연결되며 runtime Cancel→Material 순서는 코드로 확인한 사실이다. 요청 entity 소비·ItemMap의 두 참조·중복 공급·외부 운송 예약까지 전부 assert한 것은 아니다.

### D. 철거 → Sync → 테스트 바닥 정리 → 새 Placement·완공

**코드 확인:** BuildingLifecycle은 StorageApply/RoutingApply 뒤 기존 내용물을 반환하고 건물 Destroy를 ECB에 기록한다. 그 뒤 Sync가 건물 점유를 없앤다. 다음 Command에서 보는 Map은 이 경계 이후의 상태다. Completion은 AwaitingItemClearance를 보류 조건으로 사용하므로 바닥 item과 재배치는 별도 경계다.

**EditMode 확인:** `Phase7EndToEndConstructionPipelineTests.Test04_ImmediateRepositioning_DemolishAndReconstructOnSameTile` 통과. 기존 Storage 철거 뒤 entity/Map 제거, 테스트가 해당 좌표 item을 직접 삭제하고 추가 Sync 틱 실행, 새 Belt 현장 위치·flags=None, 자재 공급 후 Map의 Belt 점유를 확인한다. Validator 누적 0도 확인한다.

**한계:** 같은 틱 철거+새 배치가 아니다. 환급품 수량/Owner/렌더를 검증한 뒤 수거하는 경로도 아니며, 자동 바닥 정리 구현이 생겼다는 증거가 아니다. 신규 완공 site 소멸과 공급 자재 소비는 여기서 각각 직접 assert하지 않는다. 정사각형 1×1·fallback이므로 F-023/F-024를 검사하지 않는다.

**공개 계약 유지 변경 사례 [코드 기반 분석, 변경 실험 없음]:**

1. Miner 진행 계산을 분리하거나 ItemLifecycle의 생성 loop를 다른 Job으로 나누되 ProductResult 의미·같은 EndStateApply의 실체화·소비 시점을 유지하면 Output/Storage 및 최종 전달 assertion은 바뀔 필요가 없다. 반면 ‘최종 값만 같다’며 ECB 경계를 한 프레임 미루는 것은 공개 시간 계약 변경이다.
2. 목적지 예약의 내부 집계 자료구조를 바꾸되 같은 승인 결정/커서 정책을 유지하면 Merger/Apply는 변경 불필요하다. Phase6 Test03도 최종 정체·복구 결과만 확인하므로 내부 후보 배열을 알 필요가 없다. 경쟁 후보의 범위를 늘리는 F-029 수정은 새 정책/계약 검토가 필요하다.
3. 같은 프레임 최종 Owner를 유지하려는 Ownership/철거 스케줄 재배치도 현재는 Add/Remove 태그를 어느 ECB에 먼저 쓰는지 알아야 안전하다(F-004). 단순 Job 완료는 ECB 간 명령 의미를 해결하지 않는다.
4. 생산 결과의 Append를 다른 Job에 옮겨도 deferred라는 사실은 같으므로 철거의 현재 버퍼 순회로 신규 항목을 반환할 수 없다(F-005). 전체 시스템 병합이나 UpdateAfter 추가만으로 공개 폐기/대기 생성 계약을 대신할 수 없다.
5. Sync의 내부 Clear/Populate 분할이 달라져도 같은 원본→Map·Fence 계약이면 최종 점유/도착 검사는 유지된다. 테스트에 임의 중간 Complete·추가 Playback을 넣으면 실제 누락을 가릴 수 있으므로 이번 그룹 실행에는 이를 추가하지 않았다.

1. **폐기와 대기 생성:** 같은 틱 ProductResult/Spawn과 철거를 접수할 때 생성 거부·반환·보상 중 어떤 결과를 보장할지? F-005의 공개 수명 계약을 정하고 양쪽 ECB 생성 순서/실제 그룹에서 검증할 별도 사례가 필요하다.
2. **최종 소유·표시:** 일반 입고와 철거/공사 반환의 최종 Owner·DisableRendering을 누가 확정할지? F-004에 대해 요청 enable·버퍼·ECB 전후·최종 태그를 함께 보는 사례가 필요하다.
3. **실제 제작 진입/재개:** F-037 필수 구성과 슬롯 정책을 결정한 뒤 실제 Spawn→입고→제작→출고, active recipe 변경→잔여물 배출→새 제작을 연결할지? Factory 테스트만 늘려 대체하지 않는다.
4. **경합/실패:** F-023/F-024/F-026/F-027/F-029/F-030의 최소 반례를 별도 보강할지? 미완료 Fence, 누락 prefab, 비정사각형, 동일 틱 별도 요청, 일반 이동+라우팅을 의도적으로 구성해야 한다.
5. **재건축·취소 관찰:** 환급품 직접 삭제와 실제 바닥 정리 기능, 같은 틱 재배치와 다음 틱 요청을 구분한다. 새 공급 item을 현장과 다른 좌표에 두고 거부 후 위치·Owner·태그를 확인하는 보강도 제안한다. 이번에 자동 정리·새 보상 규칙을 구현하지 않았다.

선택 실행은 모두 완료했고 코드·테스트·Config·에셋 변경은 없다. 대상 두 문서를 제외한 기존 평가 폴더 32개 파일의 SHA-256이 변경 전후 일치함을 확인했다. 결과 문서와 계획의 Q30a 상태·링크·현재 진행 상황·다음 후보만 갱신하며, **Q30b 또는 수정 작업을 자동 진행하지 않는다**.
