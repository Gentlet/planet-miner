## 3. 공통 실행·데이터 가시성 계약

### 3.1 의존하는 쪽이 알아야 하는 내용

| 계약 | 공개된 실행·데이터 의미 [코드 확인] | 내부 구현으로 남겨도 되는 내용 / 구분할 가정 |
| --- | --- | --- |
| C01 — Phase | Command → Decision → Reservation → Execution → StateApply → Synchronization. 앞 Phase의 시스템 갱신이 뒤 Phase보다 먼저 예약됨 | 각 그룹의 모든 Job이 그룹 종료 때 자동 완료된다는 뜻은 아님. 순서가 없는 형제의 구체적 배열을 전제로 삼으면 안 됨 |
| C02 — EndCommand | Command 생산자가 만든 ECB는 Command 끝에서 재생. 새 엔티티·요청 삭제는 그 후 ECS 조회에 반영됨 | 생산자는 ECB 내부 PendingBuffers 구조나 후속 Decision의 Job 분할을 알 필요가 없음. 새 엔티티의 공간 인덱스 등록까지 의미하지 않음 |
| C03 — EndStateApply | Execution/StateApply의 기록은 StateApply 끝에서 재생. 후속 Synchronization이 변경된 ECS 상태를 대상으로 작업할 수 있음 | StateApply의 모든 값 쓰기를 모아 한꺼번에 반영하는 계약이나 실패 시 전체 롤백 계약은 아님 |
| C04 — producer Job | ECB에 기록하는 Job을 최종 핸들에 포함하고 AddJobHandleForProducer로 전달. 소비 프레임워크는 이 핸들을 완료한 뒤 버퍼를 재생 | producer 내부 Job의 수·이름·분할은 외부가 알 필요 없음. 그룹 속성만으로 producer 등록을 대체할 수 없음 |
| C05 — 직접 데이터와 요청 | 기존 컴포넌트·버퍼·enable 쓰기는 Job 의존성이 충족되는 시점에 읽을 수 있음. 같은 Phase에서 새 요청을 소비하려면 producer-before-consumer 제약도 필요 | 한 요청의 enable 해제가 그 요청과 관련된 모든 ECB 명령의 완료를 뜻하지는 않음 |
| C06 — 인덱스/Fence | 인덱스는 ECS 상태의 파생 조회 데이터. Reader는 Writer 핸들을 기다리고 자신의 핸들을 등록; Writer는 이전 Writer·Readers를 기다림 | 외부 Reader는 Clear/Populate Job 이름이나 내부 핸들 저장 방식을 알 필요 없음. ECB 재생만으로 최신 Map을 얻는다는 가정은 성립하지 않음 |
| C07 — World 구성 | ECB 인스턴스 생성, 해당 그룹 등록, 그룹 갱신은 구분됨. 정상 기본 구성과 테스트의 수동 구성을 각각 확인해야 함 | GetOrCreate 호출만으로 부분 World에 정렬·Playback이 모두 준비됐다고 간주할 수 없음 |

두 ECB의 API는 프레임워크 실행 계약이다. 이 API를 얻기 위한 `GetExistingSystemManaged`/`GetOrCreateSystemManaged` 호출 자체를 도메인 간 내부 제어로 분류하지 않는다. 다만 ECB가 없을 때 대기·즉시 재생·기존 인스턴스 전제 중 어떤 정책을 쓰는지는 외부 구성 조건이므로 숨기지 않는다.

### 3.2 대표 흐름의 상태 원본·Reader/Writer·소비 시점

아래 표는 공통 경계를 설명하는 표본이다. 해당 데이터의 모든 Reader/Writer를 열거한 전역 소유권 표가 아니다.

| 상태 / 책임 | Writer | Reader·소비자 | 적용·소비 경계와 의미 |
| --- | --- | --- | --- |
| ECB pending buffer와 producer 핸들 / EntityCommandBufferSystem 기반 클래스 | CreateCommandBuffer가 버퍼 등록, producer가 명령 기록, AddJobHandleForProducer가 핸들 결합 | End ECB OnUpdate가 완료 대기·재생·큐 Clear | 생산자들은 공개 메서드만 사용. private producer handle·pending 큐 직접 접근은 확인 범위에 없음 |
| GeneratedChunkReadyElement / ChunkLoad→ResourceGeneration 전달 데이터 | ChunkLoad가 생성 대상을 추가 | ResourceGeneration이 읽고 기록 성공 경로에서 Clear | EndCommand 재생 전 Ready가 비어도 생성 확정과 같지 않음. Pending/Completed로 구분 |
| GeneratedChunkCompletedElement, Tracker Map/Pending / ChunkLoad 수명주기 | ResourceGeneration이 자원 스폰과 함께 ECB에 Completed 추가. ChunkLoad가 Map 추가·Pending 제거 | 다음 Command의 ChunkLoad가 Completed 읽고 Clear | 완료 알림과 실제 스폰의 같은 재생 경계에 의존. ChunkLoad는 생성 알고리즘·프리팹 초기화 순서를 알 필요 없음 |
| TransferOwnershipRequest / 일반 입출고의 전달 계약 | BuildingItemStorageApply가 TargetOwner를 쓰고 enable | ItemOwnershipApply가 읽고 disable | 같은 StateApply의 UpdateBefore와 데이터 의존성이 필요. 소비자가 StoredItemElement를 대신 정리한다는 계약은 없음 |
| ItemOwnership / 위 일반 이전 경로의 소유권 상태, DisableRendering / 렌더 파생 상태 | ItemOwnershipApply Job이 ownership 직접 쓰기; 태그는 ECB에 기록 | ownership을 읽는 후속 데이터 작업 / 재생 후 렌더 태그를 읽는 경로 | 요청 비활성화와 태그 재생 사이에 시점 차이가 있음. 여기서는 다른 공사·스폰 경로의 Writer를 통합 평가하지 않음 |
| ResourceSpatialIndex.Map / ResourceSpatialSync 소유 파생 데이터 | ResourceSpatialSync의 Clear·Populate | 표본 Reader: MinerDecision | Sync에서 갱신한 Map을 이후 Reader가 Fence를 기다려 사용. EndCommand에 생긴 자원을 동일 tick Decision이 인덱스로 찾는다고 보장하지 않음 |
| ResourceSpatialIndexFence의 private _lastWriter/_readers / 공유 동기화 계약 | Sync가 SetWriter; MinerDecision이 AddReader | Reader/Writer가 각 GetDependency 호출 | 공유되는 것은 협력용 핸들 계약. 다른 시스템의 private JobHandle 필드에 직접 접근하지 않음 |

ItemOwnershipApply 예에서 즉시 값 변경과 ECB 구조 변경을 분리한 것은 현재 소스 사실이다. 이를 새 원자성 보장으로 설명하지 않는다. 중간 상태를 어떤 도메인이 읽어도 안전한지는 Q02 이후에서 별도로 확인한다.

필요한 동기화를 제거하면 결합이 줄어드는 것이 아니라 계약이 깨진다. 반대로 UpdateBefore가 코드에 보인다는 사실만으로 충분히 분리됐다고 판정하지 않는다. 이후 단계에서 다른 시스템의 내부 플래그·버퍼 정리 순서까지 알아야 하는지, 그 정보를 공개된 요청/결과 계약으로 설명할 수 있는지 확인한다.

확인한 공통 호출 경계에서 **불필요한 결합으로 확정한 새 사례는 없다**. 구체 소비자 타입을 참조하는 같은 Phase 순서와 부분 World 정책은 추가 판단 대상이다. 새로운 중재 시스템이나 전 도메인 통합 Utility를 도입하는 방향을 이번에 결정하지 않는다.

## 5. 공개 계약을 유지한 내부 변경의 영향 사례

아래는 실제 수정·벤치마크·회귀 실행이 아닌 **[추정: 현재 호출 경로에 근거한 변경 영향 분석]**이다. 입력 필드뿐 아니라 관찰되는 상태·소비·가시 시점을 유지해야 내부 변경으로 본다.

| 가정한 내부 변경 | 유지할 공개 계약 | 함께 바꿀 위치 / 바꾸지 않아도 되는 위치 | 판단 |
| --- | --- | --- | --- |
| ItemLifecycleApply 내부의 생산 결과·스폰·삭제 Job을 재분할 | 요청·결과 의미, 기존 데이터 충돌 순서, EndStateApply 재생, 모든 ECB 기록 작업의 최종 핸들 포함 | ItemLifecycleApply의 자체 Job 구성·최종 핸들은 수정. EndStateApply와 다른 도메인은 Job 이름·개수를 알 필요 없음 | 최종 핸들 인계가 내부 작업 순서를 숨기는 경계. 이 가정으로 무조건 병렬화 가능하다는 뜻은 아님 |
| ResourceSpatialSync의 Clear/Populate 구현을 단일 Job 또는 다른 분할로 변경 | Map 타입·내용·갱신 시점, Fence reader/writer 의미 유지 | Sync 내부 스케줄·최종 Writer 등록을 수정. MinerDecision의 GetReaderDependency/AddReader 호출은 유지 가능 | 필요한 동기화는 남기면서 내부 알고리즘 영향 제한. Map의 공개 컨테이너 타입까지 바꾸면 공개 계약 변경이므로 별도 사례 |
| ItemOwnershipApply 내부 유효성 검사·처리 구현을 재구성 | TargetOwner 의미, enable 소비, 무효 대상 Drop, 소유권·태그 반영 경계, 외부 시스템 타입 유지 | 소비자 내부 수정. StorageApply가 소비자 Job 필드나 렌더 태그 구현을 함께 바꿀 필요는 확인되지 않음 | 내부 구현 변경은 분리 가능. 소비자를 다른 시스템으로 분리하면 UpdateBefore의 명시적 타입 의존까지 재검토해야 함 |
| ECB 기반 클래스의 내부 큐·진단 구현 변경 | CreateCommandBuffer/AddJobHandleForProducer, 생성 순서 재생, 완료 대기·정리·정해진 Phase 경계 유지 | 인프라 내부 변경. 확인한 producer는 PendingBuffers 내부를 참조하지 않음 | API 경계로 영향 제한. 실제 패키지 수정 제안이 아님 |

반례: 자원 스폰을 EndCommand에서 EndStateApply로 옮기거나, 요청 disable을 완료 신호로 재정의하거나, 다른 시점의 인덱스를 제공하는 것은 공개 가시성 계약 변경이다. 이때 관련 소비자·테스트를 재검토하는 것은 정상적인 계약 변경 영향이며, 내부 구현 결합의 증거와 섞지 않는다.

## 6. 세 축 평가

| 축 | 판단 / 근거 |
| --- | --- |
| 안정성 | 공통 경계에서 새 확정 구현 결함은 발견하지 않았다. 현재 코드의 producer 핸들 전달, 지연 완료 데이터, 요청 enable 소비, 대표 Fence 프로토콜은 각각 역할이 구분된다. Q01a의 제한된 실행 근거가 이를 보조한다. 모든 도메인의 중간 상태·재생 실패·경합 안전성은 **미확인**이며 통과로 확대하지 않음 |
| 유지보수성 | 공통 Phase와 인프라 API를 통해 producer가 타 도메인 내부 Job을 모르고 협력할 수 있다. 다만 F-002의 모순된 경계 설명, 같은 Phase의 구체 타입 순서 참조, 부분 World별 다른 준비 정책은 이해 비용을 남긴다. C01–C07과 DEP 표를 후속 평가의 출발점으로 사용 |
| V2 적합성 | **공통 실행 기반의 검토 범위에 한해 적합**, 도메인 내부 결합·전체 목표 달성은 판단 보류. 대표 내부 변경 사례에서 다른 시스템의 내부 코드를 함께 수정해야 한다는 요구를 확인하지 못했다. 시스템 수·속성 수 감소로 평가하지 않으며 V1 대비 감소를 주장하지 않음 |
