# 전체 스크립트 리팩토링 점검

점검일: 2026-08-31

## 1. 점검 범위와 기준

- `Assets` 아래의 C# 스크립트 204개를 전부 파일 목록과 규모 기준으로 순회했다.
- 구성은 런타임 `Assets/Scripts` 174개, EditMode/Editor `Assets/Editor` 17개, UI `Assets/UI` 13개다.
- 전체 약 31,700줄 중 `Assets/Scripts/Systems`가 103개/약 17,500줄로 가장 크며, 드론·생산·공간 인덱스가 주요 복잡도 집중 영역이다.
- 단순 줄 수가 아니라 다음 기준으로 판단했다.
  - 한 타입 안의 책임 수와 변경 이유
  - ECS 데이터 및 상태 소유권 보존 여부
  - 구조 변경 전후 `DynamicBuffer` 수명 안전성
  - 매 프레임 전체 순회, 반복 탐색, Managed/Native 임시 할당
  - UI Toolkit 요소 재생성 및 콜백 수명주기
  - 설정값과 코드 기본값의 분산
  - 테스트 준비 코드의 반복과 회귀 검증 난이도
- 이번 점검은 정적 코드 검토다. Profiler 측정, Play Mode, UI 입력, 시각 결과, WebGL/브라우저 검증은 수행하지 않았다.
- 리팩토링 후보만 정리했으며 런타임 코드와 에셋은 변경하지 않았다.

## 2. 결론

현재 코드에서 즉시 수정해야 할 명백한 기능 결함은 발견하지 못했다. 다만 월드가 커질수록 비용이 증가하는 순회와 UI 재생성, 큰 시스템의 내부 자료구조 결합, 개발 로그 정책, 초기화 값의 분산은 정리 가치가 있다.

우선순위는 다음과 같다.

작업 난이도는 다음 기준으로 산정했다.

- **하**: 단일 파일 또는 좁은 책임 범위의 변경이며 기존 소유권과 데이터 계약을 거의 건드리지 않는다.

### R-01. `FloorChunkRenderer`의 전체 청크 폴링 제거

판정: 적용 완료 (2026-08-31)

작업 난이도: **중** — 청크 완료 알림 경계와 렌더러 수명주기를 함께 수정하고 Play Mode 시각 검증이 필요하다.

근거:

- `Assets/Scripts/Floor/FloorChunkRenderer.cs:41-52`는 매 프레임 `ChunkMapSystem.GetChunks()` 전체를 순회하고 이미 생성된 청크를 사전으로 걸러낸다.
- 현재 청크 unload가 없으므로 로드된 청크가 늘수록, 새 바닥을 만들 일이 없는 프레임에도 순회 비용이 계속 증가한다.
- `Assets/Scripts/Floor/FloorChunkRenderer.cs:160-168`은 새 청크마다 vertex, UV, variant별 triangle 리스트를 새로 만든다.
- 같은 메서드의 `Sprite.uv` 접근도 셀마다 반복된다(`:186`).

적용 내용:

1. `ChunkMapSystem`이 자원 생성 완료 표시와 `Queue<Chunk>` 알림 등록을 `MarkChunkResourcesGenerated`에서 함께 수행한다.
2. `ResourceMapGenerationSystem`은 청크를 직접 완료 처리하지 않고 위 API를 사용하며, 렌더러는 `TryDequeueResourceGeneratedChunk`로 새 완료 청크만 소비한다.
3. 완료 알림은 소비 전까지 큐에 남기 때문에 렌더러 초기화가 늦어져도 생성된 바닥 청크를 놓치지 않는다.
4. vertex/UV/variant별 triangle 리스트를 렌더러 필드로 옮겨 청크 생성마다 `Clear()` 후 재사용한다.
5. variant 생성 시 sprite UV 네 개와 material 배열을 한 번 구성해 셀 루프의 `Sprite.uv` 접근과 청크별 material 배열 생성을 제거했다.
6. 공간 데이터, 자원 생성 및 floor 값의 소유권은 계속 `ChunkMapSystem`과 기존 생성 시스템에 있으며 청크 unload 동작은 추가하지 않았다.

검증:

- 동일 seed/좌표의 바닥 선택 결과가 유지되는 EditMode 테스트
- 청크 로드 순서와 무관한 mesh/submesh 결과
- Play Mode에서 신규 청크 바닥 누락, 경계 깜빡임, material 순서 확인
- Profiler에서 빈 프레임의 `FloorChunkRenderer.Update` 비용과 청크 생성 프레임 할당 비교

검증 결과 (2026-08-31):

- Unity 재컴파일 성공, 프로젝트 전체 EditMode 테스트 119/119 통과
- 신규 테스트 2개로 같은 청크의 완료 알림 중복 방지와 여러 청크의 완료 순서 보존을 확인
- `FloorChunkRenderer`의 `GetChunks()` 전체 순회와 청크별 scratch/material 배열 생성을 정적으로 제거했음을 확인
- Play Mode 신규 청크 시각 결과와 Profiler 변경 전후 수치는 미검증

### R-03. `ChunkCell` 가변 컬렉션 지연 할당

판정: 적용 완료 (2026-08-31)

작업 난이도: **중** — 구현 자체는 작지만 중앙 공간 인덱스의 모든 등록·조회·rollback 경로를 검증해야 한다.

근거:

- `Assets/Scripts/Chunks/ChunkData.cs:12-17`에서 모든 셀이 아이템, 전신주 범위, 드론 정거장 범위용 `List<Entity>` 세 개를 즉시 생성한다.
- 청크 크기 16×16 기준 청크 하나가 256셀이고, 데이터가 없는 셀까지 768개의 리스트 객체를 만든다.
- 이는 매 프레임 GC 문제보다 청크가 계속 확장될 때 누적되는 managed 객체 수 문제다.

적용 내용:

1. 아이템, 전신주 범위, 드론 정거장 범위 리스트를 nullable 필드로 바꾸고 각 최초 등록 시에만 생성한다.
2. `Items`, `CoveringPowerPoles`, `CoveringDroneStations`는 미할당 상태에서 하나의 공유 `Array.Empty<Entity>()` 읽기 뷰를 반환한다.
3. 빈 셀의 조회·제거·`ClearItems`는 리스트를 할당하지 않으며 기존의 빈 결과/실패 계약을 유지한다.
4. 등록 후 비워진 리스트는 null로 되돌리지 않고 다음 등록에서 재사용한다.
5. `ChunkMapSystem`의 등록, 역방향 인덱스, rollback 및 managed 조회 API는 변경하지 않았다.

검증:

- 건물/자원/아이템/전신주/정거장 등록·제거 및 rollback EditMode 테스트
- 빈 셀 조회의 기존 결과 유지
- 대량 청크 로드 전후 managed object/heap snapshot 비교

검증 결과 (2026-08-31):

- Unity 재컴파일 성공, 프로젝트 전체 EditMode 테스트 120/120 통과
- 신규 구조 테스트로 빈 셀 세 목록의 공유 empty view, 최초 등록 시 할당, 제거 후 동일 리스트 재사용을 확인
- 기존 전력망·드론 정거장·아이템 운송 테스트를 포함한 전체 회귀 테스트 통과

### R-04. `DroneTaskSchedulingSystem` 내부 인덱스 구현 분리

판정: 적용 완료 (2026-08-31)

작업 난이도: **상** — 핵심 스케줄링 자료구조를 분리하면서 우선순위·거리·배터리·claim 계약을 완전히 보존해야 한다.

근거:

- `Assets/Scripts/Systems/Drones/DroneTaskSchedulingSystem.cs`는 1,020줄이다.
- 시스템의 ECS 후보 수집과 세대 관리뿐 아니라 `NetworkCandidateIndex`, `SpatialCandidateBucket`, `CellCandidateBucket`, 거리/경로 가능성 비교까지 한 파일에 들어 있다(`:561` 이후).
- 인덱스가 네트워크 → 우선순위 → 청크 → 셀의 여러 단계이고, dirty cell 정렬 및 제거 규칙도 함께 관리한다(`:837-874`).
- 현재 `DroneDispatchSystem`은 후보를 받은 뒤 direct task 또는 reservation owner에서 다시 claim하고 실패한 후보를 제거한다. 따라서 기존 2단계 검증 계약 자체는 유지해야 한다.

적용 내용:

1. `DroneTaskSchedulingSystem`은 ECS 후보 수집, 실제 드론 데이터 조회, 기존 공개 배차 계약만 담당하도록 1,020줄에서 411줄로 축소했다.
2. 새 `DroneTaskCandidateIndex`가 후보 세대 등록, network/priority/chunk/cell 버킷, dirty 정렬, ring 방문, 운반량·route feasibility 비교를 담당한다.
3. 후보 선택은 드론 셀·배터리·운반 용량을 입력받는 순수 C# 경계로 이동해 ECS world 없이 인덱스 규칙을 직접 검증할 수 있게 했다.
4. 완료 이벤트, stale 후보, claim 실패 후보 제거는 모두 동일 인덱스 API로 연결했고 `PrepareCandidates → TryGetNextCandidate → authoritative claim → RemoveCandidate` 계약은 유지했다.
5. 인덱스는 계속 `DroneTaskSchedulingSystem`이 단독 소유하는 파생 상태이며 별도 task/reservation owner나 중복 원본 cache를 만들지 않았다.

검증:

- Unity CLI 컴파일 완료: 오류 없음
- 신규 `DroneTaskCandidateIndexTests` 4건으로 emergency 우선, 거리 동률 creation order, 배터리 부족 후보 건너뛰기, 명시 제거와 세대 만료 제거를 확인
- 기존 5,000개 동일 셀 후보 배차, 우선순위·거리·배터리 fallback, claim rollback을 포함한 전체 EditMode 125/125 통과
- Play Mode의 실제 다중 드론 이동·입력·화면 동작은 미수행

검증:

- Development Build에서 toggle별 로그 출력
- 일반 build에서 정상 경로 로그/문자열 할당이 제거되는지 확인

### R-12. `DynamicBufferCopyUtility` 호출 비용 측정

판정: 측정 항목, 일괄 치환 금지

작업 난이도: **중(측정) / 상(적용)** — 측정 환경 구성은 중간 수준이지만, 실제 최적화는 구조 변경과 buffer 수명 안전성을 호출부별로 증명해야 한다.

- Crafter, Miner, Storage, item spawn, drone planning/reservation 등에서는 복사 후 같은 업데이트 안에 entity 생성·component 추가/제거 같은 구조 변경이 발생할 수 있다.

1. Profiler에서 Native Temp allocation과 복사 시간을 먼저 측정한다.
2. 구조 변경 전에 필요한 값을 소수의 scalar로 완전히 추출할 수 있는 호출부만 국소 최적화한다.
3. 장기적으로 불변 값 데이터는 BlobAsset 또는 명확한 persistent owner 후보를 검토한다.
4. `AsNativeArray()` 일괄 치환이나 유틸리티 삭제는 하지 않는다.

검증:

- Native allocation 측정 전후 비교

## 4. 현 구조 유지가 더 적절한 영역

### `ChunkMapSystem`

- 7개 partial/약 833줄이지만 건물, 아이템, 벨트, 자원, 전력 범위, 드론 범위가 하나의 중앙 공간 인덱스를 공유한다.
- partial 분리는 코드 정리이고 상태 owner는 하나다. 도메인별 별도 공간 캐시로 분해하지 않는다.

### `ItemStorageSystem`

- `StoredItem`, `Disabled`, owner buffer, world tracking을 함께 전환하는 authoritative 경계다.
- structural change를 줄인다는 이유만으로 다른 시스템이 직접 marker와 buffer를 조합하게 만들지 않는다.

### `PowerGridSystem`

- 6개 partial/약 788줄로 registration, topology, generation, participant, query가 이미 나뉘어 있다.
- topology는 dirty일 때 재구성하고 수급 계산은 별도 흐름이다. 현재는 추가 클래스 분리보다 실제 pole/participant 규모의 Profiler 측정이 우선이다.

### `SplitterSystem`과 `MergerSystem`

- 연결 방향과 cursor의 의미가 반대이고, 실제 아이템 위치 변경은 `ItemTrackingSystem` 경계를 사용한다.
- 메서드 이름이 비슷하다는 이유로 공통 base system이나 거대한 generic processor로 합치지 않는다.

### 요청 Entity를 `ToEntityArray(Allocator.Temp)`로 처리하는 시스템

- 구조 변경 중 안전한 순회를 위해 snapshot이 필요한 경우가 많다.
- 배열 생성만 보고 `SystemAPI.Query` 직접 구조 변경이나 무조건적인 Job 변환으로 바꾸지 않는다.

### `BuildingUI` partial 구조

- 파일 수는 10개/약 2,376줄이지만 선택과 ECS 접근 owner를 유지하면서 패널별 표시 코드를 분리한 구조다.
- 개선 대상은 owner 분할이 아니라 요소 바인딩과 반복 rebuild 비용이다.

## 7. 리팩토링 공통 완료 조건

- ECS 상태 owner와 요청/예약/rollback 경계를 바꾸지 않는다.
- 코드/에셋 변경 후 Unity CLI 재컴파일을 완료 상태까지 확인한다.
- 관련 EditMode 테스트를 먼저 실행하고 결과 수와 실패 내용을 기록한다.
- 컴파일/EditMode 결과와 Play Mode 입력·UI·시각 검증을 구분한다.
- 성능 목적 작업은 변경 전후 동일 시나리오의 Profiler 수치를 남긴다.
- Unity asset/source 파일을 이동한다면 대응 `.meta`를 함께 이동하고 GUID를 유지한다.
